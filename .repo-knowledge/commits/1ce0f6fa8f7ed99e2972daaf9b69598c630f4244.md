## TL;DR

Fixes `load_inline` for CUDA-only usage (no `cpp_sources`). When no C++ source is provided, the `functions` parameter is now routed to decorate `cuda_source` instead of `cpp_source`. Adds a `with_cpp` boolean flag to distinguish the two paths. Simplifies the CUDA test by removing the forward declaration requirement.

## Why

The previous `load_inline` implementation always routed function exports through the C++ source (`_decorate_with_tvm_ffi(cpp_source, functions)`), which meant that a CUDA-only call (with `cuda_sources` but no `cpp_sources`) produced no exported functions. The fix routes exports to `cuda_source` when `cpp_sources` is empty.

## What changed

- `python/tvm_ffi/cpp/load_inline.py`:
  - Added `with_cpp = len(cpp_sources) > 0` flag after sources are resolved.
  - Changed decoration logic:
    - If `with_cpp`: decorate `cpp_source` with `functions`, decorate `cuda_source` with `{}`.
    - If not `with_cpp`: decorate `cpp_source` with `{}`, decorate `cuda_source` with `functions`.
  - Updated docstring for `functions` parameter to clarify CUDA-only behavior.
- `tests/python/test_load_inline.py`:
  - Removed the forward declaration (`void add_one_cuda(DLTensor* x, DLTensor* y);`) from the CUDA-only test `test_load_inline_cuda`. The function is now directly exported from `cuda_source`.

## Public surface changes

Minor behavior fix: `load_inline(cuda_sources=..., functions=...)` now correctly exports functions when called without `cpp_sources`. No API signature changes.

## Tests & verification

`test_load_inline_cuda` simplified and now exercises the correct CUDA-only export path without requiring a C++ forward declaration.

## Risk & rollout notes

Low risk. Pure bug fix. Previously CUDA-only calls were silently producing modules with no exported functions. The fix makes them work as documented.
