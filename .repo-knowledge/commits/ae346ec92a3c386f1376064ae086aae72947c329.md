# ae346ec — [DTYPE] Align bool parsing to align with DLPack (#262)

## TL;DR
- Changed `bool` dtype representation to match DLPack standard: now uses `kDLBool` (code 6) with 8 bits instead of `kDLUInt` (code 1) with 1 bit.
- Updated the dtype string serializer and parser in `dtype.cc` accordingly.
- Added `BOOL = 6` to the `DataTypeCode` Python enum.

## Why (intent / motivation)
- The previous representation (`uint1`) diverged from the DLPack standard which defines bool as `kDLBool` (code 6, 8 bits).
- This misalignment could cause interoperability issues with other DLPack consumers.

## What changed (facts from diff)
- `src/ffi/dtype.cc`:
  - `DLDataTypeToString_`: `bool` condition changed from `bits==1 && code==kDLUInt` to `bits==8 && code==kDLBool`.
  - Added explicit `kDLBool` handling in the bit printing path.
  - `StringViewToDLDataType_`: Added `bool` case setting `code=kDLBool, bits=8`; removed the old `str=="bool"` case.
- `python/tvm_ffi/_dtype.py`: Added `BOOL = 6` to `DataTypeCode` enum.
- `tests/python/test_dtype.py`: Added `test_dtype_bool` verifying `bool` parses to `(code=6, bits=8, lanes=1)` and supports `with_lanes`.

## Public surface changes (if any)
- API: `tvm_ffi.dtype("bool")` now returns `type_code=6, bits=8` instead of `type_code=1, bits=1`. Breaking change for code relying on `bool` dtype internals.
- Flags/config: none
- Data formats/schemas: Serialized dtype string `"bool"` now maps to `kDLBool(6)/8` instead of `kDLUInt(1)/1`.

## Tests & verification
- Added/updated tests: `tests/python/test_dtype.py`
- How to verify manually: `uv run pytest -vvs tests/python/test_dtype.py::test_dtype_bool`
- CI impact: none

## Risk & rollout notes
- Risk level: medium — breaking change to `bool` dtype code/bits; any code that hardcoded `type_code=1, bits=1` for bool will break.
- Rollout/migration: Update code that checks `dtype.type_code == 1 and dtype.bits == 1` for bool to use `dtype.type_code == 6`.
- Follow-ups: none
