# ae30cd6 — fix: out-of-bounds read in `StringViewToDLDataType_` with non-null-terminated strings (#387)

## TL;DR
- Fixes a critical security/correctness bug: `strtoul()` was called on `std::string_view::data()` without a null terminator, causing reads past the string boundary
- Replaces all `strtoul()` usages in `StringViewToDLDataType_` with bounded manual digit parsers (`parse_digits` and `parse_lanes` lambdas)
- Particularly affects Electron apps due to aggressive memory reuse by Chromium's allocator
- Adds 10 targeted regression tests covering non-null-terminated inputs

## Why (intent / motivation)
- `strtoul()` requires a null-terminated string but `std::string_view` makes no such guarantee; reading beyond the view bounds is undefined behavior and could expose data from adjacent memory regions or cause crashes in allocator-reuse scenarios like Chromium/Electron

## What changed (facts from diff)
- `src/ffi/dtype.cc`: Replaced `strtoul(scan, &xdelim, 10)` calls with a `parse_digits` lambda that iterates only while `ptr < end`; added a `parse_lanes` lambda that handles both regular (`x<n>`) and scalable vector (`xvscale<n>`) lane specifications; all integer results are now range-checked against `UINT32_MAX`/`UINT8_MAX`/`UINT16_MAX` before narrowing casts
- `tests/cpp/test_dtype.cc`: New `TEST(DType, NonNullTerminatedStringView)` with 10 test cases covering digit-garbage contamination, cross-string lane specification, scalable vectors, and truly non-null-terminated buffers

## Public surface changes (if any)
- API: Behavior of `TVMFFIDataTypeFromString` for valid dtype strings is unchanged; invalid or out-of-range numeric fields now throw `ValueError` with a descriptive message instead of undefined behavior
- Flags/config: none
- Data formats/schemas: none

## Tests & verification

## Risk & rollout notes

- Rollout/migration: none for well-formed dtype strings
- Follow-ups: Consider adding a fuzzer for `TVMFFIDataTypeFromString`
