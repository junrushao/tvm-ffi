# 5e648f0 — Introduce dtype protocol (#178)

## TL;DR
- Adds support for `__dlpack_data_type__` protocol, allowing any object that implements it to be automatically converted to a TVM FFI dtype in function calls.
- Adds `dtype.from_dlpack_data_type()` static method for explicit construction.
- Renames internal `__tvm_ffi_dtype__` slot to `_tvm_ffi_dtype` (private by convention, no double underscores).

## Why (intent / motivation)
- DLPack protocol should be the primary way to exchange dtype information; using `__dlpack_data_type__` allows third-party dtype objects (e.g., ml_dtypes, custom dtype classes) to be passed directly into TVM FFI functions without explicit conversion.

## What changed (facts from diff)
- `python/tvm_ffi/_dtype.py`: Renamed `__tvm_ffi_dtype__` slot to `_tvm_ffi_dtype`; added `dtype.from_dlpack_data_type(tuple[int, int, int])` static method.
- `python/tvm_ffi/cython/dtype.pxi`: Updated `make_ret_dtype` to use `_tvm_ffi_dtype`.
- `python/tvm_ffi/cython/function.pxi`: Added `TVMFFIPyArgSetterDLPackDataTypeProtocol_` Cython setter; registered in `TVMFFIPyArgSetterFactory_` for classes with `__dlpack_data_type__`.
- `tests/python/test_dtype.py`: Added `test_dtype_from_dlpack_data_type`.
- `tests/python/test_function.py`: Added `test_function_with_dlpack_data_type_protocol`.

## Public surface changes (if any)
- API: New `tvm_ffi.dtype.from_dlpack_data_type((code, bits, lanes))` static method; objects with `__dlpack_data_type__()` are now automatically accepted as dtype arguments in FFI calls.
- Flags/config: none
