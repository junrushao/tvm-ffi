# Fix Tuple variadic constructor SFINAE to prevent ambiguous overload with iterator forwarding
## TL;DR
- The `Tuple<Types...>` variadic constructor (`Tuple(UTypes&&... args)`) lacked SFINAE guards, causing it to greedily match when a `Tuple` value was forwarded through iterators (e.g., `std::vector::insert` from `Array::iterator`). The fix adds `enable_if_t` constraints to reject the single-argument case where the argument is the same `Tuple` type.
- `IterAdapter` gains `operator+=` and `operator-=` to satisfy `LegacyRandomAccessIterator` requirements used by `std::vector::insert` range overloads.
- Two new test cases (`ArrayIterForwarding`, `ArrayIterForwardSingleElem`) reproduce the bug and validate the fix.

## Impact
- API: None. The constructor signature is `explicit`, so this is an internal SFINAE refinement that does not change the public API surface. Callers constructing tuples from values continue to work identically.
- Flags/config: None.
- Data formats/schemas: None.

## Reflection
- The root cause is a classic C++ perfect-forwarding pitfall: `Tuple(UTypes&&...)` with a single argument of type `Tuple<TInt>&&` was a better match than the move constructor, because the forwarding reference (`UTypes&&` = `Tuple<TInt>&&`) bound more tightly than `Tuple<Types...>&&` which requires an implicit conversion via the upcast constructor. The fix uses `std::is_same_v` to exclude this case from the variadic overload.
- The `static_assert` for size matching was moved into the `enable_if_t` condition, making it participate in SFINAE rather than being a hard error after overload selection.
- The `IterAdapter` additions (`+=`, `-=`) are needed because `std::vector::insert(pos, first, last)` in some standard library implementations dispatches to an algorithm that requires compound assignment on random-access iterators, not just `operator+`/`operator-`.
