# [FFI] Lightweight json parser/writer (#18186)
## TL;DR
- Adds a self-contained JSON parser (`json::Parse`) and writer (`json::Stringify`) under `tvm::ffi::json`, backed entirely by existing FFI value types (`Any`, `Array<Any>`, `Map<Any,Any>`).
- Both are placed in the `extra/` directory, gated by `TVM_FFI_USE_EXTRA_CXX_API`, following ADR-0009.
- Registers two global functions (`ffi.json.Parse`, `ffi.json.Stringify`) for cross-language access.

## Impact
- API: Two new C++ functions (`json::Parse`, `json::Stringify`) and two new global-registry names. No existing API changed.
- Flags/config: None new; reuses existing `TVM_FFI_USE_EXTRA_CXX_API` gate.
- Data formats/schemas: None.

## Key Design Choices

**Reuse FFI type system as JSON DOM.** Instead of introducing dedicated JSON AST nodes, the implementation aliases `json::Value = Any`, `json::Object = Map<Any,Any>`, `json::Array = Array<Any>`. This means parsed JSON is immediately usable by any FFI consumer without conversion. The `Map<Any,Any>` choice (vs `Map<String,Any>`) is deliberate: it avoids key-type checking overhead at construction time; the check is deferred to key access.

**Parser architecture.** `JSONParserContext` is a low-level cursor that owns character-level scanning (peek, skip-spaces, string/number parsing). `JSONParser` is the recursive-descent driver that handles value/object/array grammar. Temporary stacks (`array_temp_stack_`, `object_temp_stack_`) accumulate children before batch-constructing immutable containers with exact size, avoiding per-element `Array::push_back` overhead.

**Non-standard extensions.** Supports `Infinity`, `-Infinity`, and `NaN` as literals (JavaScript-style), and distinguishes `int64_t` from `double` (integers are parsed via `strtoimax` first, falling back to `strtod`). This round-trip property is enforced by the writer printing integer-valued doubles with `.0` suffix.

**Fast-math safety.** Both parser and writer use bit-level IEEE 754 manipulation under `__FAST_MATH__` to correctly handle NaN/Inf, since `-ffast-math` makes `std::isnan`/`std::isinf` unreliable.

**Writer features.** Handles `Array`, `List<Any>` (with cycle detection via `unordered_set<const void*>`), and `Map` (with runtime string-key enforcement). Supports optional pretty-printing with configurable indent.

**Error reporting.** Parser produces Python-style error messages with line/column/char-offset context. Supports both exception-throwing and error-string-out modes via `String* error_msg` parameter.

## Design Elements
Design elements this commit consumes:
- [ADR-0009: extra/ API isolation](.memory/ADRs/0009-extra-api-isolation.md) -- follows the established `extra/` directory pattern and `TVM_FFI_EXTRA_CXX_API` visibility macro.
- [Design 0004: Container library](.memory/designs/0004-container-library.md) -- reuses `Array<Any>`, `Map<Any,Any>`, `List<Any>` as JSON DOM types.
- [Design 0001: Type-erased Any value system](.memory/designs/0001-type-erased-any-value-system.md) -- `json::Value = Any` is the fundamental representation.

Design elements this commit produces:
- A new `tvm::ffi::json` namespace with `Parse`/`Stringify` as the canonical JSON interface for the FFI layer.
- Two global-registry functions (`ffi.json.Parse`, `ffi.json.Stringify`) enabling Python/Rust access without C++ headers.

## Reflection
- The decision to reuse `Any` as the JSON value type is elegant but means the parser cannot represent JSON `null` distinctly from C++ `nullptr`/`None` -- they are conflated. This is acceptable for the intended use case (config files, serialization) but worth noting.
- The `Map<Any,Any>` choice trades type safety at construction for performance. A `Map<String,Any>` alternative would catch non-string keys earlier but would require `as<String>()` checking on every key insertion during parsing.
- Test coverage is thorough: unicode surrogate pairs, all escape sequences, nested structures, error messages with position context, writer cycle detection, and Inf/NaN round-trips are all exercised.
