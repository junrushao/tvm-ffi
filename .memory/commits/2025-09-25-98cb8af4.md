# feat: Auto-create Python classes when missing (#49)
## TL;DR
- When a C++ object type is returned to Python but no Python class is registered, the runtime now auto-generates a fallback stub class instead of issuing a warning and returning a bare `Object`.
- The fallback class inherits from the parent type's class (creating parents recursively if needed) and attaches all reflected fields/methods.
- Refactored internal registry helpers: `_lookup_type_info_from_type_key` -> `_lookup_or_register_type_info_from_type_key`, `_set_type_cls` now takes `type_info` instead of `type_index`, `_register_object_by_index` factored out `_update_registry`.
## Impact
- API: `_lookup_type_info_from_type_key` renamed to `_lookup_or_register_type_info_from_type_key`; `_set_type_cls` signature changed. Internal APIs, unlikely to affect external callers.
- Flags/config: none
- Data formats/schemas: `TypeInfo` dataclass gains `type_ancestors` field (list of ancestor type indices).
## Design Elements
Design elements this commit consumes:
- Object reflection system (TVMFFITypeInfo, fields, methods)
- `type_acenstors` renamed to `type_ancestors` in C ABI (typo fix in same commit)

Design elements this commit produces:
- Auto-generated fallback class pattern for unregistered types
- `TypeInfo.type_ancestors` field for ancestor chain traversal
- `TypeMethod.as_callable()` and `_member_method_wrapper()` for attaching methods to auto-generated classes
## Reflection
- The rename from `type_acenstors` to `type_ancestors` is a C ABI-level change bundled into this feature commit.
- The `_register_object_by_index(kTVMFFIObject, Object)` call in `string.pxi` ensures the root Object type is always in the registry as a base for fallback classes.
