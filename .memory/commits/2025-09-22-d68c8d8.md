# fix: Fallback for unregistered object types (#44)
## TL;DR
- Fixes a crash in `make_ret_object` (Cython) when a C++ object's type index maps to a `TypeInfo` entry that exists but has `type_cls=None` (i.e., the type is registered in C++ but not in Python via `register_object`).
- Adds a null check on `type_info` in addition to the existing `cls` null check, preventing `AttributeError` on `None.type_cls`.
- Adds `TestUnregisteredObject` C++ class and `testing.make_unregistered_object` global function for test coverage.
- The fallback emits a `UserWarning` and returns a base `Object` instance.
## Impact
- API: none (bugfix). Objects with unregistered Python types now gracefully fall back to `Object` with a warning instead of crashing.
- Flags/config: none
- Data formats/schemas: none
## Design Elements
Design elements this commit consumes:
- `TYPE_INDEX_TO_INFO` array indexed by type index, populated by `register_object`.
Design elements this commit produces:
- Defensive null-check pattern: check both `type_info is not None` and `type_info.type_cls is not None` before constructing the Python object.
## Reflection
- The root cause was that `TYPE_INDEX_TO_INFO[tindex]` can be `None` when the type index exists (allocated by C++) but no Python class was registered for it. The original code only checked `cls is not None` but accessed `.type_cls` on a potentially `None` `type_info`.
