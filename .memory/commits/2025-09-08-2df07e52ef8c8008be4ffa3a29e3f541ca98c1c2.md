# [FFI][Bugfix] Fix bug of `ffi.cpp.load_inline` on Windows (#18281)
## TL;DR
- Added Windows-specific MSVC compiler flags (`/MD`, `/EHsc`, warning suppressions), `msvc`-style dep tracking in ninja, and `/link /out:$out` link rule.
- Changed output extension from hardcoded `.so` to platform-conditional `.dll` on Windows.
- Escaped colons in Windows paths for ninja (`:` -> `$:`) and linked against `tvm_ffi.lib` via `find_libtvm_ffi()`.
- Updated xfail markers to allow `win32` platform (tests no longer expected to fail on Windows).
## Impact
- API: none
- Flags/config: Windows builds now use MSVC-compatible default flags; `find_libtvm_ffi` is imported and used for library linking.
- Data formats/schemas: none
## Design Elements
Design elements this commit consumes:
- `_generate_ninja_build` ninja template generation in `load_inline.py`
- `find_libtvm_ffi` from `tvm_ffi.libinfo`
- Platform-conditional test marks from commit 236e9e9
Design elements this commit produces:
- Cross-platform ninja build generation supporting both GCC-style (Linux/macOS) and MSVC-style (Windows) compilation
- Colon-escaping utility for Windows drive letter paths in ninja files
## Reflection
- The key Windows issues were: (1) missing MSVC flags causing compilation failures, (2) `.so` extension instead of `.dll`, (3) unescaped `:` in `C:\...` paths breaking ninja syntax, (4) missing TVM FFI library link.
- The `oem` encoding for Windows subprocess output is important for correct error message display on non-UTF-8 Windows locales.
