# [FFI] Fix SmallMapInit with duplicated keys (#18178)
## TL;DR
- `MapObj::CreateFromRange` previously called `SmallMapObj::CreateFromRange` directly for small maps (cap < `kMaxSize`), which assumed unique keys and produced a map with duplicate entries.
- Fix: for small maps with cap >= 2, use `SmallMapObj::Empty` + `InsertMaybeReHash` loop (same pattern already used for `DenseMapObj`), so duplicate keys are deduplicated on insert. Cap < 2 is trivially unique, so the fast path is preserved.
- Added `Map_DuplicatedKeysInit` test: constructs a map from `{{"a",1},{"a",2},{"a",3}}` and asserts size 1 with last-writer-wins value 3.
## Impact
- API: none -- `Map(begin, end)` contract unchanged; callers that passed duplicate keys previously got a corrupt small map, now get correct behavior.
- Flags/config: none
- Data formats/schemas: none
## Design Elements
Design elements this commit consumes:
- `SmallMapObj::InsertMaybeReHash` -- existing insert-with-dedup routine, previously only used by the dense-map path in `CreateFromRange`.
- `SmallMapObj::Empty(cap)` -- allocator for an empty small map with given capacity.
Design elements this commit produces:
- Correctness invariant: `MapObj::CreateFromRange` now guarantees unique keys regardless of input for both small and dense map branches.
## Reflection
- The bug was that `SmallMapObj::CreateFromRange` bulk-copied entries without checking for duplicates, while `DenseMapObj` already used `InsertMaybeReHash`. The fix mirrors the dense-map pattern for small maps, keeping a fast path for size 0-1 where duplicates are impossible.
