# [FFI] Optimize atomic decref in Object (#18077)
## TL;DR
- Replaces shared `AtomicDecrementRelAcq` (ACQ_REL on every decrement) with a split pattern: `RELEASE` on the fetch-sub, then an `ACQUIRE` fence only when the refcount drops to zero and the deleter must run.
- Inlines all atomic operations (`IncRef`, `DecRef`, `use_count`) directly into `Object` methods, removing the helper functions from `base_details.h`.
- The `DecRef` path on non-MSVC now avoids the acquire barrier in the common case where the object is not being freed, reducing memory-ordering overhead on weakly-ordered architectures (ARM).
## Impact
- API: none -- `IncRef`/`DecRef` are private to `Object`; `use_count()` signature unchanged.
- Flags/config: none.
- Data formats/schemas: none.
- Performance: reduces barrier cost on the hot decref path. The previous `ACQ_REL` on every decrement is replaced with `RELEASE`-only; `ACQUIRE` is paid only on the final decrement (refcount 1 -> 0). This is the same pattern used by `std::shared_ptr` in libstdc++ and libc++.
- MSVC path: semantics unchanged (`_InterlockedDecrement` implies a full barrier), but the return-value comparison is adjusted from `== 1` (old fetch value) to `== 0` (new value), matching `_InterlockedDecrement` semantics directly and avoiding the `+1` fixup in the removed helper.
## Design Elements
Design elements this commit consumes:
- Object refcount protocol (header_.ref_counter, header_.deleter) as defined in `include/tvm/ffi/object.h`
- Standard release-acquire fence pattern for reference counting (Boost.Atomic documentation, C++ Core Guidelines)

Design elements this commit produces:
- Canonical inline refcount manipulation in `Object::IncRef`/`Object::DecRef`/`Object::use_count` -- future refcount changes should be made directly in `object.h`, not via shared helpers
- `details::AtomicIncrementRelaxed`, `details::AtomicDecrementRelAcq`, `details::AtomicLoadRelaxed` are removed from `base_details.h`
## Reflection
- The split release/acquire pattern is well-established (Boost docs call it out explicitly for refcounting). The key insight is that the acquire fence is only needed to ensure visibility of all prior writes before the deleter runs; all other decrementers only need release ordering.
- On x86 the practical difference is negligible (store-load already has acquire semantics), but on ARM/RISC-V this avoids an unnecessary `dmb` on every non-final decrement.
- Inlining the atomics removes a layer of indirection and keeps the MSVC/GCC split local to the one place it matters, improving readability.
