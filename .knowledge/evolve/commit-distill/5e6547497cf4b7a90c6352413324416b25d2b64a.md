# Skill /commit-distill - Self-Evolution
- **Template mismatch**: The `0023-cubin-launcher.md` new design record covers three distinct concerns (error macro, device guard, cubin loading) that are tightly coupled but each independently useful. The template doesn't have a clear mechanism for "component group" docs that cover a family of utilities under one header namespace — they fit awkwardly as a single doc or as three micro-docs. A "subsystem" template with a per-component Key Classes section would help.
- **Upstream skill gap**: The `d49effdb2239` ledger included a `TVM_FFI_CHECK_CUDA_ERROR` mention in both the cubin_launcher and base.h sections, but the companion commit `cdfd04109f74` ledger described refactoring that macro into `base.h`. The two ledgers were necessary to establish causality — if only one had been processed, the factoring decision (why base.h exists separately) would have been unclear. Ledgers should explicitly call out "refactored from <prior commit>" when they extract code from a companion commit.
- **Quality bar friction**: The requirement for ≥3 distinct evolutionary steps before adding an Evolution Timeline felt too strict for 0022-torch-dlpack-addon (which hit v7 in this batch). The 3-commit threshold should be clarified as "3 commits representing distinct design phases" not "3 commits touching the same file."
- **Procedure friction**: For a large-bringup commit (d49effdb) combined with a companion commit (cdfd0410) that refactors the first commit's internals, it was ambiguous whether to treat them as one design or two. The planner should have a tiebreaker rule: companion commits that refactor/extract shared code from a bringup commit should be merged into a single design doc.
- **Suggested skill change**: Add a "companion commit" concept to Step 1.5 triage: when two commits in the same batch have complementary scopes (one bringup, one refactor of the same components), flag them as a "companion cluster" and plan a single unified design record in Step 2.
