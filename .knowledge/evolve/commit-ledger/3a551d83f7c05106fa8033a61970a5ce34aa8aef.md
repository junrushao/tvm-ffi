# Skill /commit-ledger - Self-Evolution
- **Procedure friction**: The rename shape's "generate rename mapping table" instruction works well, but there is no guidance on how to handle secondary concerns that are *not* renames (e.g., the `Module.entry_func` cleanup bundled in this commit). It is unclear whether to expand a rename ledger's Key Exports for non-rename secondary concerns or to note them only in TL;DR.
- **Template gap**: None — the rename mapping table section in the template covered the primary need cleanly.
- **Wasted effort**: Step 3.3 breaking-change analysis for a rename commit required special-casing: the C ABI function names are breaking changes but the enum *value* is not. The procedure's "additive-only fast-skip" does not apply here, so full breaking-change analysis ran. A fast-path for "rename-only — check ABI value stability, then summarize" would save time.
- **Suggested skill change**: For `rename` shape, add an explicit sub-step: "check whether any renamed C ABI enum values changed (integer value must be stable for ABI compatibility); note separately from renamed C function/symbol names." This would prevent conflating symbol-level breaks with value-level breaks.
