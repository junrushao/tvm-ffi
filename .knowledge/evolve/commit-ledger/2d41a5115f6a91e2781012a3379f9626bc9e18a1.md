# Skill /commit-ledger - Self-Evolution
- **Procedure friction**: Step 3.5 Key Exports guidance for `large-bringup` says cap to ~15 most significant symbols, but a bringup that is primarily Python bindings of already-documented C++ elements needs a different lens — the interesting question is "what's the Python API surface and how does it map to C++ ABI" rather than listing the same 15 symbols that appear in C++ design records. The guidance could distinguish "binding bringup" from "new subsystem bringup."
- **Template gap**: No section for "library loading / packaging" design elements — `libinfo.py` / `base.py` / `pyproject.toml` don't fit naturally into Key Exports (they are not callable APIs) nor Impact (they are structural, not behavioral changes). A brief "Packaging / distribution" subsection in Impact would help.
- **Wasted effort**: Step 3.4 cross-layer consistency was straightforward here (Python wraps C++ ABI, trivially consistent), but required deliberate confirmation. For bringup commits that are explicitly adding a Python layer atop a stable C ABI, the check can be fast-pathed to "wrapping only, consistency assumed."
- **Suggested skill change**: For `large-bringup` commits with shape label "Python FFI binding bringup", add a fast-path note: focus Key Exports on (a) the Cython/ctypes type hierarchy, (b) the public Python `__init__.py` surface, and (c) any C ABI changes. Skip re-documenting C++ types already in design records unless their contracts changed.
