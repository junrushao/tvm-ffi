# Skill /commit-ledger - Self-Evolution
- **Procedure friction**: Step 3.4 (Invariants) for a combined feature+refactor commit blends well when the primary concern is a new type (`ShapeView`) whose introduction causes the refactor. The "bugfix-specific" invariant language (what was violated / what is restored) didn't fit; it was easy to adapt, but the template language could acknowledge feature+refactor hybrids more explicitly.
- **Template gap**: The `Impact` section has no explicit field for "lifetime safety" changes — this commit changes `Tensor::shape()` return type from owning `Shape` to non-owning `ShapeView`, which is a correctness hazard for callers that hold the result past the tensor's lifetime. A dedicated "Lifetime / ownership change" impact field would surface this more prominently than burying it under "API".
- **Wasted effort**: None.
- **Suggested skill change**: Add a "Lifetime / ownership change" bullet to the `Impact` section template for commits that change return-type ownership semantics (owning → view, or view → owning). This is distinct from pure API signature changes and has different risk profile.
