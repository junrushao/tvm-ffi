# Fix test segfaults by adding gc.collect() + del mod to test_stl
## TL;DR
- Adds `gc.collect()` and `del mod` after `run_check(mod)` in `tests/python/test_stl.py` to force garbage collection of objects holding DSO-resident destructors before the module is unloaded.
- Prevents segfaults caused by CPython's non-deterministic GC delaying destruction of objects whose deleters reside in the loaded library's code segment.
- Reinforces the "module must outlive returned objects" invariant documented in the module system design.

## Design Elements
Design elements this commit consumes:
- **Module must outlive returned objects** (documented in `.knowledge/designs/0011-module-system.md`, "Contracts, Assumptions and Invariants" section). When a loaded DSO module returns objects (e.g., tuples, vectors, maps, functions), those objects' destructors reside in the library's code segment. If `dlclose` runs before those destructors, the process segfaults. The existing `run_check()` nested-function pattern scopes temp lifetimes, but CPython may still hold references in exception traceback chains or cycle-collector queues. This commit adds an explicit `gc.collect()` + `del mod` to flush those.

Design elements this commit produces: none

## Usage Examples
**Before** (segfault-prone): `run_check(mod)` returns but CPython's GC may still hold references to objects with DSO-resident deleters. When `mod` is garbage-collected and the DSO is unloaded, those delayed destructor calls jump to unmapped memory.

**After** (fixed):
```python
run_check(mod)
# Force garbage collection to ensure that all objects created from the
# module are destroyed before the module itself is unloaded.
gc.collect()
del mod
```

Note: This approach was later superseded in commit 5a82940 which moved all assertions into the nested `run_check()` function body, making `gc.collect()` / `del mod` unnecessary.
