# Fix type mismatch aborts on OpaquePyObject

## TL;DR
- Registers `TypeIndex::kTVMFFIOpaquePyObject` (index 74) as a builtin depth-1 object type in the global `TypeTable`, fixing a crash where passing an `OpaquePyObject` to a C++ function expecting a different type (e.g. `int`) caused the program to abort with `exit(1)` instead of raising a proper `TypeError`.
- Adds `StaticTypeKey::kTVMFFIOpaquePyObject = "ffi.OpaquePyObject"` constant to `object.h`.
- Adds a `testing.add_one` C++ test function and corresponding Python wrapper/test to verify the fix produces a readable error message.

## Key Exports

```cpp
// New constant for the type key string. Consumed by TypeTable::ReserveDepthOneObjectTypeIndex
// during static initialization.
```



## Impact
- API: Adds `StaticTypeKey::kTVMFFIOpaquePyObject` constant (purely internal).
- Behavioral: Before this fix, passing an unregistered Python object (wrapped as `OpaquePyObject`) to a C++ function expecting a different type caused the process to abort via `exit(1)` inside `TVMFFIGetTypeInfo`, because `TypeTable::GetTypeEntry(74)` returned `nullptr` (the type was never registered). After this fix, the type table lookup succeeds, returning `"ffi.OpaquePyObject"` as the type key, which allows `GetMismatchTypeInfo` to produce a proper `TypeError` like: `Expected 'int' but got 'ffi.OpaquePyObject'`.
- Flags/config: none
- Data formats/schemas: none

## Design Elements
Design elements this commit consumes:
- **TypeTable and builtin type registration** (`src/ffi/object.cc`): The `TypeTable` constructor reserves type entries for all builtin type indices. `ReserveDepthOneObjectTypeIndex` registers a type at depth 1 (child of `ffi.Object`) with no child slots. See [0002-object-system.md](../designs/0002-object-system.md).
- **StaticTypeKey constants** (`include/tvm/ffi/object.h`): Centralized string constants for all builtin type keys. See [0002-object-system.md](../designs/0002-object-system.md).
- **TypeTraits::GetMismatchTypeInfo** (`include/tvm/ffi/type_traits.h`): When a type mismatch is detected, calls `TypeIndexToTypeKey(source->type_index)` which delegates to `TVMFFIGetTypeInfo`. See [0006-type-traits.md](../designs/0006-type-traits.md).
- **TVMFFIGetTypeInfo / TVM_FFI_LOG_EXCEPTION_CALL_END** (`src/ffi/object.cc`): `TVMFFIGetTypeInfo` uses the log-and-abort error path (`TVM_FFI_LOG_EXCEPTION_CALL_END`) rather than the safe-call path (`TVM_FFI_SAFE_CALL_BEGIN/END`), so any failure inside it results in `exit(1)`. See [0005-error-system.md](../designs/0005-error-system.md).
- **OpaquePyObject / TVMFFIObjectCreateOpaque** (`include/tvm/ffi/c_api.h`, `python/tvm_ffi/cython/function.pxi`): Python objects that don't match any known TVM FFI type are wrapped as `OpaquePyObject` with type_index=74. See [0001-c-abi.md](../designs/0001-c-abi.md).
- **refl::GlobalDef** (`src/ffi/extra/testing.cc`): Global function registration via reflection. See [0008-reflection.md](../designs/0008-reflection.md).

Design elements this commit produces: none (bugfix to existing type registration)

## Usage Examples

**Type mismatch now produces a clear error instead of abort** (from `tests/python/test_object.py::test_opaque_type_error`):
```python
import tvm_ffi
from tvm_ffi.testing import add_one

class MyObject:
    def __init__(self, name: str) -> None:
        self.name = name

obj = MyObject("hello")
# Before fix: process aborts with exit(1) and cryptic traceback
# After fix: raises TypeError with actionable message
add_one(obj)
# TypeError: Mismatched type on argument #0 when calling:
#   `testing.add_one(0: int) -> int`. Expected `int` but got `ffi.OpaquePyObject`
```
