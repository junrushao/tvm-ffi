# Register OpaquePyObject as builtin type index to fix abort on type mismatch
## TL;DR
- When an `OpaquePyObject` was passed to a function expecting a different type (e.g. `int`), the error path called `TypeIndexToTypeKey(74)` which looked up type info for index 74 in the `TypeTable`. Since `kTVMFFIOpaquePyObject` was never registered there, the lookup failed with `TVM_FFI_ICHECK`, triggering `TVM_FFI_LOG_EXCEPTION_CALL_END` which calls `exit(-1)` -- aborting the entire process instead of raising a proper `TypeError`.
- Fix: add `StaticTypeKey::kTVMFFIOpaquePyObject = "ffi.OpaquePyObject"` and call `ReserveBuiltinTypeIndex` for it during `TypeTable` initialization, so the type info is always available for error messages.
- Adds a test helper `testing.add_one` (C++ side) and `tvm_ffi.testing.add_one` (Python side) to exercise the type mismatch error path.

## Impact
- API: none -- no public API changes; only internal type registration and test helpers added.
- Behavioral: OpaquePyObject type mismatch errors now produce a proper `TypeError` with message `"Expected 'int' but got 'ffi.OpaquePyObject'"` instead of aborting the process via `exit(-1)`.
- Flags/config: none
- Data formats/schemas: none

## Design Elements
Design elements this commit consumes:
- **TypeTable / ReserveBuiltinTypeIndex** (`src/ffi/object.cc`): The mechanism for registering builtin type indices at `TypeTable` construction time. POD types (indices 0-12) were already reserved here. See `0001-any-anyview-value-system.md`.
- **StaticTypeKey** (`include/tvm/ffi/object.h`): Compile-time string constants mapping type index enum values to human-readable type keys. See `0001-any-anyview-value-system.md`.
- **TypeIndexToTypeKey** (`include/tvm/ffi/object.h`): Called by `TypeTraitsBase::GetMismatchTypeInfo` to produce error messages when type conversion fails. See `0005-type-traits-protocol.md`.
- **TVM_FFI_LOG_EXCEPTION_CALL_BEGIN/END** (`include/tvm/ffi/base_details.h`): Exception-to-abort wrapper used by `TVMFFIGetTypeInfo`. Catches exceptions and calls `exit(-1)`. See `0007-c-abi.md`.
- **GlobalDef** (`src/ffi/extra/testing.cc`): Used to register the new `testing.add_one` global function. See `0008-reflection.md`.

Design elements this commit produces:
- None -- this is a pure bugfix that fills a gap in existing registration.

## Usage Examples
**Before (abort)**: Passing an OpaquePyObject to a typed function caused process abort:
```python
# Before fix: this aborts the process with exit(-1) and a stderr dump
obj = MyObject("hello")
tvm_ffi.testing.add_one(obj)  # ABORT: "Cannot find type info for type_index=74"
```

**After (proper TypeError)**: The same call now raises a catchable `TypeError`:
```python
# After fix: raises TypeError with informative message
obj = MyObject("hello")
try:
    tvm_ffi.testing.add_one(obj)
except TypeError as e:
    # "Mismatched type on argument #0 when calling: `testing.add_one(0: int) -> int`.
    #  Expected `int` but got `ffi.OpaquePyObject`"
    pass
```

## Reflection

### Design docs to write or update
- `0001-any-anyview-value-system.md`: Could note that static object type indices (64-128 range) also need `ReserveBuiltinTypeIndex` if they lack a C++ `ObjectDef<T>()` registration (the case for `OpaquePyObject`, which is created dynamically from Python). Currently the design record only describes POD type reservations. Low priority -- the invariant is now satisfied by the fix.
- `0007-c-abi.md`: The `TVM_FFI_LOG_EXCEPTION_CALL_END` abort behavior (`exit(-1)`) is a design trap -- any `TVM_FFI_ICHECK` failure inside a `LOG_EXCEPTION_CALL` function causes process abort rather than a catchable error. This is by design (these are "should never fail" paths), but the OpaquePyObject gap shows that missing type registrations can trigger it. Worth noting as a known pitfall.
