# Register kTVMFFIOpaquePyObject as builtin type index to fix abort on type mismatch
## TL;DR
- When an `OpaquePyObject` was passed to a TVM-FFI function expecting a different type (e.g., `int`), the program aborted with `exit(-1)` instead of raising a proper `TypeError`, because `kTVMFFIOpaquePyObject` (index 74) was not registered in the `TypeTable` and `TVMFFIGetTypeInfo(74)` failed inside the `TVM_FFI_LOG_EXCEPTION_CALL_END` boundary.
- The fix adds `ReserveBuiltinTypeIndex(StaticTypeKey::kTVMFFIOpaquePyObject, TypeIndex::kTVMFFIOpaquePyObject)` to the `TypeTable` constructor, and adds `StaticTypeKey::kTVMFFIOpaquePyObject = "ffi.OpaquePyObject"` to the C++ header.
- A new `testing.add_one` helper function and `test_opaque_type_error` test verify the fix end-to-end.

## Key Exports
**Constants/Strings**:
- `StaticTypeKey::kTVMFFIOpaquePyObject` — `static constexpr const char* = "ffi.OpaquePyObject"` (new entry in `StaticTypeKey` struct, `include/tvm/ffi/object.h`)

**Functions** (testing only):
- `testing.add_one(int) -> int` — C++ lambda registered via `refl::GlobalDef()`, `src/ffi/extra/testing.cc`
- `tvm_ffi.testing.add_one(x: int) -> int` — Python wrapper, `python/tvm_ffi/testing.py`

## Impact
- API: None. No public API signatures changed.
- Behavioral: Type mismatch errors involving `OpaquePyObject` now produce a proper `TypeError` with message `"Expected \`int\` but got \`ffi.OpaquePyObject\`"` instead of aborting the process via `exit(-1)`.
- Flags/config: None.
- Data formats/schemas: None.

## Design Elements
Design elements this commit consumes:
- **TypeTable builtin registration** (`src/ffi/object.cc`): The `ReserveBuiltinTypeIndex` mechanism that populates the type table for static type indices at startup. See [0003-object-system.md](../designs/0003-object-system.md).
- **StaticTypeKey** (`include/tvm/ffi/object.h`): Compile-time string constants mapping type indices to human-readable keys, used by `TypeIndexToTypeKey`. See [0003-object-system.md](../designs/0003-object-system.md).
- **TypeTraitsBase::GetMismatchTypeInfo** (`include/tvm/ffi/type_traits.h`): Called when `TryCastFromAnyView` fails, delegates to `TypeIndexToTypeKey(source->type_index)` which requires the type index to be registered. See [0005-type-traits.md](../designs/0005-type-traits.md).
- **TVM_FFI_LOG_EXCEPTION_CALL_END** (`include/tvm/ffi/base_details.h`): Exception boundary around `TVMFFIGetTypeInfo` that calls `exit(-1)` on failure -- this is the code path that turned a recoverable error into a process abort. See [0006-error-handling.md](../designs/0006-error-handling.md).
- **Type index layout** — `kTVMFFIOpaquePyObject = 74` in the static object range `[64, 128)`. See [ADR 0004-type-index-layout.md](../ADRs/0004-type-index-layout.md).

Design elements this commit produces:
- None. This commit fills a registration gap; it does not introduce new design elements.

## Usage Examples
**Before** (incorrect behavior -- program aborts):
```python
import tvm_ffi

class MyObject:
    def __init__(self, name):
        self.name = name

# Calling a typed FFI function with an opaque Python object:
obj = MyObject("hello")
tvm_ffi.testing.add_one(obj)  # ABORT: exit(-1) with cryptic stderr message
# "Exception caught during TVMFFIGetTypeInfo:
#  InternalError: Check failed: (entry != nullptr) is false:
#  Cannot find type info for type_index=74"
```

**After** (correct behavior -- clean TypeError):
```python
import tvm_ffi

class MyObject:
    def __init__(self, name):
        self.name = name

obj = MyObject("hello")
tvm_ffi.testing.add_one(obj)
# TypeError: Mismatched type on argument #0 when calling:
#   `testing.add_one(0: int) -> int`.
#   Expected `int` but got `ffi.OpaquePyObject`
```
