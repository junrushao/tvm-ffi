# Fix Cython TypeInfo parent_type_info propagation by enforcing registration order
## TL;DR
- `_register_object_by_index` calls were scattered across individual `.pxi` files in arbitrary order; `Object` (the root) was registered last (in `string.pxi`), causing derived types' `parent_type_info` to resolve to a placeholder `TypeInfo` with `type_cls=None`.
- All registration calls are now centralized in `core.pyx` in strict inheritance order (base before derived), ensuring `TypeInfo.__post_init__` resolves `parent_type_info` correctly.
- New `TYPE_CLS_TO_INFO` reverse-lookup dict and `_type_cls_to_type_info()` function added; comprehensive parametrized test covers all built-in and test types.

## Impact
- API: `_set_class_object` stub removed from `core.pyi`; `_type_cls_to_type_info` added. Both are internal/private APIs (underscore-prefixed).
- Behavioral: `parent_type_info` on `TypeInfo` for all built-in Cython types (Error, Function, String, Bytes, Tensor, Device, DataType) now correctly points to the parent's `TypeInfo` with `type_cls` populated. Previously, some had `parent_type_info.type_cls = None`.
- Flags/config: none
- Data formats/schemas: none

## Design Elements
Design elements this commit consumes:
- **TypeInfo / type registration registry** (`.knowledge/designs/0012-python-bindings.md`, "Type registration registries" section) -- the three registries `TYPE_INDEX_TO_INFO`, `TYPE_INDEX_TO_CLS`, `TYPE_KEY_TO_INFO` and the `_register_object_by_index` function.
- **TypeInfo.__post_init__ parent resolution** (see commit `98cb8af`) -- `parent_type_info` auto-resolved from `type_ancestors[-1]` via `_lookup_or_register_type_info_from_type_key`.

Design elements this commit produces:
- **TYPE_CLS_TO_INFO registry** -- a new `dict[type, TypeInfo]` reverse-lookup from Python class to TypeInfo. Populated by `_update_registry` and `_set_type_cls`.
- **`_type_cls_to_type_info` function** -- public (within cython module) reverse-lookup API.
- **Registration ordering invariant** -- base classes MUST be registered before derived classes in `core.pyx` to ensure `parent_type_info` propagation. Enforced by comment and test, not mechanically.

## Usage Examples

Before (broken): registrations scattered in `.pxi` files in arbitrary order.
```python
# string.pxi (OLD) -- Object registered AFTER its derived types
class String(str, PyNativeObject): ...
_register_object_by_index(kTVMFFIStr, String)   # parent Object not yet registered
_register_object_by_index(kTVMFFIBytes, Bytes)
_register_object_by_index(kTVMFFIObject, Object) # too late -- String's parent_type_info already resolved
```

After (fixed): centralized in `core.pyx` in inheritance order.
```python
# core.pyx (NEW)
include "./object.pxi"
_register_object_by_index(kTVMFFIObject, Object)   # root first
include "./error.pxi"
_register_object_by_index(kTVMFFIError, Error)      # derived after parent
include "./string.pxi"
_register_object_by_index(kTVMFFIStr, String)
_register_object_by_index(kTVMFFIBytes, Bytes)
# ... etc.
```

Test verifying correct parent resolution:
```python
def test_type_info_attachment(test_cls, type_key, parent_cls):
    type_info = tvm_ffi.core._type_cls_to_type_info(test_cls)
    assert type_info is not None
    assert type_info.type_key == type_key
    if type_info.parent_type_info is not None:
        assert type_info.parent_type_info.type_cls is parent_cls
```
