# Fix Cython TypeInfo registration ordering so parent_type_info propagates correctly
## TL;DR
- Moved all `_register_object_by_index` calls from scattered `.pxi` files into `core.pyx`, ordered by inheritance hierarchy (base before derived), so `TypeInfo.parent_type_info` is correctly resolved for all built-in Cython classes.
- Added `TYPE_CLS_TO_INFO` dict and `_type_cls_to_type_info()` public function for reverse lookup (Python class -> TypeInfo).
- Added parametrized test `test_type_info_attachment` covering 20+ classes to guard parent chain correctness.

## Impact
- API: Added `_type_cls_to_type_info()` (internal/testing API). Removed `_set_class_object` from `.pyi` stub. No public API breakage.
- Behavioral: `TypeInfo.parent_type_info` is now correctly set for all built-in Cython classes (Object, Error, DataType, Device, String, Bytes, Tensor, Function). Previously, some had `None` parent due to registration ordering.
- Flags/config: none
- Data formats/schemas: none

## Design Elements
Design elements this commit consumes:
- **TypeInfo / type registry** ([0015-ffi-python-type-system](../design-records/0015-ffi-python-type-system.md)): uses `_register_object_by_index`, `_update_registry`, `_set_type_cls`, `TYPE_INDEX_TO_CLS`, `TYPE_INDEX_TO_INFO`, `TYPE_KEY_TO_INFO`.
- **TypeInfo.parent_type_info auto-resolution** ([0015](../design-records/0015-ffi-python-type-system.md)): the `__post_init__` resolves parent from `type_ancestors`, but requires ancestor to already be registered.

Design elements this commit produces:
- **TYPE_CLS_TO_INFO reverse registry**: new `dict[type, TypeInfo]` enabling class-to-TypeInfo lookup, populated in `_update_registry` and `_set_type_cls`.
- **_type_cls_to_type_info() function**: public accessor for the reverse registry.
- **Registration ordering invariant in core.pyx**: `_register_object_by_index` calls are now centralized in `core.pyx` in strict inheritance order, enforced by an inline comment.

## Usage Examples

**Before (bug)**: `_register_object_by_index(kTVMFFIObject, Object)` was called in `string.pxi` (at the bottom, after String/Bytes), so when `Error` was registered in `error.pxi`, Object's TypeInfo did not yet exist -- causing `Error.parent_type_info` to be `None`.

**After (fix)**: Registration order in `core.pyx`:
```python
# core.pyx -- base classes registered before derived
include "./object.pxi"
_register_object_by_index(kTVMFFIObject, Object)      # 1. base
include "./error.pxi"
_register_object_by_index(kTVMFFIError, Error)         # 2. derives from Object
include "./dtype.pxi"
_register_object_by_index(kTVMFFIDataType, DataType)   # 3. ...
# ... etc
```

**Test for parent chain correctness**:
```python
import tvm_ffi
from tvm_ffi.core import _type_cls_to_type_info

info = _type_cls_to_type_info(tvm_ffi.core.Error)
assert info is not None
assert info.type_key == "ffi.Error"
assert info.parent_type_info.type_cls is tvm_ffi.Object
```
