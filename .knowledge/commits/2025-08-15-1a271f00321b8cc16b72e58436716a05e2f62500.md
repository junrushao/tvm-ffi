# Make JSON parser and writer safe under -ffast-math by using bit-level IEEE 754 fallbacks for NaN/Inf
## TL;DR
- Replaces `std::numeric_limits<double>::infinity()`, `std::numeric_limits<double>::quiet_NaN()`, `std::isnan()`, and `std::isinf()` in the JSON parser and writer with `FastMathSafe*` helper functions that use direct IEEE 754 bit manipulation when compiled with `-ffast-math` (`__FAST_MATH__`), falling back to the standard library otherwise.
- Adds corresponding `FastMathSafeIsNaN` / `FastMathSafeIsInf` helpers in the test file so that test assertions remain valid under `-ffast-math`.
- No behavioral change when `-ffast-math` is not enabled; the `#else` branches are identical to the prior code.

## Impact
- API: none -- the `json::Parse` and `json::Stringify` public signatures and behavior are unchanged. The helpers are private static methods within `JSONParserContext` and `JSONWriter`.
- Flags/config: none -- the change is activated automatically by the compiler's `__FAST_MATH__` preprocessor macro, which is set by GCC/Clang `-ffast-math` or `-Ofast`.
- Data formats/schemas: none.

The commit preserves the documented contract that `Parse` handles `NaN`, `Infinity`, and `-Infinity` as extended JSON literals, and that `Stringify` emits them correspondingly.
- **Any system** ([`.knowledge/designs/0002-any-system.md`](../designs/0002-any-system.md)): The parsed `NaN`/`Infinity` values are stored as `double` inside `json::Value` (which is `Any`). The commit ensures the bit patterns written into `Any` are valid IEEE 754 special values even when the compiler's optimizer would otherwise constant-fold them away.

Design elements this commit **produces**:

- **FastMathSafe IEEE 754 helper pattern**: A reusable pattern for creating and detecting `NaN`/`Inf` doubles via raw bit manipulation under `__FAST_MATH__`. The pattern is duplicated across three locations (parser, writer, tests). This is an internal implementation detail, not a public design element, but it establishes a convention for future code that needs to handle special floating-point values safely under aggressive compiler optimizations.

## Key Implementations

### Why `-ffast-math` breaks standard NaN/Inf handling

Under `-ffast-math`, compilers (GCC, Clang) assume floating-point values are never NaN or Inf. This causes:
1. `std::numeric_limits<double>::infinity()` and `quiet_NaN()` to potentially return unexpected values or be optimized away.
2. `std::isnan(x)` and `std::isinf(x)` to be compiled as constant `false`, since the compiler assumes no NaN/Inf exist.
3. JSON round-trip breakage: `json::Parse("NaN")` would produce a garbage double, and `json::Stringify` would fail to detect NaN/Inf for special-case output.

### Bit-level creation (parser side)

Three private static helpers in `JSONParserContext` (`src/ffi/extra/json_parser.cc`):
- `FastMathSafePosInf()`: returns `+Inf` via bit pattern `0x7FF0000000000000ULL`.
- `FastMathSafeNegInf()`: returns `-Inf` via bit pattern `0xFFF0000000000000ULL`.
- `FastMathSafeNaN()`: returns quiet NaN via bit pattern `0x7FF8000000000000ULL`.

These use `reinterpret_cast<const double*>(&bits)` in the original commit diff, though the current codebase uses a union-based type-pun approach (likely a follow-up refinement for stricter C++ compliance).

### Bit-level detection (writer side)

Two private static helpers in `JSONWriter` (`src/ffi/extra/json_writer.cc`):
- `FastMathSafeIsNaN(double x)`: extracts exponent (bits 52-62) and mantissa (bits 0-51). NaN iff exponent == 0x7FF and mantissa != 0.
- `FastMathSafeIsInf(double x)`: same extraction. Inf iff exponent == 0x7FF and mantissa == 0.

Both include `static_assert(sizeof(double) == sizeof(uint64_t))` as a platform safety check.

### Test-side duplication

The test file `tests/cpp/extra/test_json_parser.cc` duplicates `FastMathSafeIsNaN` and `FastMathSafeIsInf` as free `inline` functions in an anonymous namespace. The test assertions `EXPECT_EQ(FastMathSafeIsNaN(json::Parse("NaN").cast<double>()), true)` etc. replace the former `std::isnan`/`std::isinf` calls. This duplication is necessary because the test binary may also be compiled with `-ffast-math`.

### Invariants

- **IEEE 754 double layout assumed**: All helpers assume standard 64-bit IEEE 754 double with 11-bit exponent at bits 52-62 and 52-bit mantissa at bits 0-51. The `static_assert` on `sizeof(double) == sizeof(uint64_t)` guards against exotic platforms.
- **Round-trip preservation**: `json::Stringify(json::Parse("NaN"))` must produce `"NaN"`, `json::Stringify(json::Parse("Infinity"))` must produce `"Infinity"`, etc. This was already the contract; the commit ensures it holds under `-ffast-math`.
- **No behavioral change without `-ffast-math`**: The `#else` branches are identical to the code they replace.

### Extension points

- If additional floating-point special-value handling is needed elsewhere in the codebase under `-ffast-math`, the `FastMathSafe*` pattern can be extracted into a shared utility header (e.g., `include/tvm/ffi/extra/math_compat.h`).
