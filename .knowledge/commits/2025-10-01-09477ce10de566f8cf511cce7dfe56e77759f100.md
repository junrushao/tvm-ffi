# Initial bringup of experimental Rust bindings for TVM FFI
## TL;DR
- Introduces a complete Rust crate workspace (`rust/`) with three crates: `tvm-ffi-sys` (raw C ABI bindings), `tvm-ffi-macros` (proc-macros for `#[derive(Object)]` and `#[derive(ObjectRef)]`), and `tvm-ffi` (safe Rust API wrapping the FFI).
- The Rust bindings faithfully mirror the C++ design: `Any`/`AnyView` type-erased values, `ObjectArc<T>`/`ObjectRef` ref-counted objects, `Function` with packed calling convention, `String`/`Bytes` with small-string optimization, `Error` with traceback appending, `Tensor`/`Shape`/`Module`/`DType`/`Device`.
- Implements native Rust ref-counting (`inc_ref`/`dec_ref` in `object::unsafe_`) matching the C++ two-phase destruction protocol (strong/weak deleter flag dispatch), avoiding C API calls for the hot path.
- Adds `cargo test` to CI pipeline (`.github/workflows/ci_test.yml`), gated after the Python package install step (since Rust links against `libtvm_ffi`).

## Impact
- **API**: Adds a new first-class language binding surface. Rust users can now: create/call `Function` objects, register global functions, load modules via `Module::load_from_file`, work with `Tensor`/`Shape`/`String`/`Bytes`, and export functions via `tvm_ffi_dll_export_typed_func!` macro. The Rust API is public but marked experimental.
- **Flags/config**: Build system relies on `tvm-ffi-config --libdir` CLI tool (from the Python package) for library discovery. A `CARGO_FEATURE_EXAMPLE` feature flag in `tvm-ffi/build.rs` triggers optional example lib generation.
- **Data formats/schemas**: No changes to existing C ABI or C++ API. The Rust crate hand-mirrors `TVMFFIAny`, `TVMFFIObject`, `TVMFFIFunctionCell`, etc. as `#[repr(C)]` structs, establishing a new consumer of the C ABI layout contract.
- **CI**: Adds a `cargo test` step to the test workflow, creating a new CI dependency on `tvm-ffi-config` being available in PATH after Python install.

## Design Elements

Design elements this commit **consumes**:

- **C ABI layer** ([`.knowledge/designs/0001-c-abi.md`]): The `tvm-ffi-sys` crate manually transcribes all core C ABI types (`TVMFFIAny`, `TVMFFIObject`, `TVMFFIFunctionCell`, `TVMFFIByteArray`, `TVMFFIErrorCell`, `TVMFFIShapeCell`, `TVMFFITypeIndex`, `TVMFFIObjectDeleterFlagBitMask`, etc.) into Rust `#[repr(C)]` structs/enums. Also declares `extern "C"` bindings for ~15 C API functions (`TVMFFIFunctionGetGlobal`, `TVMFFIFunctionSetGlobal`, `TVMFFIFunctionCreate`, `TVMFFIErrorCreate`, `TVMFFIErrorMoveFromRaised`, `TVMFFIErrorSetRaised`, `TVMFFIAnyViewToOwnedAny`, `TVMFFITypeKeyToIndex`, `TVMFFIGetTypeInfo`, `TVMFFITensorFromDLPack`, `TVMFFITensorToDLPack`, `TVMFFIStringFromByteArray`, `TVMFFIBytesFromByteArray`, `TVMFFIDataTypeFromString`, `TVMFFIDataTypeToString`, `TVMFFITraceback`).
- **Any/AnyView system** ([`.knowledge/designs/0002-any-system.md`]): Rust `Any`/`AnyView` mirror the C++ design with identical 16-byte `#[repr(C)]` layout wrapping `TVMFFIAny`. The `AnyCompatible` trait is the Rust analogue of `TypeTraits<T>`, providing the same protocol: `copy_to_any_view`, `move_to_any`, `check_any_strict`, `copy_from_any_view_after_check`, `move_from_any_after_check`, `try_cast_from_any_view`. The strict/lenient distinction is preserved.
- **Object system** ([`.knowledge/designs/0003-object-system.md`]): `ObjectArc<T>` is the Rust analogue of `ObjectPtr<T>`. The two-phase destruction protocol (strong bit 0 = destructor, weak bit 1 = free) is implemented natively in Rust (`object::unsafe_::dec_ref`). `ObjectCore` trait = type key + type index + header access. `ObjectRefCore` trait = data accessor for ObjectRef wrappers. Proc-macros generate the boilerplate.
- **Function system** ([`.knowledge/designs/0004-function-system.md`]): `Function` wraps `FunctionObj` which contains `TVMFFIFunctionCell`. Supports packed calling (`call_packed`), tuple calling (`call_tuple`/`call_tuple_with_len`), global get/set, construction from packed/typed/extern-C closures. `AsPackedCallable` trait + `impl_as_packed_callable!` macro mirror C++ `FromTyped` argument unpacking for 0-8 args. `into_typed_fn!` macro provides typed function wrappers (Rust analogue of `TypedFunction<R(Args...)>`).
- **Error handling** ([`.knowledge/designs/0007-error-handling.md`]): `Error` wraps `ErrorObj` with the `TVMFFIErrorCell` layout. Implements `from_raised()`/`set_raised()` for TLS error transport. `with_appended_backtrace` supports both single-owner mutation and copy-on-write. `bail!`/`ensure!`/`check_safe_call!`/`attach_context!` macros provide ergonomic error handling with file/line traceback info.
- **Module system** ([`.knowledge/designs/0013-module-system.md`]): `Module` wraps `ModuleObj` at type index `kTVMFFIModule`. `load_from_file` and `get_function` delegate to `ffi.ModuleLoadFromFile` and `ffi.ModuleGetFunction` global functions via lazy-initialized `Function::get_global`.
- **Small-string optimization** ([`.knowledge/designs/0005-containers.md`], [`.knowledge/designs/0002-any-system.md`]): `String`/`Bytes` in Rust implement the same SSO scheme as C++: strings up to 7 bytes use `kTVMFFISmallStr`/`kTVMFFISmallBytes` with inline storage in `TVMFFIAny.v_bytes`, while longer strings allocate `StringObj`/`BytesObj` with `ObjectCoreWithExtraItems` trailing data.
- **CI/CD pipeline** ([`.knowledge/designs/0021-ci-cd-pipeline.md`]): Adds Rust test step to existing workflow.

Design elements this commit **produces**:

- **Rust bindings architecture**: A new three-crate workspace design (`tvm-ffi-sys` / `tvm-ffi-macros` / `tvm-ffi`). This is the first third-language binding (after C++ and Python) and validates the C ABI's language-agnosticism.
- **`AnyCompatible` trait**: The Rust analogue of `TypeTraits<T>` -- an `unsafe trait` with 7 required methods mapping exactly to the C++ protocol. Implementations provided for: `bool`, integer types (`i8`-`i64`, `u8`-`u64`, `isize`, `usize`), float types (`f32`, `f64`), `()` (maps to `kTVMFFINone`), `*mut c_void`, `Option<T>`, `DLDataType`, `DLDevice`, plus `ObjectRef`-derived types via proc-macro.
- **`ObjectCore` / `ObjectRefCore` traits and proc-macros**: `#[derive(Object)]` auto-generates `ObjectCore` impl (type_key, type_index, object_header_mut with transitive parent delegation). `#[derive(ObjectRef)]` auto-generates `ObjectRefCore` + `AnyCompatible` impls. Custom attributes `#[type_key = "..."]` and `#[type_index(...)]` control registration.
- **`ObjectCoreWithExtraItems` trait**: Rust analogue of `InplaceArrayBase` for objects with trailing variable-length data (used by `StringObj`, `BytesObj`, `ShapeObj`). Provides `extra_items()` / `extra_items_mut()` via pointer arithmetic past `sizeof::<Self>()`.
- **Native Rust ref-counting**: `object::unsafe_::inc_ref`/`dec_ref` implement the full two-phase destruction protocol in pure Rust (no C API call), using `AtomicU64::fetch_sub` with `Ordering::Relaxed` for the common path and `fence(Ordering::Acquire)` on final decrement. Also provides `object_deleter_for_new` and `object_deleter_for_new_with_extra_items` as `extern "C"` deleters.
- **`CallbackFunctionObjImpl<F>`**: Internal `#[repr(C)]` struct that extends `FunctionObj` with a Rust closure, using the C++ pattern of placing the callable immediately after the function cell. Enables `Function::from_packed` and `Function::from_typed`.
- **Macro-based argument handling**: `IntoArgHolder` / `ArgIntoRef` / `IntoArgHolderTuple` / `TupleAsPackedArgs` traits with `impl_into_arg_holder_default!`, `impl_arg_into_ref!`, `impl_tuple_as_packed_args!` macros provide tuple-to-packed-args conversion for 0-8 argument functions.
- **`tvm_ffi_dll_export_typed_func!` macro**: Rust analogue of `TVM_FFI_DLL_EXPORT_TYPED_FUNC`, generating `__tvm_ffi_<name>` C symbols for module export.
- **Build system integration**: Both `tvm-ffi-sys/build.rs` and `tvm-ffi/build.rs` use `tvm-ffi-config --libdir` for library discovery and platform-specific `LD_LIBRARY_PATH`/`DYLD_LIBRARY_PATH`/`PATH` propagation via `cargo:rustc-env`.

  - This doc helps future commit mining because subsequent Rust-related commits (new container types, API additions, bug fixes, clippy lints) will reference these Rust-specific design elements.

### ADRs to write

- **`.knowledge/ADRs/0040-native-rust-ref-counting.md`**
  - **Context**: The Rust bindings could call `TVMFFIObjectIncRef`/`TVMFFIObjectDecRef` C API functions, or implement ref-counting natively in Rust using the same atomic protocol.
  - **Alternatives**: (1) Call C API for every inc/dec-ref, ensuring single implementation. (2) Duplicate the ref-counting logic in Rust for zero-overhead hot paths.
  - **Trade-offs**: Option 2 was chosen for performance (avoids FFI overhead on every ref-count change) at the cost of duplicated invariant enforcement. If the C ABI changes ref-counting semantics (e.g., changing `combined_ref_count` layout), the Rust implementation must be updated in sync.

- **`.knowledge/ADRs/0041-manual-c-api-transcription-in-rust.md`**
  - **Context**: The `tvm-ffi-sys` crate could auto-generate bindings from `c_api.h` via `bindgen`, or manually write `#[repr(C)]` Rust equivalents.
  - **Alternatives**: (1) Use `bindgen` for automatic binding generation. (2) Hand-write Rust struct definitions with careful `#[repr(C)]` annotations.
  - **Trade-offs**: Option 2 was chosen because the C ABI is small and stable, and manual transcription gives precise control over atomic types (`AtomicU64` vs bindgen's generated types), union safety, and Rust-idiomatic naming. Risk: manual copies can drift from `c_api.h`.

### Skill evolution (`/commit-ledger`)

- For very large initial-bringup commits (6000+ lines, 40+ new files), Step 3 produces a large number of consumer/producer design elements because the commit touches every major subsystem. Consider adding a heuristic to Step 2: if a commit is classified as "initial bringup of a new language binding," recommend focusing Step 3 on (a) which C ABI types/functions are consumed, (b) what new abstraction layer is produced, and (c) where the Rust design diverges from C++ (e.g., native ref-counting). This would reduce noise and focus the analysis on architectural decisions rather than exhaustive enumeration.
- The template could benefit from a "Files" or "Key Paths" section listing the most important files for future reference, since large commits touch many files but only a handful encode the core design decisions.

## Self-Evolution of Skill /commit-ledger

The main difficulty encountered during this run was the sheer breadth of the commit: 40+ new files spanning raw C bindings, proc-macros, safe wrappers, tests, CI, and build scripts. The procedure worked well for analyzing each subsystem, but the resulting ledger is long. Two potential improvements:

1. **Add a "commit size heuristic" to Step 2**: If `git show --stat` reports >30 new files or >3000 lines added, flag the commit as "large initial bringup" and suggest a structured analysis template focused on: (a) what existing design elements are consumed, (b) what new design elements are produced, (c) where the new code diverges from existing patterns. This avoids file-by-file narration.

2. **Stabilize scope labels**: This commit introduces the `rust-bindings` scope label. Future Rust commits should reuse this label. Consider adding a note in the procedure to check existing scope labels from prior ledger entries before introducing new ones (this is already in the criterions but easy to overlook in practice).
