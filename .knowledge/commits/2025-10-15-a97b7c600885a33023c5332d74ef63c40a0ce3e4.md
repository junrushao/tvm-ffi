# Fix test object-vs-module destruction ordering and document Module lifetime pitfall
## TL;DR
- Added a `Notes` section to the `Module` class docstring documenting the object-vs-module destruction ordering pitfall: objects returned by module functions have their deleter inside the loaded library, so the module must outlive all returned objects.
- Fixed `test_load_inline_with_env_tensor_allocator` and `test_cuda_memory_alloc_noleak` by wrapping object-using code in nested `run_check()` functions, ensuring returned tensors are destroyed before the module variable goes out of scope.

## Design Elements
Design elements this commit consumes:
- Module system lifetime model: when a `Module` wraps a `DSOLibrary`, all objects whose deleters reside in the loaded `.so` must be destroyed before the `DSOLibrary` is unloaded (see `.knowledge/designs/0013-module-system.md`, DSOLibrary section: `dlclose` on destructor)
- Object deleter is a function pointer stored in the `TVMFFIObject` header, pointing into the allocating library's code segment (see `.knowledge/designs/memory.md`, deleter protocol)

Design elements this commit produces:
- **Module lifetime documentation pattern**: The `Module` docstring now documents the "bad pattern" (flat scope, nondeterministic destruction order) vs "good pattern" (nested function scope, deterministic LIFO destruction). This is a reference for all future tests and user code that loads modules in local scopes.

## Usage Examples
The docstring added to `Module` demonstrates the pattern directly:

```python
# BAD: destruction order of `tensor` and `mod` is not guaranteed
def bad_pattern(x):
    mod = tvm_ffi.load_module("path/to/library.so")
    tensor = mod.func_create_and_return_tensor(x)

# GOOD: `tensor` is freed before `mod` goes out of scope
def good_pattern(x):
    mod = tvm_ffi.load_module("path/to/library.so")
    def run_some_tests():
        tensor = mod.func_create_and_return_tensor(x)
        # ... do something with the tensor
    run_some_tests()
```

The test fix applies this same pattern:
