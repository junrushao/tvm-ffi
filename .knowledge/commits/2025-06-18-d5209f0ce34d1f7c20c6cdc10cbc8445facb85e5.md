# Optimize atomic DecRef in Object by splitting ACQ_REL into RELEASE + conditional ACQUIRE fence

## TL;DR
- `Object::DecRef` now uses `__ATOMIC_RELEASE` on the fetch-sub and only acquires via `__atomic_thread_fence(__ATOMIC_ACQUIRE)` when the ref-counter reaches zero (deleter path). Previously used `__ATOMIC_ACQ_REL` on every decrement.
- Three standalone atomic helper functions (`AtomicIncrementRelaxed`, `AtomicDecrementRelAcq`, `AtomicLoadRelaxed`) are removed from `details` namespace in `base_details.h`; the atomic intrinsics are now inlined directly into `Object::IncRef`, `Object::DecRef`, and `Object::use_count`.
- MSVC path for `DecRef` changes the comparison from `== 1` (old fetch-sub returned pre-decrement value) to `== 0` (new `_InterlockedDecrement` returns post-decrement value), correcting the comparison to match the intrinsic's semantics.

## Key Exports
No new public API. The change is internal to `Object`'s private `IncRef`/`DecRef` and public `use_count`. Signatures are unchanged.

```python
class Object:
    # Unchanged public interface; internal implementation optimized.

    def use_count(self) -> int32: ...
        # Implementation: __atomic_load_n(&ref_counter, __ATOMIC_RELAXED)  [GCC/Clang]
        #                 volatile load via reinterpret_cast               [MSVC]

    # private:
    def IncRef(self) -> None: ...
        # Implementation: __atomic_fetch_add(&ref_counter, 1, __ATOMIC_RELAXED)
        # Invariant: caller must already hold a valid reference

    def DecRef(self) -> None: ...
        # OLD: __atomic_fetch_sub(&ref_counter, 1, __ATOMIC_ACQ_REL) == 1 -> delete
        # NEW: __atomic_fetch_sub(&ref_counter, 1, __ATOMIC_RELEASE) == 1
        #      -> __atomic_thread_fence(__ATOMIC_ACQUIRE)
        #      -> delete
        # Invariant: acquire fence only taken on the deletion path
        # Interacts with: header_.deleter (calls deleter when ref_counter reaches 0)
```

## Impact
- API: None -- all public signatures unchanged.
- Behavioral: DecRef is faster on the common (non-deletion) path because it avoids the acquire barrier. The acquire fence is only taken when ref_counter drops to zero and the deleter will execute. This follows the same pattern as Boost/libc++ `shared_ptr` implementations.
- Flags/config: None.
- Data formats/schemas: None.

These descriptions remain accurate. The specific memory ordering choice (RELEASE+conditional ACQUIRE vs ACQ_REL) is an implementation detail below the design record's abstraction level.
