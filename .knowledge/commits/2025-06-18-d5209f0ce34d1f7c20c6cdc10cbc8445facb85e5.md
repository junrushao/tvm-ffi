# Optimize atomic decref in Object by splitting release/acquire fences
## TL;DR
- Replaces the `__ATOMIC_ACQ_REL` atomic in `DecRef` with a cheaper `__ATOMIC_RELEASE` fetch-sub followed by a conditional `__ATOMIC_ACQUIRE` fence only when the deleter must run, matching the well-known pattern used by `std::shared_ptr` implementations (Boost, libstdc++).
- Removes the generic atomic helper functions (`AtomicIncrementRelaxed`, `AtomicDecrementRelAcq`, `AtomicLoadRelaxed`) from `base_details.h` and inlines platform-specific intrinsics directly into `Object::IncRef`, `Object::DecRef`, and `Object::use_count` in `object.h`.

## Impact
- API: none. `IncRef`, `DecRef`, and `use_count` are private/internal to `Object`; no public signature changes. The behavioral contract (ref-counted lifetime management) is unchanged.
- Flags/config: none.
- Data formats/schemas: none.
- Performance: On non-MSVC platforms, the decrement path is cheaper in the common case (object not yet freed). Previously, every `DecRef` paid for a combined acquire+release barrier (`__ATOMIC_ACQ_REL`). Now, the common-case decrement uses only `__ATOMIC_RELEASE`, and the acquire fence is issued only on the final decrement (when `ref_counter` transitions from 1 to 0). This matters because `DecRef` is on the hot path of every `ObjectPtr` destruction and `Any::reset()`.

## Design Elements

Design elements this commit **consumes**:
- **Object system ref-counting** ([`.knowledge/designs/0003-object-system.md`](../designs/0003-object-system.md)): The commit directly modifies `Object::IncRef`/`DecRef`/`use_count`, which are the core ref-counting primitives documented in the object system design. The invariant that `ref_counter` starts at 1 and the deleter runs when it reaches 0 is preserved.
- **C ABI TVMFFIObject header** ([`.knowledge/designs/0001-c-abi.md`](../designs/0001-c-abi.md)): The `ref_counter` field at offset 4 in the 16-byte `TVMFFIObject` header is the target of all atomic operations. The layout is unchanged.

Design elements this commit **produces**:
- **Split release/acquire pattern for DecRef**: Introduces a new implementation idiom for the decrement path. The old code used a single `__ATOMIC_ACQ_REL` fetch-sub (via `AtomicDecrementRelAcq`). The new code uses `__ATOMIC_RELEASE` fetch-sub + conditional `__ATOMIC_ACQUIRE` thread fence. This is the canonical pattern from the C++ memory model literature and matches `boost::intrusive_ptr` / `libstdc++ shared_ptr` implementations. The key insight: acquire semantics are only needed when the deleter will run (to ensure all prior writes to the object's fields are visible before destruction), so paying for acquire on every non-final decrement is wasteful.
- **Removal of `details::Atomic*` helpers**: The generic helper layer in `base_details.h` is eliminated. Atomic operations are now inlined directly at the call site in `object.h`. This reduces abstraction overhead and makes the memory ordering at each site explicit and locally visible, which is important for reasoning about correctness in lock-free code.

## Reflection

### Design docs to write

- **`.knowledge/designs/0003-object-system.md` (update)**: The existing design doc documents `IncRef`/`DecRef` at a functional level but does not detail the memory ordering semantics. After this commit, the doc should be updated to capture:
  - `IncRef` uses `__ATOMIC_RELAXED` (safe because the caller already holds a reference, so the object cannot be concurrently freed).
  - `DecRef` uses `__ATOMIC_RELEASE` for the fetch-sub, with a conditional `__ATOMIC_ACQUIRE` fence only on the final decrement (when previous count was 1).
  - The MSVC path uses `_InterlockedDecrement` which provides a full barrier implicitly.
  - This matters for future commits that might add weak references, custom deleters, or thread-safe container mutations that depend on these ordering guarantees.

### ADRs to write

None. This is an optimization within an existing design decision (intrusive ref-counting, documented in `.knowledge/ADRs/0003-slot-based-type-allocation.md` and `.knowledge/designs/0003-object-system.md`). No new architectural decisions were made; the change is a well-known refinement of the same approach.

### Design diagrams to draw

None. The change is internal to the `DecRef` implementation and does not alter any component relationships.

### Skill evolution (`/commit-ledger`)

- **Memory-ordering analysis heuristic**: When a commit modifies atomic operations, the skill should explicitly compare before/after memory orderings and verify correctness against the C++ memory model. For this commit, the verification is: (1) relaxed increment is safe because the incrementing thread already holds a live reference, (2) release decrement ensures all stores before the decrement are visible to the thread that will run the deleter, (3) the acquire fence before the deleter ensures the deleter sees all stores from all threads that previously decremented. The skill could add a "memory ordering audit" substep to Step 4 when atomics are involved.

## Self-Evolution of Skill /commit-ledger

- The current procedure does not distinguish between "refactor that preserves semantics" and "refactor that changes semantics subtly." This commit technically changes the memory ordering semantics (from `ACQ_REL` to `RELEASE` + conditional `ACQUIRE`), which is semantically equivalent for correctness but not identical at the instruction level. The skill should prompt the analyst to explicitly call out whether a refactor is strictly semantics-preserving or involves subtle behavioral changes, especially for concurrency-related code.
- For small, focused commits (2 files, ~60 lines changed), the procedure's Step 1 mechanical overview is sufficient and Step 3 can be done in a single pass. The skill could add a "commit size" heuristic: for commits touching fewer than 5 files and fewer than 200 lines, skip the file-prioritization triage and examine all diffs in full.
