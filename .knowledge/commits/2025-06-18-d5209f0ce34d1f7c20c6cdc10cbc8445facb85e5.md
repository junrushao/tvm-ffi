# Optimize atomic decref in Object

## TL;DR
- Replaces the shared `details::AtomicIncrementRelaxed`, `details::AtomicDecrementRelAcq`, and `details::AtomicLoadRelaxed` helper functions in `base_details.h` with platform-specific intrinsics inlined directly into `Object::IncRef`, `Object::DecRef`, and `Object::use_count` in `object.h`.
- Changes `DecRef` from a single `ACQ_REL` atomic decrement to a weaker `RELEASE`-only decrement followed by a conditional `ACQUIRE` fence only on the deletion path. This reduces memory ordering overhead on the common (non-deleting) decrement path.
- Removes the three atomic helper functions from `details` namespace (`base_details.h`), eliminating a layer of indirection.

## Key Changes

### `Object::DecRef` memory ordering optimization (`include/tvm/ffi/object.h`)

**Before:** `DecRef` called `details::AtomicDecrementRelAcq(&ref_counter)` which used `__ATOMIC_ACQ_REL` (GCC/Clang) or `_InterlockedDecrement` (MSVC). The acquire barrier was paid on every decrement, even when the object was not being deleted.

**After (GCC/Clang path):**
1. `__atomic_fetch_sub(&ref_counter, 1, __ATOMIC_RELEASE)` -- release-only decrement. This ensures all prior writes from this thread are visible to the thread that will eventually delete the object, without requiring an acquire on the fast path.
2. Only when `fetch_sub` returns `1` (meaning the counter just hit zero), an explicit `__atomic_thread_fence(__ATOMIC_ACQUIRE)` is issued before calling the deleter. This ensures all writes from other threads that previously released their references are visible before the deleter runs.

**After (MSVC path):** Uses `_InterlockedDecrement` which returns the new value (not the old), so the check is `== 0`. `_InterlockedDecrement` on MSVC implies a full barrier, so no separate fence is needed.

This pattern matches the canonical `shared_ptr` decref optimization described in the C++ standards discussions and used by Boost and libstdc++.

### `Object::IncRef` inlining (`include/tvm/ffi/object.h`)

The `details::AtomicIncrementRelaxed` call is replaced with a direct `__atomic_fetch_add(&ref_counter, 1, __ATOMIC_RELAXED)` (GCC/Clang) or `_InterlockedIncrement` (MSVC). Memory ordering is unchanged (`RELAXED`).

### `Object::use_count` inlining (`include/tvm/ffi/object.h`)

The `details::AtomicLoadRelaxed` call is replaced with a direct `__atomic_load_n(&ref_counter, __ATOMIC_RELAXED)` (GCC/Clang) or volatile load (MSVC). Memory ordering is unchanged (`RELAXED`).

### Removal of `details::Atomic*` helpers (`include/tvm/ffi/base_details.h`)

The three functions `AtomicIncrementRelaxed`, `AtomicDecrementRelAcq`, and `AtomicLoadRelaxed` are deleted from `tvm::ffi::details`. They had no other callers.

## Impact
- **API:** No public API changes. `Object::IncRef`, `DecRef`, `use_count` are private/internal methods not in the public API contract.
- **ABI:** No ABI change. The `TVMFFIObject` header layout and `ref_counter` field are unchanged. Only the implementation of refcount manipulation changed.
- **Behavioral:** Faster `DecRef` on the non-deleting path for GCC/Clang targets. The release-only atomic is cheaper than `ACQ_REL` on weakly-ordered architectures (e.g., ARM). No observable semantic difference; correctness is preserved because the acquire fence on the deletion path ensures all prior releases are visible before the deleter executes.
- **Internal API:** `details::AtomicIncrementRelaxed`, `details::AtomicDecrementRelAcq`, `details::AtomicLoadRelaxed` are removed. Any downstream code calling these (unlikely, as they are in a `details` namespace) would break.

## Design Elements

Design elements this commit consumes:
- **Object pattern** (from `7d34eb8`) -- `Object` base class with `TVMFFIObject header_` containing `ref_counter`, `type_index`, and `deleter`.
- **Intrusive ref-counting** (from `7d34eb8`) -- `IncRef`/`DecRef` called by `ObjectPtr<T>` copy/move/destroy operations.

Design elements this commit produces:
- **Split release/acquire DecRef pattern** -- `DecRef` now uses `RELEASE`-only on the fast path and `ACQUIRE` fence only when the counter reaches zero. This is the canonical optimization for intrusive/shared pointer implementations and reduces overhead on weakly-ordered architectures.
