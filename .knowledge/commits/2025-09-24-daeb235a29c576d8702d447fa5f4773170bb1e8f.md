# Add `field(init=...)` parameter to `@c_class` for excluding fields from generated `__init__`
## TL;DR
- Adds `init: bool` parameter to `field()` and `Field` class, allowing `@c_class` fields to be excluded from the generated `__init__` signature (matching Python `dataclasses.field(init=...)` semantics).
- Rewrites `method_init()` from `inspect.Signature`-based binding to `exec()`-based code generation (matching the pattern used by stdlib `dataclasses` and `pydantic`), supporting three field categories: init-with-default, init-without-default, and non-init.
- Adds C++ test fixture `TestCxxInitSubsetObj` and Python tests verifying the init-subset behavior.

    #   1. init=True, no default  -> positional arg (first in signature)
    #   2. init=True, has default -> keyword arg with MISSING sentinel (after positional)

## Impact
- API: `field()` gains `init: bool = True` keyword parameter. Fully backward-compatible since default is `True`.
- Behavioral: `method_init()` now uses `exec()`-based code generation instead of `inspect.Signature`-based binding. The generated `__init__` no longer wraps exceptions in a custom `TypeError` message. `__post_init__` calling convention unchanged.
- Flags/config: none
- Data formats/schemas: none

## Design Elements
Design elements this commit consumes:
- Reflection system `__ffi_init__` method protocol (0008-reflection): `method_init` requires `__ffi_init__` registered as a type method
- `@c_class` decorator pipeline (0012-python-bindings, `e98b94e`): `fill_dataclass_field` attaches `Field` instances to `TypeField`; `method_init` is called during class decoration
- `TypeInfo`/`TypeField` hierarchy traversal: walks parent chain collecting all fields

Design elements this commit produces:
- **`field(init=False)` protocol**: New three-way field forwarding logic: init+default -> forwarded from user/default, non-init+default -> forwarded from factory only, non-init+no-default -> not forwarded (C++ handles)
- **`exec()`-based `__init__` generation**: Replaces `inspect.Signature` approach with dynamic source code construction (same pattern as stdlib `dataclasses` and `pydantic`)

## Usage Examples
C++ type with a field not in the constructor, paired with Python `@c_class`:
```python
# C++ side (src/ffi/extra/testing.cc):
# TestCxxInitSubsetObj has 3 fields but constructor takes only (int64_t, String).
# optional_field is initialized to -1 by C++ constructor.

# Python side:
from tvm_ffi.dataclasses import c_class, field

@c_class("testing.TestCxxInitSubset")
class _TestCxxInitSubset:
    required_field: int
    optional_field: int = field(init=False)           # excluded from __init__, C++ sets to -1
    note: str = field(default_factory=lambda: "py-default", init=False)  # excluded, default forwarded

obj = _TestCxxInitSubset(required_field=42)
assert obj.required_field == 42
assert obj.optional_field == -1       # set by C++ constructor
assert obj.note == "py-default"       # default_factory value forwarded to C++
```
