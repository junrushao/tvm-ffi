# Add `field(init=...)` parameter to `@c_class` for selective constructor inclusion

## TL;DR
- Extends `field()` and `Field` with an `init: bool` parameter that controls whether a field appears in the generated `__init__` signature, aligning `@c_class` with Python `dataclasses.field(init=...)` semantics.
- Rewrites `method_init()` from `inspect.Signature`/`bind_args` runtime binding to `exec()`-based code generation (matching the approach used by `dataclasses` and `pydantic`), handling three field categories: init-no-default, init-with-default, and no-init-with-default.
- Adds `TestCxxInitSubsetObj` C++ test class and `_TestCxxInitSubset` Python proxy to demonstrate fields excluded from the Python constructor but initialized by C++.

## Impact
- API: Additive -- `field()` gains `init` keyword parameter (default `True` preserves backward compat). `Field` gains `init` slot.
- Behavioral: `method_init()` completely rewritten from `inspect.Signature`-based to `exec()`-based code generation. Generated `__init__` methods now have proper native Python signatures (visible to `inspect.signature()`) rather than `(*args, **kwargs)` with a `__signature__` attribute.
- Flags/config: none
- Data formats/schemas: none

## Design Elements
Design elements this commit consumes:
- **`@c_class` decorator** (`python/tvm_ffi/dataclasses/c_class.py`) -- entry point that calls `method_init`
- **`TypeInfo`/`TypeField`** (`python/tvm_ffi/core`) -- reflected field metadata, `TypeField.dataclass_field` attribute
- **`ObjectDef<T>`** (`include/tvm/ffi/reflection/registry.h`) -- C++ reflection registration with `def_rw`, `def_static`, `refl::init`
- **`Object.__ffi_init__`** (Cython base class) -- canonical C++ constructor call path

Design elements this commit produces:
- **`Field.init` attribute** -- new boolean controlling constructor inclusion, extending the `Field` descriptor
- **`field(init=...)` parameter** -- public API for controlling field init behavior
- **`method_init` exec-based code generation** -- new implementation strategy producing real Python function objects with proper signatures; replaces the `inspect.Signature`/`bind_args` pattern
- **Three-category field forwarding protocol**: (1) init+no-default = required arg forwarded, (2) init+default or no-init+default = default value forwarded, (3) no-init+no-default = omitted from `__ffi_init__` call entirely

## Usage Examples

C++ side defines a type where the constructor only takes a subset of fields:
```cpp
class TestCxxInitSubsetObj : public Object {
 public:
  int64_t required_field;
  int64_t optional_field;
  String note;
  explicit TestCxxInitSubsetObj(int64_t value, String note)
      : required_field(value), optional_field(-1), note(note) {}
  static constexpr bool _type_mutable = true;
  TVM_FFI_DECLARE_OBJECT_INFO("testing.TestCxxInitSubset", TestCxxInitSubsetObj, Object);
};
// Register: __ffi_init__ takes (int64_t, String), but all 3 fields are reflected
```

Python side marks non-constructor fields with `init=False`:
```python
@c_class("testing.TestCxxInitSubset")
class _TestCxxInitSubset:
    required_field: int
    optional_field: int = field(init=False)  # C++ sets to -1
    note: str = field(default_factory=lambda: "py-default", init=False)  # default forwarded to C++

obj = _TestCxxInitSubset(required_field=42)
assert obj.required_field == 42
assert obj.optional_field == -1       # set by C++ constructor
assert obj.note == "py-default"       # Python default forwarded to C++
```
