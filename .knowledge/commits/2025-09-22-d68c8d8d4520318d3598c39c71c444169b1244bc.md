# Fallback for unregistered object types
## TL;DR
- Fixes a crash in the Cython FFI return path (`make_ret_object` in `object.pxi`) when a C++ object's type index has an entry in `TYPE_INDEX_TO_INFO` but that entry is `None` (i.e., the type was allocated an index on the C++ side but never registered on the Python side via `register_object`).
- Before this fix, accessing `.type_cls` on a `None` entry raised an `AttributeError`. After this fix, a `None` entry is handled identically to the "not found" fallback: emit a `UserWarning` and return a bare `Object`.
- Adds `TestUnregisteredObject` (a C++-only object type with no Python `register_object` counterpart) and a `testing.make_unregistered_object` global function for exercising this path.
- Adds a Python test (`test_unregistered_object_fallback`) that verifies the warning is emitted and the returned value has type `tvm_ffi.Object`.

## Key Exports
New testing helpers (not public API):

| Module | Symbol | Description |
|--------|--------|-------------|
| `src/ffi/extra/testing.cc` | `TestUnregisteredObject` | C++ object class registered as `"testing.TestUnregisteredObject"` but intentionally without a Python `register_object` counterpart |
| `src/ffi/extra/testing.cc` | `testing.make_unregistered_object` | Global function returning a `TestUnregisteredObject` through the FFI |
| `python/tvm_ffi/testing.py` | `make_unregistered_object()` | Python wrapper calling `testing.make_unregistered_object` |

## Impact
- API: None -- no public API changes.
- ABI: None.
- Behavioral: Previously, returning a C++ object whose type index maps to a `None` entry in `TYPE_INDEX_TO_INFO` would crash with an `AttributeError`. Now it gracefully falls back to `Object` with a `UserWarning`, matching the existing behavior for indices beyond the length of `TYPE_INDEX_TO_INFO`.
- Flags/config: None.
- Data formats/schemas: None.

## Design Elements
Design elements this commit consumes:
- **Cython object return path** (`.knowledge/designs/0014-python-bindings.md`): The `make_ret_object` function in `object.pxi` that maps a `TVMFFIAny` result containing an object handle back to a Python `Object` subclass using the `TYPE_INDEX_TO_INFO` lookup table. This commit fixes the null-guard logic in this function.
- **Object system type registration** (`.knowledge/designs/object-system.md`): The C++ side allocates type indices for all object types declared with `TVM_FFI_DECLARE_OBJECT_INFO`. The Python side separately registers classes via `register_object`. This commit handles the case where these two registrations are out of sync.

Design elements this commit produces:
- None. This is a defensive fix to an existing code path, not a new design element.

## Usage Examples
```python
import tvm_ffi
import warnings

# Requesting an object whose C++ type has no Python registration
# gracefully falls back to tvm_ffi.Object with a warning
with warnings.catch_warnings(record=True) as w:
    warnings.simplefilter("always")
    obj = tvm_ffi.testing.make_unregistered_object()
    assert type(obj) is tvm_ffi.Object
    assert len(w) == 1
    assert "not registered via register_object" in str(w[0].message)
```
