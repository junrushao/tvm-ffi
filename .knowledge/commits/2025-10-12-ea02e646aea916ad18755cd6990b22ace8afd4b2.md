# feat: stub generation (#101)
## TL;DR
- Introduces `tvm-ffi-stubgen`, a CLI tool (`python/tvm_ffi/stub/stubgen.py`) that scans `.py`/`.pyi` files for special comment markers and fills them with `TYPE_CHECKING`-guarded type stubs derived from the TVM FFI runtime registry.
- Replaces the hand-written `_ffi_api.pyi` stub file with auto-generated inline stubs in `_ffi_api.py`, and adds inline object stubs to `access_path.py`, `testing.py`, and `module.py`.
- Registers the CLI as `tvm-ffi-stubgen` entry point in `pyproject.toml`; adds comprehensive pytest coverage in `test_stubgen.py`.

## Impact
- API: New public CLI tool `tvm-ffi-stubgen` and Python module `tvm_ffi.stub.stubgen`. No existing API signatures changed.
- Behavioral: `_ffi_api.pyi` deleted; type stubs now live inline in `_ffi_api.py` under `TYPE_CHECKING`. Type-checker behavior improves (richer signatures with concrete return types instead of `*args: Any -> Any`). Several `# type: ignore[attr-defined]` suppressions removed in `access_path.py` and `module.py` because stubs now declare the attributes.
- Flags/config: New `--dlls` and `--indent` CLI flags for stub generation.
- Data formats/schemas: The marker comment protocol (`tvm-ffi-stubgen(begin/end/ty_map/skip-file)`) is a new convention embedded in Python source files.

## Design Elements
Design elements this commit consumes:
- **FFI global function registry** (`registry.list_global_func_names()`, `registry.get_global_func_metadata()`) -- used to enumerate and introspect all registered global functions. See [0004-ffi-function-system](../design-records/0004-ffi-function-system.md).
- **FFI reflection / TypeInfo** (`core._lookup_or_register_type_info_from_type_key()`, `TypeSchema.from_json_str()`, `TypeInfo.fields`, `TypeInfo.methods`) -- used to introspect object fields and methods. See [0015-ffi-python-type-system](../design-records/0015-ffi-python-type-system.md), [0007-ffi-reflection](../design-records/0007-ffi-reflection.md).
- **TypeSchema** (Cython class in `core`) -- `repr()` method with a `ty_map` callback for rendering type annotations as strings.
- **Module system** (`Module` object type, its methods) -- stubs generated for `ffi.Module` fields/methods. See [0011-ffi-module-system](../design-records/0011-ffi-module-system.md).

Design elements this commit produces:
- **Stub generation protocol**: The comment-marker convention (`tvm-ffi-stubgen(begin/end/ty_map/skip-file)`) and the CLI tool that processes them. This is a new tooling convention that downstream packages are expected to adopt.
- **Inline stub pattern**: Replaces `.pyi` sidecar files with `if TYPE_CHECKING:` blocks inside `.py` files, co-located with runtime code. This is a new structural convention.
- **Type remapping (`ty_map`)**: A per-block mechanism for renaming type names in generated output (e.g., `list -> Sequence`, `testing.SchemaAllTypes -> _SchemaAllTypes`). Default mappings: `list -> Sequence`, `dict -> Mapping`.

## Usage Examples

Annotating a module with global function stubs:
```python
# In your_package/_ffi_api.py:
from typing import TYPE_CHECKING
import tvm_ffi

tvm_ffi.init_ffi_api("your_prefix", __name__)

# tvm-ffi-stubgen(begin): global/your_prefix
# (stubs will be generated here by running: tvm-ffi-stubgen your_package/)
# tvm-ffi-stubgen(end)
```

Annotating an object class with field/method stubs:
```python
from typing import TYPE_CHECKING
from tvm_ffi.registry import register_object

@register_object("testing.TestIntPair")
class TestIntPair:
    # tvm-ffi-stubgen(begin): object/testing.TestIntPair
    # tvm-ffi-stubgen(ty_map): testing.TestIntPair -> TestIntPair
    if TYPE_CHECKING:
        a: int
        b: int
        @staticmethod
        def __c_ffi_init__(_0: int, _1: int, /) -> Object: ...
    # tvm-ffi-stubgen(end)
```

Running the tool programmatically (from tests):
```python
from pathlib import Path
from tvm_ffi.stub import stubgen

stubgen._main(Path("my_file.py"), stubgen.Options(indent=4, suppress_print=True))
```
