# Guard torch dtype mappings with hasattr for older PyTorch compatibility
## TL;DR
- Moved 9 newer PyTorch dtype mappings (uint16/32/64, float8_*, float4_*) from the inline dict literal to a `hasattr`-guarded loop, preventing `AttributeError` on PyTorch < 2.x.
- Core dtype mappings (int8-64, float16-64, bfloat16, bool, uint8) remain unconditional since they exist in all supported PyTorch versions (>= 1.10).
- Unified the two existing ad-hoc `hasattr` checks (`float8_e8m0fnu`, `float4_e2m1fn_x2`) into the same loop.

## Key Exports
None -- no new public API introduced. Internal mapping table initialization refactored.

## Impact
- API: none
- Behavioral: `import tvm_ffi` no longer crashes when PyTorch < 2.0 is installed; dtype conversions for unavailable types gracefully skip registration instead of raising `AttributeError` at module load
- Flags/config: none
- Data formats/schemas: none

## Design Elements
Design elements this commit consumes:
- `TORCH_DTYPE_TO_DL_DATA_TYPE` mapping dict in `python/tvm_ffi/cython/dtype.pxi` (part of 0012-ffi-python-package) -- the torch-to-DLDataType conversion table
- DLDataType struct type codes from DLPack (code 0=int, 1=uint, 2=float, 4=bfloat, 6=bool, 10-14=float8 variants, 17=float4)

Design elements this commit produces: none

## Usage Examples
Before (crashed on PyTorch < 2.0):
```python
# dtype.pxi inline dict -- AttributeError if torch.uint16 missing
TORCH_DTYPE_TO_DL_DATA_TYPE = {
    ...
    torch.uint16: DLDataType(1, 16, 1),  # fails on PyTorch 1.x
}
```

After (graceful skip):
```python
extra_types = [
    ("uint16", DLDataType(1, 16, 1)),
    ("uint32", DLDataType(1, 32, 1)),
    ...
]
for attr_name, dl_dtype in extra_types:
    if hasattr(torch, attr_name):
        TORCH_DTYPE_TO_DL_DATA_TYPE[getattr(torch, attr_name)] = dl_dtype
```
