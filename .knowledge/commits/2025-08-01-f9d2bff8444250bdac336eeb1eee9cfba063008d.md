# Move StringObj/BytesObj into details namespace to hide implementation types from public API
## TL;DR
- Moves `BytesObjBase`, `BytesObj`, and `StringObj` from `tvm::ffi` into `tvm::ffi::details`, hiding these implementation classes from the public API surface.
- All call sites that referenced `BytesObjBase`, `BytesObj`, or `StringObj` directly (in `any.h`, `structural_equal.cc`, `structural_hash.cc`) are updated to use the `details::` prefix.
- The public-facing ref wrappers `String` and `Bytes` remain in `tvm::ffi` and are unchanged in API; their `TVM_FFI_DEFINE_NOTNULLABLE_OBJECT_REF_METHODS` macros now reference `details::StringObj` / `details::BytesObj` as the container type.

## Impact
- API: The `Obj` types (`StringObj`, `BytesObj`, `BytesObjBase`) are no longer directly accessible as `tvm::ffi::StringObj` etc. Any downstream C++ code that referenced these types by their old fully-qualified names will need to add the `details::` prefix. However, user code is expected to interact with `String`/`Bytes` (the ref wrappers), not the `Obj` types directly, so practical breakage is minimal.
- Flags/config: none.
- Data formats/schemas: none.
- ABI: No C ABI change. The `TVMFFIByteArray` C struct and type indices (`kTVMFFIStr`, `kTVMFFIBytes`) are unchanged. The C++ namespace change is source-level only.

## Design Elements
Design elements this commit **consumes**:

- **Object Obj/Ref pattern** ([`.knowledge/designs/0003-object-system.md`](../designs/0003-object-system.md)): The commit relies on the `FooObj` (data) + `Foo` (ref wrapper) convention. By moving `FooObj` into `details`, the commit leverages the fact that `TVM_FFI_DEFINE_NOTNULLABLE_OBJECT_REF_METHODS` accepts the `Obj` type as a template parameter, so the macro invocation in `Bytes`/`String` just needs to change to `details::BytesObj`/`details::StringObj`.
- **AnyHash / AnyEqual** ([`.knowledge/designs/0002-any-system.md`](../designs/0002-any-system.md)): The `AnyHash` and `AnyEqual` structs in `any.h` directly access `BytesObjBase*` to compare string/bytes content. These are updated to `details::BytesObjBase*`.
- **Container String/Bytes** ([`.knowledge/designs/0005-containers.md`](../designs/0005-containers.md)): The existing design documents `StringObj` and `BytesObj` as extending `BytesObjBase`. This hierarchy is preserved; only the namespace location changes.
- **Structural equality/hashing** (`src/ffi/extra/structural_equal.cc`, `src/ffi/extra/structural_hash.cc`): These internal implementation files access `BytesObjBase*` for content-based comparison. Updated to `details::BytesObjBase*`.

Design elements this commit **produces**:

- **Implementation hiding via `details` namespace**: Establishes the pattern that `Obj` types for built-in containers can be placed in `tvm::ffi::details` when they are not intended for direct use by downstream code. This is a preparatory step: the commit message explicitly states this "will prepare us for future changes such as SmallStr support," suggesting the `StringObj` implementation may be replaced or supplemented with an optimized variant without breaking the public `String` API.

## Key Implementations

**Namespace boundary change in `include/tvm/ffi/string.h`**: The `namespace details {` opening brace was moved from line 80 (after `StringObj`) to line 49 (before `BytesObjBase`), wrapping all three `Obj` classes (`BytesObjBase`, `BytesObj`, `StringObj`) plus the existing `details`-only helpers (`BytesObjStdImpl`, `MakeInplaceBytes`) into a single contiguous `details` block. The closing brace was removed where `namespace details {` previously ended (after `MakeInplaceBytes`). This is a pure namespace re-scoping with no code changes to the classes themselves.

**Ref wrapper updates in `string.h`**: All constructor bodies in `Bytes` and `String` that previously referenced `BytesObj` or `StringObj` directly now use `details::BytesObj` / `details::StringObj`. For example:
- `Bytes(const char* data, size_t size)` changed from `MakeInplaceBytes<BytesObj>(...)` to `MakeInplaceBytes<details::BytesObj>(...)`.
- `TVM_FFI_DEFINE_NOTNULLABLE_OBJECT_REF_METHODS(String, ObjectRef, StringObj)` changed to `..., details::StringObj)`.

**Invariants assumed**:
- The `details` namespace is an established convention in the codebase for internal implementation types. Code outside `tvm::ffi` should not depend on types in `details`.
- `String` and `Bytes` are the stable public API. Their `get()` method returns a pointer to the `Obj` type, so callers using `string.get()->data` still work (the `get()` return type is deduced from the `ContainerType` typedef set by the macro).

**Invariants enforced**:
- By moving `Obj` types into `details`, the commit makes it a compile error for downstream code to use `tvm::ffi::StringObj` without the `details::` qualifier, encouraging use of the ref wrappers instead.

**Extension point**: The commit message mentions "SmallStr support" as a motivating future change. With `StringObj` in `details`, the implementation could introduce a `SmallStringObj` variant (e.g., using the `small_len` field in `TVMFFIAny` mentioned in [`.knowledge/designs/0002-any-system.md`](../designs/0002-any-system.md)) without changing the public `String` type.

## Reflection

### Design docs to write
- **Update `.knowledge/designs/0005-containers.md`**: The `StringObj` / `BytesObj` entries in the "Key Classes" section should note that these types now live in `tvm::ffi::details`, not `tvm::ffi`. The class diagram should be updated to reflect the namespace change. This helps future commit mining when SmallStr or similar optimizations land, as the reader will know the Obj types are intentionally hidden.

### ADRs to write
- **`.knowledge/ADRs/0011-hide-obj-types-in-details.md`**: Record the decision to move built-in container `Obj` types (`StringObj`, `BytesObj`) into the `details` namespace. Context: the public API should only expose ref wrappers (`String`, `Bytes`), allowing internal implementation changes (e.g., SmallStr) without API breakage. Alternatives considered: (1) keep `Obj` in `tvm::ffi` and rely on convention -- rejected because it does not prevent downstream coupling. (2) Use a `_private` or `internal` namespace -- rejected in favor of the existing `details` convention already used for `BytesObjStdImpl`, `MakeInplaceBytes`, etc.

### Design diagrams to draw
- **Mermaid**: A namespace containment diagram showing what lives in `tvm::ffi` (public: `String`, `Bytes`, `Array<T>`, `Map<K,V>`) vs. `tvm::ffi::details` (internal: `StringObj`, `BytesObj`, `BytesObjBase`, `BytesObjStdImpl`, `MakeInplaceBytes`). This would clarify the public/private boundary for future commits that add more container implementation types.
