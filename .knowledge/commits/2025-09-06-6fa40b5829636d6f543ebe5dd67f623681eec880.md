# Add Tensor::strides() accessor and migrate examples from DLTensor* to ffi::Tensor
## TL;DR
- Adds `Tensor::strides()` method that returns a `Shape` by lazily materializing `strides_data_` from the raw `DLTensor::strides` pointer, mirroring the existing `Tensor::shape()` pattern with `shape_data_`.
- Renames the internal `TensorObj` member `stride_data_` to `strides_data_` for consistency with the plural "strides" naming convention used in the public API and `DLTensor::strides`.
- Migrates example code (`examples/packaging/`, `examples/quick_start/`) from raw `DLTensor*` parameters to `ffi::Tensor`, demonstrating idiomatic use of the typed Tensor wrapper instead of raw C pointers.

## Impact
- **API**: New public method `Tensor::strides()` on the `Tensor` ref class. No existing API is broken; this is purely additive. The method lazily caches strides in `strides_data_` on the mutable `TensorObj` (via `get_mutable()`), so first access on a tensor without cached strides writes the field. Note: this version returned `tvm::ffi::Shape` (owning); the current codebase has since refactored it to return `ShapeView` (non-owning) and removed the `strides_data_` caching entirely, with strides stored inline in `TensorObjFromNDAlloc` subclasses.
- **Flags/config**: None.
- **Data formats/schemas**: None.

## Design Elements

Design elements this commit **consumes**:

- **Container System / Tensor (formerly NDArray)** ([`.knowledge/designs/0005-containers.md`](../designs/0005-containers.md)): The `TensorObj` class with its `DLTensor` base, `shape_data_` / `strides_data_` optional members, and the `Tensor` ref wrapper. The `strides()` method mirrors the existing `shape()` pattern, which lazily caches a `Shape` object from the raw `DLTensor::shape` pointer.
- **NDArray stride invariant** (produced by `ca95b41`): The immediately preceding commit `ca95b41` established that `TensorObj::strides` is always non-null for all tensors created via `TensorObjFromNDAlloc` or `TensorObjFromDLPack`. This invariant makes the `ICHECK(obj->strides != nullptr)` in `strides()` a safety assertion rather than a behavioral branch.
- **NDArray-to-Tensor rename** (commit `3a551d8`): The parent commit renamed `NDArray` / `NDArrayObj` to `Tensor` / `TensorObj`. This commit is the first to add new API surface to the renamed class.

Design elements this commit **produces**:

- **Tensor::strides() accessor**: Provides a `Shape`-returning method on the `Tensor` ref class that makes stride access ergonomic in C++. The lazy caching via `strides_data_` was later removed in favor of direct `ShapeView` construction from inplace-allocated stride storage, but the public API surface (`Tensor::strides()`) persists in the current codebase.
- **Example migration to ffi::Tensor**: The examples now demonstrate passing `ffi::Tensor` through the FFI instead of raw `DLTensor*`. This establishes the convention that extension libraries should use the typed `Tensor` wrapper for function signatures, while still using `DLTensor` member access (via `operator->`) internally. This is significant because the `Tensor` type participates in the `Any`/`AnyView` type system (type index `kTVMFFITensor`), enabling automatic conversion in packed function calls, whereas `DLTensor*` uses the POD type index `kTVMFFIDLTensorPtr`.

## Reflection

### Design docs to write

- **Update `.knowledge/designs/0005-containers.md`**: The containers design doc still refers to `NDArrayObj` and `stride_data_` in the "NDArray: Explicit Strides Invariant" section. This should be updated to reflect the rename to `TensorObj` / `strides_data_` and the current inplace-stride storage architecture (no `shape_data_` / `strides_data_` members on `TensorObj` base; strides are stored inline in `TensorObjFromNDAlloc` subclasses). Future commits modifying tensor storage would benefit from having the current architecture documented.

### ADRs to write

None. The decision to add `strides()` is straightforward given the existing `shape()` pattern. The later architectural shift from lazy-cached `Shape` to direct `ShapeView` was a separate decision that may warrant its own ADR if not already covered.

### Design diagrams to draw

None.

### Skill evolution (`/commit-ledger`)

- When a commit immediately follows a rename commit (like `3a551d8` NDArray->Tensor), the skill should explicitly note that the diff operates on newly-renamed symbols. In Step 1, after reading the commit message, check the parent commit message (via `git show -s HEAD~1`) to detect recent renames that provide essential context for understanding the diff. This would have surfaced the NDArray->Tensor rename context more naturally.

## Self-Evolution of Skill /commit-ledger

- For commits that change example/demo code alongside library code, the skill should explicitly distinguish "library API change" from "example migration." The procedure's Step 4 (Mining Key Implementations) does not currently prompt for this distinction, but it is important because example migrations signal intended usage patterns and API stability commitments. Consider adding a sub-step: "Does this commit modify example/demo code? If so, what usage pattern does the example establish?"

- The current procedure does not prompt for checking whether the commit's code has been superseded by later changes in the same file. For commits on historical SHAs (not HEAD), Step 1 should include: "Compare the committed code with the current HEAD version of the same file to note any subsequent refactoring." This would have caught the `Shape`->`ShapeView` return type change and the removal of `strides_data_` caching from `TensorObj`.
