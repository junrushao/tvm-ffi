# Fix Windows inline compilation by running ninja in MSVC developer environment
## TL;DR
- Adds `_run_command_in_dev_prompt()` to `load_inline.py` that locates the Visual Studio Developer Command Prompt (`VsDevCmd.bat`) via `vswhere.exe` and runs build commands within its environment, ensuring MSVC toolchain (`cl`, `link`) is available to `ninja`.
- Modifies `_build_ninja()` to use `_run_command_in_dev_prompt()` on Windows instead of bare `subprocess.run`, fixing the root cause of Windows inline-compilation failures.
- Removes all four `@pytest.mark.xfail` decorators for Windows from `test_load_inline.py` and the now-unused `import sys`, confirming the fix works on Windows CI.

## Key Exports

**Functions** (internal):

| Symbol | Signature | Description |
|--------|-----------|-------------|
| `_run_command_in_dev_prompt` | `(args: list, cwd: str, capture_output: bool) -> subprocess.CompletedProcess` | Locates VS installation via `vswhere.exe`, sources `VsDevCmd.bat -arch=x64`, then runs the given command in that environment via `cmd.exe /c` with shell=True |

## Impact
- API: none -- no public API changes
- ABI: none
- Behavioral: `tvm_ffi.cpp.load_inline()` now works on Windows without requiring the user to manually launch a Developer Command Prompt. The ninja build subprocess inherits the MSVC environment automatically.
- Flags/config: none
- Data formats/schemas: none

## Design Elements
Design elements this commit consumes:
- **Inline module compilation** (`.knowledge/designs/0017-inline-module-compilation.md`): the `_build_ninja` function and the Ninja-based build pipeline are the targets of this fix. The commit specifically addresses the gap where `_build_ninja` called `subprocess.run(["ninja", ...])` directly, which on Windows lacked the MSVC environment variables (`PATH`, `INCLUDE`, `LIB`) needed by `cl.exe` and `link.exe`.
- **IS_WINDOWS platform detection** (`python/tvm_ffi/cpp/load_inline.py`): the existing `IS_WINDOWS = sys.platform == "win32"` constant is used to gate the new code path.

Design elements this commit produces:
- **MSVC Developer Environment Discovery** (`_run_command_in_dev_prompt`): a new internal helper that encapsulates the three-step pattern of (1) finding VS via `vswhere.exe`, (2) locating `VsDevCmd.bat`, and (3) chaining commands with `cmd.exe`. This could be reused by any future subprocess invocations that need MSVC toolchain access.

## Usage Examples

The fix is transparent to callers -- no usage change is needed. The behavioral difference:

**Before (broken on Windows):**
```python
# _build_ninja ran: subprocess.run(["ninja", ...], cwd=build_dir, capture_output=True)
# Failed because cl.exe/link.exe were not on PATH outside a Developer Command Prompt
```

**After (fixed):**
```python
# _build_ninja now runs on Windows:
# _run_command_in_dev_prompt(["ninja", ...], cwd=build_dir, capture_output=True)
# Which executes: cmd.exe /c "VsDevCmd.bat -arch=x64 & ninja ..."
# MSVC tools are now on PATH and environment is properly configured
```
