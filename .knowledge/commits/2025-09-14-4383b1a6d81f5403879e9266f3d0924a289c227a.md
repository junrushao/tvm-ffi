# Fix Windows load_inline by running ninja in MSVC Developer Command Prompt environment
## TL;DR
- Adds `_run_command_in_dev_prompt()` helper that locates Visual Studio via `vswhere.exe`, sources `VsDevCmd.bat -arch=x64`, and runs a command within the MSVC developer environment on Windows.
- Modifies `_build_ninja()` to use `_run_command_in_dev_prompt()` on Windows instead of bare `subprocess.run()`, fixing the root cause of ninja build failures (MSVC toolchain not on PATH).
- Removes all four `@pytest.mark.xfail(sys.platform.startswith("win"), ...)` decorators from `test_load_inline.py`, marking Windows `load_inline` tests as expected-to-pass.

## Key Exports
**Functions** (internal, not public API):
- `_run_command_in_dev_prompt(args: list, cwd: str, capture_output: bool) -> subprocess.CompletedProcess` -- Locates VS install via `vswhere.exe`, constructs a `cmd.exe` invocation that sources `VsDevCmd.bat -arch=x64` then chains the given command, and executes it via `subprocess.run(..., shell=True)`. Raises `RuntimeError` if VS or `VsDevCmd.bat` is not found.

No public API surface changes. `tvm_ffi.cpp.load_inline()` signature is unchanged.

## Impact
- API: None -- `load_inline()` signature unchanged.
- Behavioral: `_build_ninja()` on Windows now runs ninja inside the MSVC developer environment, ensuring `cl.exe`, `link.exe`, and MSVC headers are available. Previously, ninja was invoked in a bare shell where MSVC tools were not on PATH, causing build failures unless the user manually ran from a Developer Command Prompt.
- Flags/config: None.
- Data formats/schemas: None.

## Design Elements
Design elements this commit consumes:
- **Inline module compilation workflow** ([0014-python-package.md](../designs/0014-python-package.md)): The existing `load_inline` -> `_generate_ninja_build` -> `_build_ninja` -> `load_module` pipeline is preserved. Only the subprocess invocation in `_build_ninja` is changed for Windows.
- **Module system** ([0013-module-system.md](../designs/0013-module-system.md)): `load_module()` loads the built `.dll` after successful ninja build.
- **IS_WINDOWS platform flag** (`sys.platform == "win32"`): Used to gate the MSVC dev prompt path.
- **Prior Windows fix** (commit 2df07e5): That commit fixed Ninja build file generation for MSVC (compiler flags, linker syntax, path escaping). This commit fixes the complementary problem: the ninja *execution* environment.

Design elements this commit produces:
- **`_run_command_in_dev_prompt` helper** -- New internal function for executing commands within the MSVC developer environment. This is a platform-specific utility that could be reused by other Windows build steps in the `tvm_ffi.cpp` package.

## Usage Examples
**Before (broken)**: On Windows, `_build_ninja` called `subprocess.run(["ninja", "-v"], ...)` directly. If the user's shell did not have MSVC tools on PATH (the common case outside Developer Command Prompt), ninja would invoke `cl.exe` which would fail with "not found" or produce errors due to missing MSVC headers.

**After (fixed)**: On Windows, `_build_ninja` calls `_run_command_in_dev_prompt(["ninja", "-v"], ...)`, which:
1. Finds VS installation via `vswhere.exe` at `%ProgramFiles(x86)%\Microsoft Visual Studio\Installer\vswhere.exe`
2. Resolves `VsDevCmd.bat` at `<vs_install>\Common7\Tools\VsDevCmd.bat`
3. Runs `cmd.exe /c "VsDevCmd.bat -arch=x64 & ninja -v"` -- sourcing the MSVC environment before invoking ninja
