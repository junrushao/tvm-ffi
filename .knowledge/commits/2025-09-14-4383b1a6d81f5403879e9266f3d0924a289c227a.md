# Fix Windows load_inline by running ninja inside MSVC Developer Command Prompt environment
## TL;DR
- Adds `_run_command_in_dev_prompt()` helper that locates the MSVC Developer Command Prompt via `vswhere.exe`, sources `VsDevCmd.bat -arch=x64`, then chains the original command -- ensuring `cl.exe`, `link.exe`, and MSVC environment variables are available to ninja.
- `_build_ninja()` now dispatches through `_run_command_in_dev_prompt()` on Windows instead of bare `subprocess.run`, fixing builds that fail when ninja is invoked outside a Developer Command Prompt.
- Removes `@pytest.mark.xfail(sys.platform.startswith("win"), ...)` from all four `test_load_inline_cpp*` tests and the now-unused `import sys`, re-enabling Windows CI coverage.

## Impact
- API: none -- `load_inline` public signature unchanged
- Behavioral: `load_inline` now works on Windows even when invoked outside a Developer Command Prompt (e.g., from a plain PowerShell or Jupyter notebook). Previously, ninja would fail because `cl.exe`/`link.exe` were not on PATH.
- Flags/config: none
- Data formats/schemas: none

## Usage Examples
Before (Windows, outside Developer Command Prompt):
```python
# ninja invoked via subprocess.run fails because cl.exe is not on PATH
mod = tvm_ffi.cpp.load_inline(name="hello", cpp_sources=src, functions=["f"])
# RuntimeError: ninja exited with status 1 -- 'cl' is not recognized
```

After (Windows, any shell):
```python
# _build_ninja dispatches through _run_command_in_dev_prompt, which sources VsDevCmd.bat
mod = tvm_ffi.cpp.load_inline(name="hello", cpp_sources=src, functions=["f"])
# Works -- cl.exe found via VsDevCmd.bat environment
```
