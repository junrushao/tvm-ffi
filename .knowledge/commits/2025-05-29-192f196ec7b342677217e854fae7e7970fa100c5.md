# Cleanup PackedFunc redirections: introduce TVM_FFI_DLL_EXPORT and TVM_FFI_DLL_EXPORT_TYPED_FUNC
## TL;DR
- Introduces `TVM_FFI_DLL_EXPORT` macro in `c_api.h` -- an always-export companion to `TVM_FFI_DLL` (which may be import or export depending on `TVM_FFI_EXPORTS`). Defined for all three platform branches: Emscripten, MSVC, and GCC/Clang.
- Adds `TVM_FFI_DLL_EXPORT_TYPED_FUNC` macro in `function.h` to export typed C++ functions as `SafeCallType` C symbols, replacing the downstream-owned `TVM_DLL_EXPORT_TYPED_FUNC` macro.
- Hoists `tvm::ffi::Any` and `tvm::ffi::AnyView` into the `tvm::` namespace via `using` declarations in `any.h` for ergonomic usability outside the `ffi` sub-namespace.

## Impact
- **API**: Two new public macros (`TVM_FFI_DLL_EXPORT`, `TVM_FFI_DLL_EXPORT_TYPED_FUNC`) that downstream consumers should adopt, replacing the legacy `TVM_DLL_EXPORT_TYPED_FUNC`. The legacy macro is flagged for removal once downstream bindings are updated. `tvm::Any` and `tvm::AnyView` are now usable without the `ffi::` qualifier.
- **Flags/config**: none
- **Data formats/schemas**: none

## Design Elements

Design elements this commit **consumes**:

- **C ABI visibility macros** ([`.knowledge/designs/0001-c-abi.md`](../designs/0001-c-abi.md)): `TVM_FFI_DLL` macro and its three-platform `#if` chain. The new `TVM_FFI_DLL_EXPORT` is added to the same chain, following the identical platform-detection pattern.
- **Function packed calling convention** ([`.knowledge/designs/0004-function-system.md`](../designs/0004-function-system.md)): `TVM_FFI_DLL_EXPORT_TYPED_FUNC` uses the existing `FunctionInfo<TCallable>`, `unpack_call<RetType>`, `TVM_FFI_SAFE_CALL_BEGIN/END`, and `AnyView`/`Any` reinterpret_cast pattern from the function system internals.
- **Safe call ABI boundary** ([`.knowledge/ADRs/0005-safe-call-abi-boundary.md`](../ADRs/0005-safe-call-abi-boundary.md)): The new macro generates an `extern "C"` function with `TVMFFISafeCallType` signature, conforming to the safe_call convention (return 0 on success, -1 on error with TLS storage).
- **Any/AnyView type erasure** ([`.knowledge/designs/0002-any-system.md`](../designs/0002-any-system.md)): The `using` declarations expose `Any` and `AnyView` to the `tvm::` namespace. This does not change semantics but broadens the qualified name resolution.

Design elements this commit **produces**:

- **`TVM_FFI_DLL_EXPORT` macro** (`include/tvm/ffi/c_api.h:37-57`): A new visibility macro that always marks a symbol as exported (never `dllimport`). This fills a gap in the C ABI layer -- `TVM_FFI_DLL` may resolve to `dllimport` on MSVC when `TVM_FFI_EXPORTS` is not defined (i.e., when consuming the DLL from outside). `TVM_FFI_DLL_EXPORT` is always `dllexport`/`visibility("default")`/`KEEPALIVE`, making it the correct attribute for symbols that a shared library is exporting regardless of build context. This is a core design addition to the C ABI visibility contract.
- **`TVM_FFI_DLL_EXPORT_TYPED_FUNC` macro** (`include/tvm/ffi/function.h:910-957`): Generates an `extern "C"` function named `ExportName` (note: at commit time, no `__tvm_ffi_` prefix yet; that was added later) with `TVMFFISafeCallType` signature. Internally uses `FunctionInfo<decltype(Function)>` for arity/return type deduction and `unpack_call` for argument unpacking. This is the canonical way to export a typed C++ function from a shared library (module) into the FFI ecosystem. It consumes the function system's unpacking machinery and the safe-call boundary pattern.
- **`tvm::Any` / `tvm::AnyView` aliases** (`include/tvm/ffi/any.h:586-591`): `using` declarations that hoist `tvm::ffi::Any` and `tvm::ffi::AnyView` into the parent `tvm` namespace. This is a usability improvement -- downstream code can write `tvm::Any` instead of `tvm::ffi::Any`.

### ADRs to write

- **`.knowledge/ADRs/0006-dll-export-vs-dll-import.md`**: Records the decision to introduce `TVM_FFI_DLL_EXPORT` as a separate macro from `TVM_FFI_DLL`. Context: `TVM_FFI_DLL` on MSVC toggles between `dllexport` and `dllimport` based on `TVM_FFI_EXPORTS`, which is correct for the core library's own API surface but incorrect for symbols exported by user-compiled shared libraries (modules) that link against the FFI. Alternatives: (1) always use `dllexport` in `TVM_FFI_DLL` (breaks consumers), (2) require users to define their own export macro (fragile). Trade-off: a second macro adds API surface but provides correct semantics for both library-internal and module-external exports.
