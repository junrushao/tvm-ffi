# Guard float4_e2m1fn registration in _dtype.py behind hasattr for ml_dtypes < 0.5 compatibility

## TL;DR
- Wraps `dtype._NUMPY_DTYPE_TO_STR[np.dtype(ml_dtypes.float4_e2m1fn)]` in a `hasattr(ml_dtypes, "float4_e2m1fn")` guard in `python/tvm_ffi/_dtype.py`, preventing `AttributeError` on `ml_dtypes < 0.5.0`.
- Followup to PR #198 (commit `9574e9d`), which applied the same guard pattern in the Cython file `dtype.pxi` but missed this pure-Python registration site.

## Key Exports
None

## Impact
- API: None
- ABI: None
- Behavioral: On `ml_dtypes < 0.5.0`, importing `tvm_ffi` no longer raises `AttributeError` from the `_dtype.py` module-level registration block. The `float4_e2m1fn` entry is simply absent from `dtype._NUMPY_DTYPE_TO_STR` when using an older `ml_dtypes`. On `ml_dtypes >= 0.5.0`, behavior is unchanged.
- Flags/config: None
- Data formats/schemas: None

## Design Elements
Design elements this commit consumes:
- **`dtype._NUMPY_DTYPE_TO_STR` mapping** (`python/tvm_ffi/_dtype.py`): The pure-Python dict mapping `numpy.dtype` objects to TVM dtype string names, populated at module-import time for optional `ml_dtypes` entries.
- **`hasattr`-based version guard pattern**: Same pattern used in PR #198 (`.knowledge/commits/2025-10-28-9574e9d0afb50eca58f56cf0cdce9f64f8cd319f.md`) for the Cython `MLDTYPES_DTYPE_TO_DTYPE` table, and originally in commit `eb5492a1` for torch dtype guards.

Design elements this commit produces:
- None. This is a one-line backward-compatibility fix.
