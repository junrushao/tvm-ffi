# Fix potential flaky issue in Cython dispatcher by keeping alive registered types

## TL;DR
- Adds a module-level `_DISPATCH_TYPE_KEEP_ALIVE` set (with a `threading.Lock` for thread safety) to `function.pxi` that retains strong references to every `PyTypeObject*` registered in `TVMFFIPyCallManager`'s dispatch map, preventing type pointer reuse after garbage collection.
- At the top of `TVMFFIPyArgSetterFactory_`, `type(arg)` is added to the set before the isinstance dispatch chain runs, ensuring the type object remains alive for the lifetime of the process.

## Key Exports

```python
# No new public API symbols. All changes are internal to function.pxi.

# --- python/tvm_ffi/cython/function.pxi ---

# Module-level Cython variables (cdef):
_DISPATCH_TYPE_KEEP_ALIVE: set      # Holds strong refs to all PyTypeObject* seen by the factory
_DISPATCH_TYPE_KEEP_ALIVE_LOCK: threading.Lock  # Guards set mutations for thread safety

# Modified function:
cdef int TVMFFIPyArgSetterFactory_(PyObject* value, TVMFFIPyArgSetter* out) except -1:
    # NEW: adds type(arg) to _DISPATCH_TYPE_KEEP_ALIVE under lock before dispatch
    # Interacts with: TVMFFIPyCallManager.dispatch_map_ (C++ thread-local cache keyed by PyTypeObject*)
    # Invariant: once a type is in _DISPATCH_TYPE_KEEP_ALIVE, its PyTypeObject* address is stable
    ...
```

## Impact
- API: None -- no signature changes, no new public symbols.
- Behavioral: Eliminates a race condition where a locally-defined Python type could be garbage collected after being registered in the C++ `dispatch_map_`, and a new type could be allocated at the same memory address, causing the dispatcher to use the wrong arg setter. This was a flaky/non-deterministic bug that depended on GC timing and memory allocator behavior.
- Memory: Marginal increase -- each unique type passed through FFI is retained permanently. The total number of distinct types is expected to be small in practice (tens, not thousands).
- Thread safety: The lock prepares for a future GIL-free Python (PEP 703 / free-threaded builds). Under the current GIL, the lock is uncontended but adds negligible overhead.
- Flags/config: None.
- Data formats/schemas: None.

## Design Elements
Design elements this commit consumes:
- **Cached PyTypeObject dispatch** (`.knowledge/ADRs/0011-cached-type-dispatch-ffi-call.md`) -- the dispatch_map_ uses `PyTypeObject*` as cache key, which is only safe if the type object remains alive.
- **TVMFFIPyArgSetterFactory_** (`.knowledge/designs/0012-python-bindings.md`) -- the Cython factory that populates the dispatch cache.

Design elements this commit produces:
- **Type keep-alive invariant**: `_DISPATCH_TYPE_KEEP_ALIVE` guarantees that any `PyTypeObject*` registered in the C++ `dispatch_map_` will not be freed and its address will not be reused, closing the safety gap in the `PyTypeObject*`-keyed cache design.

## Usage Examples
None -- no new APIs or changed calling conventions. The fix is fully transparent to users.

## Reflection

### Design docs to write or update
- `.knowledge/designs/0012-python-bindings.md` -- The "Contracts, Assumptions and Invariants" section should add a bullet noting the `_DISPATCH_TYPE_KEEP_ALIVE` set and the type lifetime invariant it enforces for the dispatch cache.
- `.knowledge/ADRs/0011-cached-type-dispatch-ffi-call.md` -- Should note that `PyTypeObject*` stability depends on keeping types alive via `_DISPATCH_TYPE_KEEP_ALIVE`, correcting the earlier assumption that Python types are always singletons (local/dynamic types can be GC'd).

### ADRs to write or update
None new. ADR 0011 should be updated as noted above.

### Stale knowledge references
- ADR 0011 states "No cache invalidation is needed" which is still true, but the implicit assumption that `PyTypeObject*` addresses are stable needs the new caveat about type GC and the keep-alive mechanism.
- Design doc 0012 bullet "Type dispatch cache" states "No cache invalidation is needed because Python types are immutable" -- this is still correct for type identity, but needs the type-lifetime qualification.
