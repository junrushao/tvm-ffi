# Formalize namespace for all object type keys from 'object.*' to 'ffi.*'

## TL;DR
- Renames the `_type_key` strings of all core FFI objects from the `object.*` namespace to the `ffi.*` namespace (e.g., `"object.Object"` -> `"ffi.Object"`, `"object.Array"` -> `"ffi.Array"`, `"object.String"` -> `"ffi.String"`, etc.), ensuring no built-in object sits in a bare or ambiguous root namespace.
- Centralizes the previously inline string literals for `Object`, `Function`, `Array`, and `Map` type keys into `StaticTypeKey` constants (`kTVMFFIObject`, `kTVMFFIFunction`, `kTVMFFIArray`, `kTVMFFIMap`), matching the existing pattern used by `Bytes`, `String`, `Shape`, and `NDArray`.
- The `ErrorObj` type key is changed from `"object.Error"` to `"ffi.Error"` via a direct string literal rather than a `StaticTypeKey` constant (it does not receive a centralized constant in this commit).

## Impact
- API: **Breaking for any consumer that matches on type key strings.** All cross-language bindings (Python `@register_object`, Rust `type_key` matching) that reference `"object.Object"`, `"object.Array"`, `"object.Map"`, `"object.Function"`, `"object.Error"`, `"object.String"`, `"object.Bytes"`, `"object.Shape"`, or `"object.NDArray"` must be updated to use the `"ffi.*"` prefix. The `TVMFFITypeInfo::type_key` returned by `TVMFFIGetTypeInfo` changes for all built-in types.
- Flags/config: none
- Data formats/schemas: The `_type_key` string is part of the type registration ABI -- it is the string passed to `TVMFFIGetOrAllocTypeIndex` and returned by `TVMFFIGetTypeInfo`. Any serialized data that encodes type keys (e.g., JSON-based IR serialization) must be updated.

## Design Elements

Design elements this commit **consumes**:
- **Object system / `_type_key` convention** ([`.knowledge/designs/0003-object-system.md`](../designs/0003-object-system.md)): Every `Object` subclass declares a `static constexpr const char* _type_key` that identifies the type in the global `TypeTable`. This string is used for cross-language type registration, `IsInstance` slow-path lookups (via `TVMFFITypeKeyToIndex`), and Python `@register_object` dispatch. This commit modifies the key values for all 9 built-in object types.
- **C ABI / StaticTypeKey** ([`.knowledge/designs/0001-c-abi.md`](../designs/0001-c-abi.md)): The `StaticTypeKey` struct in `object.h` provides compile-time constants for type key strings used in `TypeTraits` and type conversion error messages. This commit extends it with 4 new constants.
- **Container system** ([`.knowledge/designs/0005-containers.md`](../designs/0005-containers.md)): `ArrayObj` and `MapObj` are core containers whose `_type_key` values change from `"object.Array"`/`"object.Map"` to `StaticTypeKey::kTVMFFIArray`/`StaticTypeKey::kTVMFFIMap`.
- **Function system** ([`.knowledge/designs/0004-function-system.md`](../designs/0004-function-system.md)): `FunctionObj::_type_key` changes from `"object.Function"` to `StaticTypeKey::kTVMFFIFunction`.
- **Error handling** ([`.knowledge/designs/0007-error-handling.md`](../designs/0007-error-handling.md)): `ErrorObj::_type_key` changes from `"object.Error"` to `"ffi.Error"`.

Design elements this commit **produces**:
- **`ffi.*` type key namespace convention**: Establishes the `"ffi."` prefix as the canonical namespace for all built-in FFI object type keys. Prior to this commit, built-in types used the `"object."` prefix. The `"ffi."` prefix aligns with the C++ namespace `tvm::ffi` and clearly distinguishes built-in FFI types from user-defined types (which would use their own namespace prefix, e.g., `"relay.Expr"`).
- **Centralized `StaticTypeKey` constants for all built-in object types**: Adds `kTVMFFIObject`, `kTVMFFIFunction`, `kTVMFFIArray`, `kTVMFFIMap` to the `StaticTypeKey` struct, completing the set. Previously, `Object`, `Function`, `Array`, and `Map` used inline string literals while `Bytes`, `String`, `Shape`, and `NDArray` used `StaticTypeKey` constants. Now all built-in types except `Error` use centralized constants, reducing the risk of typos and enabling single-point-of-change for key renames.

## Reflection

### Design docs to write

- **Update `.knowledge/designs/0003-object-system.md`**: The design doc references `_type_key` as a static constant on every `Object` subclass but does not document the namespace convention for the key string. A subsection should be added under "Object Declaration Macros" or "Contracts, Assumptions and Invariants" specifying:
  - Built-in FFI types use the `"ffi."` prefix (e.g., `"ffi.Object"`, `"ffi.Array"`).
  - User-defined types should use their own namespace prefix (e.g., `"relay.Expr"`, `"tir.PrimFunc"`).
  - The full set of centralized constants lives in `StaticTypeKey`.
  - Why this helps: future commits that add new built-in types or rename type keys can be validated against this convention.

- **Update `.knowledge/designs/0001-c-abi.md`**: The `StaticTypeKey` struct is documented there but the doc does not enumerate all constants. Update the evidence matrix to include the 4 new constants added by this commit.

### ADRs to write

- **`.knowledge/ADRs/0006-type-key-namespace-convention.md`**: Record the decision to use `"ffi."` as the type key namespace prefix for all built-in FFI objects.
  - Context: built-in types originally used `"object."` prefix, which was ambiguous -- it could refer to any object system, not specifically the FFI. The rename to `"ffi."` aligns with the C++ namespace (`tvm::ffi`) and the Python package name (`tvm_ffi`).
  - Alternatives: (1) No prefix for built-in types (rejected: collides with user-defined types); (2) Keep `"object."` prefix (rejected: ambiguous, does not align with namespace); (3) Use `"tvm_ffi."` prefix (viable but verbose, and the C++ namespace is `ffi` not `tvm_ffi`).
  - Trade-off: The rename is an ABI-breaking change that requires updating all language bindings, but it establishes a clearer, more consistent naming scheme going forward.
