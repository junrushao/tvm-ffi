# Fix Map.get to never throw when element is missing by correcting DenseMapObj exception type from IndexError to KeyError

## TL;DR
- Changes `DenseMapObj::At` in `include/tvm/ffi/container/map.h` (line 693 pre-patch) to throw `KeyError` instead of `IndexError` when a key is not found, making it consistent with `SmallMapObj::at` which already threw `KeyError`.
- Adds `test_large_map_get` to `tests/python/test_container.py` that creates a 100-element map (forcing `DenseMapObj` layout) and verifies `Map.get` returns `None` for missing keys and correct values for present keys.

## Key Exports
No new public APIs. The change corrects the exception type thrown by `DenseMapObj::At` (private C++ method) from `IndexError` to `KeyError`.

| Symbol | Location | Change |
|--------|----------|--------|
| `DenseMapObj::At` | `include/tvm/ffi/container/map_base.h:531` | Now throws `KeyError` (was `IndexError`) |
| `test_large_map_get` | `tests/python/test_container.py` | New test function |

## Impact
- API: None -- `Map.__getitem__` and `Map.get` behavior from Python is unchanged for the success path. The failure path now consistently raises `KeyError` across both map layouts.
- ABI: None -- the exception type is part of the runtime error payload, not the C ABI.
- Behavioral: Before this fix, `Map.__getitem__` on a missing key in a large map (>8 entries, backed by `DenseMapObj`) raised `IndexError` instead of the expected `KeyError`. `Map.get` on a large map would propagate this `IndexError` through the `MapGetItemOrMissing` try/catch in `src/ffi/container.cc` (which catches `tvm::ffi::Error`, the common base), so `Map.get` itself was not broken -- it correctly returned the default. However, direct `Map.__getitem__` access (`amap[key]`) on a missing key in a large map raised the wrong exception type (`IndexError` instead of `KeyError`), violating Python's `Mapping` protocol. The existing `test_key_not_found` test used a 2-element map (backed by `SmallMapObj`), which already threw `KeyError`, so it did not catch the bug.
- Flags/config: None.
- Data formats/schemas: None.

## Design Elements
Design elements this commit consumes:
- **Map dual-layout architecture** (`.knowledge/designs/containers.md`): The `MapObj` type dispatches between `SmallMapObj` (linear scan, n<=8) and `DenseMapObj` (open-addressing hash map, n>8) using the MSB tag in `slots_`. Both layouts must throw the same exception types for the same error conditions.
- **Error type hierarchy** (`.knowledge/designs/error-handling.md`): `IndexError` and `KeyError` are both subclasses of `tvm::ffi::Error`. The choice of exception type determines which Python exception class is raised when the error crosses the FFI boundary.
- **MapGetItemOrMissing pattern** (`src/ffi/container.cc:155-162`): The `Map.get` Python method calls `ffi.MapGetItemOrMissing`, which wraps `n->at(k)` in a try/catch for `tvm::ffi::Error` and returns a `MISSING` sentinel on failure. This catch-all approach masked the wrong exception type from `DenseMapObj::At`.

Design elements this commit produces:
- **Consistent KeyError across map layouts**: Both `SmallMapObj::at` and `DenseMapObj::At` now throw `KeyError` for missing keys, making the exception behavior layout-independent. This is a bug fix, not a new design element, but it establishes a correctness invariant: all `MapObj` key-not-found paths must throw `KeyError`.

## Usage Examples
```python
import tvm_ffi

# Before fix: large maps (>8 entries) raised IndexError on missing key
large_map = tvm_ffi.convert({k: k**2 for k in range(100)})

# Map.__getitem__ now correctly raises KeyError (was IndexError for DenseMapObj)
try:
    large_map[101]
except KeyError:
    pass  # correct behavior after fix

# Map.get returns None for missing keys (worked before too, but via catch-all)
assert large_map.get(101) is None
assert large_map.get(3) == 9
```
