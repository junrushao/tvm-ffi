# Fix memory leak in Cython make_tensor_from_chandle when tensor is returned to Python

## TL;DR
- `make_tensor_from_chandle` in `tensor.pxi` failed to call `TVMFFIObjectDecRef(chandle)` after a successful DLPack conversion, leaving the original C handle's ref-count one higher than it should be — causing a memory leak every time a C++ function returned a freshly allocated `Tensor` to Python.
- On the exception path inside the DLPack conversion block, `dlpack.deleter(dlpack)` was missing, so the intermediate `DLManagedTensorVersioned` was also leaked on failure.
- Version bumped `0.1.0b14` → `0.1.0b15` in `pyproject.toml` and `tvm_ffi/__init__.py`.

## Key Exports

```python
# No new public API. The fix is in an internal Cython inline function:
# cdef inline object make_tensor_from_chandle(TVMFFIObjectHandle chandle, DLPackToFn dlpack_to):
#
# Ownership invariant BEFORE fix (broken):
#   - chandle passed in with ref-count N (caller keeps reference)
#   - c_dlpack_to_pyobject() converts to DLManagedTensor, which increments chandle's ref-count to N+1
#   - DLManagedTensor holds ref, Python tensor wraps DLManagedTensor — chandle never decremented
#   - Result: persistent +1 ref-count leak per call
#
# Ownership invariant AFTER fix (correct):
#   - On success: TVMFFIObjectDecRef(chandle) called after c_dlpack_to_pyobject() succeeds
#     => net effect: DLManagedTensor holds one ref, original chandle ref returned to N
#   - On exception: dlpack.deleter(dlpack) called to free the partially-constructed DLManagedTensor
#     => no leak of the intermediate DLPack struct
#
# Interacts with: TVMFFIObjectDecRef (0001-c-abi), c_dlpack_to_pyobject (0016-py-ffi-call-dispatch),
#                 DLManagedTensorVersioned.deleter (DLPack protocol), TensorObj (0007-containers)
# Invariant: after make_tensor_from_chandle returns, caller must NOT use chandle as an owning ref
#            — ownership has been transferred to the returned Python Tensor
```

## Impact
- API: none — internal Cython function, no public signature change
- Behavioral: Eliminates per-call +1 ref-count leak when a C++ function allocates and returns a `Tensor` to Python. Under the old code, every such call would permanently retain one extra ref-count on the underlying `TensorObj`, preventing deallocation until Python process exit.
- Flags/config: none
- Data formats/schemas: none

## Design Elements

Design elements this commit produces: None — bugfix restoring existing ownership invariant.

## Usage Examples

**Before (leaked):**
```python
# C++ function returning ffi::Tensor
# mod.return_tensor(x) — on each call, TensorObj ref-count grows by 1 and never decreases
for i in range(8):
    mod.return_tensor(x)
# after 8 calls, 8 orphaned TensorObj refs remain, CUDA memory never freed
```

**After (correct):**
```python
# Regression test added in test_load_inline.py: test_cuda_memory_alloc_noleak
x = torch.arange(1024 * 1024, dtype=torch.float32, device="cuda")
current_allocated = torch.cuda.memory_allocated()
for i in range(8):
    mod.return_tensor(x)
    diff = torch.cuda.memory_allocated() - current_allocated
    assert diff <= 1024**2 * 8  # memory must not grow monotonically
```

The C++ side of the test uses `Tensor::FromDLPackAlloc(TVMFFIEnvGetTensorAllocator(), ...)` to allocate a new CUDA tensor, which is the allocation path that exercised the leak.
