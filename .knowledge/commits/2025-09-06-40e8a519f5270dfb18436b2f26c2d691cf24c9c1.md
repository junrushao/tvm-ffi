# Append __tvm_ffi_ symbol prefix for FFI-exported function symbols to prevent symbol conflicts
## TL;DR
- Changes `TVM_FFI_DLL_EXPORT_TYPED_FUNC(ExportName, Function)` to emit the extern "C" symbol as `__tvm_ffi_##ExportName` instead of the raw `ExportName`, preventing symbol collisions between FFI-exported functions and non-FFI symbols in the same shared library.
- Introduces a two-tier symbol naming convention in the `Library` interface: `GetSymbol(name)` resolves a raw/prefixed symbol, while a new virtual `GetSymbolWithSymbolPrefix(name)` prepends `symbol::tvm_ffi_symbol_prefix` (`"__tvm_ffi_"`) before resolution. `LibraryModuleObj::GetFunction` now uses the latter.
- Updates well-known symbol constants in `symbol::` namespace: internal symbols (`library_ctx`, `library_bin`, `metadata_prefix`) gain a double-underscore separator (`__tvm_ffi__library_ctx` etc.) to avoid collision with user-prefixed symbols, while `tvm_ffi_main` becomes `__tvm_ffi_main` (user-facing, single underscore). Python `Module` now looks up `"main"` (resolved to `__tvm_ffi_main` via the prefix).

## Impact
- **API**: Breaking ABI change. All shared libraries built with `TVM_FFI_DLL_EXPORT_TYPED_FUNC` will now emit symbols with the `__tvm_ffi_` prefix. Existing compiled `.so`/`.dll` modules are incompatible -- they must be recompiled. Any code that loads DSO symbols by raw name (bypassing the `Module` API) must update to include the prefix. The LLVM codegen and other upstream TVM compiler backends must also be updated to emit the prefixed symbol names.
- **Flags/config**: None.
- **Data formats/schemas**: None. The `__tvm_ffi_library_bin` binary format itself is unchanged, but the well-known symbol name it is stored under changes to `__tvm_ffi__library_bin`.

## Design Elements

Design elements this commit **consumes**:

- **Module Export System** ([`.knowledge/designs/0008-module-export-system.md`](../designs/0008-module-export-system.md)): The `TVM_FFI_DLL_EXPORT_TYPED_FUNC` macro is the sole consumer -- this commit modifies the generated symbol name from `ExportName` to `__tvm_ffi_##ExportName`.
- **Module System / Library interface** ([`.knowledge/designs/0013-module-system.md`](../designs/0013-module-system.md)): `LibraryModuleObj::GetFunction` delegates to `Library::GetSymbol` for symbol resolution. The commit changes the delegation target to the new `GetSymbolWithSymbolPrefix` virtual method.
- **Module System / Well-Known Symbols** ([`.knowledge/designs/0013-module-system.md`](../designs/0013-module-system.md)): The commit renames all four well-known symbol constants (`tvm_ffi_library_ctx`, `tvm_ffi_library_bin`, `tvm_ffi_metadata_prefix`, `tvm_ffi_main`).
- **C ABI / Visibility Macros** ([`.knowledge/designs/0001-c-abi.md`](../designs/0001-c-abi.md)): `TVM_FFI_DLL_EXPORT` is used by the macro to ensure the prefixed symbol has external linkage.

Design elements this commit **produces**:

- **Symbol prefix convention** (`symbol::tvm_ffi_symbol_prefix = "__tvm_ffi_"`): A new constant establishing the canonical prefix for all FFI-exported function symbols in shared libraries. This is the core design element introduced by this commit.
- **Two-tier symbol resolution on `Library`**: A new virtual method `Library::GetSymbolWithSymbolPrefix(const String& name)` that prepends the `__tvm_ffi_` prefix. The base class provides a default implementation (`prefix + name -> GetSymbol`), while `SystemLibrary` overrides it to handle its own `symbol_prefix_` stacking (`__tvm_ffi_` + `symbol_prefix_` + `name`).
- **Internal symbol double-underscore convention**: Internal/infrastructure symbols (`library_ctx`, `library_bin`, `metadata_prefix`) use `__tvm_ffi__` (double underscore before the sub-name) to avoid collision with user-exported FFI functions whose names are prefixed with `__tvm_ffi_`.
- **Python-side symbolic name abstraction**: The Python `Module` class now uses the logical name `"main"` for the entry function, relying on the C++ `GetFunction` + prefix resolution to find the actual symbol `__tvm_ffi_main`. This is a step toward decoupling Python-level names from raw symbol names.

Future commits touching module loading or symbol lookup will need to understand this layering.

### ADRs to write

- **`.knowledge/ADRs/0027-ffi-symbol-prefix.md`**: Record the decision to prefix all FFI-exported DSO symbols with `__tvm_ffi_`. Context: previously, `TVM_FFI_DLL_EXPORT_TYPED_FUNC(Foo, ...)` emitted `Foo` as the raw symbol, risking collision with non-FFI C functions in the same library. The alternative of using a mangled or unique-per-library prefix was rejected in favor of a single global prefix because it keeps symbol resolution simple and deterministic. The double-underscore convention for internal symbols (`__tvm_ffi__`) was chosen to partition the namespace between user-exported functions and infrastructure symbols.

### Design diagrams to draw

- **Mermaid sequence diagram**: Depict the two-tier symbol resolution path from `LibraryModuleObj::GetFunction("foo")` through `GetSymbolWithSymbolPrefix("foo")` which calls `GetSymbol("__tvm_ffi_foo")`, showing the difference between `DSOLibrary` (direct dlsym) and `SystemLibrary` (registry lookup with additional `symbol_prefix_` stacking). This would clarify the layering that currently requires reading three different source files.
