# Restrict stride normalization to 1D tensors on DLPack export to fix PyTorch issue #163274

## TL;DR
- Fixes a bug in the embedded PyTorch DLPack export code (`toDLPackImpl` in `_optional_torch_c_dlpack.py`) where the stride normalization logic incorrectly modified strides of multi-dimensional tensors with size-1 dimensions, causing data corruption or incorrect views for broadcasted/transposed tensors.
- The old code walked all dimensions in reverse, checking whether any size-1 dimension had a non-contiguous stride, and if so normalized all size-1 dimensions to stride 1. This was overly aggressive for multi-dimensional cases.
- The new code restricts normalization to only the trivial case: 1D tensors with `size(0) == 1` and `stride(0) != 1`, where the stride value is irrelevant (only one element, so any stride is equivalent) but non-1 strides could confuse downstream DLPack consumers.

## Key Exports
None (no new APIs). This modifies the inline C++ source compiled by `torch.utils.cpp_extension.load_inline` inside `_optional_torch_c_dlpack.py`.

Changed function:
| Symbol | Kind | Change |
|--------|------|--------|
| `toDLPackImpl<T>` | C++ template (JIT-compiled) | Stride normalization condition narrowed from "any size-1 dim with non-contiguous stride in any ndim tensor" to "1D tensor with size 1 and non-unit stride" |

## Impact
- API: None.
- ABI: None.
- Behavioral: Multi-dimensional tensors with size-1 dimensions and non-unit strides (e.g., result of `torch.broadcast_to`, `unsqueeze`, or `transpose` producing size-1 dims) are no longer incorrectly re-strided during DLPack export. Previously, a tensor like `shape=[1, 3, 224, 224]` with `stride=[0, 224*224, 224, 1]` (broadcast in dim 0) would have dim 0's stride silently changed to 1, producing a wrong view of the data. Now such tensors pass through unmodified.
- The 1D scalar-like case (`shape=[1], stride=[N]` where N != 1) is still normalized to `stride=[1]`, which is the only case where normalization is safe and necessary (the single element is correctly addressed regardless of stride, but some DLPack consumers assume contiguous strides).
- Data formats/schemas: None.
- Flags/config: None.

## Usage Examples
```python
import torch
import tvm_ffi

# Before this fix, broadcasting could produce incorrect DLPack exports:
x = torch.randn(3, 224, 224)
y = x.unsqueeze(0)  # shape=[1, 3, 224, 224], stride=[0, 224*224, 224, 1]

# Export via DLPack fast path (through TorchDLPackFromPyObject)
f = tvm_ffi.get_global_func("testing.echo")
z = f(y)  # round-trips through DLPack

# After fix: strides preserved correctly; dim-0 stride remains 0 (broadcast)
# Before fix: dim-0 stride was incorrectly normalized to 1
```
