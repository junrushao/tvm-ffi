# Reorganize C API layout in c_api.h and move env APIs to extra tier

## TL;DR
- Reorders declarations in `c_api.h` so that user-facing C API functions (object, function, error, DLPack, dtype, type-reflection) appear immediately after the struct/enum definitions they operate on, replacing the old monolithic "User APIs" section at the bottom.
- Moves `TVMFFIEnvCheckSignals` and `TVMFFIEnvRegisterCAPI` out of `c_api.h` into the extra-tier header `include/tvm/ffi/extra/c_env_api.h`, with their implementation relocated from `src/ffi/function.cc` to a new `src/ffi/extra/env_c_api.cc`.
- Renames three module-scoped C API symbols to include a `Mod` infix (`TVMFFIEnvLookupFromImports` -> `TVMFFIEnvModLookupFromImports`, `TVMFFIEnvRegisterContextSymbol` -> `TVMFFIEnvModRegisterContextSymbol`, `TVMFFIEnvRegisterSystemLibSymbol` -> `TVMFFIEnvModRegisterSystemLibSymbol`) to disambiguate module-level operations from general environment operations.
- Moves `src/ffi/testing.cc` from the core build to `src/ffi/extra/testing.cc` in the extra-tier build.

## Impact
- API: **Breaking** for callers of `TVMFFIEnvRegisterCAPI` (signature change from `const TVMFFIByteArray*` to `const char*`), `TVMFFIEnvLookupFromImports`, `TVMFFIEnvRegisterContextSymbol`, and `TVMFFIEnvRegisterSystemLibSymbol` (all renamed with `Mod` infix). `TVMFFIEnvCheckSignals` and `TVMFFIEnvRegisterCAPI` are no longer declared in `c_api.h` -- callers must now include `tvm/ffi/extra/c_env_api.h`. Internal callers (Cython bindings, module implementations) need updating.
- Flags/config: `testing.cc` is now only compiled when `TVM_FFI_USE_EXTRA_CXX_API=ON` (was unconditional before). This shrinks the core library when extra APIs are disabled.
- Data formats/schemas: none

## Design Elements

Design elements this commit consumes:

- **C ABI layer** (`.knowledge/designs/0001-c-abi.md`): The commit restructures the declaration order in `c_api.h` but does not change any struct layouts, type indices, or ABI contracts. All existing `extern "C"` functions retain identical signatures (except the four renamed/moved ones).
- **Extra API tier** (`.knowledge/designs/0011-extra-api-tier.md`): The commit extends the extra tier to include environment C APIs (`EnvCAPIRegistry`, `TVMFFIEnvCheckSignals`, `TVMFFIEnvRegisterCAPI`) and testing utilities. This reinforces the layering contract that environment-specific runtime hooks are non-core.
- **Function system** (`.knowledge/designs/0004-function-system.md`): `EnvCAPIRegistry` was previously co-located with `GlobalFunctionTable` in `src/ffi/function.cc`. The commit separates these concerns, leaving `function.cc` focused purely on the function system.
- **Module export system** (`.knowledge/designs/0008-module-export-system.md`): The `Mod` infix rename clarifies that `TVMFFIEnvModLookupFromImports`, `TVMFFIEnvModRegisterContextSymbol`, and `TVMFFIEnvModRegisterSystemLibSymbol` are module-scoped operations (used by loaded library modules), not general environment operations.

Design elements this commit produces:

- **c_api.h section ordering convention**: The commit establishes a new convention where C API function declarations are grouped by the struct/enum they operate on, placed immediately after those definitions. This replaces the prior layout where all user-facing functions were grouped in a single "User APIs" section at the end of the file. This convention, while not a new class or invariant, is an organizational design element that future `c_api.h` changes should follow.
- **Env API tier separation**: `TVMFFIEnvCheckSignals` and `TVMFFIEnvRegisterCAPI` are now part of the extra API tier, not the core C ABI. This formally classifies host-environment integration (Python signal checking, GIL management) as non-core functionality. Deployments without a Python host can exclude these symbols.
- **`Mod` naming convention for module-scoped C APIs**: The `TVMFFIEnvMod*` prefix convention distinguishes C API functions that operate in the context of a loaded module (callee-side) from those that operate in the general host environment. This naming pattern should be followed for future module-scoped C APIs.

## Reflection

### Design docs to write

- **`.knowledge/designs/0001-c-abi.md` update**: Add a subsection documenting the c_api.h section ordering convention (structs/enums followed immediately by their operating functions). This helps future contributors know where to place new C API declarations and prevents regression to the old monolithic layout. Commits adding new C API functions would reference this.

### ADRs to write

- **`.knowledge/ADRs/0018-env-mod-naming-convention.md`**: Document the decision to use `TVMFFIEnvMod*` prefix for module-scoped C API functions vs `TVMFFIEnv*` for general host environment operations. Context: the three renamed symbols were ambiguous about whether they operated on a specific module context or the global environment. Alternatives: use a separate `TVMFFIMod*` prefix (rejected because these are still "environment" APIs from the callee perspective), keep flat `TVMFFIEnv*` naming (rejected because it conflates module-scoped and global-scoped operations). Trade-off: slightly longer symbol names for clearer scoping.

### Design diagrams to draw

- None. The changes are organizational (file/symbol renaming and relocation) rather than introducing new relationships between components.

### Skill evolution (`/commit-ledger`)

- **Recognize "reorganization-only" commits explicitly**: This commit is primarily a reorganization/relocation of existing code with some renames. Step 2's classification options do not include "reorganization" as a distinct category. Consider adding "reorganization" (code movement, section reordering, symbol renames without behavioral change) as a commit characterization option in Step 2, separate from "refactor" which implies structural code changes.
- **Track API renames systematically**: When a commit renames C API symbols, Step 4 should explicitly enumerate old-name -> new-name mappings and note signature changes (like `const TVMFFIByteArray*` -> `const char*` for `TVMFFIEnvRegisterCAPI`). This is critical for downstream consumers who search by symbol name. Consider adding a "Symbol Renames" subsection to the template.

## Self-Evolution of Skill /commit-ledger

The template's `## Impact` section worked well for capturing the breaking API changes. However, for commits that are primarily about code organization (moving code between files, reordering sections within a file), the current procedure spends significant effort in Steps 3-4 looking for behavioral changes that do not exist. A lightweight "reorg fast path" in Step 2 (after confirming no behavioral changes via diff inspection) could skip deep mining and focus on documenting the organizational rationale and any symbol renames. This would reduce analysis time for layout-focused commits while still capturing the important downstream-facing changes (renamed symbols, moved headers).
