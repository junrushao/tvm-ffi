# Fix Cython c_handle() mishandling of ctypes.c_void_p(0), where .value returns None instead of 0

## TL;DR

- `ctypes.c_void_p(0).value` returns `None` in Python (not `0`) — a well-known ctypes quirk for null pointer values.
- The Cython inline `c_handle()` function in `base.pxi` previously assigned `handle.value` directly into a `uint64`, silently interpreting `None` as invalid rather than `0`.
- Fix: capture `.value` into a Python object first, then guard with `0 if value is None else value`.

None

## Impact

- API: none — `c_handle()` is an internal Cython inline, not part of the public Python API.
- Behavioral: `ctypes.c_void_p(0)` passed to any FFI call now correctly routes as a null pointer (address `0x0`) rather than crashing or passing garbage.
- Flags/config: none
- Data formats/schemas: none

## Design Elements

Design elements this commit consumes:
- `c_handle()` / `ctypes_handle()` Cython inlines in `python/tvm_ffi/cython/base.pxi` — the low-level pointer marshalling layer between Python `ctypes.c_void_p` objects and raw C `void*` values. Not separately documented in design records; part of [0012-ffi-python-package](../design-records/0012-ffi-python-package.md) Cython binding layer.

Design elements this commit produces: none — restores existing invariant only.

## Usage Examples

**Before (broken):**
```python
# ctypes.c_void_p(0).value is None in CPython — c_handle() would pass None directly
# into an unsigned long long cast, producing undefined behavior or a type error.
result = fecho(ctypes.c_void_p(0))  # could crash or produce wrong pointer value
```

**After (fixed):**
```python
# c_handle() now correctly maps None -> 0 before the cast
result = fecho(ctypes.c_void_p(0))
assert result is None  # ctypes round-trips null pointer as None on return path
```

The invariant restored: `c_handle(ctypes.c_void_p(v))` must yield `<void*> v` for all `v`, including `v == 0`.
