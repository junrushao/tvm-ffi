# Align bool dtype parsing to use kDLBool (code=6, bits=8) instead of kDLUInt (code=1, bits=1)

## TL;DR
- Changes the C++ dtype string parser (`StringViewToDLDataType_`) to map `"bool"` to `{code=kDLBool(6), bits=8}` instead of the legacy `{code=kDLUInt(1), bits=1, lanes=1}`. The old early-return path is removed in favor of a standard parsing branch that supports lane suffixes (e.g., `boolx4`).
- Changes the C++ dtype-to-string function (`DLDataTypeToString_`) to recognize `{code=kDLBool, bits=8, lanes=1}` as `"bool"`, and suppresses the bit-width suffix for `kDLBool` when `bits==8` (avoiding `"bool8"`).
- Adds `BOOL = 6` to the Python `DataTypeCode` enum, and adds a Python test verifying round-trip parsing and lane support for `"bool"` / `"boolx4"`.

```python
class DataTypeCode(IntEnum):

    UINT = 1

    Float8E3M4 = 7
    # ...
    # Interacts with: DLDataType struct (code field), DLDataTypeToString_(), StringViewToDLDataType_()
    # Invariant: values must match DLPack's DLDataTypeCode enum (kDLBool = 6)

# C++ behavioral change (pseudocode):
# OLD: StringViewToDLDataType_("bool") -> DLDataType(code=kDLUInt, bits=1, lanes=1) [early return]
# NEW: StringViewToDLDataType_("bool") -> DLDataType(code=kDLBool, bits=8, lanes=<parsed>)
#   Interacts with: DLDataTypeToString_ (inverse), dtype() Python class, Tensor dtype field
#   Invariant: bool is now {kDLBool, 8, 1} -- 8-bit storage, matching DLPack spec

# OLD: DLDataTypeToString_(code=kDLUInt, bits=1, lanes=1) -> "bool"
# NEW: DLDataTypeToString_(code=kDLBool, bits=8, lanes=1) -> "bool"
#   Invariant: suppresses bit-width suffix when code==kDLBool && bits==8 (prints "bool" not "bool8")
#   Invariant: multi-lane bools print as "boolx4" (lane suffix still appended)
```

## Impact
- API: `DataTypeCode.BOOL = 6` is newly available in Python. No existing API removed, but the wire representation of `"bool"` changes.
- Behavioral: `tvm_ffi.dtype("bool")` now returns `{type_code=6, bits=8, lanes=1}` instead of `{type_code=1, bits=1, lanes=1}`. Any code comparing bool dtypes by numeric fields will see different values. Multi-lane bools (e.g., `"boolx4"`) now work via the standard lane-suffix parsing path.
- Flags/config: none
- Data formats/schemas: Serialized `DLDataType` values for bool change from `(1, 1, 1)` to `(6, 8, 1)`. Any persisted dtype values or cross-process dtype comparisons will break if not updated.

## Usage Examples

Before/after pattern showing the corrected bool dtype behavior (from `tests/python/test_dtype.py`):

```python
import tvm_ffi

# BEFORE (old behavior):
# dtype = tvm_ffi.dtype("bool")
# dtype.type_code == 1  # kDLUInt -- WRONG per DLPack
# dtype.bits == 1       # sub-byte -- inconsistent with DLPack kDLBool
# dtype.with_lanes(4)   # would produce "uint1x4" -- not "boolx4"

# AFTER (new behavior):
dtype = tvm_ffi.dtype("bool")
assert dtype.type_code == 6   # kDLBool -- matches DLPack
assert dtype.bits == 8        # 8-bit storage
assert dtype.lanes == 1

dtype_vec = dtype.with_lanes(4)
assert dtype_vec.type_code == 6
assert dtype_vec.bits == 8
assert dtype_vec.lanes == 4
assert dtype_vec == "boolx4"  # round-trips correctly
```
