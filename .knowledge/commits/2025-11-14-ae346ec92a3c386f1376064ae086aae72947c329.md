# Align bool dtype parsing to DLPack: kDLBool with bits=8, not kDLUInt with bits=1

## TL;DR
- `src/ffi/dtype.cc`: changes `bool` string → DLDataType mapping from `{code=kDLUInt, bits=1}` to `{code=kDLBool, bits=8}` to match DLPack spec.
- `DLDataTypeToString_()` updated to recognize `{kDLBool, bits=8, lanes=1}` → `"bool"` (previously matched `{kDLUInt, bits=1}`).
- `python/tvm_ffi/_dtype.py`: adds `BOOL = 6` to `DataTypeCode` enum.
- Adds 13 test lines.

## Key Exports

```python
# python/tvm_ffi/_dtype.py
class DataTypeCode(IntEnum):
    INT = 0
    UINT = 1
    FLOAT = 2
    HANDLE = 3
    BFLOAT = 4
    BOOL = 6  # NEW: kDLBool code value from DLPack spec
    ...

# Before:
# dtype("bool") → {code=kDLUInt, bits=1, lanes=1}  # non-standard
# After:
# dtype("bool") → {code=kDLBool, bits=8, lanes=1}  # DLPack compliant
```

## Impact
- API: `DataTypeCode.BOOL = 6` added to Python enum.
- Behavioral: Breaking change for any code expecting `bool` → `{kDLUInt, bits=1}`. Now produces `{kDLBool, bits=8}`.
- Flags/config: none
- Data formats/schemas: Serialized dtype for `bool` changes; affects any checkpoint format that stored `"bool"` dtype strings.

## Design Elements
Design elements this commit consumes: `dtype` type system, `DLDataType` parsing (0001-c-abi)
Design elements this commit produces:
- Corrected `bool` ↔ DLDataType mapping: `{kDLBool, bits=8}` (0001-c-abi mutation)

After:
```python

```
