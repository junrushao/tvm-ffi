# Fix torch_c_dlpack_ext import and build-time circular import issues
## TL;DR
- Fix broken `import core` in `torch_c_dlpack_ext/__init__.py` to use relative import (`from . import core`), which was preventing the prebuilt package from working.
- Add `TVM_FFI_DISABLE_TORCH_C_DLPACK=1` env var during wheel build to prevent circular import: building the extension triggers `tvm_ffi` import, which tries to load the not-yet-built `torch_c_dlpack_ext`.
- Change the prebuilt-package detection logic in `load_torch_c_dlpack_extension()` to verify the extension actually worked (checks `__c_dlpack_exchange_api__` attribute) rather than returning immediately after import.
- Version bump `torch_c_dlpack_ext` from 0.1.0 to 0.1.1.

## Key Exports
None -- no new public API surface. The behavioral fix is internal to the import/load path.

## Impact
- API: None.
- ABI: None.
- Behavioral: `torch_c_dlpack_ext` prebuilt packages now work correctly. Previously, installing the prebuilt wheel would fail at import time due to `import core` (bare, non-relative) not resolving. Additionally, building the wheel could fail or produce incorrect results due to a circular import where `tvm_ffi` tried to load the extension during the build process itself.
- Flags/config: The `TVM_FFI_DISABLE_TORCH_C_DLPACK` environment variable is now set during `build_wheel` in `build_backend.py`, suppressing the extension loader while the extension is being built.
- Data formats/schemas: None.

## Design Elements
Design elements this commit consumes:
- DLPack fast-path protocol and `__c_dlpack_exchange_api__` detection (`.knowledge/designs/0018-dlpack-fast-path.md`)
- `TVM_FFI_DISABLE_TORCH_C_DLPACK` environment variable guard in `_optional_torch_c_dlpack.py` (already existed before this commit)
- `torch_c_dlpack_ext` addon build backend pattern (`.knowledge/designs/0018-dlpack-fast-path.md`, PyTorch Integration Module section)

Design elements this commit produces:
- Build-time circular-import prevention pattern: set `TVM_FFI_DISABLE_TORCH_C_DLPACK=1` in the subprocess environment when building the extension to prevent `tvm_ffi` from attempting to load the not-yet-built extension
- Prebuilt-package verification pattern: after importing the prebuilt package, verify the extension actually installed its protocol attribute (`__c_dlpack_exchange_api__`) before returning early; fall through to JIT build path if not

## Usage Examples

### Before/After: Prebuilt package import fix
**Before (broken):** `torch_c_dlpack_ext/__init__.py` used bare `import core`, which fails when the package is installed as a wheel because `core` is not a top-level module.

```python
# BROKEN -- bare import fails for installed packages
import core
```

**After (fixed):** Uses relative import so the `core` submodule is found within the package.

```python
# CORRECT -- relative import works in all installation modes
from . import core
```

### Before/After: Build-time circular import
**Before (broken):** Building the wheel invokes `tvm_ffi` (via the build script), which imports `_optional_torch_c_dlpack`, which tries to `import torch_c_dlpack_ext` -- the package currently being built.

**After (fixed):** The build backend sets `TVM_FFI_DISABLE_TORCH_C_DLPACK=1` in the subprocess environment, so `_optional_torch_c_dlpack` skips extension loading during the build.

```python
subprocess.run(
    [...],
    check=True,
    env={**os.environ, "TVM_FFI_DISABLE_TORCH_C_DLPACK": "1"},
)
```

### Before/After: Prebuilt detection
**Before (broken):** `load_torch_c_dlpack_extension()` returned `None` immediately after successfully importing `torch_c_dlpack_ext`, without checking whether the extension actually installed the protocol attribute.

**After (fixed):** After importing the prebuilt package, the function checks `hasattr(torch.Tensor, "__c_dlpack_exchange_api__")` before returning early. If the attribute is not present, execution falls through to the JIT build path.
