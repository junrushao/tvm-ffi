# Add file-based build() and load() to tvm_ffi.cpp extension module
## TL;DR
- Adds `tvm_ffi.cpp.build()` and `tvm_ffi.cpp.load()` functions that compile C++/CUDA from **source files on disk** (as opposed to inline source strings), following the interface of `torch.utils.cpp_extension.load`.
- Renames `load_inline.py` to `extension.py` and refactors `build_inline` to delegate to a shared `_build_impl()` helper that both the inline and file-based APIs use.
- Refactors `_generate_ninja_build()` to accept explicit `cpp_files`/`cuda_files` lists (multiple files per category) instead of assuming a single hardcoded `main.cpp`/`cuda.cu`.

## Key Exports
**Functions**:
- `tvm_ffi.cpp.build(name, *, cpp_files=None, cuda_files=None, extra_cflags=None, extra_cuda_cflags=None, extra_ldflags=None, extra_include_paths=None, build_directory=None) -> str` -- Compiles C++/CUDA source files into a shared library and returns the path. Does **not** auto-decorate with FFI headers/export macros (user must use `TVM_FFI_DLL_EXPORT_TYPED_FUNC` manually).
- `tvm_ffi.cpp.load(name, *, cpp_files=None, cuda_files=None, extra_cflags=None, extra_cuda_cflags=None, extra_ldflags=None, extra_include_paths=None, build_directory=None) -> Module` -- Calls `build()` then `load_module()` on the result. Convenience wrapper.

**Internal functions**:
- `_build_impl(name, cpp_files, cuda_files, extra_cflags, extra_cuda_cflags, extra_ldflags, extra_include_paths, build_directory, need_lock=True) -> str` -- Shared implementation for both `build()` and `build_inline()`. Generates ninja build, compiles, returns library path.
- `_str_seq2list(seq: Sequence[str] | str | None) -> list[str]` -- Normalizes string/sequence/None to list. Extracted from duplicated patterns in `build_inline()`.

**Renames**:
| Old | New |
|-----|-----|
| `python/tvm_ffi/cpp/load_inline.py` | `python/tvm_ffi/cpp/extension.py` |
| Doc section title "Inline Loading" | "C++ Extension" |

## Impact
- API: New public functions `tvm_ffi.cpp.build` and `tvm_ffi.cpp.load` added. Existing `build_inline`/`load_inline` remain backward-compatible (they still work identically, just internally delegate to `_build_impl`). The import path `from tvm_ffi.cpp.load_inline import ...` is broken by the rename; callers should use `from tvm_ffi.cpp import ...` or `from tvm_ffi.cpp.extension import ...`.
- ABI: none
- Behavioral: `_generate_ninja_build()` now builds numbered object files (`cpp_0.o`, `cpp_1.o`, `cuda_0.o`, ...) from explicit file lists instead of a single hardcoded `main.o`/`cuda.o`. The `build_dir` parameter is removed from `_generate_ninja_build()`. `_hash_sources()` now accepts optional `cpp_files`/`cuda_files` parameters for content-addressable caching of file-based builds.
- Flags/config: none
- Data formats/schemas: none

## Design Elements
Design elements this commit consumes:
- **Inline module compilation** (`.knowledge/designs/0017-inline-module-compilation.md`): Existing Ninja-based build pipeline, `_hash_sources`, `_generate_ninja_build`, `_maybe_write`, `build_ninja`, `FileLock`, content-addressable cache.
- **Module system** (`.knowledge/designs/0013-module-system.md`): `load_module()` to load the compiled shared library as a `Module`, `TVM_FFI_DLL_EXPORT_TYPED_FUNC` macro for symbol export.
- **Python packaging** (`.knowledge/designs/0015-python-packaging.md`): `find_include_path()`, `find_dlpack_include_path()`, `find_libtvm_ffi()` for locating build dependencies.

Design elements this commit produces:
- **File-based C++ extension build API**: New `build()`/`load()` functions that accept file paths instead of inline source strings. Key difference from `build_inline`/`load_inline`: no automatic FFI header decoration or export macro injection -- users must include headers and export macros in their source files explicitly.
- **Multi-file ninja build support**: `_generate_ninja_build()` now supports arbitrary numbers of C++ and CUDA source files, producing indexed object files and linking them all.
- **Shared `_build_impl()` internal**: Consolidates the build logic so both inline and file-based APIs share the same code path for ninja generation, locking, and compilation.

## Usage Examples
File-based build and load workflow (from `tests/python/test_build.py`):
```python
import pathlib
import numpy
import tvm_ffi.cpp
from tvm_ffi.module import Module

# Build from a .cc file that already contains TVM_FFI_DLL_EXPORT_TYPED_FUNC
cpp_path = pathlib.Path(__file__).parent.resolve() / "test_build.cc"
output_lib_path: str = tvm_ffi.cpp.build(
    name="hello",
    cpp_files=[str(cpp_path)],
)

# Separately load the compiled library
mod: Module = tvm_ffi.load_module(output_lib_path)

x = numpy.array([1, 2, 3, 4, 5], dtype=numpy.float32)
y = numpy.empty_like(x)
mod.add_one_cpu(x, y)
numpy.testing.assert_equal(x + 1, y)
```

Equivalent one-step load:
```python
mod = tvm_ffi.cpp.load(name="hello", cpp_files="test_build.cc")
```
