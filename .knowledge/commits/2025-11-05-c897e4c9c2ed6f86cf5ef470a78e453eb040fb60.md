# Add file-based `build`/`load` APIs for C++/CUDA extension compilation alongside inline variants
## TL;DR
- Adds `tvm_ffi.cpp.build()` and `tvm_ffi.cpp.load()` -- file-path-based counterparts to the existing `build_inline()`/`load_inline()` that accept paths to `.cc`/`.cu` files instead of raw source strings. Interface modeled after `torch.utils.cpp_extension.load`.
- Renames `python/tvm_ffi/cpp/load_inline.py` to `extension.py` and extracts shared build logic into `_build_impl()`, which `build_inline` now delegates to.
- Refactors `_generate_ninja_build` and `_hash_sources` to accept file lists generically, enabling both inline and file-based compilation paths to share the same ninja generation and caching infrastructure.

Secondary: rename of `load_inline.py` -> `extension.py` (file rename, not symbol rename).

## Impact
- API: Additive -- new `tvm_ffi.cpp.build()` and `tvm_ffi.cpp.load()` public functions. Existing `build_inline`/`load_inline` signatures unchanged. Internal import `from tvm_ffi.cpp.load_inline import build_ninja` updated to `from tvm_ffi.cpp.extension import build_ninja` in `_build_optional_torch_c_dlpack.py`.
- Behavioral: `_generate_ninja_build` now produces per-file object targets (`cpp_0.o`, `cpp_1.o`, etc.) instead of fixed `main.o`/`cuda.o`. This is transparent to callers but changes ninja build file content.
- Flags/config: none
- Data formats/schemas: none

## Design Elements
Design elements this commit consumes:
- **Module system** (`.knowledge/designs/0011-module-system.md`) -- `load_module()`, `Module` class, `TVM_FFI_DLL_EXPORT_TYPED_FUNC` macro for exporting functions from shared libraries.
- **Ninja build pipeline** -- `_generate_ninja_build`, `build_ninja`, `_maybe_write`, `FileLock` (all in `extension.py`).
- **`_hash_sources` caching** -- SHA-256 content-addressable cache in `~/.cache/tvm-ffi` (or `TVM_FFI_CACHE_DIR`).
- **`libinfo` utilities** -- `find_include_path`, `find_dlpack_include_path`, `find_libtvm_ffi`.

Design elements this commit produces:
- **File-based C++ extension API** (`build`/`load`) -- a new compilation pathway that accepts source file paths rather than inline strings. Key difference from `build_inline`/`load_inline`: no automatic `TVM_FFI_DLL_EXPORT_TYPED_FUNC` decoration -- users must manually include export macros in their source files.
- **`_build_impl` shared build core** -- internal extraction that unifies the ninja generation + compilation + caching logic used by both file-based and inline APIs.
- **Multi-file ninja build targets** -- `_generate_ninja_build` generalized from fixed `main.o`/`cuda.o` to N-file `cpp_i.o`/`cuda_i.o` targets, enabling compilation of multiple source files in one module.

## Usage Examples

File-based build and load (from test `tests/python/test_build.py`):

```python
import pathlib
import numpy
import tvm_ffi.cpp
from tvm_ffi.module import Module

# Build a C++ file that uses TVM_FFI_DLL_EXPORT_TYPED_FUNC manually
cpp_path = pathlib.Path(__file__).parent.resolve() / "test_build.cc"
output_lib_path: str = tvm_ffi.cpp.build(
    name="hello",
    cpp_files=[str(cpp_path)],
)

# Load and use the module
mod: Module = tvm_ffi.load_module(output_lib_path)
x = numpy.array([1, 2, 3, 4, 5], dtype=numpy.float32)
y = numpy.empty_like(x)
mod.add_one_cpu(x, y)
numpy.testing.assert_equal(x + 1, y)
```

The `load` convenience function combines build + load:
```python
mod = tvm_ffi.cpp.load(name="hello", cpp_files="test_build.cc")
```

Key difference from `load_inline`: source files contain their own `#include` directives and `TVM_FFI_DLL_EXPORT_TYPED_FUNC` invocations. No automatic header prepending or function decoration occurs.
