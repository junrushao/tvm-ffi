# Improve string/bytes and nested container argument passing by moving conversion logic into C++ and adding formal C API for string/bytes creation
## TL;DR
- Introduces two new C API functions (`TVMFFIStringFromByteArray`, `TVMFFIBytesFromByteArray`) for creating `String`/`Bytes` (supporting SSO) directly from `TVMFFIByteArray`, eliminating the need for Python-side `kTVMFFIRawStr`/`kTVMFFIByteArrayPtr` intermediate representations when packing string arguments.
- Redesigns the Cython argument packing layer to handle `list`, `tuple`, `dict`, and `ObjectConvertible` conversion directly in C++/Cython via recursive `ConstructorCall` (calling `ffi.Array`/`ffi.Map` constructors), replacing the previous `_FUNC_CONVERT_TO_OBJECT` Python callback approach. This preserves torch CUDA stream context propagation through nested container construction.
- Fixes a temp-object recycling bug by using `TVMFFIObjectDecRef` instead of directly calling the deleter, and replaces Python-side temp object tracking (`TVMFFIPyPushTempPyObject`) with FFI-side ref management (`TVMFFIPyPushTempFFIObject`) for newly constructed string/bytes/callable/container objects.

## Impact
- API: Two new C API functions added to `c_api.h` (`TVMFFIStringFromByteArray`, `TVMFFIBytesFromByteArray`). The Python-side `_set_func_convert_to_object` callback and `_FUNC_CONVERT_TO_OBJECT` global are removed; `_convert.py` no longer registers itself into the Cython core layer. `_STR_CONSTRUCTOR` and `_BYTES_CONSTRUCTOR` module-level variables removed from `string.pxi` and `function.pxi`. `_OBJECT_FROM_JSON_GRAPH_STR` and `_OBJECT_TO_JSON_GRAPH_STR` moved from Python-level globals to Cython `cdef` variables in `function.pxi`.
- Flags/config: Version bump `0.1.0a12` -> `0.1.0a13` in `pyproject.toml`.
- Data formats/schemas: String arguments now arrive at C++ as `kTVMFFISmallStr`/`kTVMFFIStr` objects instead of `kTVMFFIRawStr` pointers; bytes arguments arrive as `kTVMFFISmallBytes`/`kTVMFFIBytes` objects instead of `kTVMFFIByteArrayPtr`. This is an ABI-level semantic change for callee functions.

## Design Elements
Design elements this commit consumes:
- **C ABI layer** ([`.knowledge/designs/0001-c-abi.md`](../designs/0001-c-abi.md)): Adds new `extern "C"` functions following the established pattern (section-grouped, Doxygen-documented, returning `int` error code via safe-call convention).
- **Container system** ([`.knowledge/designs/0005-containers.md`](../designs/0005-containers.md)): Uses `String`/`Bytes` SSO dual representation (`kTVMFFISmallStr` vs `kTVMFFIStr`), `Array` and `Map` constructors for recursive container building. Relies on `TypeTraits<String>::MoveToAny` and `TypeTraits<Bytes>::MoveToAny` to correctly populate `TVMFFIAny` with small or heap representation.
- **Python bindings** ([`.knowledge/designs/0014-python-bindings.md`](../designs/0014-python-bindings.md)): Modifies the `make_args` argument packing priority order. Adds new Cython setter functions. Consumes `TVMFFIPyCallContext` for stream/device context propagation. Uses `TVMFFIPyPushTempFFIObject` for ref-count management.
- **Function system** ([`.knowledge/designs/0004-function-system.md`](../designs/0004-function-system.md)): Uses `TVMFFIFunctionCall` for nested constructor invocations via the packed calling convention.
- **Thread-local stream context** ([`.knowledge/ADRs/0020-thread-local-stream-context.md`](../ADRs/0020-thread-local-stream-context.md)): The `ConstructorCall` propagates `device_type`, `device_id`, `stream`, `c_dlpack_tensor_allocator`, and `c_dlpack_to_pyobject` from nested context back to parent context, ensuring torch CUDA stream detection works through nested container conversion.
- **OpaquePyObject fallback** ([`.knowledge/ADRs/0026-opaque-pyobject-fallback.md`](../ADRs/0026-opaque-pyobject-fallback.md)): The fallback setter now uses the more efficient `_convert_to_opaque_object_handle` (cdef inline) instead of the Python-level `_convert_to_opaque_object`.

Design elements this commit produces:
- **C API for String/Bytes from ByteArray**: New functions `TVMFFIStringFromByteArray` and `TVMFFIBytesFromByteArray` provide a formal C ABI entry point for constructing `String`/`Bytes` (with SSO) from raw `(data, size)` pairs. This replaces the informal pattern of passing `kTVMFFIRawStr`/`kTVMFFIByteArrayPtr` and relying on the callee to convert. These functions are consumed by the Cython `TVMFFIPyArgSetterStr_` and `TVMFFIPyArgSetterBytes_` setters.
- **Recursive argument conversion via ConstructorCall**: A new `TVMFFIPyConstructorCall` / `TVMFFIPyCallManager::ConstructorCall` C++ function and the Cython `ConstructorCall` wrapper enable recursive argument packing. Unlike `FuncCall`, `ConstructorCall` does not set stream/allocator itself but propagates detected context back to the parent `TVMFFIPyCallContext`. This is the foundation for C++-side nested container conversion.
- **Specialized Cython argument setters for containers**: `TVMFFIPyArgSetterTuple_`, `TVMFFIPyArgSetterTupleLike_`, `TVMFFIPyArgSetterMap_`, `TVMFFIPyArgSetterObjectConvertible_` replace the former `_FUNC_CONVERT_TO_OBJECT` Python callback approach. Each setter directly calls the appropriate `ffi.Array` or `ffi.Map` constructor via `ConstructorCall`.
- **Separated PyNativeObject setters**: `TVMFFIPyArgSetterPyNativeObjectStr_`, `TVMFFIPyArgSetterPyNativeObjectBytes_`, `TVMFFIPyArgSetterPyNativeObjectGeneral_` split the former mixed `isinstance(arg, PyNativeObject)` checks from `TVMFFIPyArgSetterStr_`/`TVMFFIPyArgSetterBytes_`/`TVMFFIPyArgSetterFallback_` into distinct setters, dispatched earlier in `TVMFFIPyArgSetterFactory_`.
- **Inline handle-returning conversion helpers**: `_convert_to_ffi_func_handle` and `_convert_to_opaque_object_handle` are `cdef inline` functions that return raw `TVMFFIObjectHandle` instead of constructing Python wrapper objects, avoiding intermediate Python object allocation in the argument packing hot path.
- **Revised make_args priority order**: The factory now checks `PyNativeObject` (with sub-dispatch for `str`, `bytes`, general) before plain `str`/`bytes`, then adds `tuple`, `list`, `dict` as separate entries before `ctypes.c_void_p`. `ObjectConvertible` moves to a separate setter after `Exception`. This changes the documented priority order in the Python bindings design doc.

## Reflection

* **Design docs to write**:
  - `.knowledge/designs/0019-python-arg-packing-c-helpers.md`: Document the `TVMFFIPyCallManager` / `TVMFFIPyCallContext` / `TVMFFIPyArgSetter` system in `tvm_ffi_python_helpers.h`, including the `FuncCall` vs `ConstructorCall` distinction, temp-object management (`TVMFFIPyPushTempFFIObject` vs `TVMFFIPyPushTempPyObject`), stream/device context propagation, and the `TVMFFIPyArgSetterFactory_` dispatch table. This is a substantial piece of architecture (500+ lines of C++) that mediates every Python-to-FFI call and is not documented in any existing design doc. Future commits that modify argument packing, stream handling, or DLPack interop would reference it.

* **ADRs to write**:
  - `.knowledge/ADRs/0033-string-bytes-c-api-creation.md`: Record the decision to add `TVMFFIStringFromByteArray`/`TVMFFIBytesFromByteArray` C APIs and to pass strings as `kTVMFFIStr`/`kTVMFFISmallStr` objects rather than `kTVMFFIRawStr` pointers. Context: the old approach required callee-side conversion and did not leverage SSO. Alternatives: keep `kTVMFFIRawStr` with callee-side conversion (simpler but loses SSO benefit), or add a `TVMFFISmallStrFromCStr` micro-API (too specialized). Trade-off: slight overhead for small strings that previously fit in `kTVMFFIRawStr` with zero-copy, but uniform handling and ownership clarity.
  - `.knowledge/ADRs/0034-recursive-arg-conversion-in-cython.md`: Record the decision to move `list`/`tuple`/`dict`/`ObjectConvertible` conversion from the Python `convert()` callback into Cython-level `ConstructorCall` with context propagation. Context: the old approach broke torch stream detection for nested containers because the Python callback did not participate in the `TVMFFIPyCallContext`. Alternatives: pass stream context as a Python-level thread-local (fragile, two sources of truth), or require users to pre-convert containers (poor ergonomics). Trade-off: increased complexity in Cython/C++ layer, but correct stream propagation and faster conversion.

* **Design diagrams to draw**:
  - **Mermaid flowchart**: Updated `make_args` argument packing priority order reflecting the new `PyNativeObject` early-dispatch, container-specific setters (`Tuple_`, `TupleLike_`, `Map_`), and `ObjectConvertible` placement. Should replace the existing textual priority list in `0014-python-bindings.md`.
  - **Mermaid sequence diagram**: `ConstructorCall` recursive invocation showing how a `dict` with nested `list` values triggers `TVMFFIPyArgSetterMap_` -> `ConstructorCall(ffi.Map, ...)` -> `TVMFFIPyArgSetterTuple_` -> `ConstructorCall(ffi.Array, ...)`, with stream context propagation from inner to outer `TVMFFIPyCallContext`.

## Self-Evolution of Skill /commit-ledger
- The `TVMFFIPyCallManager` class and its `TVMFFIPyCallContext` struct are an important but undocumented architectural component. The commit-ledger skill should be aware that `tvm_ffi_python_helpers.h` is a key file for any commit that touches Python-to-C++ argument conversion, and should proactively read it when the changed file list includes `function.pxi` or `tvm_ffi_python_helpers.h`. Consider adding this to Step 1 as a known "sentinel file" pattern.
- The skill should note when a commit removes a Python-to-Cython callback wiring (like `_set_func_convert_to_object`) because these represent architectural simplifications that reduce layering dependencies. This pattern is valuable to track for understanding initialization order changes.
- Consider adding a sub-step to Step 4 for "temporary object management patterns" -- specifically whether objects are tracked via Python refcount (`TVMFFIPyPushTempPyObject`) vs FFI refcount (`TVMFFIPyPushTempFFIObject`) and what the implications are for GIL requirements and destruction ordering.
