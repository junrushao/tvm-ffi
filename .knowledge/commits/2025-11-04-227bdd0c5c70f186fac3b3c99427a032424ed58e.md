# Fix error propagation order in TVMFFIEnvTensorAlloc so allocator errors reach the caller
## TL;DR
- Reorders the null-pointer check in `TVMFFIEnvTensorAlloc` to check the allocator return code **before** asserting the output pointer is non-null, allowing errors set by the allocator callback (via `SetError`) to propagate correctly instead of being masked by an `InternalError` from `TVM_FFI_ICHECK`.
- Registers `MemoryError` as a new error kind in both the Python error registry and the Torch DLPack allocator's error callback.
- Upgrades the test to verify that error kind and message survive the full allocator-error round-trip.

## Key Exports
**Error registration (Python)**:
- `register_error("MemoryError", MemoryError)` -- new mapping in `python/tvm_ffi/error.py`, enabling C++ `MemoryError` errors to surface as Python `MemoryError` exceptions.

**No new C++/C API symbols introduced.**

## Impact
- API: None. No public signatures changed.
- ABI: None.
- Behavioral: `TVMFFIEnvTensorAlloc` now correctly propagates the error kind and message set by the `DLPackManagedTensorAllocator` callback. Previously, a failing allocator would trigger `TVM_FFI_ICHECK(dlpack_tensor != nullptr)` before the return code was checked, producing a generic `InternalError` instead of the allocator's specific error (e.g., `MemoryError`). After this fix, the return code is checked first; if non-zero, the TLS error (already set by `TVMFFIEnvTensorAllocSetError`) is returned immediately. The `TVM_FFI_ICHECK` is replaced with `TVM_FFI_CHECK(..., RuntimeError)` as a fallback for the edge case where the allocator returns 0 but the pointer is null.
- Flags/config: None.
- Data formats/schemas: None.

## Design Elements
Design elements this commit consumes:
- TLS error propagation pattern (`TVMFFIErrorSetRaisedFromCStr` via `TVMFFIEnvTensorAllocSetError`), see `.knowledge/designs/error-handling.md` and `.knowledge/ADRs/002-tls-error-propagation.md`
- DLPack allocator callback error contract (`SetError(ctx, kind, message)` pattern), see `.knowledge/designs/0018-dlpack-fast-path.md` "Allocator callback error contract"
- `TVM_FFI_CHECK` user-facing typed check macro (since 327e8cc6), see `.knowledge/designs/error-handling.md` "User-facing typed checks"

Design elements this commit produces:
- Corrected error propagation ordering in `TVMFFIEnvTensorAlloc`: return-code check must precede null-pointer assertion. This establishes the invariant that allocator-set TLS errors are never masked by subsequent assertions on output pointers.
- `MemoryError` as a registered error kind across the Python FFI layer and the Torch DLPack allocator, completing the error-kind vocabulary for allocation failures.

## Usage Examples
**Before (incorrect -- allocator error masked)**:
```cpp
// In env_context.cc (before this fix):
int ret = (*dlpack_alloc)(prototype, &dlpack_tensor, nullptr, TVMFFIEnvTensorAllocSetError);
TVM_FFI_ICHECK(dlpack_tensor != nullptr);  // Fires InternalError, masking the MemoryError
if (ret != 0) return ret;                   // Never reached
```

**After (correct -- allocator error propagated)**:
```cpp
// In env_context.cc (after this fix):
int ret = (*dlpack_alloc)(prototype, &dlpack_tensor, nullptr, TVMFFIEnvTensorAllocSetError);
if (ret != 0) return ret;  // Propagates the allocator's MemoryError via TLS
TVM_FFI_CHECK(dlpack_tensor != nullptr, RuntimeError)
    << "TVMFFIEnvTensorAlloc: failed to allocate a tensor from the allocator";
```

**C++ test verifying error kind survives round-trip**:
```cpp
try {
  Tensor::FromEnvAlloc(TVMFFIEnvTensorAlloc, {1, 2, 3},
                       DLDataType({kDLFloat, 32, 1}), DLDevice({kDLCPU, 0}));
} catch (const tvm::ffi::Error& e) {
  EXPECT_EQ(e.kind(), "MemoryError");
  EXPECT_EQ(e.message(), "TestDLPackManagedTensorAllocatorError");
  throw;
}
```
