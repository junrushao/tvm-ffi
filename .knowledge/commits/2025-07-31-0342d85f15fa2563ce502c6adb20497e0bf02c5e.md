# Fix SmallMapObj::CreateFromRange to handle duplicate keys via InsertMaybeReHash

## TL;DR
- `MapObj::CreateFromRange` had a fast path for small maps (`cap < SmallMapObj::kMaxSize == 4`) that called `SmallMapObj::CreateFromRange`, which blindly copies all input elements in-order without deduplication — causing a map with size > 1 when constructed from a range with duplicate keys.
- Fix: when `cap >= 2` (i.e., the small-map fast path could hit the duplicate bug), use `SmallMapObj::InsertMaybeReHash` in a loop instead, which overwrites duplicate keys like `DenseMapObj` already did.
- `cap < 2` (0 or 1 elements) is still handled by `CreateFromRange` since duplicates are impossible there.

## Key Exports

```python
# MapObj::CreateFromRange — internal factory (not public API)
# Old behavior (cap in [2, kMaxSize)):
#   SmallMapObj::CreateFromRange(cap, first, last)
#   → blindly places all (key, value) pairs in-order; duplicate keys produce extra entries
#
# New behavior (cap in [2, kMaxSize)):
#   obj = SmallMapObj::Empty(cap)
#   for kv in range: SmallMapObj::InsertMaybeReHash(kv, &obj)
#   → overwrites on duplicate key; final map has exactly one entry per unique key
#
# Invariant (restored): Map constructed from any input range satisfies len(map) == len(unique_keys(range))
# Interacts with: SmallMapObj::InsertMaybeReHash (hash-based upsert), SmallMapObj::CreateFromRange (direct copy, only safe for 0-1 elements now)
```

## Impact
- API: none — `Map<K,V>` constructor interface is unchanged.
- Behavioral: `Map<K,V>(range_with_dups)` now correctly deduplicates. Previously, a map constructed with 2–3 duplicate keys (within small-map capacity) would report `size() > 1` and contain repeated keys, corrupting lookups. After the fix, the last value wins (consistent with `DenseMapObj` behavior).
- Flags/config: none
- Data formats/schemas: none

## Design Elements

Design elements this commit consumes:

- `SmallMapObj::InsertMaybeReHash` — the existing upsert path already used by `DenseMapObj` code; now also invoked for the small-map path.

Design elements this commit produces:

## Usage Examples

**Before (broken):**
```cpp
// Constructing from a range with duplicate keys — small map fast path
std::vector<std::pair<String, int>> data = {{"a", 1}, {"a", 2}, {"a", 3}};
Map<String, int> m(data.begin(), data.end());
// m.size() == 3  (BUG: three entries all with key "a")
// m["a"] is undefined / returns first or last depending on implementation
```

**After (fixed):**
```cpp
std::vector<std::pair<String, int>> data = {{"a", 1}, {"a", 2}, {"a", 3}};
Map<String, int> m(data.begin(), data.end());
// m.size() == 1  (last value wins, consistent with DenseMapObj)
// m["a"] == 3
```
