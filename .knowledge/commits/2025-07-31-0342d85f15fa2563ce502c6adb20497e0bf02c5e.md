# Fix SmallMapObj initialization to handle duplicated keys correctly
## TL;DR
- Fixes a bug where `MapObj::CreateFromRange` for small maps (capacity < `SmallMapObj::kMaxSize`) would blindly copy all input key-value pairs without deduplication, producing a map with duplicate keys and incorrect `size_`.
- The fix changes the small-map path (for `cap >= 2`) to use `SmallMapObj::InsertMaybeReHash` per element instead of `SmallMapObj::CreateFromRange`, which performs a linear scan to detect and overwrite existing keys.
- Adds a regression test `Map.DuplicatedKeysInit` that constructs a map from a vector with three entries sharing the same key and asserts `size() == 1` with the last value winning.

## Impact
- API: none -- `Map<K,V>` constructor from iterators retains the same signature; the behavioral fix is that duplicate keys are now correctly deduplicated (last-write-wins) for small maps, matching the existing behavior of `DenseMapObj::InsertMaybeReHash` for large maps.
- Flags/config: none.
- Data formats/schemas: none.
- Behavioral: Any caller constructing a `Map` from an iterator range with duplicate keys and fewer than `SmallMapObj::kMaxSize` elements previously got a corrupted map (duplicate entries, wrong size). Now the map correctly contains a single entry per unique key with the last value. This is a correctness fix, not a performance optimization.

## Design Elements
Design elements this commit **consumes**:

- **MapObj dual-representation (SmallMapObj / DenseMapObj)** ([`.knowledge/designs/0005-containers.md`](../designs/0005-containers.md)): The fix depends on understanding the two-tier map representation. `MapObj::CreateFromRange` dispatches to either the `SmallMapObj` path (inplace array, linear scan) or the `DenseMapObj` path (hash table) based on `cap < SmallMapObj::kMaxSize`. The `DenseMapObj` path already used `InsertMaybeReHash` per element, which correctly handles duplicates. The `SmallMapObj` path did not.
- **SmallMapObj::InsertMaybeReHash** (`include/tvm/ffi/container/map.h:385-404` at commit): This method performs a linear `find()` before insertion. If the key already exists (`itr.index < size_`), it overwrites the value. The fix leverages this existing deduplication logic by routing through `InsertMaybeReHash` instead of the bulk `CreateFromRange`.
- **SmallMapObj::CreateFromRange** (`include/tvm/ffi/container/map.h:359-366` at commit): This method blindly placement-news each pair from the iterator range into the inplace array without checking for key collisions. It is now only used for `cap < 2` (i.e., 0 or 1 elements, where duplication is impossible or a no-op).
- **Container data indirection** ([`.knowledge/ADRs/0009-container-data-indirection.md`](../ADRs/0009-container-data-indirection.md)): The fix uses `SmallMapObj::Empty(cap)` to pre-allocate an empty inplace array with the correct capacity, then populates it via `InsertMaybeReHash`. This relies on the `data_` / `data_deleter_` indirection being correctly set up by `Empty()`.

Design elements this commit **produces**:

- **Invariant: MapObj::CreateFromRange deduplicates keys for all map sizes**. Previously, deduplication was only guaranteed for large maps (DenseMapObj path). After this fix, the invariant holds for both small and large maps. This is an invariant tightening, not a new design element.

## Key Implementations

**Changed function**: `MapObj::CreateFromRange<IterType>` at `include/tvm/ffi/container/map.h:1260-1290` (at commit).

**Bug root cause**: The old code for the `cap < SmallMapObj::kMaxSize` branch was:
```cpp
return SmallMapObj::CreateFromRange(cap, first, last);
```
`SmallMapObj::CreateFromRange` performs bulk copy: it iterates `[first, last)` and placement-news each `KVType` into consecutive slots, incrementing `size_` for each. It never checks for existing keys. When the input range contains duplicate keys (e.g., `{{"a",1}, {"a",2}, {"a",3}}`), the resulting map has `size_ == 3` with three entries all keyed `"a"`.

**Fix structure**: The new code splits into two sub-cases:
1. `cap < 2`: Delegates to `SmallMapObj::CreateFromRange` (safe -- 0 or 1 elements cannot have duplicates).
2. `cap >= 2`: Creates an empty `SmallMapObj` via `SmallMapObj::Empty(cap)`, then inserts each element via `SmallMapObj::InsertMaybeReHash(std::move(kv), &obj)`. `InsertMaybeReHash` calls `find()` first; if the key exists, it overwrites the value in-place.

The `else` branch (large maps / `DenseMapObj`) is structurally unchanged but reformatted into an explicit `else` block for symmetry.

**Invariants assumed**:
- `SmallMapObj::InsertMaybeReHash` correctly handles the case where the map needs to grow (rehash to `DenseMapObj`). If after deduplication the map exceeds `kMaxSize`, `InsertMaybeReHash` handles the transition.
- `SmallMapObj::Empty(cap)` correctly allocates an inplace array with `slots_ == cap` and `size_ == 0`.

**Invariants enforced**:
- After `CreateFromRange` returns, each key in the map is unique.
- Last-write-wins semantics for duplicate keys (consistent with `DenseMapObj::InsertMaybeReHash` and standard `std::unordered_map::insert_or_assign` semantics).

**Common failure mode**: Without this fix, constructing `Map<String, int>({{"a",1},{"a",2}})` produces a map with `size() == 2` but only one unique key. Iteration yields two entries; lookups may return either value depending on `find()` implementation (linear scan returns the first match, so `map["a"] == 1` while the second entry is unreachable but counted in `size_`).

**Extension point**: If a future optimization wants to avoid the per-element `find()` cost for small maps when the caller can guarantee uniqueness (e.g., copying from another map), a separate `CreateFromRangeUnchecked` method could be introduced, analogous to the existing `CreateFromRange` for `cap < 2`.

**Test**: `TEST(Map, DuplicatedKeysInit)` at `tests/cpp/test_map.cc:359-365`. Constructs from `{{"a",1}, {"a",2}, {"a",3}}`, asserts `size() == 1` and `map["a"] == 3`.

## Reflection

### Design docs to write
- **`.knowledge/designs/0005-containers.md` update**: The existing containers design doc should be updated to explicitly document the deduplication invariant for `MapObj::CreateFromRange`: "All `Map` constructors from iterator ranges guarantee key uniqueness with last-write-wins semantics." This helps future commit mining by making it clear that any change to map construction paths must preserve this invariant. Currently the design doc describes the `SmallMapObj` / `DenseMapObj` split but does not mention deduplication guarantees.

### ADRs to write
None. The fix restores an expected invariant (key uniqueness) rather than making a new architectural decision. The existing ADR-0009 (container data indirection) covers the relevant storage mechanics.

### Design diagrams to draw
None. The existing class diagram in `.knowledge/designs/0005-containers.md` adequately depicts the `SmallMapObj` / `DenseMapObj` split. The fix does not change relationships between components.

### Skill evolution (`/commit-ledger`)
- **Pre/post invariant diffing**: For bugfix commits, the skill should explicitly document (a) what invariant was violated before the fix, and (b) what invariant is restored/tightened after the fix. This commit is a good example: the invariant "CreateFromRange deduplicates keys" was violated for small maps and is now restored. Adding a sub-step to Step 4 like "For bugfixes: state the violated invariant and the restored invariant" would make this systematic.

## Self-Evolution of Skill /commit-ledger
- The asymmetry between the SmallMapObj and DenseMapObj paths in `CreateFromRange` (one already deduplicated, the other did not) is the kind of structural inconsistency that the skill could flag more aggressively. Consider adding a heuristic in Step 3: "When a commit fixes a bug in one code path, check if sibling code paths (e.g., the other branch of an if/else, the other overload of a function) have the same bug or were already correct. Document the asymmetry."
