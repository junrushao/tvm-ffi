# Fix SmallMapInit with duplicated keys in MapObj::CreateFromRange

## TL;DR
- Fixes a bug where `MapObj::CreateFromRange` used `SmallMapObj::CreateFromRange` for small maps (cap < `kMaxSize`), which blindly copied all entries from the input range without deduplication. When the input contained duplicate keys, the resulting `SmallMapObj` would hold multiple entries for the same key, violating the map invariant.
- The fix splits the small-map path: for `cap < 2` (0 or 1 elements), the direct `CreateFromRange` is safe and still used. For `cap >= 2`, the code now creates an empty `SmallMapObj` and inserts entries one by one via `SmallMapObj::InsertMaybeReHash`, which checks for existing keys and overwrites values on collision.
- The large-map (`DenseMapObj`) path was already correct because it used `DenseMapObj::InsertMaybeReHash` for each entry, which handles duplicates. The fix restructures the code so both paths follow the same insert-based pattern, with the only exception being the trivial cap < 2 case.
- Adds a `DuplicatedKeysInit` test case that constructs a `Map<String, int>` from a vector with three entries sharing the same key `"a"`, asserting the map has size 1 and the last value wins.

## Key Exports
None. No new public API surface is introduced. The change modifies the internal `MapObj::CreateFromRange` template function in `include/tvm/ffi/container/map.h`.

## Impact
- API: None. The `Map<K, V>` constructor accepting iterator ranges has the same signature.
- ABI: None. No layout or symbol changes; `SmallMapObj` and `DenseMapObj` are header-only internal classes.
- Behavioral: `Map` construction from iterator ranges with duplicate keys now correctly deduplicates in the small-map path. Previously, the resulting map could contain multiple entries with the same key, leading to incorrect `size()` and unpredictable lookup behavior. After the fix, the last value for a duplicated key wins (consistent with `DenseMapObj` behavior and the `InsertMaybeReHash` semantics).
- Flags/config: None.
- Data formats/schemas: None.

## Design Elements
Design elements this commit consumes:
- **`SmallMapObj::InsertMaybeReHash`** (`include/tvm/ffi/container/map.h`, lines 382-401): The insert method that checks for existing keys via `find()` before inserting. If the key already exists, it overwrites the value. If the map is full, it grows the backing array via `CreateFromRange` and retries. This was already used by the large-map path indirectly (via `MapObj::InsertMaybeReHash`) and is now also used for the small-map initialization path.
- **`SmallMapObj::CreateFromRange`** (`include/tvm/ffi/container/map.h`, lines 358-366): The direct bulk-copy initialization that placement-news each KV pair from the iterator range. Still used for the cap < 2 case where duplicates are impossible (0 or 1 elements).
- **`SmallMapObj::Empty(uint64_t n)`** (`include/tvm/ffi/container/map.h`, lines 342-349): Creates an empty SmallMapObj with `n` allocated slots. Now used as the starting point for the insert-based small-map initialization path.
- **Two-tier map dispatch** (documented in `.knowledge/designs/containers.md`, lines 90-98): `SmallMapObj` for small maps (n <= `kMaxSize` = 4/8) with linear scan, `DenseMapObj` for large maps with open-addressing hash.

Design elements this commit produces:
- None. This is a correctness fix to an existing code path, not a new design element.

## Usage Examples

### Constructing a Map from a range with duplicate keys
```cpp
#include <tvm/ffi/container/map.h>
#include <vector>

using namespace tvm::ffi;

// Before this fix, this would create a map with size 3 (all three entries stored)
// After this fix, duplicates are resolved: last value wins, size is 1
std::vector<std::pair<String, int>> data = {{"a", 1}, {"a", 2}, {"a", 3}};
Map<String, int> map(data.begin(), data.end());
// map.size() == 1
// map["a"] == 3
```
