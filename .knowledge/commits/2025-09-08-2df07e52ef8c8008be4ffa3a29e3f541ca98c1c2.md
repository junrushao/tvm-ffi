# Fix ffi.cpp.load_inline to work on Windows

## TL;DR
- Adapts `_generate_ninja_build` to emit MSVC-compatible ninja rules on Windows: `/Fo` output flag, `/showIncludes` + `deps = msvc`, `/link /out:` link syntax, and `.dll` output extension instead of `.so`.
- Adds MSVC compiler flags (`/MD`, `/EHsc`, warning suppressions `/wd*`) and links against `tvm_ffi.dll` via `find_libtvm_ffi()` + `/LIBPATH:` for Windows DLL exports.
- Escapes colons in absolute paths with `$:` for ninja on Windows (drive letter `C:` conflicts with ninja syntax).
- Uses `"oem"` encoding for subprocess output decoding on Windows instead of `"utf-8"`.
- Updates test markers to allow `win32` in addition to `linux`.

## Impact
- API: none -- `load_inline()` signature unchanged
- Behavioral: `load_inline()` now works on Windows; previously it would fail with MSVC compilation/linking errors and wrong output extension
- Flags/config: none
- Data formats/schemas: none

## Design Elements
Design elements this commit consumes:
- Module system (`load_module`): loads the built `.dll`/`.so` at the end of `load_inline()` -- see [0011-ffi-module-system](../design-records/0011-ffi-module-system.md)
- `find_libtvm_ffi()` from `libinfo.py`: locates the native TVM FFI shared library for linking -- see [0012-ffi-python-package](../design-records/0012-ffi-python-package.md)
- `find_include_path()` / `find_dlpack_include_path()` from `libinfo.py`: locates headers for compilation

Design elements this commit produces: none -- all changes are internal to `load_inline.py` build logic.

## Usage Examples

Before/after pattern -- the calling code is identical, but the behavior changes on Windows:

```python
# Before: fails on Windows with MSVC errors (wrong flags, missing .lib, wrong extension)
# After: works on Windows
import tvm_ffi.cpp

mod = tvm_ffi.cpp.load_inline(
    name="hello",
    cpp_sources=r"""
    int MyAdd(int a, int b) { return a + b; }
    """,
    functions=["MyAdd"],
)
result = mod["MyAdd"](3, 4)  # returns 7
```
