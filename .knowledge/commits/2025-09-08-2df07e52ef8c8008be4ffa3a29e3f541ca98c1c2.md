# Fix load_inline Windows support: MSVC flags, DLL linking, Ninja path escaping
## TL;DR
- Fixes `tvm_ffi.cpp.load_inline` to work on Windows by adapting the Ninja build generation for MSVC toolchain: compiler flags, linker invocation, dependency tracking, path escaping, and output extensions.
- Adds explicit linking against `libtvm_ffi` via `find_libtvm_ffi()` on Windows, since DLLs require import library linking (unlike Unix `-shared` which resolves symbols at load time).
- Updates test `xfail` markers to allow `win32` alongside `linux`.

## Key Exports
None -- no new public API surface. The existing `tvm_ffi.cpp.load_inline()` signature is unchanged. Internal behavior of `_generate_ninja_build`, `_build_ninja`, and `load_inline` is modified for Windows.

## Impact
- API: None -- `load_inline()` signature unchanged.
- Behavioral: `load_inline()` now produces working `.dll` files on Windows. Previously, the generated Ninja build file used Unix-only compiler/linker flags and `.so` extension, causing builds to fail on Windows.
- Flags/config: New default MSVC cflags on Windows: `/MD`, `/EHsc`, `/wd4819`, `/wd4251`, `/wd4244`, `/wd4267`, `/wd4275`, `/wd4018`, `/wd4190`, `/wd4624`, `/wd4067`, `/wd4068`. New default ldflags: `/LIBPATH:<tvm_ffi_lib_dir>`, `<tvm_ffi_lib_name>.lib`.
- Data formats/schemas: None.

## Design Elements
Design elements this commit consumes:
- **Module system** ([0013-module-system.md](../designs/0013-module-system.md)): `load_module()` is used to load the built `.dll`/`.so`. The format-based dispatch normalizes `dll`/`dylib`/`dso` to `so`, so `.dll` files route to the same `ffi.Module.load_from_file.so` loader.
- **Python package / libinfo** ([0014-python-package.md](../designs/0014-python-package.md)): `find_libtvm_ffi()`, `find_include_path()`, `find_dlpack_include_path()` are used to locate build dependencies. The commit newly imports `find_libtvm_ffi` for Windows linking.
- **Inline module compilation workflow** ([0014-python-package.md](../designs/0014-python-package.md), extension points): The existing `load_inline` infrastructure (Ninja-based build, SHA-256 caching, `FileLock`) is preserved; only platform-specific build rules are adapted.

Design elements this commit produces:
- None -- no new design elements. This is a platform-portability fix within existing architecture.

## Usage Examples
**Before (broken on Windows)**: `load_inline` generated Unix-only Ninja rules:
```ninja
rule compile
  depfile = $out.d
  deps = gcc
  command = $cxx -MMD -MF $out.d $cflags -c $in -o $out

rule link
  command = $cxx $in $ldflags -o $out

build hello.so: link main.o
```

**After (works on Windows)**: Platform-appropriate rules generated:
```ninja
rule compile
  command = $cxx /showIncludes $cflags -c $in /Fo$out
  deps = msvc

rule link
  command = $cxx $in /link $ldflags /out:$out

build hello.dll: link main.o
```

Key differences: MSVC uses `/showIncludes` + `deps = msvc` for header dependency tracking (vs gcc's `-MMD` depfile), `/Fo` for output path, `/link ... /out:` for linking, and `.dll` extension. Windows paths with drive letters (e.g., `C:\...`) are escaped as `C$:\...` in Ninja syntax.
