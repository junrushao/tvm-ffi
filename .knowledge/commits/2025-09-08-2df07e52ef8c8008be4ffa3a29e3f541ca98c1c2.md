# Fix load_inline on Windows: MSVC flags, library linking, ninja rules, and path escaping
## TL;DR
- Fixes `tvm_ffi.cpp.load_inline()` on Windows by adding comprehensive MSVC compiler flags (`/MD`, `/EHsc`, warning suppressions), linking against `tvm_ffi.dll` via `find_libtvm_ffi()`, generating MSVC-compatible ninja compile/link rules (`/showIncludes`, `deps = msvc`, `/Fo`, `/link /out:`), and using `.dll` instead of `.so` for the output extension.
- Escapes colon characters in Windows absolute paths within ninja build files (e.g., `C:\...` -> `C$:\...`) to prevent ninja from misinterpreting drive letters as rule separators.
- Decodes ninja build error output using `"oem"` encoding on Windows (instead of `"utf-8"`) to handle MSVC's OEM code page output correctly.
- Updates test markers from `xfail(not linux)` to `xfail(not linux and not win32)` so the `load_inline` tests run on Windows CI.

## Impact
- API: No new public API. The existing `tvm_ffi.cpp.load_inline()` function now works on Windows in addition to Linux. macOS remains `xfail`-marked.
- Flags/config: None changed. The commit adds internal MSVC flags (`/MD`, `/EHsc`, `/wd*` warning suppressions) and linker flags (`/LIBPATH:`, `tvm_ffi.lib`) to the ninja build generation, but these are not user-configurable.
- Data formats/schemas: The on-disk cache layout changes on Windows: output file is `{name}.dll` instead of `{name}.so`. The `build.ninja` format uses MSVC-style `deps = msvc` and `/showIncludes` instead of GCC-style `depfile`/`deps = gcc`.
- Dependencies: Now imports `find_libtvm_ffi` from `tvm_ffi.libinfo` to locate the TVM FFI shared library for Windows linking. This function already existed in `libinfo.py`; no new dependency.

## Design Elements

Design elements this commit consumes:
- **Inline module compilation pipeline** ([`.knowledge/designs/0017-inline-module-compilation.md`](../designs/0017-inline-module-compilation.md)): This commit is a direct bugfix to the pipeline introduced in `83805ec`. The design doc's "Ninja Build Generation" section already notes platform differences between Windows and Unix, but the initial implementation had incomplete Windows support. This commit fills in the gaps.
- **Python bindings / libinfo** ([`.knowledge/designs/0014-python-bindings.md`](../designs/0014-python-bindings.md)): Newly imports `find_libtvm_ffi()` from `tvm_ffi.libinfo` to resolve the path to `tvm_ffi.dll` on Windows. This function was already available (used elsewhere in the package for library loading) but was not consumed by `load_inline` until now.
- **Module export system** ([`.knowledge/designs/0008-module-export-system.md`](../designs/0008-module-export-system.md)): On Windows, the compiled `.dll` must link against the TVM FFI shared library because `TVM_FFI_DLL_EXPORT_TYPED_FUNC`-generated symbols resolve FFI runtime functions at link time. On Unix, these symbols are resolved lazily at `dlopen` time, so no explicit library linkage was needed.

Design elements this commit produces:
- **No new design elements.** This is a bugfix that completes the Windows platform support already anticipated by the inline module compilation design. However, it establishes several platform-specific invariants within the ninja build generation that were previously only sketched:
  - Windows compile rule uses `deps = msvc` with `/showIncludes` (not `depfile`/`deps = gcc`).
  - Windows link rule uses `/link $ldflags /out:$out` (not `$ldflags -o $out`).
  - Windows requires explicit linkage to `tvm_ffi.lib` via `/LIBPATH:` + lib name.
  - Ninja paths on Windows must escape colons in drive letters (`C:` -> `C$:`).
  - Error output uses `"oem"` encoding on Windows.
