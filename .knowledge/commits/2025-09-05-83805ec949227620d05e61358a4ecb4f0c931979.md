# Add load_inline for JIT-compiling C++/CUDA source into FFI modules from Python
## TL;DR
- Introduces `tvm_ffi.cpp.load_inline()`, a PyTorch-`torch.utils.cpp_extension.load_inline`-inspired API that JIT-compiles inline C++ and/or CUDA source code into a TVM FFI `Module`, using `TVM_FFI_DLL_EXPORT_TYPED_FUNC` to export functions and `ninja` to build.
- Creates two new Python sub-packages: `python/tvm_ffi/cpp/` (housing the `load_inline` implementation) and `python/tvm_ffi/utils/` (housing a cross-platform `FileLock` utility).
- Adds a content-addressed build cache (`~/.cache/tvm-ffi` or `$TVM_FFI_CACHE_DIR`) with SHA-256 hashing to avoid redundant recompilation, and a `FileLock` to serialize concurrent builds in the same cache directory.

## Impact
- API: Adds a new public Python function `tvm_ffi.cpp.load_inline(name, *, cpp_source, cuda_source, cpp_functions, cuda_functions, extra_cflags, extra_cuda_cflags, extra_ldflags, extra_include_paths) -> Module`. This is a new feature that does not break any existing API.
- Flags/config: Introduces environment variables `TVM_FFI_CACHE_DIR` (cache root), `TVM_FFI_CUDA_ARCH_LIST` (CUDA target architectures), `CXX` (C++ compiler), `MAX_JOBS` (ninja parallelism). These are new; no existing variables are affected.
- Data formats/schemas: None. The on-disk cache layout is `{cache_dir}/{name}_{hash16}/` containing `main.cpp`, optionally `cuda.cu`, `build.ninja`, and the output `.so`.
- Dependencies: Requires `ninja` to be installed and available on `$PATH` at runtime for build invocation.

## Design Elements

Design elements this commit consumes:
- **Module system** ([`.knowledge/designs/0013-module-system.md`](../designs/0013-module-system.md)): The final step of `load_inline` calls `load_module(path)` to load the compiled `.so` via the existing `DSOLibrary` -> `LibraryModuleObj` pipeline. The returned `Module` object supports attribute-style function access (`mod.func_name(...)`) through `Module.__getattr__` -> `ModuleObj::GetFunction`.
- **Module export system** ([`.knowledge/designs/0008-module-export-system.md`](../designs/0008-module-export-system.md)): `_decorate_with_tvm_ffi()` appends `TVM_FFI_DLL_EXPORT_TYPED_FUNC(exported_name, func_name_in_source)` lines to the user's source code, generating `extern "C"` symbols with `TVMFFISafeCallType` signature that `LibraryModuleObj::GetFunction` can discover.
- **Python bindings / libinfo** ([`.knowledge/designs/0014-python-bindings.md`](../designs/0014-python-bindings.md)): Uses `find_include_path()` and `find_dlpack_include_path()` from `tvm_ffi.libinfo` to locate the installed TVM FFI headers and DLPack headers for compilation `-I` flags.
- **C ABI headers**: The generated source includes `<tvm/ffi/dtype.h>`, `<tvm/ffi/error.h>`, `<tvm/ffi/extra/c_env_api.h>`, `<tvm/ffi/function.h>` -- the standard C/C++ API surface needed for typed function export and DLTensor manipulation.

Design elements this commit produces:
- **Inline module compilation pipeline** (new, `python/tvm_ffi/cpp/load_inline.py`): A Python-side JIT compilation workflow: source decoration with FFI macros -> content-addressed cache lookup -> ninja build file generation -> subprocess compilation -> `load_module`. This is a new design element at the Python tooling level that bridges the gap between the C++ module export macros and the Python module loading API.
- **Cross-platform FileLock utility** (new, `python/tvm_ffi/utils/lockfile.py`): Advisory file locking using `fcntl.flock` (Unix) / `msvcrt.locking` (Windows) with blocking/non-blocking acquire and optional timeout. Used by `load_inline` to serialize concurrent builds; potentially reusable by other caching or build utilities.
- **Ninja build generation** (new, internal to `load_inline.py`): Platform-aware `build.ninja` generation with proper C++17 flags, CUDA compilation rules, and shared library linking. Handles Windows (MSVC flags) vs. Unix (GCC/Clang flags) differences.

### ADRs to write

- **`.knowledge/ADRs/0023-ninja-based-jit-compilation.md`**
  - Context: The `load_inline` feature needs to compile C++/CUDA source at runtime. Alternatives include invoking the compiler directly, using CMake, or using ninja. Ninja was chosen for its simplicity, speed, and dependency tracking (depfile support).
  - Alternatives: (1) Direct compiler invocation via `subprocess` (simpler but no incremental builds, no depfile tracking); (2) CMake (more powerful but heavyweight for single-file compilation, requires CMake at runtime); (3) Makefile (widespread but slower than ninja, less portable on Windows).
  - Trade-offs: Ninja adds a runtime dependency but provides minimal overhead, correct incremental rebuilds, and simple programmatic build file generation.

- **`.knowledge/ADRs/0024-content-addressed-build-cache.md`**
  - Context: JIT-compiled modules should be cached to avoid recompilation. The cache key is a SHA-256 hash of all inputs (source, function mappings, flags, include paths). The cache directory defaults to `~/.cache/tvm-ffi` but is configurable via `TVM_FFI_CACHE_DIR`.
  - Alternatives: (1) No caching (recompile every time -- too slow); (2) Timestamp-based invalidation (fragile, cannot detect content changes); (3) Separate compilation database (more complex, not needed for the single-module use case).
  - Trade-offs: Content-addressed caching is robust to source edits but the hash only covers the top-level inputs. If a transitive header changes, the cache will serve stale results. Ninja's depfile tracking partially mitigates this for incremental builds within the same cache directory, but not across cache directories.
