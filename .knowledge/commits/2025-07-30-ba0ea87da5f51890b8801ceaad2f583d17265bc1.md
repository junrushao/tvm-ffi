# Optimize string equality/hash by adding memequal and aligned-load hashing

## TL;DR
- Introduces `Bytes::memequal` -- a dedicated equality check using `std::memcmp` that short-circuits on length mismatch, replacing the slower `memncmp(...) == 0` pattern in all `operator==` paths and `AnyEqual`.
- Optimizes `StableHashBytes` for little-endian platforms by using a direct `uint64_t` load when the data pointer is 8-byte aligned, falling back to byte-by-byte copy only for unaligned data.
- Inlines `String::compare(const char*)` to avoid the overhead of `strlen` + `memncmp`, instead doing a single pass that detects null terminator directly.
- Adds tests for `String::compare` (various ordering and length cases) and `StableHashBytes` (aligned vs. unaligned data produces identical hash).

## Impact
- **API**: New public static method `Bytes::memequal(const char*, const char*, size_t, size_t) -> bool`. `Bytes::memncmp` is moved from out-of-class definition to inline definition (no signature change). `String::compare(const char*)` body is rewritten inline. All are source-compatible changes; no callers need modification.
- **Performance**: `operator==(String, String)`, `operator==(String, std::string)`, and `AnyEqual` (used by `Map<K,V>` hash table lookups) now call `memequal` which uses `std::memcmp` -- typically a highly optimized platform intrinsic -- instead of a hand-rolled byte-by-byte loop via `memncmp`. `StableHashBytes` gains an aligned fast path that avoids per-byte union stores on little-endian platforms.
- **Flags/config**: None.
- **Data formats/schemas**: None.

## Design Elements

Design elements this commit consumes:
- **AnyHash / AnyEqual** (`.knowledge/designs/0002-any-system.md`, section "AnyHash and AnyEqual"): `AnyEqual` previously called `Bytes::memncmp(...) == 0` for string comparison. This commit replaces that with the new `Bytes::memequal` for a direct equality path. `AnyHash` indirectly benefits via the optimized `StableHashBytes`.
- **String / Bytes container** (`.knowledge/designs/0005-containers.md`, section "String / Bytes"): `Bytes::memncmp` was the sole string-comparison primitive. This commit factors out the equality-only case into `memequal` and keeps `memncmp` for ordering comparisons.
- **StableHashBytes** (`include/tvm/ffi/base_details.h`): A platform-stable hash function used by `AnyHash`, `Map`, structural hashing, and dataclass hashing. This commit optimizes its inner loop.

Design elements this commit produces:
- **Bytes::memequal**: A new dedicated equality primitive that separates the equality concern from the three-way comparison concern. This method is now the canonical way to check string/byte equality throughout the codebase (used in `AnyEqual`, `operator==`, and `structural_equal`). It enables the use of `std::memcmp` -- which compilers can lower to SIMD instructions -- instead of a hand-rolled byte loop.
- **Aligned-load optimization in StableHashBytes**: An architecture-aware fast path that checks pointer alignment at runtime and uses a direct `uint64_t` dereference when safe. This is a micro-optimization pattern relevant to any future hashing or serialization code.

## Reflection

### Design docs to write
- **`.knowledge/designs/0005-containers.md` update (String/Bytes primitives)**: The current design doc mentions `StringObj` and `BytesObj` but does not document the low-level comparison primitives (`memncmp`, `memequal`) or their performance characteristics. A subsection should describe: (1) `memncmp` for three-way comparison, (2) `memequal` for equality using `std::memcmp`, (3) `String::compare(const char*)` as an optimized single-pass comparison avoiding `strlen`. This would help future commits that touch string comparison or add new comparison operators.
- **`.knowledge/designs/0002-any-system.md` update (AnyHash/StableHashBytes internals)**: The current doc mentions `AnyHash` uses `StableHashBytes` but does not document the hashing algorithm (FNV-like polynomial hash with `kMultiplier = 1099511628211`, `kMod = 2147483647`) or its alignment optimization. A subsection should cover: (1) the hash algorithm and its stability guarantees, (2) the endian-swap logic, (3) the aligned vs. unaligned fast paths. This would help future commits that modify hashing behavior or add new hashable types.

### ADRs to write
- **`.knowledge/ADRs/0011-memequal-over-memncmp-for-equality.md`**: Context: Equality checks previously went through `memncmp(...) == 0`, which performs a full three-way comparison even when only a boolean result is needed. The alternative was to keep `memncmp` for all cases (simpler, one function). The trade-off: `memequal` adds a second method to maintain but enables `std::memcmp` which compilers can vectorize, and short-circuits on length mismatch before touching data.

### Design diagrams to draw
- **Mermaid: String comparison dispatch**: A flowchart showing how `operator==`, `operator<`, `AnyEqual`, and `String::compare` route through `memequal` vs `memncmp` vs inline comparison, clarifying which primitive is used in each path.
