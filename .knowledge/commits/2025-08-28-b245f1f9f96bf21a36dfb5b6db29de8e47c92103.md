# Add explicit git download URL for libbacktrace in CMake ExternalProject
## TL;DR
- Adds `GIT_REPOSITORY` and `GIT_TAG` parameters to the `ExternalProject_Add` call for libbacktrace in `cmake/Utils/AddLibbacktrace.cmake`, providing a direct download path from the upstream GitHub repository at a pinned commit (`793921876c981ce49759114d7bb89bb89b2d3a2d`).
- This is a 2-line addition to a single CMake file, with no functional behavior change to the library build itself.
- **Note**: This change was reverted in the immediately following commit `7d09d6a` ([#18249](https://github.com/apache/tvm/pull/18249)) in favor of using the git submodule mechanism instead, after discussion concluded that the submodule approach was preferred and the upstream libbacktrace already incorporated the needed macOS patch.

## Impact
- API: none
- Flags/config: none -- the `ExternalProject_Add` already had `SOURCE_DIR` pointing to the vendored `3rdparty/libbacktrace`; the new `GIT_REPOSITORY`/`GIT_TAG` provide an alternative download mechanism when the submodule source is absent.
- Data formats/schemas: none

The `ExternalProject_Add` pattern is the mechanism used to compile libbacktrace as a static library (`libbacktrace.a`) and expose it as an imported target. This commit modifies only the download step of that external project.
- **`TVM_FFI_USE_LIBBACKTRACE` option**: The build option that gates whether libbacktrace is compiled at all. This commit does not change the option but operates within the code path it enables.

## Reflection

### Design docs to write
None. The build system is already well-documented in `.knowledge/designs/0016-packaging-and-build.md`. The `AddLibbacktrace.cmake` utility is a relatively small, self-contained piece of that system.

### ADRs to write
- **`.knowledge/ADRs/0023-libbacktrace-vendoring-strategy.md`**: This commit and its immediate revert (`7d09d6a`) represent an architectural decision about how third-party C dependencies should be sourced. The decision context is: CMake `ExternalProject_Add` with `GIT_REPOSITORY` vs. git submodule. The trade-off is that `GIT_REPOSITORY` makes builds work without submodule initialization but introduces a network dependency during the build; git submodule keeps the source vendored and offline-buildable but requires `git submodule update --init`. The conclusion (per `7d09d6a`) was to keep the submodule approach and update the submodule to upstream HEAD. This ADR would help future contributors understand why direct URL downloads in CMake are avoided for vendored deps.

### Skill evolution (`/commit-ledger`)
- The procedure could benefit from a **"short-lived change" annotation** in the template: when a commit is known to be reverted by a later commit (detectable from git history), the ledger should prominently note this at the top of TL;DR, as this drastically changes the commit's long-term relevance. The current template does not have a standard field for "reverted_by" in the frontmatter. Consider adding an optional `reverted_by: "<sha>"` YAML key to the template to make this machine-parseable.
- For trivial commits (Step 2 classification), the procedure says "you may skip detailed investigation in Step 3." However, even trivial commits can reveal interesting architectural decisions (as this one did -- it led to a revert and an ADR-worthy discussion). The guidance could be refined to: "Skip Step 3 only for truly mechanical chores (formatting, CI config tweaks). For any commit that touches build logic or dependency management, proceed with Step 3 even if the diff is small."

## Self-Evolution of Skill /commit-ledger
- **Add `reverted_by` frontmatter field**: When analyzing a commit, the skill should check whether any subsequent commit in the repo's history reverts or undoes the change (e.g., by searching for "Revert" in messages or checking if the diff is exactly negated). If so, add `reverted_by: "<sha>"` to the YAML frontmatter. This makes it trivial for downstream tooling to filter out or de-prioritize reverted changes.
- **Refine trivial-commit skip criteria**: The current "chore-only" heuristic is too coarse. A 2-line CMake change classified as "chore" can still carry design-level significance (dependency sourcing strategy). Suggest rewording Step 2 to: "Skip Step 3 only for commits with zero semantic content (whitespace, formatting, CI badge updates). For any build/dependency change, always proceed to Step 3."
- **Cross-reference adjacent commits**: For commits that are part of a quick "add then revert" pair (same file, within a few commits), the skill should automatically read the reverting commit's message and diff to provide full context. This was done manually here but could be systematized as: "If any of the next 5 commits touch the same file with an inverse diff, read and summarize the reverting commit."
