# Fix integer overflow in GetDataSize on 32-bit platforms (WASM)
## TL;DR
- `GetDataSize(numel, dtype)` multiplied three `size_t`/`uint8_t` values before dividing by 8; on 32-bit platforms (`size_t` = 32 bits) the intermediate product could overflow even when the final byte count was representable.
- The fix casts `numel` to `uint64_t` before the multiplication, promoting the entire expression to 64-bit arithmetic, then truncates back to `size_t` after dividing.
- Reported against WASM/WebLLM via mlc-llm: large model tensors silently allocated 0-byte buffers instead of failing or allocating correctly.

## Key Exports

```python
def GetDataSize(numel: size_t, dtype: DLDataType) -> size_t:
    """Returns the number of bytes required to store `numel` packed elements of `dtype`.
    # Old (broken on 32-bit):
    #   return (numel * dtype.bits * dtype.lanes + 7) / 8
    # New (safe on 32-bit):
    #   return size_t((uint64_t(numel) * dtype.bits * dtype.lanes + 7) / 8)
    # Invariant: result fits in size_t on the target platform (caller's responsibility
    #            to avoid requesting a buffer larger than addressable memory).
    # Invariant: for kDLUInt + bits=1 + lanes=1 (bool), returns numel directly (no overflow path).
    # Interacts with: GetDataSize(DLTensor), GetDataSize(Tensor), GetDataSize(TensorView)
    #                 — all three overloads delegate to this two-argument form.
    # Interacts with: Tensor allocation callers (AllocData, Tensor.view strided constructor)
    """
```

## Impact
- API: None — same signature, same return type.
- Behavioral: On 32-bit platforms, large tensors (where `numel * bits * lanes` overflows 32 bits before the `/8` reduction) now produce the correct byte count instead of a wrapped-around (potentially 0) value. On 64-bit platforms, the existing code was already safe; this change is a no-op there.
- Flags/config: None.
- Data formats/schemas: None.

## Usage Examples
**Before (incorrect on 32-bit/WASM for large tensors):**
```cpp
// numel=1048576, dtype.bits=32, dtype.lanes=1 on a 32-bit platform:
// numel * dtype.bits = 1048576 * 32 = 33554432  (still fits)
// 33554432 * dtype.lanes = 33554432             (still fits)
// But for numel=134217728, bits=32: product = 4294967296 -> wraps to 0 on uint32
size_t sz = (numel * dtype.bits * dtype.lanes + 7) / 8;  // sz = 0 — wrong
```

**After (correct on 32-bit/WASM):**
```cpp
// Cast numel to uint64_t before multiplying
size_t sz = static_cast<size_t>(
    (static_cast<uint64_t>(numel) * dtype.bits * dtype.lanes + 7) / 8
);  // sz = 536870912 — correct
```
