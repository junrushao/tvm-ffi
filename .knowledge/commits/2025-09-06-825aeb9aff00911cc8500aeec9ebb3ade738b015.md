# Align load_inline API with torch.utils.cpp_extension.load_inline conventions
## TL;DR
- Renames `cpp_source` to `cpp_sources` and `cuda_source` to `cuda_sources`, accepting `Sequence[str] | str` to allow multiple source fragments that are joined with newlines before compilation.
- Replaces the split `cpp_functions` / `cuda_functions` parameters (each `Mapping[str, str]` mapping exported name to source name) with a single unified `functions` parameter (`Sequence[str] | Mapping[str, str] | str`) where the mapping variant now maps function name to docstring (exported name == source name).
- Adds a `build_directory` parameter that bypasses the content-addressed cache, allowing users to specify an explicit build directory (useful for debugging and reproducible builds).

## Impact
- **API**: Breaking change to `tvm_ffi.cpp.load_inline()`. All three renamed parameters (`cpp_sources`, `cuda_sources`, `functions`) are keyword-only, so all existing callers that used the old names (`cpp_source`, `cuda_source`, `cpp_functions`, `cuda_functions`) must update. The semantic of the mapping variant changes: previously `{exported_name: source_func_name}` (allowing different export and source names), now `{func_name: docstring}` (export name always equals source name). This removes the ability to export a function under a name different from its C++ definition.
- **Flags/config**: None. The `TVM_FFI_CACHE_DIR` environment variable and its behavior are unchanged. The new `build_directory` parameter provides an alternative to the environment variable for per-call control.
- **Data formats/schemas**: None. The on-disk cache layout is unchanged; only the hash inputs shift (unified `functions` instead of separate `cpp_functions` / `cuda_functions`).

## Design Elements

Design elements this commit **consumes**:

- **Inline module compilation pipeline** ([`.knowledge/designs/0017-inline-module-compilation.md`](../designs/0017-inline-module-compilation.md)): Modifies the public API surface and internal helpers (`_hash_sources`, `_decorate_with_tvm_ffi`, `load_inline`) of the existing pipeline introduced in `83805ec`. The compilation flow (source decoration -> cache lookup -> ninja build -> load_module) is preserved.
- **Module export system** ([`.knowledge/designs/0008-module-export-system.md`](../designs/0008-module-export-system.md)): The `_decorate_with_tvm_ffi` function continues to emit `TVM_FFI_DLL_EXPORT_TYPED_FUNC(name, name)` lines. A key behavioral change: previously it could emit `TVM_FFI_DLL_EXPORT_TYPED_FUNC(exported_name, different_source_name)` with different first and second arguments; now both arguments are always the same function name. This constrains usage but simplifies the API and aligns with typical PyTorch patterns where the exported name matches the C++ function name.
- **PyTorch API conventions** (external): The commit message explicitly states the goal is to match `torch.utils.cpp_extension.load_inline`. PyTorch uses `functions` as a list of function names (not separate cpp/cuda splits), and `cpp_sources`/`cuda_sources` as pluralized source parameters accepting lists.

Design elements this commit **produces**:

- **Unified `functions` parameter with docstring mapping** (evolution of `0017-inline-module-compilation`): The new `functions` parameter accepts three forms: `Sequence[str]` (function names with empty docstrings), `Mapping[str, str]` (function names to docstrings), or `str` (single function name). A `_ = func_doc` TODO comment in `_decorate_with_tvm_ffi` signals intent to embed docstrings in FFI function metadata in the future.
- **`build_directory` parameter** (evolution of `0017-inline-module-compilation`): When provided, skips the content-addressed cache entirely (`_hash_sources` is not called) and uses the given directory as the build root. The directory is created with `os.makedirs(build_dir, exist_ok=True)`. This provides a deterministic build location for debugging but trades off the cache deduplication guarantee.
- **Multi-source joining** (evolution of `0017-inline-module-compilation`): `cpp_sources` and `cuda_sources` accept `Sequence[str]`, joining fragments with `"\n".join(...)` before feeding to `_decorate_with_tvm_ffi`. The `with_cuda` flag is now determined by `len(cuda_sources) > 0` (list non-empty) rather than `len(cuda_source.strip()) > 0` (string non-whitespace).
- **CUDA function export moved to cpp_sources** (behavioral change): CUDA functions are no longer decorated separately. The `cuda_source` is always decorated with an empty function mapping (`{}`), and all function exports (including CUDA functions) must be declared in `cpp_sources` with a forward declaration (e.g., `void add_one_cuda(DLTensor* x, DLTensor* y);`) and exported from there. The test changes demonstrate this pattern explicitly.

### Design docs to write

- **Update `.knowledge/designs/0017-inline-module-compilation.md`**

  - The content-addressed cache section (line 76) documents hash inputs as `(cpp_source, cuda_source, cpp_functions, cuda_functions, ...)`. This must be updated to reflect the unified `functions` parameter and the `build_directory` bypass path.
  - The compilation pipeline diagram (lines 36-47) should be updated to show the `build_directory` bypass that skips hashing.
  - Why: Any future commit that further evolves the `load_inline` API (e.g., adding HIP support, implementing the docstring TODO, supporting multiple files per source language) would reference this doc. Stale parameter names would cause confusion.

### ADRs to write

- **`.knowledge/ADRs/0027-load-inline-torch-alignment.md`**
  - Context: The original `load_inline` API used separate `cpp_functions`/`cuda_functions` mappings where keys were export names and values were source function names, allowing renaming. This PR aligns with PyTorch's `torch.utils.cpp_extension.load_inline` which uses a single `functions` parameter and does not support renaming.
  - Alternatives: (1) Keep the rename capability via the old split-mapping interface (more flexible but diverges from PyTorch conventions, adds user confusion about which parameter to use for CUDA functions); (2) Support both old and new interfaces with deprecation warnings (more migration-friendly but adds code complexity).
  - Trade-offs: Dropping the rename capability simplifies the API and mental model but removes a feature (exporting a function under a different name than its C++ definition). Users who need renaming must now use thin wrapper functions in C++.
