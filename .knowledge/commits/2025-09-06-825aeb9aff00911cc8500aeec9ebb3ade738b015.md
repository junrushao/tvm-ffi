# Update load_inline interface to match torch.utils.cpp_extension.load_inline

## TL;DR
- Renames `cpp_source`→`cpp_sources`, `cuda_source`→`cuda_sources`; both now accept `str | list[str]`, joined with `\n` before compilation.
- Unifies `cpp_functions` + `cuda_functions` into a single `functions` parameter that accepts `str | Sequence[str] | Mapping[str, str]`; semantics change — mapping values are now **docstrings** (not function aliases in source), so exported name == source name.
- Adds `build_directory` parameter to bypass the hash-based cache and use a caller-specified directory instead.

| Old name | New name | Semantic change |
|---|---|---|
| `cpp_source: str` | `cpp_sources: str \| list[str]` | Now joined if list |
| `cuda_source: str` | `cuda_sources: str \| list[str]` | Now joined if list |
| `cpp_functions: Mapping[str,str]` | `functions: str \| Seq[str] \| Mapping[str,str]` | Values = docstrings (not alias); name must match source |
| `cuda_functions: Mapping[str,str]` | *(removed, merged into `functions`)* | Both cpp and cuda share one functions list |
| *(absent)* | `build_directory: str \| None` | Skip hash-cache, use explicit dir |

## Impact
- API: **Breaking rename** for all existing callers of `load_inline` — `cpp_source`, `cuda_source`, `cpp_functions`, `cuda_functions` keyword arguments no longer exist. Callers must migrate to `cpp_sources`, `cuda_sources`, `functions`.
- Behavioral: The `functions` mapping no longer allows `exported_name != function_name_in_source`. The exported symbol name must now match the C++ function name directly. Any caller that relied on aliased exports (e.g., `{"add_one_cpu": "AddOne"}`) must rename their C++ function.
- Flags/config: New `build_directory` parameter. `TVM_FFI_CACHE_DIR` env var still controls default cache; `build_directory` fully overrides it.
- Data formats/schemas: Cache directory structure unchanged (`{name}_{hash}/`); but because `functions` hash now uses docstrings (not aliases), existing cached builds with the old interface will produce different hashes even for equivalent compilation.

## Design Elements

Design elements this commit consumes:
- **`TVM_FFI_DLL_EXPORT_TYPED_FUNC`** (`0004-function-system`, `0001-c-abi`): `_decorate_with_tvm_ffi` appends this macro to every source file; it wraps the named C++ function as a C ABI `safe_call` symbol loadable by `ffi.Module`.
- **`ffi.Module`** (`0011-module-system`): Return type of `load_inline`; the compiled `.so` is loaded via `load_module`, exposing functions as `Module` attributes.
- **`load_inline` API convention** (this file): Mirrors `torch.utils.cpp_extension.load_inline` interface — `cpp_sources` / `cuda_sources` / `functions` naming.

Design elements this commit produces:
- **Updated `load_inline` signature** (`python/tvm_ffi/cpp/load_inline.py`): New canonical interface for compiling inline C++/CUDA modules. The three-form `functions` parameter (`str | Sequence | Mapping`) and the `build_directory` escape hatch are the new stable surface.

## Usage Examples

**Basic C++ inline module (new interface):**
```python
import tvm_ffi
mod = tvm_ffi.cpp.load_inline(
    name="hello",
    cpp_sources=r"""
        void add_one_cpu(DLTensor* x, DLTensor* y) { ... }
    """,
    functions=["add_one_cpu"],  # list form — names must match C++ function names
)
mod.add_one_cpu(x, y)
```

**With docstrings (mapping form, docstring unused today):**
```python
mod = tvm_ffi.cpp.load_inline(
    name="hello",
    cpp_sources=r"""void add_one_cpu(DLTensor* x, DLTensor* y) { ... }""",
    functions={"add_one_cpu": "add two float32 1D tensors element-wise"},
)
```

**Multiple sources + explicit build directory:**
```python
mod = tvm_ffi.cpp.load_inline(
    name="hello",
    cpp_sources=[source_a, source_b],
    functions=["add_one_cpu", "add_two_cpu"],
    build_directory="./build_add_one",  # skips hash-cache
)
```
