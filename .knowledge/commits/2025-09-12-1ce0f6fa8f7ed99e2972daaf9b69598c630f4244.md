# Allow CUDA-only load_inline without requiring cpp_sources forward declarations
## TL;DR
- Changes `load_inline` so that when `cpp_sources` is empty and only `cuda_sources` is provided, the `functions` list is exported from the CUDA source file instead of the C++ source file. Previously, CUDA-exported functions always required a forward declaration in `cpp_sources`.
- Updates the `test_load_inline_cuda` test to remove the now-unnecessary `cpp_sources` forward declaration, validating the CUDA-only workflow.
- Improves the docstring for the `functions` parameter to document the new dispatch behavior.

## Impact
- API: Behavioral change to `tvm_ffi.cpp.load_inline()`. Previously, the `functions` parameter always placed `TVM_FFI_DLL_EXPORT_TYPED_FUNC` macros into `main.cpp` (the C++ source), requiring a forward declaration of CUDA functions in `cpp_sources`. Now, if `cpp_sources` is empty (no C++ source fragments provided), the export macros are placed into `cuda.cu` instead. This is a backwards-compatible relaxation: existing calls that provide both `cpp_sources` (with forward declarations) and `cuda_sources` continue to work identically.
- Flags/config: None.
- Data formats/schemas: None.

## Design Elements
Design elements this commit consumes:
- **Inline module compilation pipeline** ([`.knowledge/designs/0017-inline-module-compilation.md`](../designs/0017-inline-module-compilation.md)): The core `load_inline` function and its `_decorate_with_tvm_ffi` helper. The commit modifies the dispatch logic that decides which source file (`main.cpp` vs `cuda.cu`) receives the `TVM_FFI_DLL_EXPORT_TYPED_FUNC` macro lines.
- **Module export system / `TVM_FFI_DLL_EXPORT_TYPED_FUNC`** ([`.knowledge/designs/0008-module-export-system.md`](../designs/0008-module-export-system.md)): The export macro is what `_decorate_with_tvm_ffi` appends to source files. The macro generates `extern "C"` symbols that `load_module` discovers. The key insight is that this macro can be placed in either a `.cpp` or `.cu` file, as long as the function it wraps is defined (or at least declared) in that compilation unit.

Design elements this commit produces:
- **CUDA-only export dispatch rule** (new behavioral invariant, not yet documented): When `cpp_sources` is empty (`with_cpp == False`), `functions` are exported from `cuda_sources`. When `cpp_sources` is non-empty (`with_cpp == True`), `functions` are exported from `cpp_sources` (unchanged from prior behavior). This is a conditional dispatch on the `with_cpp` boolean, introduced at `python/tvm_ffi/cpp/load_inline.py` lines 387-393. The invariant is: exactly one of `cpp_source` or `cuda_source` receives the `functions` dict for decoration; the other receives an empty dict.

## Reflection

### Design docs to write

- **`.knowledge/designs/0017-inline-module-compilation.md` (update)**: The "API Surface" section currently states: "CUDA function exports must be declared in `cpp_sources` with a forward declaration." This is no longer true after this commit. The doc should be updated to describe the new dispatch behavior: when `cpp_sources` is empty, `functions` are exported directly from `cuda_sources`. The "Source Decoration" section should also mention the `with_cpp` conditional. This helps future commit mining for any changes to the export dispatch logic or CUDA-only workflows.

### ADRs to write

None. The change is a straightforward UX improvement that removes an unnecessary requirement. No new architectural decision or trade-off is introduced.

None. The existing pipeline flowchart in `0017-inline-module-compilation.md` does not need modification; the change is within the `_decorate_with_tvm_ffi()` step, which is already depicted. The conditional dispatch is a detail within that step rather than a new pipeline stage.
