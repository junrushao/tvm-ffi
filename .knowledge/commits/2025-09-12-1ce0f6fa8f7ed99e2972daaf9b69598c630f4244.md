# Allow CUDA-only load_inline without requiring a C++ forward declaration
## TL;DR
- Changes `load_inline` so that when only `cuda_sources` is provided (no `cpp_sources`), the `TVM_FFI_DLL_EXPORT_TYPED_FUNC` export macros are appended to the CUDA source instead of the (empty) C++ source. Previously, export macros were always placed in `cpp_source`, requiring users to provide a C++ forward declaration even for pure-CUDA modules.
- Updates the `test_load_inline_cuda` test to remove the now-unnecessary `cpp_sources` forward declaration, validating the CUDA-only workflow.
- Updates the `functions` parameter docstring to clarify the new dispatch behavior: functions must be declared in `cpp_sources` if present, or defined in `cuda_sources` if `cpp_sources` is absent.

## Key Exports
None. The `load_inline` function signature is unchanged. The behavioral change is internal: which source file receives the export macros depends on whether `cpp_sources` is provided.

## Impact
- API: None -- `load_inline` signature unchanged.
- ABI: None -- no C/C++ ABI changes.
- Behavioral: **CUDA-only modules no longer require a C++ forward declaration.** Before this commit, calling `load_inline(name="x", cuda_sources="...", functions=["f"])` would place the `TVM_FFI_DLL_EXPORT_TYPED_FUNC` macro in the empty `main.cpp`, causing a compilation error because `f` is not declared there. After this commit, the macro is placed in `cuda.cu` where the function is defined. Mixed C++/CUDA usage is unchanged (macros still go in `cpp_source`).
- Flags/config: None.
- Data formats/schemas: None.

## Design Elements
Design elements this commit consumes:
- **Inline module compilation** (`.knowledge/designs/0017-inline-module-compilation.md`): the `_decorate_with_tvm_ffi` helper, the `with_cuda` flag pattern, and the Ninja build generation pipeline.
- **Module system** (`.knowledge/designs/0013-module-system.md`): `TVM_FFI_DLL_EXPORT_TYPED_FUNC` macro for exporting functions from shared libraries.

Design elements this commit produces:
- **`with_cpp` flag**: A new local variable `with_cpp = len(cpp_sources) > 0` that gates whether FFI export macros are directed to the C++ source or the CUDA source. This mirrors the existing `with_cuda` pattern and establishes the convention that the "primary" source (the one receiving export macros) is C++ when available, CUDA otherwise.
- **Conditional export macro placement**: The invariant that `_decorate_with_tvm_ffi(source, functions)` is called with the non-empty `functions` dict on whichever source is the "primary" one, and with an empty dict `{}` on the other. This replaces the previous unconditional "C++ gets functions, CUDA gets nothing" policy.

## Usage Examples
**CUDA-only module (new pattern enabled by this commit):**
```python
import tvm_ffi.cpp

mod = tvm_ffi.cpp.load_inline(
    name="hello",
    cuda_sources=r"""
        __global__ void AddOneKernel(float* x, float* y, int n) {
            int i = blockIdx.x * blockDim.x + threadIdx.x;
            if (i < n) y[i] = x[i] + 1.0f;
        }
        void add_one_cuda(DLTensor* x, DLTensor* y) {
            int n = x->shape[0];
            AddOneKernel<<<(n+255)/256, 256>>>(
                static_cast<float*>(x->data), static_cast<float*>(y->data), n);
        }
    """,
    functions=["add_one_cuda"],  # export macros go into cuda.cu directly
)
```

**Before this commit**, the same call would require a redundant `cpp_sources` forward declaration:
```python
mod = tvm_ffi.cpp.load_inline(
    name="hello",
    cpp_sources="void add_one_cuda(DLTensor* x, DLTensor* y);",  # required before
    cuda_sources=r"""...""",
    functions=["add_one_cuda"],
)
```
