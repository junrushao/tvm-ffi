# Guard dsymutil post-build step behind TVM_FFI_USE_LIBBACKTRACE on Apple

## TL;DR

- `add_dsymutil()` in `cmake/Utils/Library.cmake` previously ran `dsymutil` unconditionally on any Apple platform, regardless of whether `libbacktrace` was enabled.
- The fix adds `AND TVM_FFI_USE_LIBBACKTRACE` to the guard, so the `dsymutil` post-build step only fires when the backtrace backend that actually needs DWARF symbols is active.
- **Diff-message alignment note**: The commit message describes a Metal runtime `MetalModuleNode::GetFunction` / `autoreleasepool` bug (upstream PR #18034), but only the CMake portion of that PR is present in this repository's diff. Analysis is scoped to the actual diff.

## Key Exports

None

## Impact

- API: none
- Behavioral: `dsymutil` post-build step is now skipped on macOS/Apple builds that do not set `TVM_FFI_USE_LIBBACKTRACE=ON`. Builds with `TVM_FFI_USE_LIBBACKTRACE=ON` on Apple are unchanged.
- Flags/config: `TVM_FFI_USE_LIBBACKTRACE` — existing flag; now also gates the `dsymutil` step in `add_dsymutil()` (previously only gated the traceback capture logic in C++ source).
- Data formats/schemas: none

## Design Elements

Design elements this commit consumes:
- `TVM_FFI_USE_LIBBACKTRACE` CMake option — controls whether native stack traces are captured (documented in design record `0004-error-propagation` as the traceback backend toggle).
- `add_dsymutil(target_name)` CMake function in `cmake/Utils/Library.cmake` — post-build step that runs `dsymutil` on Apple to generate DWARF debug symbols for backtrace support.

Design elements this commit produces: None

## Usage Examples

Before (incorrect — always ran dsymutil on Apple):
```cmake
if(APPLE)
  find_program(DSYMUTIL dsymutil) ...
endif()
```

After (correct — only runs dsymutil when libbacktrace is active):
```cmake
if(APPLE AND TVM_FFI_USE_LIBBACKTRACE)
  find_program(DSYMUTIL dsymutil) ...
endif()
```
