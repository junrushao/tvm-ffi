# Misc fixups for Windows compatibility: CMake modernization, Tuple SFINAE fix, non-ASCII comment cleanup, and test output path normalization
## TL;DR
- Replaces deprecated `FetchContent_Populate` + manual `add_subdirectory` with `FetchContent_MakeAvailable` for GoogleTest in `cmake/Utils/AddGoogleTest.cmake`, modernizing the CMake integration.
- Fixes the `Tuple<Ts...>` variadic constructor SFINAE guard to use `std::decay_t<UTypes>` instead of `std::remove_cv_t<UTypes>`, correctly excluding reference-qualified types from hijacking copy/move semantics.
- Replaces non-ASCII en-dash characters (U+2013) with plain ASCII hyphens in comments within `json_parser.cc`, removing a potential encoding issue on Windows toolchains.
- Normalizes the test binary output directory from `bin/` to `lib/` and removes the hardcoded `MSVC_RUNTIME_LIBRARY` property from the test CMakeLists.txt.

## Impact
- API: none -- no public C++ or Python API changes. All changes are internal to the build system, a type trait in a template constructor, and source comments.
- Flags/config: The removal of the explicit `MSVC_RUNTIME_LIBRARY "MultiThreaded$<$<CONFIG:Debug>:Debug>"` setting from the test target means the test binary will now use CMake's default MSVC runtime library policy (controlled by `CMAKE_MSVC_RUNTIME_LIBRARY` or the global default, which is typically `MultiThreadedDLL`/`MultiThreadedDebugDLL`). This is a deliberate change to avoid forcing a static runtime for tests, improving compatibility when the rest of the project uses the dynamic runtime.
- Data formats/schemas: none.

Design elements this commit **produces**:

- **Refinement: Tuple SFINAE guard now uses `std::decay_t`**: The previous guard used `std::remove_cv_t<UTypes>` to detect when the single argument to `Tuple<T>(arg)` is itself a `Tuple<T>`. However, `std::remove_cv_t` only strips top-level `const`/`volatile` qualifiers -- it does not strip references. When `UTypes` deduces as `Tuple<T>&` or `const Tuple<T>&`, `std::remove_cv_t<Tuple<T>&>` remains `Tuple<T>&`, causing the SFINAE check `std::is_same_v<std::remove_cv_t<UTypes>, Tuple<Types>>` to fail. The forwarding constructor would then not be excluded, hijacking copy construction. `std::decay_t` strips both references and cv-qualifiers, correctly identifying the underlying type. This is a correctness fix for edge cases where the argument is an lvalue reference, which is the common case on MSVC where copy elision behavior can differ.
- **Build modernization: `FetchContent_MakeAvailable`**: Replaces the three-step `FetchContent_Populate` + `message` + `add_subdirectory` pattern with the single-call `FetchContent_MakeAvailable`. This is the idiomatic CMake 3.14+ pattern (available given the project's 3.18 minimum). It is cleaner, and more importantly, `FetchContent_MakeAvailable` handles edge cases like `FETCHCONTENT_FULLY_DISCONNECTED` mode correctly, which improves offline/CI build scenarios.

## Key Implementations

### Tuple SFINAE: `std::remove_cv_t` vs `std::decay_t`

The critical change is in `include/tvm/ffi/container/tuple.h`, the variadic forwarding constructor of `Tuple<Types...>`:

```cpp
// Before:
std::is_same_v<std::remove_cv_t<UTypes>, Tuple<Types>>
// After:
std::is_same_v<std::decay_t<UTypes>, Tuple<Types>>
```

**Invariant assumed**: When `sizeof...(Types) == 1`, the forwarding constructor must NOT match when the single argument is a `Tuple<Types>` value, reference, or cv-qualified reference. `std::decay_t` handles all these cases by applying: (1) remove reference, (2) remove cv, (3) array-to-pointer / function-to-pointer decay.

**Failure mode before fix**: On MSVC, when calling `Tuple<T> t2(t1)` where `t1` is an lvalue `Tuple<T>`, `UTypes` deduces as `Tuple<T>&`. The SFINAE check with `remove_cv_t` evaluates `std::is_same_v<Tuple<T>&, Tuple<T>>` which is `false`, so the guard does not exclude the forwarding constructor. The forwarding constructor wins overload resolution over the copy constructor, leading to incorrect behavior (attempting to construct a `Tuple` element from a `Tuple` reference rather than copy-constructing the `Tuple` itself).

**Extension point**: The same SFINAE pattern should be used for any single-element wrapper type that has both a forwarding constructor and copy/move constructors.

### CMake: MSVC runtime library removal

Removing `MSVC_RUNTIME_LIBRARY "MultiThreaded$<$<CONFIG:Debug>:Debug>"` from the test target is significant because it was forcing `/MT` (static CRT) for tests. If `tvm_ffi_shared` itself is built with `/MD` (dynamic CRT, the CMake default), mixing `/MT` tests linked against `/MD` libraries leads to runtime heap corruption or link errors on Windows. Removing the explicit setting lets the test inherit the project-wide CRT policy.

### CMake: Test output directory normalization

Changing `RUNTIME_OUTPUT_DIRECTORY` from `"${CMAKE_BINARY_DIR}/bin"` to `"${CMAKE_BINARY_DIR}/lib"` puts the test binary in the same directory as the shared library (`libtvm_ffi.so` / `tvm_ffi.dll`). On Windows, where DLLs must be in the same directory as the executable (or on `PATH`), this ensures the test binary can find `tvm_ffi.dll` at runtime without additional `PATH` manipulation.

### Non-ASCII comment cleanup

The en-dash characters (U+2013, `\xe2\x80\x93`) in `json_parser.cc` comments are replaced with plain hyphens (`-`). While not a functional issue on most compilers, some Windows toolchains and editors may not handle non-ASCII in source comments gracefully, especially when source files are expected to be pure ASCII or UTF-8 with BOM.

## Reflection

### Design docs to write

- **Update `.knowledge/designs/0005-containers.md` -- Tuple SFINAE Guard subsection**: The current text says "the variadic constructor has a SFINAE guard that excludes the case where the single argument type is `Tuple<Types>`" but does not specify which type trait is used for the detection. It should explicitly state that `std::decay_t` (not `std::remove_cv_t`) is the canonical trait for this pattern, and explain why: `decay_t` handles lvalue references deduced in forwarding contexts, whereas `remove_cv_t` does not strip references. This helps future contributors avoid regressing to `remove_cv_t` or `remove_reference_t` alone.

- **Update `.knowledge/designs/0016-packaging-and-build.md` -- Test target configuration**: The design doc does not mention the test target properties (output directory, MSVC runtime). Adding a brief subsection about test binary placement conventions (co-locate with shared library for DLL discovery on Windows) and the policy of not hardcoding MSVC runtime libraries on test targets would prevent future regressions.
