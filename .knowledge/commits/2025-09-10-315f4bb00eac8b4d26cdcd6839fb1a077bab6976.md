# Fix SystemLibrary symbol lookup to handle names with or without prefix
## TL;DR
- Fixes `SystemLibrary::GetSymbol` and `SystemLibrary::GetSymbolWithSymbolPrefix` to try both prefixed and unprefixed symbol names, because callers may pass names that already include the symbol prefix.
- Before this fix, lookups would fail when the incoming `name` already contained the prefix (resulting in double-prefixing) or when the registry stored the symbol under a different prefix combination than the single lookup attempted.
- The fix adds a fallback path in both methods: try with prefix first, then without (or with a shorter prefix).

## Impact
- API: No public API change. The `Library` virtual interface (`GetSymbol`, `GetSymbolWithSymbolPrefix`) is internal and not exposed across the FFI boundary. The behavioral fix is transparent to callers of `LibraryModuleObj::GetFunction` and `CreateLibraryModule`.
- Flags/config: None.
- Data formats/schemas: None.
- Runtime correctness: This is a correctness fix for system library module function discovery. Without it, functions registered in `SystemLibSymbolRegistry` under names that already include the symbol prefix (or the `__tvm_ffi_` prefix) could not be found, causing `GetFunction` to return `nullopt` and downstream `RuntimeError` on function resolution.

## Design Elements
Design elements this commit consumes:
- **Module system / Library abstraction** ([`.knowledge/designs/0013-module-system.md`](../designs/0013-module-system.md)): The `Library` base class defines `GetSymbol` and `GetSymbolWithSymbolPrefix` as virtual methods. `SystemLibrary` overrides both. The base class default for `GetSymbolWithSymbolPrefix` simply prepends `symbol::tvm_ffi_symbol_prefix` and delegates to `GetSymbol`. `SystemLibrary` must do something more nuanced because it has its own `symbol_prefix_` layer on top.
- **Module export system / symbol naming convention** ([`.knowledge/designs/0008-module-export-system.md`](../designs/0008-module-export-system.md)): `TVM_FFI_DLL_EXPORT_TYPED_FUNC` generates symbols with the `__tvm_ffi_` prefix. Callers may or may not strip this prefix before passing names to `GetSymbol`.
- **Well-known symbols** ([`.knowledge/designs/0013-module-system.md`](../designs/0013-module-system.md)): `symbol::tvm_ffi_symbol_prefix = "__tvm_ffi_"` is the constant used in prefix construction. The call chain `LibraryModuleObj::GetFunction -> lib_->GetSymbolWithSymbolPrefix(name)` passes undecorated function names, but `TVMFFIEnvModRegisterSystemLibSymbol` registers symbols under their full decorated names (with `__tvm_ffi_` prefix already included).
- **Extra API tier** ([`.knowledge/designs/0011-extra-api-tier.md`](../designs/0011-extra-api-tier.md)): The file lives in `src/ffi/extra/` and is gated by `TVM_FFI_USE_EXTRA_CXX_API`.

Design elements this commit produces:
- **Prefix-tolerant symbol lookup invariant** (new, not documented): Both `GetSymbol` and `GetSymbolWithSymbolPrefix` in `SystemLibrary` now implement a "try-with-prefix, fallback-to-without" pattern. This makes the lookup robust to callers that pass names with or without the prefix already attached. This is a defensive coding pattern specific to `SystemLibrary` (the `DSOLibrary` does not need it because `dlsym` directly resolves the exact symbol name from the shared object).

## Reflection

### Design docs to write

- **`.knowledge/designs/0013-module-system.md` (update)**: The existing design doc should be updated to document the prefix-tolerant lookup invariant in `SystemLibrary`. Specifically, the "Contracts, Assumptions and Invariants" section should note that `SystemLibrary::GetSymbol` and `GetSymbolWithSymbolPrefix` try both prefixed and unprefixed lookups because `TVMFFIEnvModRegisterSystemLibSymbol` registrants may use fully-qualified or bare names. This helps future commit mining for any changes to the symbol registration or lookup path.
