# Guard ml_dtypes >= 0.5-only dtype mappings behind hasattr check for backward compatibility

## TL;DR
- Fixes `AttributeError` when using `ml_dtypes < 0.5.0` (e.g., 0.4.x), which does not export `int2`, `uint2`, `float8_e3m4`, `float8_e4m3`, `float8_e8m0fnu`, `float6_e2m3fn`, `float6_e3m2fn`, or `float4_e2m1fn`.
- Splits `MLDTYPES_DTYPE_TO_DTYPE` initialization: 8 universally-available entries (`int4`, `uint4`, `bfloat16`, `float8_e4m3b11fnuz`, `float8_e4m3fn`, `float8_e4m3fnuz`, `float8_e5m2`, `float8_e5m2fnuz`) remain unconditional; 8 entries added only in `ml_dtypes >= 0.5.0` are guarded behind `hasattr(ml_dtypes, "int2")`.

## Key Exports
None

## Impact
- API: None
- ABI: None
- Behavioral: On `ml_dtypes < 0.5.0`, `import tvm_ffi` no longer raises `AttributeError`. The 8 dtype entries exclusive to `ml_dtypes >= 0.5.0` are simply absent from the mapping table when using an older version; attempting to convert those dtypes through FFI would hit a `KeyError` at the lookup table. On `ml_dtypes >= 0.5.0`, behavior is unchanged.
- Flags/config: None
- Data formats/schemas: None

## Design Elements
Design elements this commit consumes:
- **`MLDTYPES_DTYPE_TO_DTYPE` lookup table** (`python/tvm_ffi/cython/dtype.pxi`): The module-level dict mapping `numpy.dtype(ml_dtypes.X)` to `DLDataType` structs, introduced in commit `d77606af` (`.knowledge/commits/2025-09-19-d77606afb21e3a40bc1da9cfaabd04562afbc1d0.md`).
- **`hasattr`-based version guard pattern**: Same pattern used for torch dtype guards in commit `eb5492a1` (`.knowledge/commits/2025-09-25-eb5492a1d2feaff5f11a51f32cf5ad339c789665.md`), where `hasattr(torch, "float8_e8m0fnu")` gates torch >= 2.8 entries.

Design elements this commit produces:
- None. This is a backward-compatibility fix, not a new design element.
