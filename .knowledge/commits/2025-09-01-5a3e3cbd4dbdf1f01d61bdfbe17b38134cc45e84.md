# Add missing files in packaging example and rename get_started to quick_start
## TL;DR
- Adds two missing files to the `examples/packaging/` directory: `run_example.py` (Python driver using torch + tvm_ffi_extension) and `src/extension.cc` (C++ extension demonstrating both `TVM_FFI_DLL_EXPORT_TYPED_FUNC` and `GlobalDef` registration).
- Renames the `examples/get_started/` directory to `examples/quick_start/get_started/`, nesting it under a new `quick_start` parent folder. All seven files are pure renames with zero content changes.

## Impact
- API: None. No public C++, Python, or Cython interfaces are added or changed.
- Flags/config: None.
- Data formats/schemas: None.
- Documentation: The packaging example is now self-contained and runnable. The quick_start directory reorganization improves discoverability but changes no documentation content.

## Design Elements

Design elements this commit consumes:

- **Module export system** ([`.knowledge/designs/0008-module-export-system.md`]): The new `extension.cc` uses `TVM_FFI_DLL_EXPORT_TYPED_FUNC(add_one, ...)` to export a function via the C ABI. This is a direct consumer of the export macro's code-generation and `TVMFFISafeCallType` wrapping.
- **Reflection / GlobalDef** ([`.knowledge/designs/0006-reflection.md`]): The new `extension.cc` uses `TVM_FFI_STATIC_INIT_BLOCK` + `refl::GlobalDef().def("tvm_ffi_extension.raise_error", RaiseError)` to register a function into the global function table. This demonstrates the alternative registration path (reflection-based vs symbol-based export).
- **Function system** ([`.knowledge/designs/0004-function-system.md`]): Both the exported `add_one` and the globally-registered `raise_error` are backed by the packed function calling convention (`AnyView*` args -> `Any*` result).
- **Module system / load_module** ([`.knowledge/designs/0013-module-system.md`]): The existing `quick_start/get_started/run_example.py` uses `tvm_ffi.load_module("build/add_one_cpu.so")` to load the compiled `.so` via the `DSOLibrary` -> `LibraryModuleObj` pipeline.
- **Error handling** ([`.knowledge/designs/0007-error-handling.md`]): `extension.cc` demonstrates `TVM_FFI_THROW(RuntimeError) << msg` for cross-language error propagation and `TVM_FFI_ICHECK(...)` for internal assertion-style checks.
- **Packaging and build** ([`.knowledge/designs/0016-packaging-and-build.md`]): The packaging example is a downstream consumer of `find_package(tvm_ffi CONFIG)` and the `tvm-ffi-config` CLI for discovering include paths and link flags.

Design elements this commit produces:

- None. This commit adds example/documentation code only. It does not introduce or modify any design elements that other parts of the system depend on.

### Design diagrams to draw

- **Format**: Mermaid
- **Content**: A diagram showing the two function export pathways side by side: (1) `TVM_FFI_DLL_EXPORT_TYPED_FUNC` -> C symbol -> `LibraryModuleObj::GetFunction` -> `Function`, and (2) `TVM_FFI_STATIC_INIT_BLOCK` + `GlobalDef().def(...)` -> global function table -> `get_global_func`. The packaging example's `extension.cc` is the first place both pathways are demonstrated in a single file, making it a natural anchor for such a diagram. This would complement `.knowledge/designs/0008-module-export-system.md` and clarify when to use which approach.

## Self-Evolution of Skill /commit-ledger

- **Rename detection**: The `git show --numstat` output for renames shows `0\t0\t{old => new}` with no additions or deletions. The current procedure does not explicitly call out how to handle pure renames (Step 1 produces `git show --format="" $COMMIT -- $DIFFFILE` for each file, but renamed files with no content changes produce only a `rename from/to` diff header and no hunks). Consider adding a note in Step 1 that pure renames can be batch-inspected via the `--numstat` summary alone, skipping per-file diff for zero-change renames.
- **Example vs. library code distinction**: The skill could benefit from an explicit heuristic: if all changed files are under `examples/`, `docs/`, or `tests/`, the commit is unlikely to produce new design elements (only consume existing ones). This would help the Step 3.2 (Producers) analysis converge faster.
