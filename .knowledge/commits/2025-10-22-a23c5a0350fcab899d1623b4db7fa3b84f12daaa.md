# Fix missing FunctionInfo specialization for function reference types
## TL;DR
- Adds `FunctionInfo<R(&)(Args...), void>` specialization so that function references (not just function types and function pointers) are correctly deduced by the `FunctionInfo` SFINAE dispatch.
- Fixes a compile error when `TVM_FFI_DLL_EXPORT_TYPED_FUNC` is invoked with extra parentheses around a function name or with a `constexpr auto&` binding to a function.

## Key Exports
```python
# FunctionInfo SFINAE dispatch (include/tvm/ffi/function_details.h):
#
# Existing specializations (unchanged):
#   FunctionInfo<R(Args...), void>     : FuncFunctorImpl<R, Args...>   # free function type
#   FunctionInfo<R(*)(Args...), void>  : FuncFunctorImpl<R, Args...>   # function pointer
#
# NEW specialization (a23c5a0):
#   FunctionInfo<R(&)(Args...), void>  : FuncFunctorImpl<R, Args...>   # function reference
#
# Interacts with: TVM_FFI_DLL_EXPORT_TYPED_FUNC, Function::FromTyped
# Invariant: all three free-function forms (type, pointer, reference) map to
#            the same FuncFunctorImpl<R, Args...>, producing identical behavior.
```

## Impact
- API: none -- no public API changes; existing code that avoided the bug pattern continues to work unchanged.
- Behavioral: previously-failing compile scenarios now succeed (function references passed to `TVM_FFI_DLL_EXPORT_TYPED_FUNC` or `Function::FromTyped`).
- Flags/config: none
- Data formats/schemas: none

## Usage Examples
Before/after pattern showing the bug and fix:

```cpp
// BEFORE (compile error): extra parentheses cause decltype to produce R(&)(Args...)
// instead of R(*)(Args...)
TVM_FFI_DLL_EXPORT_TYPED_FUNC(add_one_cuda, (tvm_ffi_example_cuda::AddOne));
// ERROR: FunctionInfo primary template selected, tries &T::operator() on a function ref

// BEFORE (compile error): constexpr auto& binds as a function reference
static constexpr auto& func = tvm_ffi_example_cuda::AddOne;
TVM_FFI_DLL_EXPORT_TYPED_FUNC(add_one_cuda_1, func);
// ERROR: same issue

// AFTER (a23c5a0): both patterns compile correctly because FunctionInfo<R(&)(Args...)>
// is now specialized, mapping to the same FuncFunctorImpl<R, Args...> as R(*)(Args...).
```
