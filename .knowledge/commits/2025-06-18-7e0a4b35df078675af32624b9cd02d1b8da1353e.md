# Stabilize container ABI by introducing explicit data pointers and data_deleter_ to ArrayObj, MapObj, and DenseMapObj
## TL;DR
- Introduces an explicit `void* data_` pointer and `void (*data_deleter_)(void*)` callback into `ArrayObj` and `MapObj`, decoupling element storage location from the object itself and enabling future non-inplace allocation strategies (e.g., separately heap-allocated buffers, cross-DLL-safe deallocation).
- Fixes `DenseMapObj` hash table semantics: `slots_` now stores the actual slot count (not `slots - 1`), probing uses modulo (`%`) instead of bitwise AND (`&`), and `CalcNumBlocks` / `IsFull` / rehash logic is corrected accordingly. This eliminates off-by-one errors and removes the implicit power-of-two assumption on probing.
- Renames internal dispatch macros from `TVM_DISPATCH_MAP` / `TVM_DISPATCH_MAP_CONST` to `TVM_FFI_DISPATCH_MAP` / `TVM_FFI_DISPATCH_MAP_CONST`, conforming to the project `TVM_FFI_` prefix convention.

## Impact
- **API**: Breaking ABI change to `ArrayObj` and `MapObj` field layout. `ArrayObj` gains three new fields (`data_`, `data_deleter_`, and reorders `size_`/`capacity_`). `MapObj` replaces the `slots_`-first layout with `data_`, `size_`, `slots_`, `data_deleter_`. `DenseMapObj` removes its private `Block* data_` member (now uses the base class `void* data_`). `SmallMapObj`'s `InplaceArrayBase` template parameter changes from `KVType` to `KVRawStorageType`. `ArrayObj::at()` return type changes from `const Any` (by value) to `const Any&` (by reference). New method `Array<T>::emplace_back(Args&&...)`.
- **Flags/config**: None.
- **Data formats/schemas**: The in-memory layout of `ArrayObj`, `SmallMapObj`, and `DenseMapObj` changes. Any serialized or binary-compatible representation of these objects is invalidated. The `DenseMapObj::slots_` semantic change (from `n_slots - 1` to `n_slots`) affects hash table sizing and probing calculations.

## Design Elements
Design elements this commit **consumes**:

- **Container system** ([`.knowledge/designs/0005-containers.md`](../designs/0005-containers.md)): Directly modifies `ArrayObj`, `MapObj`, `SmallMapObj`, and `DenseMapObj` -- all core container types. The commit preserves the COW invariant for `Array<T>` and the inplace allocation pattern via `InplaceArrayBase`, but changes the data access path from `InplaceArrayBase::AddressOf(0)` to `data_`.
- **Object system** ([`.knowledge/designs/0003-object-system.md`](../designs/0003-object-system.md)): Relies on `make_inplace_array_object` and `make_object` for allocation. The `data_` pointer is initialized to `AddressOf(0)` at creation time, maintaining backward compatibility for inplace arrays.
- **C ABI layer** ([`.knowledge/designs/0001-c-abi.md`](../designs/0001-c-abi.md)): The commit message explicitly targets ABI stabilization. The new field layout is intended to become the stable ABI contract for containers.
- **Any/AnyView type erasure** ([`.knowledge/designs/0002-any-system.md`](../designs/0002-any-system.md)): The `ArrayObj` explicit destructor calls `Any::~Any()` on each element, respecting the `Any` ownership model. The `InplaceArrayBase` template parameter changes from `Any` to `TVMFFIAny` for `ArrayObj` and from `KVType` to `KVRawStorageType` for `SmallMapObj`, ensuring the base class does not attempt to call destructors on elements (destruction is now explicitly managed).

Design elements this commit **produces**:

- **Container data indirection pattern**: `ArrayObj` and `MapObj` now have a `void* data_` field that points to the element storage, plus a `data_deleter_` callback for deallocation. For inplace arrays, `data_` points to `AddressOf(0)` (trailing storage). For `DenseMapObj`, `data_` points to a separately `new[]`-allocated `Block` array with `data_deleter_ = BlockDeleter`. This pattern enables future non-inplace storage (e.g., externally owned buffers, mmap-backed arrays) by simply setting `data_` and `data_deleter_` to point elsewhere. This is a new design element not previously documented.
- **Cross-DLL-safe deallocation via `data_deleter_`**: The `DenseMapObj::BlockDeleter` static function and the `data_deleter_` callback ensure that memory allocated in one shared library is freed using the same allocator. The commit comment explicitly notes: "assign block deleter so even if we take re-alloc data in another shared-lib that may have different malloc/free behavior it will still be safe." This addresses a real cross-DLL ABI safety concern.
- **DenseMapObj slot semantics correction**: `slots_` now stores the actual slot count (not `slots - 1`). Probing uses `% slots_` instead of `& slots_`. `CalcNumBlocks(n_slots)` no longer adds 1. `IsFull()` uses `size_ + 1 > slots_ * kMaxLoadFactor` (not `(slots_ + 1) * kMaxLoadFactor`). Rehash doubles with `slots_ * 2` (not `slots_ * 2 + 2`). This simplifies the mental model and removes a class of off-by-one errors.
- **KVRawStorageType for SmallMapObj**: New `MapObj::KVRawStorageType` struct with `TVMFFIAny first; TVMFFIAny second;` provides a POD-layout-compatible storage type for the `InplaceArrayBase`. This separates the storage representation (raw C structs) from the access representation (`std::pair<Any, Any>`), preventing `InplaceArrayBase` from invoking `Any` destructors during its own destruction -- destruction is now handled explicitly in `SmallMapObj::~SmallMapObj()`.

## Reflection

### Design docs to write

- **`.knowledge/designs/0005-containers.md` (update)**: The existing container design doc should be updated to reflect the new `data_` / `data_deleter_` indirection pattern. The doc currently describes `ArrayObj` as using `InplaceArrayBase<ArrayObj, Any>` with elements stored "contiguously after the object header." The new reality is that elements are accessed via `data_` which *may* point to inplace storage or an external buffer. The `data_deleter_` callback pattern for cross-DLL safety should also be documented. This update helps future commits that introduce non-inplace storage modes (e.g., mmap-backed arrays, external DLPack-style ownership).

- **`.knowledge/designs/0008-container-abi-layout.md`**: A new doc should cover the concrete field layout and byte offsets of `ArrayObj`, `MapObj` (base), `SmallMapObj`, and `DenseMapObj` after this stabilization. It should include:
  - `ArrayObj` field order: `data_`, `size_`, `capacity_`, `data_deleter_` (after `Object` header and `InplaceArrayBase`)
  - `MapObj` field order: `data_`, `size_`, `slots_`, `data_deleter_`
  - `DenseMapObj` additional fields: `fib_shift_`, `iter_list_head_`, `iter_list_tail_`
  - The `InplaceArrayBase` template parameter choices (`TVMFFIAny` for ArrayObj, `KVRawStorageType` for SmallMapObj) and why
  - This doc helps classify future commits that add new fields or change the layout.

### ADRs to write

- **`.knowledge/ADRs/0006-container-data-indirection.md`**: Decision to add `void* data_` and `data_deleter_` to `ArrayObj` and `MapObj` instead of relying solely on `InplaceArrayBase::AddressOf()`. Context: the previous design tightly coupled element access to inplace storage; this prevents external buffers and makes cross-DLL deallocation unsafe. Alternatives: (a) keep pure inplace arrays and add a separate `ExternalArrayObj` subclass; (b) use `std::unique_ptr<void, Deleter>`. Trade-off: the chosen approach keeps a single `ArrayObj` class with a runtime-switchable data source, at the cost of one additional pointer and one function pointer per array instance.

- **`.knowledge/ADRs/0007-dense-map-slot-semantics.md`**: Decision to change `DenseMapObj::slots_` from storing `n_slots - 1` (for bitwise AND probing) to storing `n_slots` directly (with modulo probing). Context: the previous `& slots_` pattern assumed power-of-two slot counts and created off-by-one confusion in `CalcNumBlocks` and `IsFull`. Alternatives: keep bitwise AND and enforce power-of-two. Trade-off: modulo is slightly slower than bitwise AND on some architectures, but eliminates a class of subtle bugs and makes the code more readable.

### Design diagrams to draw
