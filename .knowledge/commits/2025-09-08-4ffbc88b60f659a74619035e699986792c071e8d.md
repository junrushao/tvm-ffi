# Fix load_inline on macOS by linking libtvm_ffi in the non-Windows build path
## TL;DR
- Fixes `tvm_ffi.cpp.load_inline` on macOS by adding `-L<libdir> -ltvm_ffi` to the linker flags for non-Windows (Unix/macOS) builds, matching the Windows build path which already linked against `tvm_ffi.lib`.
- Hoists the `find_libtvm_ffi()` call and path/name extraction out of the Windows-only block into the shared preamble so both platforms use the same library discovery.
- Removes four `@pytest.mark.xfail` decorators that gated the `load_inline` tests to Linux/Windows only, enabling them on all platforms.

## Key Exports
None. No public API surface is introduced or changed. The fix is internal to `_generate_ninja_build()`.

## Impact
- API: none
- Behavioral: `tvm_ffi.cpp.load_inline()` now works on macOS. Previously, compiled inline modules failed to link because the generated shared library could not resolve symbols from `libtvm_ffi.dylib`. The non-Windows `default_ldflags` was `["-shared"]` alone, missing the library link. Now it is `["-shared", "-L<libdir>", "-ltvm_ffi"]`.
- Flags/config: none
- Data formats/schemas: none

## Design Elements
Design elements this commit consumes:
- **Inline module compilation workflow** ([2025-09-05-83805ec9.md](./2025-09-05-83805ec949227620d05e61358a4ecb4f0c931979.md)): The `_generate_ninja_build()` function generates Ninja build files for compiling inline C++/CUDA modules. This commit fixes its linker flag generation for non-Windows platforms.
- **`find_libtvm_ffi()` from `tvm_ffi.libinfo`** ([0014-python-package.md](../designs/0014-python-package.md)): Used to locate the `libtvm_ffi` shared library at build time. Was already called in the Windows branch; this commit hoists it to the shared preamble.
- **Module system** ([0013-module-system.md](../designs/0013-module-system.md)): The compiled inline module is loaded via `load_module()`, which calls `Module::LoadFromFile` -> `DSOLibrary(dlopen)`. On macOS, `dlopen` of the compiled `.so` would fail at symbol resolution without the `-ltvm_ffi` link.

- None. This is a bugfix that corrects an existing implementation.

## Usage Examples

### Before/after: linking behavior on macOS
**Before** (broken): The non-Windows `default_ldflags` was `["-shared"]`. When the compiled inline module called symbols from `libtvm_ffi` (e.g., via `TVM_FFI_DLL_EXPORT_TYPED_FUNC`), the linker produced a `.so` with unresolved symbols. On Linux this happened to work because of lazy symbol resolution and the fact that `libtvm_ffi.so` was already loaded in the process, but on macOS `dlopen` fails with strict two-level namespaces.

**After** (fixed):
```python
# _generate_ninja_build() now produces for non-Windows:
default_ldflags = ["-shared", "-L/path/to/lib", "-ltvm_ffi"]
# The library path and name are derived from find_libtvm_ffi(),
# hoisted to the shared preamble alongside the Windows path.
```

The fix also means that the Linux build now explicitly links against `libtvm_ffi`, which is more correct (relying on already-loaded symbols was fragile).
