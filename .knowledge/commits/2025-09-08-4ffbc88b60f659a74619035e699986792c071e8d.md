# Fix load_inline on macOS by linking libtvm_ffi in non-Windows builds
## TL;DR
- Fixes `tvm_ffi.cpp.load_inline` on macOS by adding `-L<lib_path> -ltvm_ffi` to the linker flags for non-Windows (Unix/macOS) builds. Previously, only the Windows code path linked against `libtvm_ffi`; Unix builds used `-shared` alone, causing unresolved symbol errors on macOS.
- Hoists `find_libtvm_ffi()` and the derived `tvm_ffi_lib_path`/`tvm_ffi_lib_name` variables out of the Windows-only branch so they are computed unconditionally and available to both platform branches.
- Removes `@pytest.mark.xfail` decorators from four `test_load_inline` test cases that previously marked non-Linux/non-Windows platforms as expected failures.

## Impact
- API: None. No public API change; the `load_inline` function signature and behavior are unchanged for callers.
- Flags/config: None. No new environment variables or configuration options.
- Data formats/schemas: None.
- Behavioral: Inline module compilation now succeeds on macOS. The compiled shared library correctly links against `libtvm_ffi.dylib`, resolving `TVM_FFI_DLL_EXPORT_TYPED_FUNC`-generated symbols that depend on the FFI runtime (e.g., packed function registration, safe-call boundary).

## Design Elements

Design elements this commit consumes:
- **Inline module compilation pipeline** ([`.knowledge/designs/0017-inline-module-compilation.md`](../designs/0017-inline-module-compilation.md)): The fix modifies `_generate_ninja_build()` in `python/tvm_ffi/cpp/load_inline.py`, specifically the linker flags generation. The ninja build generation section of the design doc describes platform-aware flag generation, and this commit corrects the Unix branch to match the Windows branch's linking behavior.
- **Module export system** ([`.knowledge/designs/0008-module-export-system.md`](../designs/0008-module-export-system.md)): The reason linking is required is that `TVM_FFI_DLL_EXPORT_TYPED_FUNC`-generated symbols reference FFI runtime functions (argument unpacking, safe-call boundary, error handling). On Linux, `-shared` with lazy binding may resolve these symbols at `dlopen` time from the host process, but macOS's stricter linker (`ld64`) requires explicit linkage.
- **Python bindings / libinfo** ([`.knowledge/designs/0014-python-bindings.md`](../designs/0014-python-bindings.md)): Uses `find_libtvm_ffi()` from `tvm_ffi.libinfo` to locate the installed `libtvm_ffi.dylib`/`libtvm_ffi.so` for deriving the library path and name.

Design elements this commit produces:
- None. This is a bugfix that corrects an existing design element's implementation without introducing new abstractions.

## Reflection

### Design docs to write

- **Update `.knowledge/designs/0017-inline-module-compilation.md`** -- The "Ninja Build Generation" section states the link rule produces a "shared library output linking against `tvm_ffi_shared`" but the actual design doc does not detail the platform-specific linking strategy (Windows vs Unix). After this fix, the Unix branch now explicitly links `-ltvm_ffi`, making the two branches symmetric. The doc should be updated to note:
  - Windows: `/LIBPATH:<path> <name>.lib`
  - Unix: `-shared -L<path> -ltvm_ffi`
  - Why the explicit link is necessary (macOS strict linker vs Linux lazy binding)
