# Fix load_inline on macOS by linking libtvm_ffi in non-Windows ldflags
## TL;DR
- Fixes `tvm_ffi.cpp.load_inline` on macOS by adding `-L<tvm_ffi_lib_path> -ltvm_ffi` to the Unix/macOS linker flags in `_generate_ninja_build`, so the compiled shared library can resolve FFI symbols at load time.
- Hoists `find_libtvm_ffi()` call and path extraction out of the Windows-only branch to be shared by all platforms.
- Removes four `@pytest.mark.xfail` decorators from `test_load_inline.py` that previously marked `load_inline` tests as expected failures on non-Linux/non-Windows platforms.

## Key Exports
None. This commit changes internal behavior of `_generate_ninja_build` but does not alter public API signatures or introduce new public symbols.

## Impact
- API: None -- `load_inline` signature is unchanged.
- ABI: None -- no C/C++ ABI changes.
- Behavioral: `load_inline` now works on macOS. Previously, compiled modules would fail to load because the linker did not link against `libtvm_ffi.dylib`, causing unresolved FFI symbols at dlopen time.
- Flags/config: The Unix `default_ldflags` list changes from `["-shared"]` to `["-shared", "-L<path>", "-ltvm_ffi"]`. This also affects Linux, where it was presumably working via `LD_LIBRARY_PATH` or rpath before, but explicit linking is more robust.
- Data formats/schemas: None.

## Design Elements
Design elements this commit consumes:
- **Inline module compilation** (`.knowledge/designs/0017-inline-module-compilation.md`): The Ninja build generation pipeline, specifically `_generate_ninja_build` and its platform-branched linker flag construction.
- **Python packaging / libinfo** (`.knowledge/designs/0015-python-packaging.md`): `find_libtvm_ffi()` for locating the shared library at build time. Previously only consumed on Windows; now consumed on all platforms.
- **Module system** (`.knowledge/designs/0013-module-system.md`): The loaded `.so` must resolve FFI symbols (e.g., `TVMFFISafeCall`) provided by `libtvm_ffi`. This is the root cause of the macOS bug -- without `-ltvm_ffi`, dlopen fails with unresolved symbols.

Design elements this commit produces:
- None. This is a bugfix that corrects an existing design's implementation without changing contracts.

## Usage Examples
**Before (broken on macOS)**: `load_inline` would compile successfully but `load_module` would fail at dlopen with unresolved FFI symbols because the shared library was not linked against `libtvm_ffi.dylib`.

**After (fixed)**: The generated `build.ninja` link rule on Unix includes `-L/path/to/lib -ltvm_ffi`, so the compiled module resolves all FFI symbols correctly:
```python
# This now works on macOS (previously xfail):
import tvm_ffi.cpp
mod = tvm_ffi.cpp.load_inline(
    name="hello",
    cpp_sources="void Hello(int x) { ... }",
    functions={"hello": ""},
)
mod.hello(42)  # succeeds on Linux, macOS, and Windows
```
