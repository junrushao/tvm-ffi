# Fix config loading in Windows case
## TL;DR
- On Windows (`sys.platform.startswith("win32")`), loads the native library even in config CLI mode because the DLL search path must be set for Cython extensions that some test cases still import in wheel-packaged environments.

## Impact
- **API**: Windows config-mode invocations now load `libtvm_ffi` via `libinfo.load_lib_ctypes(...)`, while non-Windows config mode continues to skip library loading entirely. This is a platform-specific fix that maintains the config-mode import optimization from commit `5c0deb9` on non-Windows platforms.
- **Behavioral**: On Windows, `tvm_ffi.LIB` is defined even in config mode. On other platforms, `tvm_ffi.LIB` is not defined in config mode (only accessible in normal mode).
- **Flags/config**: None.
- **Data formats/schemas**: None.

## Design Elements

Design elements this commit **consumes**:

- **Config-mode import bypass** (from commit `5c0deb9`): The `_is_config_mode()` detection and conditional import guard introduced in the previous commit. This commit adds a Windows-specific exception to that guard.
- **Packaging and Build** ([`.knowledge/designs/0016-packaging-and-build.md`](../designs/0016-packaging-and-build.md)): Windows wheel packaging where `core.pyd` (Cython extension) requires `libtvm_ffi.dll` to be loaded for DLL search path resolution.

Design elements this commit **produces**:

- **Windows config-mode library loading**: An `elif sys.platform.startswith("win32"):` branch in `__init__.py` that loads the native library even in config mode. This is the minimum necessary to make `tvm-ffi-config` work reliably on Windows where DLL loading is needed for path resolution.
