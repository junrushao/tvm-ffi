# Distinguish strict `as` from converting `cast`/`try_cast` in the Any system
## TL;DR
- Redefines the semantics of `as()` to be a **strict, non-converting** type check (backed by `CheckAnyStrict`), while `cast()` and the new `try_cast()` remain **converting** (backed by `TryCastFromAnyView`). Previously `as()` and `cast()` both called `TryConvertFromAnyView`, making them behaviorally identical.
- Renames the `TypeTraits<T>` protocol methods to match the new terminology: `CheckAnyStorage` -> `CheckAnyStrict`, `CopyFromAnyStorageAfterCheck` -> `CopyFromAnyViewAfterCheck`, `MoveFromAnyStorageAfterCheck` -> `MoveFromAnyAfterCheck`, `TryConvertFromAnyView` -> `TryCastFromAnyView`.
- Adds `Any::as() &&` (rvalue-qualified overload) and adds `DLTensor*` specializations for `CheckAnyStrict` and `CopyFromAnyViewAfterCheck` that were previously missing.

## Impact
- **API**: Breaking change to the `TypeTraits<T>` protocol -- all five renamed methods must be updated in any out-of-tree `TypeTraits` specialization. The `AnyView::as<T>()` / `Any::as<T>()` methods now return `std::nullopt` for cases that previously succeeded via implicit conversion (e.g., `AnyView(1).as<double>()` now returns `nullopt`; use `.try_cast<double>()` or `.cast<double>()` instead). Callers that relied on `as<T>()` for type-converting access must migrate to `try_cast<T>()`.
- **Flags/config**: None.
- **Data formats/schemas**: None.

## Design Elements

Design elements this commit **consumes**:

- **Any/AnyView Type Erasure** ([`.knowledge/designs/0002-any-system.md`](../designs/0002-any-system.md)): The commit directly modifies the two core value containers `AnyView` and `Any`, changing the semantics of `as<T>()` and adding `try_cast<T>()`. It relies on the existing `TypeTraits<T>` protocol and the `AnyUnsafe` internal interface.
- **TypeTraits Protocol** ([`.knowledge/designs/0002-any-system.md`](../designs/0002-any-system.md)): All `TypeTraits<T>` specializations are updated to use the new method names. The commit is a consumer of the trait-based conversion architecture -- it reorganizes the method names but preserves the two-tier strict/lenient distinction established in the foundational commit.
- **Container Storage Invariant** ([`.knowledge/designs/0005-containers.md`](../designs/0005-containers.md)): `Array<T>`, `Map<K,V>`, `Tuple<Ts...>`, and `Variant<Vs...>` all use `CheckAnyStrict` (renamed from `CheckAnyStorage`) internally for element validation. The containers also update their `TryCastFromAnyView` slow paths to call `try_cast<T>()` instead of `as<T>()`.
- **Function argument unpacking** ([`.knowledge/designs/0004-function-system.md`](../designs/0004-function-system.md)): `ArgValueWithContext::operator T()` in `function_details.h` is updated from `as<T>()` to `try_cast<T>()`, since function argument unpacking needs type conversion (e.g., accepting `int` where `float` is expected).

Design elements this commit **produces**:

- **Strict vs. converting access distinction**: A new semantic contract in the Any system:
  - `as<T>()` = strict reinterpret, no type coercion, backed by `CheckAnyStrict` + `CopyFromAnyViewAfterCheck`. Returns `nullopt` if the stored type is not exactly `T` (or an `IsInstance` subtype for objects).
  - `try_cast<T>()` = lenient conversion, may coerce (e.g., int->float, String->DLDataType), backed by `TryCastFromAnyView`. Returns `nullopt` on failure.
  - `cast<T>()` = same as `try_cast` but throws `TypeError` on failure.
  This distinction was implicit before (both `as` and `cast` did conversion); it is now explicit in both the API and the `TypeTraits` naming.
- **`Any::as() &&` rvalue overload**: New overload that enables move semantics when calling `as()` on an rvalue `Any`, using `CheckAnyStrict` + `MoveFromAnyAfterCheck`. This parallels the existing `cast() &&` overload.
- **`TypeTraits<DLTensor*>::CheckAnyStrict` and `CopyFromAnyViewAfterCheck`**: Previously `TypeTraits<DLTensor*>` only had `CopyToAnyView`, `MoveToAny` (which throws), and `TryConvertFromAnyView`. The commit adds `CheckAnyStrict` and `CopyFromAnyViewAfterCheck` so that `DLTensor*` values stored in `AnyView` can be accessed via the strict `as<DLTensor*>()` path.

## Reflection

### Design docs to write

- **`.knowledge/designs/0002-any-system.md` -- update needed**: The existing design doc describes `as()` as backed by `TryConvertFromAnyView` (see line 43: `template <typename T> std::optional<T> as() const; // TryConvertFromAnyView`). This is now incorrect. The doc's TypeTraits Protocol table (lines 73-82) needs all five method names updated, and the `AnyView`/`Any` class summaries need to reflect the `as`/`try_cast`/`cast` triple. This is the highest-priority doc update because the existing doc will actively mislead anyone reading it after this commit.

- **`.knowledge/designs/0008-as-vs-cast-semantics.md`**: A focused design doc covering the strict-vs-converting access pattern. Should include: (1) the motivation -- why conflating strict check and conversion in a single `as()` method was problematic (e.g., `Variant<int, float>` where `as<float>()` would match an int-holding variant via int->float conversion, violating the user's expectation of a strict type check), (2) the three-method API contract (`as`/`try_cast`/`cast`), (3) the mapping to `TypeTraits` methods, and (4) migration guidance for callers. This doc helps future commit mining for any PR that changes conversion behavior or adds new TypeTraits specializations.

### ADRs to write

- **`.knowledge/ADRs/0006-as-strict-cast-lenient.md`**: Records the decision to split `as()` (strict) from `cast()`/`try_cast()` (lenient). Context: previously both methods called `TryConvertFromAnyView`, making `as()` a confusing synonym for `cast()` that returned `optional` instead of throwing. Alternatives: (1) keep a single method with a boolean `strict` parameter -- rejected for ergonomic reasons, (2) name the strict method `exact<T>()` or `get<T>()` -- rejected for consistency with C++ standard library naming (`std::any::any_cast` analogy). Trade-off: existing callers that used `as<T>()` for converting access must be migrated to `try_cast<T>()`.

### Design diagrams to draw

- **Mermaid: `as()` vs `try_cast()` vs `cast()` decision flow**. Should depict: caller invokes `as<T>()` -> `CheckAnyStrict` -> if true: `CopyFromAnyViewAfterCheck` -> return value, else: return `nullopt`. Caller invokes `try_cast<T>()` -> `TryCastFromAnyView` (which internally may do `CheckAnyStrict` fast path + fallback coercion) -> return `optional<T>`. Caller invokes `cast<T>()` -> same as `try_cast` but throws on `nullopt`. This diagram clarifies the relationship between the three user-facing methods and the two TypeTraits paths.
