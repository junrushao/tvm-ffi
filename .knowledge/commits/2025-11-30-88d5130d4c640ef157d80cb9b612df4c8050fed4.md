# Fix use-after-move in std::tuple CopyToTupleImpl and signed/unsigned mismatch in std::vector TryCast
## TL;DR
- Fixes a use-after-move bug in `CopyToTupleImpl` where `std::get<Is>(std::forward<Tuple>(src))` in a fold expression could move the tuple multiple times. Replaced with `std::apply` which safely forwards each element once.
- Fixes a signed/unsigned comparison warning in `std::vector<T>::TryCastFromAnyView` by changing the loop variable from `std::size_t` to `int64_t` to match `ArrayObj::size_` type.

## Key Exports
None (no new API surface; behavioral fix only).

## Impact
- API: None.
- Behavioral: Fixes undefined behavior (use-after-move) when converting `std::tuple` with >1 element to `Any`. Before the fix, `std::get<0>(std::forward<Tuple>(src))` would move the tuple, then `std::get<1>(...)` on the moved-from tuple was UB.
- Flags/config: None.
- Data formats/schemas: None.

## Design Elements
Design elements this commit consumes:
- **STL-to-FFI bridging layer** (`stl.h`, introduced in c3fc8f7): Fixes the `CopyToTupleImpl` helper in `TypeTraits<details::ListTemplate>`.
- **ArrayObj** ([0008-containers.md](../designs/0008-containers.md)): `ArrayObj::size_` is `int64_t`, which motivates the type change in the vector loop.

Design elements this commit produces:
- None (pure bugfix).

## Usage Examples
**Before** (buggy): fold expression with `std::forward<Tuple>(src)` moved the entire tuple on each fold step:
```cpp
((::new (dst++) Any(std::get<Is>(std::forward<Tuple>(src))), array->size_++), ...);
```

**After** (fixed): `std::apply` unpacks elements once, each forwarded individually:
```cpp
std::apply(
    [&](auto&&... elems) {
      ((::new (dst++) Any(std::forward<decltype(elems)>(elems)), array->size_++), ...);
    },
    std::forward<Tuple>(src));
```
