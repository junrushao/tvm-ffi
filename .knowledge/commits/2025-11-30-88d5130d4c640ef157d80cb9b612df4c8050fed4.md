# Fix use-after-move UB in std::tuple-to-Array conversion and signed/unsigned mismatch in std::vector conversion
## TL;DR
- Fixed undefined behavior in `CopyToTupleImpl` where `std::forward<Tuple>(src)` was applied once per tuple element in a fold expression, causing use-after-move on all elements after the first.
- Replaced the fold expression with `std::apply` to destructure the tuple into individually forwarded element references, each forwarded exactly once.
- Fixed signed/unsigned comparison mismatch in `TypeTraits<std::vector<T>>::TryCastFromAnyView` by using `int64_t` instead of `auto`/`std::size_t` for the loop variable and length.

## Key Exports
No new API surface. This is a correctness fix to existing internal implementation.

```python
# CopyToTupleImpl (internal, in TypeTraits<details::ListTemplate>)
# Before (BUGGY):
#   fold expression: std::get<Is>(std::forward<Tuple>(src))
#   Bug: std::forward<Tuple>(src) is evaluated once per Is in the fold,
#        but after the first forward (move), subsequent std::get<Is> reads
#        from moved-from tuple members -> undefined behavior
#
# After (FIXED):
#   std::apply(lambda(elems...), std::forward<Tuple>(src))
#   Each elem is an individual forwarding reference, forwarded exactly once
#   Interacts with: ArrayObj::Empty, ArrayObj::MutableBegin, ArrayObj::size_
#   Invariant: size_ is incremented after each placement-new for exception safety
```

## Impact
- API: None -- internal implementation change only, no signature changes.
- Behavioral: Fixes undefined behavior when converting `std::tuple` (with move-only or non-trivial types) to `Array`. Previously, elements after the first could contain garbage data when the tuple was an rvalue.
- Flags/config: None.
- Data formats/schemas: None.

## Design Elements
Design elements this commit consumes:
- **TypeTraits protocol** ([0006-type-traits.md](../designs/0006-type-traits.md)): `CopyToTupleImpl` is part of `TypeTraits<details::ListTemplate>`, the STL bridge for tuple/vector/array conversions.
- **ArrayObj inplace allocation** ([0007-containers.md](../designs/0007-containers.md)): Uses `ArrayObj::Empty()`, `MutableBegin()`, and incremental `size_++` for exception-safe placement-new construction.

Design elements this commit produces:
- None -- no new design elements. This is a correctness fix.

## Usage Examples
**Before (buggy)**: Converting an rvalue `std::tuple<String, int>` to `Array` would move the entire tuple on the first `std::get<0>(std::forward<Tuple>(src))`, then `std::get<1>` would read from a moved-from tuple, producing undefined behavior.

**After (fixed)**: `std::apply` destructures the tuple into individual forwarding references `(elem0, elem1, ...)`, each forwarded exactly once via `std::forward<decltype(elems)>(elems)`.

```cpp
// Internal behavior (not user-facing API, but illustrates the fix):
// Old: ((::new (dst++) Any(std::get<Is>(std::forward<Tuple>(src))), array->size_++), ...);
//       ^--- std::forward applied N times to the same tuple = UB after first move
//
// New: std::apply([&](auto&&... elems) {
//        ((::new (dst++) Any(std::forward<decltype(elems)>(elems)), array->size_++), ...);
//      }, std::forward<Tuple>(src));
//       ^--- tuple destructured once, each element forwarded independently
```
