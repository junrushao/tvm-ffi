# Fix metadata/doc string allocation in DLL export macros to use libtvm_ffi-owned strings, preventing use-after-free on module unload

## TL;DR
- Both `TVM_FFI_DLL_EXPORT_TYPED_FUNC` (metadata getter) and `TVM_FFI_DLL_EXPORT_TYPED_FUNC_DOC` (docstring getter) previously constructed a `tvm::ffi::String` locally inside the exported `.so`'s code, meaning the string object was allocated in that module's heap. After the module unloads, the returned `String` object's deleter would point into freed code, causing use-after-free.
- The fix routes string construction through `TVMFFIStringFromByteArray` (a `libtvm_ffi` C ABI function), so the `String` object is allocated and owned by the long-lived main `libtvm_ffi` shared library, not the loaded kernel `.so`.
- An explanatory implementation comment is added above both macro definitions to document the allocation-ownership invariant.

## Impact
- API: None — macro signatures are unchanged; only the internal string allocation path changes.
- Behavioral: Metadata and docstring getters (`__tvm_ffi__metadata_<Name>`, `__tvm_ffi__doc_<Name>`) now return `String` objects whose deleter lives in `libtvm_ffi`, not in the loaded kernel `.so`. This closes a use-after-free window: previously, if the module was unloaded before the returned `String` was destroyed, the deleter would call into freed memory.
- Flags/config: none
- Data formats/schemas: none

## Design Elements
Design elements this commit consumes:
- `TVM_FFI_DLL_EXPORT_TYPED_FUNC` / `TVM_FFI_DLL_EXPORT_TYPED_FUNC_DOC` macros — `0004-function-system` (DLL export macros with optional metadata embedding via `TVM_FFI_DLL_EXPORT_INCLUDE_METADATA`)
- `TVMFFIStringFromByteArray` C ABI function — `0001-c-abi` (string construction from byte array, always allocated in libtvm_ffi)
- Module lifetime invariant — `0011-module-system`: "Module must outlive all objects whose deleters reside in the loaded `.so`"

Design elements this commit produces:
- Strengthened sub-invariant for metadata/doc macros: **any `String` object returned by `__tvm_ffi__metadata_*` or `__tvm_ffi__doc_*` symbols is allocated in `libtvm_ffi`, not in the loading module.** This makes module-lifetime constraints less strict for string metadata specifically.

## Usage Examples

**Before (incorrect — use-after-free risk):**
```cpp
// Inside kernel.so — metadata getter used ::tvm::ffi::String() constructor,
// allocating in kernel.so's heap. If kernel.so unloads while str is live:
// → deleter in str points to freed kernel.so code → crash.
::tvm::ffi::String str(os.str());
::tvm::ffi::TypeTraits<::tvm::ffi::String>::MoveToAny(std::move(str), result);
```

**After (correct — long-lived allocation):**
```cpp
// Inside kernel.so — TVMFFIStringFromByteArray allocates the String in libtvm_ffi.
// kernel.so may unload freely; the String's deleter still lives in libtvm_ffi.
std::string data = os.str();
TVMFFIByteArray data_array{data.data(), data.size()};
return TVMFFIStringFromByteArray(&data_array, result);
```
