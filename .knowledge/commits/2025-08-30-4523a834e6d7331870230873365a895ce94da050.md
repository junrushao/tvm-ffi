# Add wheel packaging example and fix cmake install paths for downstream consumers
## TL;DR
- Adds a complete `examples/packaging/` directory demonstrating how to build a Python ABI-agnostic wheel for a tvm-ffi-based C++ extension library, including `CMakeLists.txt`, `pyproject.toml` (scikit-build-core), and Python wrapper code (`base.py`, `_ffi_api.py`, `__init__.py`).
- Fixes the cmake install destination paths: `cmake/Utils/` trailing slash removed (was installing nested `Utils/Utils/`) and `tvm_ffi-config.cmake` moved from `lib/cmake/tvm_ffi/` to `cmake/` to match the `find_cmake_path()` lookup in `libinfo.py`.
- Lazily initializes `torch_get_current_cuda_stream` in Cython to avoid importing/JIT-compiling the torch CUDA stream helper at module load time when torch is available but no CUDA tensor is passed.

## Impact
- API: none (no public API changes; the packaging example is a new standalone project)
- Flags/config: Version bumped from `0.1.0a3` to `0.1.0a5` in `pyproject.toml`.
- Data formats/schemas: none

### cmake install path fixes (functional bug fix)
The prior install rules placed `cmake/Utils/` at `cmake/Utils/` destination with a trailing slash, which would produce a nested `cmake/Utils/Utils/` directory when the `DIRECTORY` source also has the trailing slash. The `tvm_ffi-config.cmake` was installed to `lib/cmake/tvm_ffi/` but `libinfo.py:find_cmake_path()` searched for `cmake/` relative to the package root. The fix aligns the install destinations with the discovery code:
- `cmake/Utils/` -> `cmake/Utils` (no trailing slash)
- `cmake/tvm_ffi-config.cmake` -> `cmake` (not `lib/cmake/tvm_ffi/`)

Additionally, `tvm_ffi-config.cmake` now includes `cmake/Utils/Library.cmake` so that downstream projects using `find_package(tvm_ffi CONFIG)` get the utility functions (`tvm_ffi_add_prefix_map`, `tvm_ffi_add_apple_dsymutil`, etc.) without needing to manually include them.

### Lazy torch CUDA stream initialization (performance fix)
Previously, `torch_get_current_cuda_stream` was eagerly loaded at Cython module import time whenever `torch` was importable. This triggered torch's C++ extension JIT compilation infrastructure on first import, adding latency even when no CUDA tensors were used. Now the function is initialized to `None` and lazily loaded on the first CUDA tensor encounter in `make_args`.

## Design Elements
Design elements this commit consumes:
- **Packaging and build system** ([`.knowledge/designs/0016-packaging-and-build.md`](../designs/0016-packaging-and-build.md)): The packaging example directly exercises the `find_package(tvm_ffi CONFIG)` and `add_subdirectory` integration paths documented in the design. The cmake install path fixes correct discrepancies between install destinations and the `libinfo.py` discovery paths.
- **Module export system** ([`.knowledge/designs/0008-module-export-system.md`](../designs/0008-module-export-system.md)): The packaging example's `CMakeLists.txt` references `src/extension.cc` which would use `TVM_FFI_DLL_EXPORT_TYPED_FUNC` to export functions. The example's `base.py` uses `tvm_ffi.load_module()` to load the compiled `.so`/`.dylib`/`.dll`.
- **Module system** ([`.knowledge/designs/0013-module-system.md`](../designs/0013-module-system.md)): `load_module` (backed by `Module::LoadFromFile` -> `DSOLibrary` -> `LibraryModuleObj`) is the entry point for loading the extension's shared library. The loaded module's `GetFunction` is used to call exported functions.
- **Function system** ([`.knowledge/designs/0004-function-system.md`](../designs/0004-function-system.md)): The `_ffi_api.py` pattern uses `tvm_ffi._init_api("tvm_ffi_extension", __name__)` which populates module attributes from the global function table by prefix matching. This consumes the GlobalFunctionTable design.
- **Python bindings** ([`.knowledge/designs/0014-python-bindings.md`](../designs/0014-python-bindings.md)): The `_init_api` pattern and `load_module` Python API are consumed by the packaging example.

Design elements this commit produces:
- **Wheel packaging pattern for downstream extensions**: The `examples/packaging/` directory establishes a reference pattern for how third-party projects should package tvm-ffi-based C++ extensions as Python wheels. This pattern includes: scikit-build-core configuration, CMake with both source-build and prebuilt-link paths, Python wrapper structure (`base.py` for library loading, `_ffi_api.py` for prefix-based function auto-population), and auditwheel guidance.
- **cmake/Utils availability via find_package**: The `include(${CMAKE_CURRENT_LIST_DIR}/Utils/Library.cmake)` line in `tvm_ffi-config.cmake` makes utility functions available to all downstream `find_package(tvm_ffi CONFIG)` consumers without manual includes.
