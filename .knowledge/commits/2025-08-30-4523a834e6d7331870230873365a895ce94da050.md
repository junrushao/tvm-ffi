# Add wheel packaging example and fix cmake install paths and lazy torch stream loading

## TL;DR
- Adds a complete `examples/packaging/` directory demonstrating how to build an ABI-agnostic Python wheel for a tvm-ffi-based C++ extension, using `scikit-build-core` and CMake with both source-build and pre-built tvm_ffi paths.
- Fixes cmake install destinations so `tvm_ffi-config.cmake` lands at `cmake/` (not `lib/cmake/tvm_ffi/`) and `Utils/` omits a trailing slash, aligning with `find_cmake_path()` in `libinfo.py`.
- Changes `torch_get_current_cuda_stream` from eager JIT-compiled initialization to lazy on-first-use, avoiding import-time torch C++ extension compilation when torch is available but CUDA is not needed.
- Bumps package version from `0.1.0a3` to `0.1.0a5`.

## Impact
- API: `cmake/tvm_ffi-config.cmake` now auto-includes `Utils/Library.cmake`, making `tvm_ffi_add_prefix_map` and `tvm_ffi_add_apple_dsymutil` available to downstream `find_package(tvm_ffi)` consumers. Previously these were not exported.
- Behavioral: `torch_get_current_cuda_stream` is now lazily initialized on first CUDA tensor encounter instead of eagerly at Cython import time. This avoids unnecessary torch C++ extension JIT compilation.
- Flags/config: CMake install destination for `tvm_ffi-config.cmake` changed from `lib/cmake/tvm_ffi/` to `cmake/`. Consumers using `find_package(tvm_ffi)` may need to update `CMAKE_PREFIX_PATH` if they relied on the old path.
- Data formats/schemas: none

## Design Elements
Design elements this commit consumes:
- **Module system** (`load_module` / `Module.LoadFromFile`): The packaging example loads a `.so`/`.dylib`/`.dll` via `tvm_ffi.load_module()`. See `.knowledge/designs/0011-module-system.md`.
- **Global function registry** (`_init_api` pattern): The `_ffi_api.py` uses `tvm_ffi._init_api` to auto-register prefixed global functions as Python module attributes. See `.knowledge/designs/0004-function-system.md`.
- **Context symbol injection** (`__tvm_ffi_library_ctx`): The loaded shared library uses the standard symbol-injection mechanism documented in the module system design.

Design elements this commit produces:
- **Wheel packaging pattern** (new): A reference implementation showing how to structure a `scikit-build-core` based wheel for a tvm-ffi C++ extension, including: CMake with source-build vs pre-built paths, ABI-agnostic wheel config, library loading boilerplate, debug symbol shipping with `tvm_ffi_add_apple_dsymutil`.
- **Lazy torch stream loading** (behavioral change): Changes the initialization pattern from eager to lazy for torch CUDA stream resolution.

## Usage Examples

**Packaging a tvm-ffi extension as a wheel** (from `examples/packaging/`):

```python
# base.py — load the native extension library
import tvm_ffi, os, sys

def _load_lib():
    file_dir = os.path.dirname(os.path.realpath(__file__))
    if sys.platform.startswith("win32"):
        lib_dll_name = "tvm_ffi_extension.dll"
    elif sys.platform.startswith("darwin"):
        lib_dll_name = "tvm_ffi_extension.dylib"
    else:
        lib_dll_name = "tvm_ffi_extension.so"
    return tvm_ffi.load_module(os.path.join(file_dir, lib_dll_name))

_LIB = _load_lib()
```

**Two patterns for calling C++ functions from Python**:
```python
# Pattern 1: Direct module function lookup
result = _LIB.add_one(input_tensor, output_tensor)

# Pattern 2: Global function registry via _init_api
import tvm_ffi
from .base import _LIB  # ensure lib loaded first
tvm_ffi._init_api("tvm_ffi_extension", __name__)
# now module attributes like raise_error are auto-bound
```
