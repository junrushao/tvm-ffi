# Add wheel packaging example, fix cmake install paths, and lazy-load torch stream helper
## TL;DR
- Adds a complete `examples/packaging/` project showing how to build a tvm-ffi extension as an ABI-agnostic Python wheel using scikit-build-core.
- Fixes cmake install destinations (`lib/cmake/tvm_ffi/` -> `cmake/`) and updates `find_cmake_path()` in `libinfo.py` to match.
- Defers `torch_get_current_cuda_stream` initialization from import-time to first-use, avoiding unnecessary torch JIT compilation.
- Bumps version from `0.1.0a3` to `0.1.0a5`.

## Impact
- API: none (additive example code only)
- Behavioral: torch stream helper is now lazy-loaded instead of eager; avoids import-time torch JIT compilation when torch tensors are not used in FFI calls
- Flags/config: `TVM_FFI_EXT_FROM_SOURCE` and `TVM_FFI_EXT_SHIP_DEBUG_SYMBOLS` cmake options introduced in example (not in core)
- Data formats/schemas: cmake install layout changed -- `tvm_ffi-config.cmake` now at `<prefix>/cmake/` instead of `<prefix>/lib/cmake/tvm_ffi/`; `Utils/` at `<prefix>/cmake/Utils` (no trailing slash)

## Design Elements
Design elements this commit consumes:
- **Module system (0011)**: `tvm_ffi.load_module()` used in `base.py` to load the extension shared library. This is the canonical pattern for loading DSO-backed FFI modules.
- **Function system (0003)**: `tvm_ffi._init_api()` used in `_ffi_api.py` to auto-register global functions by prefix. The extension's C++ functions are registered under `tvm_ffi_extension.*` namespace.
- **Global function registry (0003)**: The packaging example demonstrates the full producer-consumer cycle: C++ registers functions via `TVM_FFI_REGISTER_GLOBAL` (in the referenced but not committed `src/extension.cc`), Python consumes via `_init_api`.
- **cmake install layout**: `tvm_ffi-config.cmake` and `Utils/` cmake modules, consumed by `find_package(tvm_ffi)` in the example's `CMakeLists.txt`.

Design elements this commit produces:
- **Wheel packaging pattern**: A reference implementation for packaging tvm-ffi extensions as Python wheels, using scikit-build-core with `wheel.py-api = "py3"` for ABI-agnostic wheels. Not a code-level design element, but a documented convention.

## Usage Examples

End-to-end wheel packaging workflow (from `examples/packaging/README.md`):
```bash
# Build and install the example extension as a wheel
pip install .

# Use the extension from Python
python run_example.py add_one
python run_example.py raise_error
```

Python-side extension loading pattern (from `examples/packaging/python/tvm_ffi_extension/`):
```python
# base.py: Load native library
import tvm_ffi
_LIB = tvm_ffi.load_module(os.path.join(os.path.dirname(__file__), "tvm_ffi_extension.so"))

# _ffi_api.py: Auto-bind global functions prefixed "tvm_ffi_extension."
import tvm_ffi
from .base import _LIB  # ensure lib is loaded first
tvm_ffi._init_api("tvm_ffi_extension", __name__)

# __init__.py: Expose as Python API
def add_one(x, y):
    return _LIB.add_one(x, y)

def raise_error(msg):
    return _ffi_api.raise_error(msg)
```
