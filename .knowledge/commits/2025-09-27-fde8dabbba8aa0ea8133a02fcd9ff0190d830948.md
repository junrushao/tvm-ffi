# Fix Cython DLPack stream passing: check device_type instead of device_id

## TL;DR
- Fixed a bug in `TVMFFIPyArgSetterDLPackCExporter_` where the "already queried device" guard checked `ctx.device_id` instead of `ctx.device_type`, causing the stream to be silently dropped on subsequent tensor args (since `device_id=0` is a valid GPU device, the guard falsely triggered).
- Added a regression test in `test_load_inline_cuda` that passes a raw stream handle through the FFI call and asserts the received stream matches inside the CUDA kernel wrapper.
- Version bump `0.1.0b10` -> `0.1.0b11`.

## Key Exports
None -- this commit fixes a bug in existing code, no new public API surface.

The fix is a single-character change in `function.pxi`:

```python
# TVMFFIPyArgSetterDLPackCExporter_ (Cython, python/tvm_ffi/cython/function.pxi)
# Before (broken): guard used device_id, which is 0 for cuda:0 -- always truthy
#   if ctx.device_id != -1:  # BUG: device_id=0 is valid, so this fires on first tensor
#
# After (fixed): guard uses device_type, which is -1 (unset sentinel) until first tensor
#   if ctx.device_type != -1:  # CORRECT: device_type starts at -1, set to kDLCUDA on first tensor
#
# Interacts with: TVMFFIPyCallContext.device_type (sentinel -1 = unset)
# Interacts with: TVMFFIEnvSetStream (stream only set when device_type != -1 after arg loop)
# Invariant: device_type is the canonical "has device been detected" flag, not device_id
```

## Impact
- API: none -- no signature changes
- Behavioral: stream handles are now correctly propagated to `TVMFFIEnvSetStream` when multiple DLPack tensor args are passed. Previously, the second and subsequent tensor args would skip stream extraction because `device_id=0` (a valid CUDA device) failed the `!= -1` guard.
- Flags/config: none
- Data formats/schemas: none

## Design Elements
Design elements this commit consumes:
- **TVMFFIPyCallContext** (from [0012-ffi-python-package](../design-records/0012-ffi-python-package.md)): the per-call context with `device_type`, `device_id`, and `stream` fields. The sentinel value `-1` on `device_type` indicates "no device detected yet."
- **TVMFFIPyArgSetterDLPackCExporter_** (from [0012-ffi-python-package](../design-records/0012-ffi-python-package.md)): the cached setter for DLPack-exporting Python objects (e.g., torch tensors). Extracts device info and stream on first tensor arg.
- **TVMFFIEnvSetStream** (from [0011-ffi-module-system](../design-records/0011-ffi-module-system.md)): C env API for setting per-thread stream. Called by `TVMFFIPyCallManager::Call` after arg packing, using `ctx.stream`.
- **load_inline** (from [0014-ffi-load-inline](../design-records/0014-ffi-load-inline.md)): used in the regression test to compile inline CUDA code.

Design elements this commit produces: none -- pure bugfix restoring existing invariant.

## Usage Examples
Before/after pattern showing the bug:

```python
# BEFORE (broken): stream silently dropped when passing CUDA tensors
import torch, tvm_ffi

mod = tvm_ffi.cpp.load_inline(cuda_source="...")
x_cuda = torch.randn(5, device="cuda")
y_cuda = torch.empty_like(x_cuda)

stream = torch.cuda.Stream()
with torch.cuda.stream(stream):
    # BUG: TVMFFIEnvGetStream inside the kernel returns the wrong stream
    # because ctx.device_id (=0) != -1 was True on the first tensor arg,
    # so the stream was never extracted from the environment.
    mod.add_one_cuda(x_cuda, y_cuda, stream.cuda_stream)

# AFTER (fixed): stream correctly propagated
with torch.cuda.stream(stream):
    # ctx.device_type starts at -1, correctly detects "no device yet" on first tensor,
    # extracts stream via c_dlpack_from_pyobject, sets ctx.stream.
    mod.add_one_cuda(x_cuda, y_cuda, stream.cuda_stream)
    # TVMFFIEnvGetStream now returns the correct stream handle inside the kernel.
stream.synchronize()
torch.testing.assert_close(x_cuda + 1, y_cuda)
```
