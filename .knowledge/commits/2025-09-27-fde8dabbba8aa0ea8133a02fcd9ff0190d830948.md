# Fix wrong sentinel field in DLPack stream-passing guard, preventing stream from being passed when device_id == 0

## TL;DR

- In `TVMFFIPyArgSetterDLPackCExporter_` (Cython), the guard `ctx.device_id != -1` was used to detect whether the device had already been queried. Because `TVMFFIPyCallContext.device_id` is initialized to `0` (not `-1`), this guard was always true, causing the code to skip stream passing on every subsequent tensor argument regardless of context.
- The fix changes the guard to `ctx.device_type != -1`, which matches the actual sentinel: `TVMFFIPyCallContext.device_type = -1` is the canonical "not yet set" value.
- A regression test using `torch.cuda.Stream` was added to `test_load_inline_cuda` to verify correct stream propagation.

## Key Exports

```python
# TVMFFIPyCallContext (C struct, tvm_ffi_python_helpers.h)
# Tracks per-call stream/device context during Python→FFI argument conversion.
struct TVMFFIPyCallContext:
    device_type: int = -1   # Sentinel: -1 means "not yet set"
    device_id:   int = 0    # Default 0; NOT a sentinel
    stream:      void* = None
    # Invariant: device_type == -1 iff stream has not been queried for this call.
    # Interacts with: TVMFFIPyArgSetter setters (function.pxi),
    #                 TVMFFIEnvGetStream (c_env_api.h), TorchStreamContext (env-api).

# Setter that handles C DLPack exporters (objects with __c_dlpack_tensor_allocator__)
# Guard condition (bugfix):
#   BEFORE: if ctx.device_id != -1:   # WRONG — always True since device_id=0
#   AFTER:  if ctx.device_type != -1: # CORRECT — matches struct sentinel
cdef int TVMFFIPyArgSetterDLPackCExporter_(
    this: TVMFFIPyArgSetter*, ctx: TVMFFIPyCallContext*, arg: PyObject*, out: TVMFFIAny*
) -> int: ...
# Interacts with: TVMFFIEnvGetStream, c_dlpack_from_pyobject callback
# Invariant: Once ctx.device_type != -1, ctx.stream is authoritative and must not be re-queried.
```

## Impact

- API: None — no public API changes.
- Behavioral: Stream passing is now correctly propagated for CUDA device 0 (and any device where `device_id == 0`). Before the fix, passing a non-default stream (e.g., `torch.cuda.Stream`) was silently ignored on the first device-0 tensor argument, causing kernels to run on the wrong stream.
- Flags/config: None.
- Data formats/schemas: None.

## Usage Examples

Before (broken for device_id == 0):
```python
# With CUDA device 0 and a non-default stream:
stream = torch.cuda.Stream()
with torch.cuda.stream(stream):
    mod.add_one_cuda(x_cuda, y_cuda)
    # BUG: stream ignored — ctx.device_id == 0, so `0 != -1` was True,
    # causing the code to fall through to `c_dlpack_from_pyobject(arg, ..., NULL)`,
    # passing NULL stream instead of the active torch stream.
```

After (correct):
```python
stream = torch.cuda.Stream()
with torch.cuda.stream(stream):
    mod.add_one_cuda(x_cuda, y_cuda, stream.cuda_stream)
    # FIXED: ctx.device_type == -1 initially, so stream is properly looked up
    # via TVMFFIEnvGetStream and stored in ctx.stream. Subsequent tensor args
    # reuse ctx.stream without re-querying.
stream.synchronize()
torch.testing.assert_close(x_cuda + 1, y_cuda)
```
