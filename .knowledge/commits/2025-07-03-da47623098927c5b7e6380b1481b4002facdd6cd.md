# Remove _type_has_method_visit_attrs flag, completing VisitAttrs phase-out
## TL;DR
- Deletes the `static constexpr const bool _type_has_method_visit_attrs = true;` declaration from `Object` in `include/tvm/ffi/object.h`, removing the last vestige of the old `VisitAttrs` mechanism from the FFI core.
- This is the final commit in a multi-commit migration series (#18091, #18095, #18096, #18101, #18106) that transitioned attribute visiting from the legacy `VisitAttrs` pattern to the new reflection system (`ReflectionDef` / `TVMFFIFieldInfo`).

## Impact
- **API**: Removes the `Object::_type_has_method_visit_attrs` static constant. Any downstream code (in the broader TVM ecosystem, outside this FFI repo) that reads this flag at compile time will fail to compile. Within this FFI repo, no code references this flag -- the prior commits in the series already removed all consumers.
- **Flags/config**: None.
- **Data formats/schemas**: None.

## Design Elements

Design elements this commit **consumes**:
- **Object system** ([`.knowledge/designs/0003-object-system.md`](../designs/0003-object-system.md)): The `Object` base class in `include/tvm/ffi/object.h` is the site of the change. The class declares static `constexpr` flags (`_type_has_method_sequal_reduce`, `_type_has_method_shash_reduce`) as compile-time markers for optional method support. This commit removes one such flag.
- **Reflection system** ([`.knowledge/designs/0006-reflection.md`](../designs/0006-reflection.md)): The new reflection system (`ReflectionDef` / `TVMFFIFieldInfo`) is the replacement mechanism that made `VisitAttrs` obsolete. The flag being removed was the old compile-time indicator that a type supported attribute visiting; the reflection system provides this capability at runtime instead.

Design elements this commit **produces**:
- None. This is a pure removal of dead code. No new design elements are introduced.

## Key Implementation Details

**What was removed**: A single line in `Object` (the base class for all heap objects):
```cpp
static constexpr const bool _type_has_method_visit_attrs = true;
```

**Why it was always `true` on `Object`**: In the legacy TVM system, `VisitAttrs` was a visitor-pattern method that object types could override to expose their fields. The base `Object` set this flag to `true`, and subclasses that did not support attribute visiting could set it to `false`. With the reflection system, field enumeration is handled by `TVMFFIFieldInfo` registered via `TVM_FFI_REFLECTION_DEF`, making the compile-time flag redundant.

**Migration series context** (commits leading to this one):
1. `69f2484` (#18091): Introduced a bridge between old `VisitAttrs` and new reflection field visit.
2. `a5a08b2` (#18095): Migrated attrs to the new reflection mechanism.
3. `f7311e4` (#18096): Transitioned remaining `VisitAttrs` usage in `tir`/`ir_builder`/`meta_schedule`.
4. `0966c36` (#18101): Formalized namespaces for all objects.
5. `da47623` (#18106): This commit -- removes the flag itself, completing the phase-out.

**Remaining similar flags**: Two analogous compile-time flags remain on `Object`:
- `_type_has_method_sequal_reduce = false` -- reserved for structural equality.
- `_type_has_method_shash_reduce = false` -- reserved for structural hashing.

These are documented in [`.knowledge/designs/0003-object-system.md`](../designs/0003-object-system.md) as reserved extension points and are still potentially useful for future structural comparison support.

**Invariants**:
- After this commit, the `Object` class no longer carries any `VisitAttrs`-related metadata. All field enumeration goes through runtime reflection (`TVMFFIGetTypeInfo` -> `fields`/`num_fields`).
- The remaining `_type_has_method_*` flags are defaulted to `false` on `Object`, meaning no type currently declares support for structural equality or hashing via these flags.

## Reflection

### Design docs to write

- **`.knowledge/designs/0003-object-system.md` (update)**: The existing design doc at [`.knowledge/designs/0003-object-system.md`](../designs/0003-object-system.md) mentions `_type_has_method_sequal_reduce` and `_type_has_method_shash_reduce` in the Extension Points section but does not mention `_type_has_method_visit_attrs`. This is correct post-commit, but the doc should note the historical removal of `_type_has_method_visit_attrs` as evidence that these compile-time method flags can be deprecated when runtime alternatives (like the reflection system) are adopted. This helps future commit mining when similar flags are removed.

### ADRs to write

None. The decision to migrate from `VisitAttrs` to the reflection system was made across the broader TVM project (not solely within this FFI repo). The existing reflection design doc sufficiently captures the runtime mechanism that replaced `VisitAttrs`.

### Design diagrams to draw

None. The change is a single-line deletion with no structural relationship changes.

## Self-Evolution of Skill /commit-ledger

- The current procedure handles trivial commits well (Step 2 allows skipping detailed investigation for chore-only commits), but this commit is a borderline case: it is a single-line deletion that is trivial mechanically but architecturally meaningful as the capstone of a migration series. The procedure should distinguish between "mechanically trivial" and "architecturally trivial" -- a commit can be one without being the other. Consider adding guidance: "If a commit removes the last usage of a deprecated mechanism, treat it as architecturally significant even if the diff is small."
- For removal-only commits, the template could benefit from a "What was removed and why" subsection under Key Implementation Details, to ensure the ledger captures the removed API surface and its replacement. Currently, the template does not specifically guide the author to document removals.
