# Fix CUDA availability check in torch_c_dlpack extension to use torch.cuda.is_available()
## TL;DR
- Replaces `torch.version.cuda is not None` with a two-step guard: first `torch.cuda.is_available()`, then `torch.version.cuda`/`torch.version.hip` to distinguish CUDA vs ROCm. Applied consistently across the JIT loader, AOT build backend, and tests.
- Adds explicit `ValueError` when GPU is available but neither CUDA nor ROCm can be identified.
- Bumps `TVM_FFI_VERSION_PATCH` from 2 to 3 in `include/tvm/ffi/c_api.h`.

## Key Exports

No new public API surfaces. The behavioral change is internal to the CUDA detection logic. The corrected pattern is:

```python
# Before (incorrect -- torch.version.cuda can be non-None even without a GPU):
if torch.version.cuda is not None:
    device = "cuda"
elif torch.version.hip is not None:
    device = "rocm"
else:
    device = "cpu"

# After (correct -- gate on runtime GPU availability first):
if torch.cuda.is_available():
    if torch.version.cuda is not None:
        device = "cuda"
    elif torch.version.hip is not None:
        device = "rocm"
    else:
        raise ValueError("Cannot determine whether to build with CUDA or ROCm.")
else:
    device = "cpu"
# Invariant: device is "cpu" when no GPU runtime is present, even if PyTorch was compiled with CUDA headers.
# Interacts with: load_torch_c_dlpack_extension(), build_wheel(), test_build_torch_c_dlpack_extension()
```

## Impact
- API: none -- no public API changed.
- Behavioral: On CPU-only machines with CUDA-compiled PyTorch, the extension now correctly builds as `cpu` instead of attempting a CUDA build that would fail. On GPU machines where neither CUDA nor ROCm is identifiable, a `ValueError` is raised instead of silently falling through to `cpu`.
- Flags/config: none.
- Data formats/schemas: C++ macro `TVM_FFI_VERSION_PATCH` bumped from 2 to 3.

## Design Elements
Design elements this commit consumes:
- **DLPack Exchange API protocol** (`torch.Tensor.__c_dlpack_exchange_api__` dunder). See `.knowledge/ADRs/0015-dlpack-exchange-api-struct.md`. The JIT loader and AOT build backend set this attribute after building the native extension.
- **Version-and-device-specific library naming** (`libtorch_c_dlpack_addon_torch{M}{m}-{device}.so`). See commit `70577053`. The `device` component is derived from the corrected detection logic.
- **TVM FFI version macros** (`TVM_FFI_VERSION_MAJOR`, `TVM_FFI_VERSION_MINOR`, `TVM_FFI_VERSION_PATCH`). See `.knowledge/designs/0001-c-abi.md`.

Design elements this commit produces:
- **Two-step GPU detection invariant**: `torch.cuda.is_available()` must be true before inspecting `torch.version.cuda` or `torch.version.hip`. This pattern is now applied in three locations and should be considered the canonical way to detect GPU device type in this codebase.

## Usage Examples

Before (incorrect -- would attempt CUDA build on CPU-only machine with CUDA-compiled PyTorch):
```python
# torch.version.cuda returns "12.1" even on a CPU-only machine
# if PyTorch was compiled with CUDA support
if torch.version.cuda is not None:
    args.append("--build-with-cuda")  # BUG: triggers CUDA build on CPU-only env
```

After (correct):
```python
if torch.cuda.is_available():
    if torch.version.cuda is not None:
        args.append("--build-with-cuda")
    elif torch.version.hip is not None:
        args.append("--build-with-rocm")
    else:
        raise ValueError("Cannot determine whether to build with CUDA or ROCm.")
# CPU-only environments correctly skip GPU build flags
```
