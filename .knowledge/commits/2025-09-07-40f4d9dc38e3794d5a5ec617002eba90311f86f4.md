# Cleanup Python API naming and documentation for consistency with torch/array API conventions
## TL;DR
- Renames public Python API symbols for consistency with PyTorch/array API conventions: `register_func` -> `register_global_func`, `_init_api` -> `init_ffi_api`, `ObjectGeneric` -> `ObjectConvertible`, `Device.device_id` -> `Device.index`, `Device.device_type` -> `Device.type` (property) / `Device.dlpack_device_type()` (method returning int).
- Removes per-device convenience functions (`cpu()`, `cuda()`, `rocm()`, etc.) and internal symbols (`String`, `Bytes`, `DataTypeCode`, `ModulePropertyMask`) from the top-level `tvm_ffi` namespace, pushing them to `tvm_ffi.core` or removing them from the public API.
- Adds a new `DLDeviceType` IntEnum class extracted from the Device cdef class, renames internal module files (`convert.py` -> `_convert.py`, `dtype.py` -> `_dtype.py`, `tensor.py` -> `_tensor.py`), adds comprehensive docstrings with Sphinx cross-references, creates a new Python API reference page (`docs/reference/python/index.rst`), and adds `tests/python/test_examples.py`.

## Impact
- API: **Breaking**. Multiple public symbol renames (`register_func` -> `register_global_func`, `_init_api` -> `init_ffi_api`, `ObjectGeneric` -> `ObjectConvertible`). `Device.device_type` property replaced with `Device.type` (str) and `Device.dlpack_device_type()` (int method). `Device.device_id` renamed to `Device.index`. `String`, `Bytes`, `DataTypeCode`, `ModulePropertyMask` removed from `tvm_ffi.__all__`. Per-device convenience functions (`cpu`, `cuda`, etc.) removed from public API. Device constant attributes (e.g. `Device.kDLCUDA`) moved to standalone `DLDeviceType` IntEnum. `device()` function parameter changed from `dev_type, dev_id=0` to `device_type, index=None`.
- Flags/config: none
- Data formats/schemas: none

## Design Elements
Design elements this commit consumes:
- **Python bindings package architecture** ([`.knowledge/designs/0014-python-bindings.md`](../designs/0014-python-bindings.md)): This commit is a consumer of the layered initialization, `@register_object`, `_init_api`, `PyNativeObject` patterns, and `make_args` argument packing. It renames and reorganizes the public Python API surface but does not change the underlying Cython/C++ layer.
- **Documentation site** ([`.knowledge/designs/0018-documentation-site.md`](../designs/0018-documentation-site.md)): Consumes the Sphinx infrastructure to add a new Python API reference page and update cross-references in guide pages.
- **Module system** ([`.knowledge/designs/0013-module-system.md`](../designs/0013-module-system.md)): `Module` class retains the same functionality; only docstrings and the removal of `ModulePropertyMask` from `__all__` are affected.

Design elements this commit produces:
- **DLDeviceType IntEnum** (new design element): A standalone `IntEnum` subclass in `device.pxi` that decouples DLPack device type constants from the `Device` cdef class. Previously, constants like `kDLCPU`, `kDLCUDA` were class-level attributes of `Device`. Now they are members of `DLDeviceType`, which is accessible as `tvm_ffi.DLDeviceType`. This aligns with DLPack's own enum naming and enables cleaner type checking.
- **Private-module naming convention** (new convention): Internal modules that should not be directly imported are prefixed with `_` (`_convert.py`, `_dtype.py`, `_tensor.py`). Public re-exports happen via `__init__.py`. This formalizes the boundary between internal and public Python modules.
- **Sphinx Python API reference** (new doc artifact): `docs/reference/python/index.rst` uses `autosummary` with `:toctree: generated/` to auto-generate API reference pages for `Object`, `Function`, `Module`, `Array`, `Map`, `Tensor`, `Device`, `Shape`, and key registration functions.
- **Docstring convention with Sphinx cross-references**: Docstrings now use `{py:func}` and `{py:class}` MyST cross-references (e.g., `{py:func}\`tvm_ffi.register_global_func\``, `{py:class}\`tvm_ffi.Module\``), and guide pages were updated accordingly. This enables interlinked documentation.
- **Test-from-docstring pattern**: `tests/python/test_examples.py` mirrors code examples from docstrings (`register_global_func`, `Array`, `Map`) as runnable tests, extending the code-to-test correspondence invariant from the C++ guide to the Python API.

## Reflection

### Design docs to write
- **`.knowledge/designs/0014-python-bindings.md` update**: The existing design doc needs to be updated to reflect the renamed symbols (`register_func` -> `register_global_func`, `_init_api` -> `init_ffi_api`, `ObjectGeneric` -> `ObjectConvertible`), the new `DLDeviceType` IntEnum, the private module naming convention (`_convert.py`, `_dtype.py`, `_tensor.py`), and the Device property changes. Without this update, future commit mining will reference stale symbol names and miss the private-module convention.

### ADRs to write
- **`.knowledge/ADRs/0027-python-api-naming-alignment.md`**: Record the decision to align Python API naming with PyTorch and array API conventions. Context: the existing names (`register_func`, `device_id`, `device_type` as int) were TVM-internal jargon; alternatives considered were keeping backward compatibility aliases (rejected for simplicity) vs. clean break (chosen). Trade-off: breaks existing downstream code but creates a cleaner, more discoverable API.
- **`.knowledge/ADRs/0028-private-module-prefix.md`**: Record the convention of prefixing internal Python modules with `_`. Context: `convert.py`, `dtype.py`, `tensor.py` were importable but not intended as public API; alternatives were `__all__` enforcement only (insufficient -- users still `from tvm_ffi.convert import convert`) vs. underscore prefix (chosen). This ADR helps future contributors know where to place new internal vs. public modules.

### Design diagrams to draw
- **Mermaid**: Update the Package Import/Initialization Flow diagram in `0014-python-bindings.md` to show the renamed modules (`_convert.py`, `_dtype.py`, `_tensor.py`) and the new `DLDeviceType` import path. The existing diagram references `convert.py` and `tensor.py` which no longer exist.

### Skill evolution (`/commit-ledger`)

Consider adding "breaking change" as a first-class characterization tag in Step 2, with a mandatory "migration path" subsection in the Impact section when the tag is present.
- Step 3 could benefit from a heuristic: when `__init__.py` `__all__` changes, automatically flag the commit as a public API surface change and enumerate the before/after export lists for easier diffing.

## Self-Evolution of Skill /commit-ledger
- The template does not have a dedicated section for **breaking changes / migration guide**. For commits that rename public API symbols, it would be valuable to have a structured before/after table (old name -> new name) in the Impact section. This would make it much easier for downstream consumers to grep ledger entries for migration steps.
- When a commit renames files (git detects `rename from`/`rename to`), Step 1's `--numstat` output shows the rename but the format is non-obvious (e.g., `python/tvm_ffi/{convert.py => _convert.py}`). The skill procedure could note that file renames are a strong signal for API surface changes and should trigger explicit investigation of import path changes.
- The existing procedure focuses on C++ design elements. This commit is Python-only, touching no C++ code. Step 3 could add a note: "For Python-only commits, focus on the `__init__.py` exports, Cython `.pxi` class definitions, and `registry.py` function signatures as the primary design element surfaces."
