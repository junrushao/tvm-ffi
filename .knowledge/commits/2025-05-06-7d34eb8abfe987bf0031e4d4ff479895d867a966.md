# Introduce and modernize FFI system as the foundational root commit
## TL;DR
- Establishes the entire TVM FFI module from scratch (~15,300 lines across 55 files): a stable C ABI (`c_api.h`), C++17 wrappers (`Any`/`AnyView`, `Object`/`ObjectRef`, `Function`), containers (`Array`, `Map`, `String`, `Shape`, `NDArray`, `Tuple`, `Variant`), error handling, reflection, and a CMake-based build system with GoogleTest tests.
- Implements the Unified Packed and Object RFC, unifying type-erased value passing (`Any` stores both POD and ref-counted objects) with a hierarchical object type system that supports runtime type checking via `IsInstance` and dynamic type index allocation.
- Provides a global function registry (`GlobalFunctionTable`) enabling cross-language function lookup by string name, with safe-call ABI boundaries (`TVM_FFI_SAFE_CALL_BEGIN/END`) for exception propagation across C boundaries.

## Impact
- **API**: This is the genesis commit -- it defines the entire public C and C++ API surface. All downstream consumers (Python bindings, Rust bindings, compiled kernels) depend on the types and conventions established here. Key API surfaces:
  - C ABI: `TVMFFIAny`, `TVMFFIObject`, `TVMFFITypeIndex` enum, `TVMFFIFunctionCell`, all `TVMFFI*` C functions in `c_api.h`
  - C++ API: `Any`/`AnyView`, `Object`/`ObjectRef`/`ObjectPtr`, `Function`, `Array<T>`, `Map<K,V>`, `String`, `Shape`, `NDArray`, `Tuple<Ts...>`, `Variant<Vs...>`, `Optional<T>`, `Error`
  - Registration macros: `TVM_FFI_REGISTER_GLOBAL`, `TVM_FFI_REGISTER_OBJECT_TYPE`, `TVM_FFI_DECLARE_OBJECT_INFO`, `TVM_FFI_DEFINE_OBJECT_REF_METHODS`
- **Flags/config**: CMake options `TVM_FFI_BUILD_TESTS`, `TVM_FFI_BUILD_REGISTRY`, `TVM_FFI_USE_LIBBACKTRACE`, `TVM_FFI_BACKTRACE_ON_SEGFAULT` are introduced.
- **Data formats/schemas**: The `TVMFFITypeIndex` enum defines the canonical type index layout: POD types in `[0, 64)`, static objects in `[64, 128)`, dynamic objects in `[128, +inf)`. This partitioning is an ABI-level contract.

## Design Elements

Design elements this commit **consumes**:
- **DLPack** (`3rdparty/dlpack`): The C ABI builds on `DLDataType`, `DLDevice`, `DLTensor` from the DLPack standard. Used by `c_api.h`, `ndarray.h`, `dtype.h`.
- **Unified Packed and Object RFC** (external `tvm-rfcs/0097`): The commit explicitly implements this RFC, which unified packed function calling convention with the object system.

Design elements this commit **produces**:

- **C ABI Layer** (`include/tvm/ffi/c_api.h`): The stable C ABI contract that all language bindings target. Defines `TVMFFIAny` (16-byte on-stack value), `TVMFFIObject` (12-byte header with type_index + ref_counter + deleter), `TVMFFITypeIndex` enum partitioning, `TVMFFIFunctionCell` (safe_call convention), `TVMFFIByteArray`, `TVMFFIShapeCell`, `TVMFFIFieldInfo` (reflection). All extern "C" API functions (`TVMFFIObjectFree`, `TVMFFIFuncCall`, `TVMFFIGetGlobalFunc`, etc.) live here.

- **Any/AnyView Type Erasure** (`include/tvm/ffi/any.h`): Core value-passing abstraction. `AnyView` is a non-owning 16-byte view (same layout as `TVMFFIAny`). `Any` is owning -- it calls `IncRef`/`DecRef` on contained objects. Supports `as<T>()` (returns `optional<T>`) and `cast<T>()` (throws on failure). The key invariant: `Any::type_index` is never `kTVMFFIRawStr` (raw strings only appear in `AnyView`).

- **Object System** (`include/tvm/ffi/object.h`, `src/ffi/object.cc`): Ref-counted heap objects with a hierarchical type system. `Object` has a `TVMFFIObject` header. `ObjectRef` holds `ObjectPtr<Object>` (intrusive ref-counted smart pointer). Type registration via `TypeTable` with slot-based allocation for fast `IsInstance` checks -- each type reserves `_type_child_slots` contiguous indices for its children, with overflow to a global table fallback. Pattern: `FooObj` (data class) + `Foo` (ref wrapper).

- **Function System** (`include/tvm/ffi/function.h`, `src/ffi/function.cc`): Type-erased callable with packed calling convention `(const AnyView* args, int32_t num_args, Any* rv)`. `FunctionObj` extends `Object` and `TVMFFIFunctionCell`. Has dual calling paths: C++ `call` (exception-based) and C `safe_call` (return-code-based, for ABI boundaries). `GlobalFunctionTable` maps string names to `Function*` for cross-language dispatch. Registration via `TVM_FFI_REGISTER_GLOBAL`.

- **TypeTraits System** (`include/tvm/ffi/type_traits.h`): Trait-based conversion protocol between C++ types and `Any`/`AnyView`. Each `TypeTraits<T>` specialization provides: `CopyToAnyView`, `MoveToAny`, `CheckAnyStorage`, `TryConvertFromAnyView`, `TypeStr`. `CheckAnyStorage` is used by containers like `Array<T>` to verify element types without conversion. Includes `StrictBool` to prevent implicit int-to-bool conversion.

- **Memory Management** (`include/tvm/ffi/memory.h`): `make_object<T>(args...)` allocates objects via `SimpleObjAllocator`, setting `ref_counter=1`, `type_index`, and a type-specific `deleter`. `ObjectPtr<T>` is the intrusive smart pointer. The allocator uses aligned storage + placement new to avoid virtual destructor requirements. Extension point: the `ObjAllocatorBase` CRTP allows future arena/pool allocators.

- **Error Handling** (`include/tvm/ffi/error.h`, `src/ffi/error.cc`): Object-based errors (`ErrorObj` extends `Object` + `TVMFFIErrorCell`). `Error` is a `std::exception` subclass wrapping `ErrorObj`. Error categories are string-based (`"TypeError"`, `"ValueError"`, etc.). `TVM_FFI_THROW(Kind)` macro creates a stream-based error builder. `EnvErrorAlreadySet` signals errors originating in the host environment (e.g., Python). Safe-call boundary: exceptions are caught and stored in thread-local `SafeCallContext`, then re-thrown on the caller side.

- **Containers**:
  - `Array<T>` (`include/tvm/ffi/container/array.h`): Immutable array backed by `ArrayObj` with inplace storage (elements stored contiguously after the object header). Copy-on-write semantics via `CopyOnWrite()`. Supports `push_back`, `insert`, `erase` that trigger COW. `ArrayObj::Empty(cap)` allocates with capacity.
  - `Map<K,V>` (`include/tvm/ffi/container/map.h`): Insertion-order-preserving hash map. Uses dense hash table with `KVType = pair<Any, Any>`. 1606 lines -- the most complex container. Invariant: `sizeof(KVType) == 32`.
  - `String` / `Bytes` (`include/tvm/ffi/string.h`): `StringObj` / `BytesObj` extend `BytesObjBase` (Object + `TVMFFIByteArray`). Both support inplace allocation (data stored after object header) and std::string-backed allocation. `String` has `std::string_view` / `std::string` / hash / comparison interop.
  - `Shape` (`include/tvm/ffi/container/shape.h`): `ShapeObj` extends `Object` + `TVMFFIShapeCell`. Stores `int64_t*` dimensions with inplace allocation.
  - `NDArray` (`include/tvm/ffi/container/ndarray.h`): `NDArrayObj` wraps `DLTensor`. Provides `Empty`, `FromExternalDLTensor`, `CopyFromTo`, `CopyFromBytes`/`CopyToBytes`. Device-aware memory management via `DeviceAPI`.
  - `Tuple<Ts...>` (`include/tvm/ffi/container/tuple.h`): Typed tuple backed by `ArrayObj`.
  - `Variant<Vs...>` (`include/tvm/ffi/container/variant.h`): Tagged union backed by `Any`.

- **Reflection** (`include/tvm/ffi/reflection/reflection.h`): `ReflectionDef` registers field metadata (name, byte offset, getter/setter, readonly flag) per type index. `TVMFFIFieldInfo` stored in `TypeTable::Entry`. `ReflectionFieldGetter`/`ReflectionFieldSetter` use byte offset from object base to access fields generically. `TVM_FFI_REFLECTION_DEF` macro for registration.

- **Build System** (`CMakeLists.txt`, `cmake/Utils/`): CMake project with targets `dlpack_header` (interface), `tvm_ffi_header` (interface), `tvm_ffi_objs` (object lib), `tvm_ffi_static`/`tvm_ffi_shared` (link targets). Utility modules: `AddGoogleTest` (fetches GoogleTest), `AddLibbacktrace`, `CxxWarning` (strict warning flags), `Sanitizer` (ASan), `Library` (shared/static helpers).

- **Testing Infrastructure** (`tests/cpp/`, `src/ffi/testing.cc`): 17 GoogleTest files covering every major subsystem. `src/ffi/testing.cc` registers global test functions (`testing.echo`, `testing.test_raise_error`, `testing.apply`, etc.) for cross-language testing.

## Reflection

This doc grounds nearly every future commit that touches type indices, ABI compatibility, or cross-language calling.

- **`.knowledge/designs/any-system.md`**: Document the `Any`/`AnyView` duality (owning vs. non-owning), the `kTVMFFIRawStr` AnyView-only invariant, the relationship between `TVMFFIAny` C struct and `Any`/`AnyView` C++ classes (same memory layout), and the `TypeTraits` conversion protocol. This helps classify commits that add new type conversions or modify the Any storage format.

- **`.knowledge/designs/object-system.md`**: Document the `Object`/`ObjectRef`/`ObjectPtr` pattern, the `TypeTable` slot-based allocation algorithm (reserved child slots + overflow), `IsInstance` fast-path via index range check, the `FooObj`+`Foo` naming convention, and the `make_object<T>` lifecycle (allocator -> set ref_counter/type_index/deleter). Critical for classifying commits that add new object types or modify type registration.

- **`.knowledge/designs/function-system.md`**: Document the packed calling convention `(const AnyView*, int32_t, Any*)`, the dual call/safe_call paths, `GlobalFunctionTable` singleton design (intentional leak for fork safety), `FunctionObjImpl<TCallable>` type erasure, `ExternCFunctionObjImpl` for C callbacks, and the `TVM_FFI_SAFE_CALL_BEGIN/END` exception boundary. Grounds commits that register functions, modify calling convention, or add new function wrapper types.

- **`.knowledge/designs/containers.md`**: Document the container hierarchy (`Array`, `Map`, `String`, `Bytes`, `Shape`, `NDArray`, `Tuple`, `Variant`), the inplace array allocation pattern (`InplaceArrayBase`), `Array` copy-on-write invariant, `Map` insertion-order preservation, and the `TypeTraits::CheckAnyStorage` invariant for container element validation. Helps classify commits that add container methods or modify storage layout.

- **`.knowledge/designs/reflection.md`**: Document the `ReflectionDef` field registration mechanism (byte offset from object base, getter/setter function pointers), `TVMFFIFieldInfo` schema, and the `TVM_FFI_REFLECTION_DEF` macro. This grounds commits that extend reflection to support methods, computed properties, or Python-side dataclass integration.

- **`.knowledge/designs/error-handling.md`**: Document the `Error`/`ErrorObj` object-based error model, the `SafeCallContext` thread-local for exception transport across C boundaries, `EnvErrorAlreadySet` for host-environment signals, and the `TVM_FFI_THROW` macro. Helps classify commits related to error propagation, traceback, and cross-language exception handling.

### ADRs to write

- **`.knowledge/ADRs/001-unified-packed-and-object.md`**: Records the decision to unify packed function calling convention with the object system (implementing RFC 0097). Context: previously PackedFunc and Object were separate systems. Alternatives: keep them separate (simpler but duplicated type erasure), or use a different unification strategy. Trade-off: unified system is more complex but eliminates boxed-type workarounds (e.g., `Array<int>` now works directly).

- **`.knowledge/ADRs/002-type-index-partitioning.md`**: Records the decision to partition `TVMFFITypeIndex` into three ranges: POD `[0,64)`, static objects `[64,128)`, dynamic `[128,+inf)`. Context: need fast type checking without virtual dispatch. Alternatives: single flat namespace, or fully dynamic allocation. Trade-off: static ranges enable compile-time optimizations but limit the number of built-in types.

- **`.knowledge/ADRs/003-slot-based-type-allocation.md`**: Records the TypeTable slot-based allocation algorithm where parent types reserve contiguous index ranges for children, enabling O(1) `IsInstance` checks via range comparison. Context: deep type hierarchies need fast instanceof. Alternatives: linear ancestor scan, hash-set lookup. Trade-off: wastes index space when slots are over-reserved, but provides excellent cache-friendly runtime performance.

- **`.knowledge/ADRs/004-global-function-table-leak.md`**: Records the intentional memory leak of `GlobalFunctionTable` (allocated via `new`, never deleted). Context: the table may hold Python callbacks; deterministic destruction order conflicts with Python interpreter shutdown and process forking. Alternatives: static local with destructor, shared_ptr. Trade-off: leaks memory at exit but avoids use-after-free and fork-safety issues.

- **`.knowledge/ADRs/005-safe-call-abi-boundary.md`**: Records the dual call/safe_call design for `FunctionObj`. Context: C++ uses exceptions, but C ABI boundaries cannot propagate exceptions. Alternatives: return error codes everywhere (loses C++ ergonomics), or use setjmp/longjmp (fragile). Trade-off: dual paths add complexity but provide idiomatic error handling in both C++ and C contexts.

### Skill evolution (`/commit-ledger`)

- **Root commit handling**: The procedure should explicitly note that for root/initial commits, Step 3.1 (consumer mining) is limited since there is no prior codebase to consume from. The skill could add a "bootstrap" flag that adjusts expectations -- for root commits, focus on documenting the produced design elements comprehensively rather than mining consumer relationships.

- **Large commit batching**: This commit has 55 files and ~15,300 lines. The procedure does not provide guidance on how to prioritize which files to examine in detail vs. skim. Consider adding a heuristic: for commits touching >20 files, first scan the header files and public API surfaces, then sample implementation files, then tests. Tests often encode invariants that are not documented elsewhere.

- **Cross-reference with external RFCs/design docs**: The commit message references an external RFC (tvm-rfcs/0097). The skill should recommend checking if the RFC content should be internalized into `.knowledge/ADRs/` so that future commit mining does not depend on external links that may become stale.

The template should either merge these two sections or the procedure should clarify which content goes where. - For a root commit of this magnitude, the procedure's Step 1 (mechanical overview via `git show --numstat`) is effective, but Step 3 (mining design elements) becomes a full architectural survey. The skill would benefit from a "bootstrap mode" that explicitly sequences: (1) identify the module boundary (what is the public API?), (2) enumerate the core abstractions, (3) document their invariants and relationships. This would make the initial ledger more structured and reduce the risk of missing key design elements in large initial commits.

- The procedure does not mention checking for submodule additions. This commit adds `3rdparty/dlpack` as a submodule (shown as `1 0 3rdparty/dlpack` in numstat), which is a critical dependency. The skill should add a check for submodule changes in Step 1.
