# Add Sphinx documentation scaffolding with guides, concepts, examples, and test fixtures
## TL;DR
- Creates the entire `docs/` directory with a Sphinx-based documentation site: `conf.py` (MyST, nbsphinx, sphinx-book-theme, intersphinx, mermaid), `index.rst` (toctree with Get Started, Guides, Concepts), `Makefile`, `requirements.txt`, and five content pages covering installation, quick start, C++ guide, Python guide, packaging guide, and ABI overview.
- Restructures the `examples/` directory: renames `examples/quick_start/get_started/` to `examples/quick_start/` (flattening one directory level) and renames the packaging example from `tvm_ffi_extension` to `my_ffi_extension` throughout (namespace, CMake target, Python package name, pyproject.toml).
- Adds `TestIntPairObj`/`TestIntPair` to `src/ffi/extra/testing.cc` as a pre-shipped reflection example object, and adds `tests/cpp/test_example.cc` (289 lines) containing runnable GoogleTest versions of every code snippet shown in the C++ guide documentation.

## Impact
- **API**: No functional C++/Python API changes. The new `testing.TestIntPair` object type and its reflection registration (`testing.TestIntPair.__create__`, fields `a`, `b`) are added to the testing module; these are consumed by the Python guide's "Register Your Own Object" section.
- **Flags/config**: None.
- **Data formats/schemas**: None.
- **Examples**: The packaging example's Python package name changes from `tvm_ffi_extension` to `my_ffi_extension` and the C++ namespace/CMake target follow suit. The `quick_start` example directory flattens from `examples/quick_start/get_started/` to `examples/quick_start/`. These are pure rename/restructure operations.
- **Documentation**: Introduces the project's first Sphinx documentation site. All guide content is new.

## Design Elements

Design elements this commit **consumes**:

- **C ABI Layer** ([`.knowledge/designs/0001-c-abi.md`]): The ABI overview doc (`docs/concepts/abi_overview.md`) explains `TVMFFIAny` (16-byte tagged union), `TVMFFIObject` (24-byte header with ref counting), `TVMFFISafeCallType` (packed function calling convention), error handling via thread-local storage, and string storage formats (raw/small/heap). These are direct explanations of the C ABI specification.
- **Any System** ([`.knowledge/designs/0002-any-system.md`]): The C++ guide's "Any and AnyView" section documents `ffi::Any`, `ffi::AnyView`, `cast<T>()`, `as<T>()`, `try_cast<T>()` with runnable examples in `test_example.cc`.
- **Object System** ([`.knowledge/designs/0003-object-system.md`]): The C++ guide's "Object and ObjectRef" section documents the `Object`/`ObjectPtr`/`ObjectRef` pattern, `make_object<T>()`, `TVM_FFI_DECLARE_FINAL_OBJECT_INFO`, `TVM_FFI_DEFINE_OBJECT_REF_METHODS`. The `MyIntPairObj`/`MyIntPair` example is used as running illustration and tested in `test_example.cc`.
- **Function System** ([`.knowledge/designs/0004-function-system.md`]): The C++ guide documents `Function::FromTyped`, `Function::FromPacked`, `Function::GetGlobalRequired`, and `ffi::reflection::GlobalDef().def()`. The Python guide documents `tvm_ffi.get_global_func`, `tvm_ffi.register_func`, and Python callbacks. Both backed by test/example code.
- **Containers** ([`.knowledge/designs/0005-containers.md`]): The C++ guide documents `Array<T>`, `Tuple<Types...>`, `Map<K,V>`, `Optional<T>`, `Variant<Types...>`, including runtime type checking semantics and performance notes about repeated `Any -> Array<T>` conversion overhead. All backed by `test_example.cc`.
- **Reflection** ([`.knowledge/designs/0006-reflection.md`]): The Python guide's "Advanced: Register Your Own Object" section documents the `ObjectDef<T>` builder pattern (`def_ro`, `def_static("__create__")`), the C++ side registration in `testing.cc`, and the Python side `@register_object` + `__init_handle_by_constructor__` pattern.
- **Error Handling** ([`.knowledge/designs/0007-error-handling.md`]): Both the C++ guide ("Error Handling" section) and the ABI overview doc explain `TVM_FFI_THROW`, `ffi::Error` with `kind()`/`message()`/`traceback()`, and cross-language error propagation from C++ through the C ABI to Python.
- **Module Export System** ([`.knowledge/designs/0008-module-export-system.md`]): The C++ guide documents `TVM_FFI_DLL_EXPORT_TYPED_FUNC` for library symbol export. The packaging guide and quick start guide show the full workflow: export -> `tvm_ffi.load_module` -> `Module.GetFunction`. The Python guide documents `tvm_ffi.load_module`.
- **Module System** ([`.knowledge/designs/0013-module-system.md`]): The quick start guide documents `ffi::Module::LoadFromFile()` and `mod->GetFunction()` for C++ consumers.
- **Packaging and Build** ([`.knowledge/designs/0016-packaging-and-build.md`]): The packaging guide documents the downstream consumer workflow: `pyproject.toml` with scikit-build-core, CMake `find_package(tvm_ffi CONFIG)`, `target_link_libraries(... tvm_ffi_shared)`, `tvm_ffi.load_module` for library loading, and `auditwheel` exclusion of `libtvm_ffi.so`.
- **Extra API Tier** ([`.knowledge/designs/0011-extra-api-tier.md`]): The testing fixture `TestIntPairObj` is registered in `src/ffi/extra/testing.cc`, which belongs to the extra API tier compiled under `TVM_FFI_USE_EXTRA_CXX_API`.

Design elements this commit **produces**:

- **Documentation Site Architecture**: A new Sphinx documentation site with structure: `docs/conf.py` (sphinx-book-theme, MyST parser for Markdown, mermaid, intersphinx to Python/NumPy/PyTorch docs), `docs/index.rst` (toctree: Get Started -> Guides -> Concepts), `docs/Makefile` with `livehtml` target, `docs/requirements.txt` (18 dependencies). The `conf.py` loads version from `pyproject.toml` via `tomli`, generates an Apache Foundation footer with Bootstrap dropdown, and sets `github_version` path for "Edit on GitHub" links.
- **TestIntPair Reflection Fixture** (`src/ffi/extra/testing.cc`): A new test object `testing.TestIntPair` with fields `a: int64` and `b: int64`, registered via `ObjectDef<TestIntPairObj>().def_ro("a", ...).def_ro("b", ...).def_static("__create__", ...)`. This serves as the canonical example object for the Python guide documentation and is available in any `tvm_ffi` installation without external dependencies.
- **C++ Guide Test File** (`tests/cpp/test_example.cc`): 289-line GoogleTest file that mirrors every code example in the C++ guide. Test cases: `Example.Any`, `Example.Function`, `Example.NDArray`, `Example.String`, `Example.Array`, `Example.Map`, `Example.Optional`, `Example.Variant`, `Example.ObjectPtr`. This establishes the pattern that documentation code snippets should have corresponding runnable tests.
- **Packaging Example Rename** (`tvm_ffi_extension` -> `my_ffi_extension`): The packaging example is renamed to use a more generic, user-facing name. This rename touches `CMakeLists.txt`, `pyproject.toml`, `src/extension.cc` (namespace), Python files (package directory and imports), `run_example.py`, and `README.md`.

### Skill evolution (`/commit-ledger`)

- **Documentation-heavy commit handling**: This commit is primarily documentation and examples, with a small code addition (`TestIntPairObj` fixture + `test_example.cc`). The current procedure does not distinguish between "code that users run" and "prose that documents code". For documentation commits, Step 3 (Mining Design Elements) should explicitly identify which existing design elements the documentation *describes* (consumers) vs. which new *documentation patterns* it establishes (producers). The current analysis works but required manual adaptation.

- **Example rename tracking**: The procedure does not explicitly call out "rename-only" changes as a distinct pattern. For commits like this one where half the diff is mechanical renaming (namespace, CMake target, Python package), Step 2 should include a check: "Are any of the changed files purely rename/move operations?" and if so, note them briefly without deep-diving into the diffs. This would save analysis time on the 10 renamed packaging example files.

## Self-Evolution of Skill /commit-ledger

- The procedure could benefit from a "documentation commit" fast path in Step 2 that recognizes when the majority of additions are `.md`/`.rst`/`conf.py`/`requirements.txt` files. In such cases, the primary mining focus should shift from "what code changed" to "what knowledge is now documented and what code examples are tested," which is a different analytical lens than the default code-change analysis.

- Step 4 (Mining Key Implementations) is somewhat awkward for documentation-only commits since there are no behavioral code changes to trace. For such commits, Step 4 could be reframed as "Mining Key Documentation Artifacts" -- identify which code snippets are shown, whether they are tested, and what invariants/patterns the documentation establishes for downstream users.

- The `examples/` directory changes highlight that the skill should track naming conventions across examples. When an example package is renamed, it affects documentation references, and the skill should flag any potential inconsistencies between `docs/` prose and `examples/` code. In this commit, the docs and examples are consistent because they were created together, but future commits that modify one without the other could introduce drift.
