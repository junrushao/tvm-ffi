# Replace GCC/MSVC __attribute__ and __declspec with C++ standard attributes
## TL;DR
- Replaces all compiler-specific attributes (`__attribute__((always_inline))`, `__forceinline`, `__attribute__((noinline))`, `__declspec(noinline)`, `__attribute__((unused))`) with C++ standard attributes (`[[gnu::always_inline]] inline`, `[[msvc::forceinline]] inline`, `[[gnu::noinline]]`, `[[msvc::noinline]]`, `[[maybe_unused]]`).
- Reorders all `static TVM_FFI_INLINE` declarations to `TVM_FFI_INLINE static` across 16 files (88 occurrences in `type_traits.h` alone), because the new `TVM_FFI_INLINE` macro expands to an attribute + `inline` specifier, and C++ standard attributes must precede other specifiers -- placing `static` before `[[gnu::always_inline]] inline` would be ill-formed.
- Also reorders `TVM_FFI_ATTRIBUTE_UNUSED` relative to `static inline` in macro definitions (`TVM_FFI_STATIC_INIT_BLOCK_VAR_DEF`, `TVM_FFI_FUNC_REG_VAR_DEF`) for the same attribute-ordering reason.

## Impact
- API: None. No functional changes to any public or internal API. All changes are preprocessor macro definitions and the syntactic ordering of `static`/`inline`/attribute specifiers. The compiled output is semantically identical.
- Flags/config: None.
- Data formats/schemas: None.

## Design Elements
Design elements this commit consumes:
- **TypeTraits protocol** ([`.knowledge/designs/0002-any-system.md`](../designs/0002-any-system.md)): Every `TypeTraits<T>` specialization uses `TVM_FFI_INLINE` on its static methods (`CopyToAnyView`, `MoveToAny`, `CheckAnyStrict`, `TryCastFromAnyView`, `TypeStr`, etc.). The commit touches all of these methods but only to reorder the `static` keyword vs. the attribute macro. The TypeTraits protocol itself is unchanged.
- **ObjectUnsafe helper methods** ([`.knowledge/designs/0003-object-system.md`](../designs/0003-object-system.md)): `ObjectUnsafe` static methods (`GetHeader`, `ObjectPtrFromOwned`, `ObjectPtrFromUnowned`, `IncRefObjectHandle`, `DecRefObjectHandle`, etc.) all use `TVM_FFI_INLINE`. The commit reorders all 16 such declarations in `object.h`.
- **AnyUnsafe helper methods** ([`.knowledge/designs/0002-any-system.md`](../designs/0002-any-system.md)): `AnyUnsafe` static methods (`MoveAnyToTVMFFIAny`, `MoveTVMFFIAnyToAny`, `CheckAnyStrict`, etc.) use `TVM_FFI_INLINE`. Reordered in `any.h`.
- **ReflectionDefBase static helpers** ([`.knowledge/designs/0006-reflection.md`](../designs/0006-reflection.md)): `ApplyFieldInfoTrait`, `ApplyMethodInfoTrait`, `GetMethod` and related template methods use `TVM_FFI_INLINE`. Reordered in `reflection.h`.
- **Function system macros** ([`.knowledge/designs/0004-function-system.md`](../designs/0004-function-system.md)): `TVM_FFI_FUNC_REG_VAR_DEF` macro reordered to place `TVM_FFI_ATTRIBUTE_UNUSED` before `static inline`.
- **C ABI macro layer** ([`.knowledge/designs/0001-c-abi.md`](../designs/0001-c-abi.md)): `TVM_FFI_INLINE`, `TVM_FFI_NO_INLINE`, and `TVM_FFI_ATTRIBUTE_UNUSED` are foundational macros defined in `base_details.h` that are used across the entire codebase.

Design elements this commit produces:
- **Standardized attribute macros**: The `TVM_FFI_INLINE`, `TVM_FFI_NO_INLINE`, and `TVM_FFI_ATTRIBUTE_UNUSED` macros now use C++ standard attributes (`[[gnu::...]]`, `[[msvc::...]]`, `[[maybe_unused]]`) instead of compiler-specific extensions. This is a portability improvement: `[[maybe_unused]]` is standard C++17, while `[[gnu::always_inline]]` and `[[msvc::forceinline]]` are vendor-specific but use the standard attribute syntax (double-bracket). The `TVM_FFI_ATTRIBUTE_UNUSED` macro is now platform-independent (previously was `__attribute__((unused))` on GCC/Clang only, empty on MSVC).

## Reflection

### Design docs to write

- **`.knowledge/designs/0008-compiler-portability.md`**: Document the portability strategy for compiler-specific features (attributes, intrinsics, platform macros). Cover: `TVM_FFI_INLINE` / `TVM_FFI_NO_INLINE` / `TVM_FFI_ATTRIBUTE_UNUSED` / `TVM_FFI_UNREACHABLE()` / `TVM_FFI_FUNC_SIG` / `TVM_FFI_DLL`, the supported compiler matrix (GCC, Clang, MSVC, Emscripten), and the general rule "prefer C++ standard attributes, fall back to vendor extensions only when no standard equivalent exists." This doc would help classify future commits that update compiler compatibility or add new platform support, and would make it explicit which macros are fully standard vs. vendor-extended.

### ADRs to write

- **`.knowledge/ADRs/0006-standard-attributes-over-extensions.md`**: Records the decision to prefer C++ standard attribute syntax (`[[...]]`) over compiler-specific extensions (`__attribute__`, `__declspec`). Context: The codebase targets C++17 and GCC/Clang/MSVC; `[[maybe_unused]]` is fully standard, while `[[gnu::always_inline]]` and `[[msvc::forceinline]]` use the standard attribute syntax but are vendor-specific. Alternatives considered: (1) keep `__attribute__`/`__declspec` (proven, no change needed), (2) remove forced inlining entirely and trust compiler optimization (risks performance regression for hot-path TypeTraits methods). Trade-off: standard attribute syntax is more consistent and avoids platform `#ifdef` for `[[maybe_unused]]`, but `[[gnu::always_inline]]` is not more portable than `__attribute__((always_inline))` -- the benefit is syntactic consistency, not actual portability.

### Skill evolution (`/commit-ledger`)

- **Attribute-ordering awareness**: The commit reveals a subtlety: when `TVM_FFI_INLINE` expands to `[[gnu::always_inline]] inline`, the ordering `static TVM_FFI_INLINE` becomes `static [[gnu::always_inline]] inline`, which places the attribute after `static`. The C++ standard requires attributes to precede the declaration specifiers they apply to. The skill's Step 3 (Mining Design Elements) could benefit from a sub-step for "syntactic invariant changes" -- changes that are semantically no-op but enforce a language-level constraint (like attribute ordering). These are easy to misclassify as trivial when they actually encode a learned rule about C++ attribute placement.

The skill could benefit from a heuristic: "when a commit contains both macro definition changes and widespread mechanical usage changes, prioritize analyzing the macro definition changes in Step 4 (Key Implementations) and treat the usage changes as evidence."
