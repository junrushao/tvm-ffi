# Fix Tuple forwarding constructor SFINAE to prevent ambiguous overload with move/copy constructors

## TL;DR
- The variadic forwarding constructor `Tuple(UTypes&&...)` lacked proper SFINAE guards and could hijack overload resolution when `sizeof...(Types) == 1`, causing `Tuple<T>&&` to match the forwarding constructor instead of the move constructor.
- The fix moves the size check from a `static_assert` body into an `enable_if_t` constraint and adds an explicit exclusion for the single-element self-type case.
- `IterAdapter::operator+=` and `operator-=` are added to satisfy the full `LegacyRandomAccessIterator` requirement, which some STL `vector::insert` implementations need when forwarding through `Array` iterators.

## Key Exports

**`Tuple<Types...>` forwarding constructor** (changed SFINAE constraint):
```cpp
// Before: static_assert inside body, no SFINAE exclusion
template <typename... UTypes>
explicit Tuple(UTypes&&... args);

// After: SFINAE constraint in template head, excludes self-type for single-element tuples
template <typename... UTypes,
          typename = std::enable_if_t<sizeof...(Types) == sizeof...(UTypes) &&
                                      !(sizeof...(Types) == 1 &&
                                        (std::is_same_v<std::remove_cv_t<UTypes>, Tuple<Types>> &&
                                         ...))>>
explicit Tuple(UTypes&&... args);
```

**`IterAdapter::operator+=`** (new):
```cpp
IterAdapter& operator+=(difference_type offset);
```

**`IterAdapter::operator-=`** (new):
```cpp
IterAdapter& operator-=(difference_type offset);
```

## Impact
- API: No breaking change. The forwarding constructor now correctly refuses to bind when it would shadow the copy/move constructor, which is a pure correctness fix.
- Behavioral: `Tuple<T>` values can now be safely used with STL range-insert operations (e.g., `std::vector<Tuple<T>>::insert(pos, Array<Tuple<T>>::begin(), Array<Tuple<T>>::end())`) without triggering the wrong constructor.
- Flags/config: None.
- Data formats/schemas: None.

## Usage Examples

**Before (broken)**: Inserting `Array<Tuple<TInt>>` elements into a `std::vector` via iterators would invoke the forwarding constructor instead of the copy constructor, causing incorrect behavior:
```cpp
Tuple<TInt> t0(1);
Tuple<TInt> t1(2);
Array<Tuple<TInt>> arr0 = {t0, t1};
std::vector<Tuple<TInt>> vec0 = {t0};
// BUG: vec0.insert calls Tuple(UTypes&&...) with UTypes=Tuple<TInt>,
// constructing a new TupleNode from the Tuple object instead of copying the ref
vec0.insert(vec0.end(), arr0.begin(), arr0.end());
```

**After (fixed)**: The SFINAE guard disables the forwarding constructor when `UTypes` is `Tuple<Types>`, so the copy constructor is correctly selected:
```cpp
Tuple<TInt> t0(1);
Tuple<TInt> t1(2);
Array<Tuple<TInt>> arr0 = {t0, t1};
std::vector<Tuple<TInt>> vec0 = {t0};
// OK: copy constructor selected, ref semantics preserved
vec0.insert(vec0.end(), arr0.begin(), arr0.end());
EXPECT_EQ(vec0.size(), 3);
EXPECT_EQ(vec0[1].get<0>()->value, 1);
EXPECT_EQ(vec0[2].get<0>()->value, 2);
```
