# Fix Tuple variadic constructor hijacking copy/move during iterator forwarding
## TL;DR
- Fixes a bug where `Tuple<T>`'s variadic constructor `Tuple(UTypes&&...)` was selected by overload resolution instead of the move constructor when STL algorithms forwarded dereferenced Array iterators, causing `Tuple<T>&&` to be treated as an element value rather than a move source.
- Adds SFINAE constraint to the variadic constructor excluding the single-element case where `UTypes` is `Tuple<Types>` itself, preventing constructor hijacking.
- Adds missing `operator+=` and `operator-=` to `IterAdapter`, completing the `LegacyRandomAccessIterator` requirements needed by STL `insert`/`copy` algorithms.

## Key Exports

```python
# BEFORE (broken): Tuple variadic constructor used body-level static_assert
# template <typename... UTypes>
# explicit Tuple(UTypes&&... args) {
#   static_assert(sizeof...(Types) == sizeof...(UTypes));  // checked too late
# }

# AFTER (fixed): SFINAE excludes ambiguous overloads at substitution time
# template <typename... UTypes,
#           typename = enable_if_t<
#             sizeof...(Types) == sizeof...(UTypes) &&
#             !(sizeof...(Types) == 1 &&
#               is_same_v<remove_cv_t<UTypes>, Tuple<Types>>...)>>
# explicit Tuple(UTypes&&... args): ObjectRef(MakeTupleNode(forward<UTypes>(args)...)) {}
# Invariant: variadic ctor is never a candidate when UTypes is Tuple<Types> itself (single-element case)
# Interacts with: copy ctor Tuple(const Tuple&), move ctor Tuple(Tuple&&)

class IterAdapter:
    """Iterator adapter wrapping TIter with a value converter."""
    # NEW: compound assignment operators (previously missing)
    def __iadd__(self, offset: int) -> IterAdapter: ...  # operator+=
    def __isub__(self, offset: int) -> IterAdapter: ...  # operator-=
    # Interacts with: Array::begin()/end() iterators used by STL algorithms (insert, copy)
    # Invariant: satisfies LegacyRandomAccessIterator (requires +=, -=, +, -, [], <, etc.)
```

## Impact
- API: None -- no public API signature changes; SFINAE constraint is invisible to correct callers.
- Behavioral: `std::vector<Tuple<T>>::insert(pos, arr.begin(), arr.end())` now correctly move-constructs elements instead of misinterpreting them as tuple element arguments. Affects single-element `Tuple<T>` most critically.
- Flags/config: None.
- Data formats/schemas: None.

## Design Elements
Design elements this commit consumes:
- `Tuple<Types...>` variadic constructor and overload set (`.knowledge/designs/0007-containers.md`)
- `IterAdapter` random-access iterator adapter used by `Array::begin()`/`Array::end()` (`include/tvm/ffi/container/container_details.h`)
- C++ overload resolution rules (SFINAE vs body-level `static_assert`)

Design elements this commit produces:
- **Tuple constructor SFINAE guard**: New invariant that the variadic `Tuple(UTypes&&...)` constructor is excluded via `enable_if_t` when `sizeof...(Types) == 1` and `UTypes` is `Tuple<Types>` itself, preventing hijacking of copy/move semantics.
- **IterAdapter `operator+=`/`operator-=`**: Completes the `LegacyRandomAccessIterator` interface for `IterAdapter`, required by STL algorithm implementations that use compound assignment.

## Usage Examples

Before (broken): inserting Array elements into a vector of single-element Tuples would compile but produce wrong behavior:
```cpp
// BUG: Tuple<TInt>'s variadic ctor matched Tuple<TInt>&& as an element arg
Tuple<TInt> t0(1), t1(2);
Array<Tuple<TInt>> arr = {t0, t1};
std::vector<Tuple<TInt>> vec = {t0};
vec.insert(vec.end(), arr.begin(), arr.end());  // misbehavior or compile error
```

After (fixed): the move constructor is correctly selected, and IterAdapter supports `+=` needed by STL:
```cpp
// FIXED: SFINAE excludes variadic ctor; move ctor is selected
Tuple<TInt> t0(1), t1(2);
Array<Tuple<TInt>> arr = {t0, t1};
std::vector<Tuple<TInt>> vec = {t0};
vec.insert(vec.end(), arr.begin(), arr.end());  // correctly moves elements
EXPECT_EQ(vec.size(), 3);
EXPECT_EQ(vec[1].get<0>()->value, 1);
EXPECT_EQ(vec[2].get<0>()->value, 2);
```
