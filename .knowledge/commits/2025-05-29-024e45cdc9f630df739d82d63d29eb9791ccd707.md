# Fix Tuple variadic constructor to reject self-type forwarding and complete IterAdapter random-access support

## TL;DR
- Fixes a bug where `Tuple<T>::Tuple(UTypes&&...)` variadic constructor could match a `Tuple<T>&&` argument (single-element tuple case), bypassing the intended move constructor and causing incorrect behavior during `std::vector::insert` with Array iterators.
- Adds missing `operator+=` and `operator-=` to `IterAdapter`, completing the random-access iterator contract required by `std::vector::insert`.
- Adds two regression tests: `ArrayIterForwarding` (multi-element tuple) and `ArrayIterForwardSingleElem` (single-element tuple, the actual failure case).

## Key Exports

**IterAdapter compound assignment operators** (`include/tvm/ffi/container/container_details.h`):
```cpp
IterAdapter& operator+=(difference_type offset);
IterAdapter& operator-=(difference_type offset);
```

**Tuple variadic constructor** (`include/tvm/ffi/container/tuple.h`) -- constraint tightened:
```cpp
// Before: unconstrained UTypes, static_assert inside body
template <typename... UTypes>
explicit Tuple(UTypes&&... args);

// After: SFINAE constraint rejects when sizeof...(Types)==1 and UType is Tuple<Types> itself
template <typename... UTypes,
          typename = std::enable_if_t<sizeof...(Types) == sizeof...(UTypes) &&
                                      !(sizeof...(Types) == 1 &&
                                        (std::is_same_v<std::remove_cv_t<UTypes>, Tuple<Types>> && ...))>>
explicit Tuple(UTypes&&... args);
```

The size check also moved from a `static_assert` in the body to the SFINAE constraint, so overload resolution can fall through to the correct constructor instead of producing a hard error.

## Impact
- API: No public API change. The variadic constructor is `explicit` and the constraint only removes an overload that was never intended to match.
- ABI: None. Header-only template change.
- Behavioral: `Tuple<T>` single-element tuples now correctly use the move constructor when forwarded through iterators, instead of constructing a new tuple wrapping the old tuple object.
- Flags/config: None.
- Data formats/schemas: None.

## Design Elements

Design elements this commit consumes:
- **Tuple<T...>** (`include/tvm/ffi/container/tuple.h`) -- the variadic constructor, move constructor, and upcast constructors. See `.knowledge/designs/containers.md` (Tuple section).
- **IterAdapter** (`include/tvm/ffi/container/container_details.h`) -- random-access iterator adapter used by `Array::begin()`/`Array::end()`. See `.knowledge/designs/containers.md` (container_details reference).
- **Array<T>** (`include/tvm/ffi/container/array.h`) -- the container whose iterators are passed to `std::vector::insert`.

Design elements this commit produces:
- **Tuple variadic constructor SFINAE guard** -- new invariant: the `Tuple(UTypes&&...)` constructor is disabled when `sizeof...(Types) == 1` and `UTypes` is `Tuple<Types>` itself. This prevents the forwarding reference from shadowing move/copy constructors for single-element tuples.
- **IterAdapter `operator+=`/`operator-=`** -- completes the `RandomAccessIterator` named requirement. Without these, some STL algorithms (`std::vector::insert` on certain implementations) fail to compile or produce UB.

## Usage Examples

Inserting Array elements into a vector (the failing pattern before this fix):
```cpp
// Single-element Tuple -- triggered the bug before this fix
Tuple<TInt> t0(1);
Tuple<TInt> t1(2);
Array<Tuple<TInt>> arr = {t0, t1};

std::vector<Tuple<TInt>> vec = {t0};
// Before fix: insert called Tuple(Tuple<TInt>&&) variadic ctor,
//   wrapping the tuple in another tuple node.
// After fix: correctly calls move constructor.
vec.insert(vec.end(), arr.begin(), arr.end());
assert(vec[1].get<0>()->value == 1);  // was broken before
```
