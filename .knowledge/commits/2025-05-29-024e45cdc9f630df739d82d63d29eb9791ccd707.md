# Fix Tuple variadic constructor hijacking move construction during vector forwarding
## TL;DR
- Fixed `Tuple<Types...>` variadic forwarding constructor SFINAE to reject single-argument calls where the argument is `Tuple<Types>` itself, preventing it from hijacking move/copy construction during `std::vector::insert` with `Array` iterators.
- Added `operator+=` and `operator-=` to `IterAdapter` to satisfy the `LegacyRandomAccessIterator` requirement needed by `std::vector::insert`.
- Added two test cases exercising `Array<Tuple<...>>` iterator forwarding into `std::vector`, covering both multi-element and single-element tuples.

## Key Exports

```python
# IterAdapter: added compound assignment operators (previously missing)
class IterAdapter(Generic[TIter, Converter]):
    """Iterator adapter that converts underlying iterator values."""
    # Existing: operator+, operator-, operator++, operator--, operator==, operator!=, operator*
    # NEW in this commit:
    def __iadd__(self, offset: int) -> IterAdapter: ...  # operator+=
    def __isub__(self, offset: int) -> IterAdapter: ...  # operator-=
    # Invariant: these are required for LegacyRandomAccessIterator concept
    # Interacts with: Array.begin()/end() return IterAdapter; std::vector::insert requires += and -=

# Tuple variadic constructor: SFINAE constraint tightened
class Tuple(ObjectRef, Generic[*Types]):
    # OLD: template<typename... UTypes> explicit Tuple(UTypes&&... args)
    #      with static_assert(sizeof...(Types) == sizeof...(UTypes)) in body
    # NEW: template<typename... UTypes,
    #        enable_if_t<sizeof...(Types) == sizeof...(UTypes)
    #                    && !(sizeof...(Types) == 1
    #                         && is_same_v<remove_cv_t<UTypes>, Tuple<Types>>...)>>
    #      explicit Tuple(UTypes&&... args)
    # Invariant: when sizeof...(Types)==1, a Tuple<T> argument must NOT match
    #   the forwarding constructor -- it must fall through to the copy/move constructors
    # Interacts with: Array<Tuple<T>>::begin()/end() iterators dereference to Tuple<T>
```

## Impact
- API: none -- no public API signature change, only stricter SFINAE on existing constructor
- Behavioral: fixes incorrect constructor dispatch when copying `Tuple` elements from `Array` iterators into `std::vector` via `insert`. Before this fix, single-element `Tuple<T>` values forwarded from `Array` iterators were incorrectly consumed by the variadic constructor instead of the move constructor.
- Flags/config: none
- Data formats/schemas: none

## Usage Examples
Before (broken): inserting `Array<Tuple<TInt>>` elements into a `std::vector` via iterator range triggered the wrong constructor:
```cpp
// Before fix: this would fail for single-element tuples because
// IterAdapter dereference -> Tuple<TInt> rvalue -> matched by
// Tuple(UTypes&&...) forwarding constructor instead of move constructor
Tuple<TInt> t0(1);
Array<Tuple<TInt>> arr0 = {t0};
std::vector<Tuple<TInt>> vec0 = {t0};
vec0.insert(vec0.end(), arr0.begin(), arr0.end());  // BUG: wrong constructor
```

After (fixed): the SFINAE constraint on the variadic constructor rejects `Tuple<T>` arguments, forcing move construction:
```cpp
// After fix: Tuple(UTypes&&...) is SFINAE-disabled when UTypes = {Tuple<TInt>},
// so the move constructor is correctly selected
Tuple<TInt> t0(1);
Array<Tuple<TInt>> arr0 = {t0};
std::vector<Tuple<TInt>> vec0 = {t0};
vec0.insert(vec0.end(), arr0.begin(), arr0.end());  // OK: move constructor used
EXPECT_EQ(vec0[1].get<0>()->value, 1);  // correct
```
