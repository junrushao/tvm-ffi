# Fix Tuple variadic constructor hijacking copy/move when used with STL iterator insertion
## TL;DR
- Fixes a bug where `Tuple<T>`'s variadic constructor `Tuple(UTypes&&... args)` would incorrectly match when STL algorithms (e.g., `std::vector::insert`) forwarded a `Tuple<T>` value, instead of dispatching to the copy/move constructor. The root cause: for single-element tuples (`sizeof...(Types) == 1`), the forwarding constructor matched `UType&& = Tuple<T>&&` because `sizeof...(UTypes) == sizeof...(Types) == 1` was satisfied.
- Adds SFINAE guard on the variadic constructor to exclude the case where `sizeof...(Types) == 1` and the single argument type (after `remove_cv`) is `Tuple<Types>`.
- Adds `operator+=` and `operator-=` to `IterAdapter` to satisfy the full `LegacyRandomAccessIterator` requirements needed by `std::vector::insert` with `Array<T>::iterator`.

## Impact
- API: No public API change. The variadic constructor signature gains a tighter SFINAE constraint, which is a behavioral fix (not a new feature). Existing code that correctly constructs tuples from values is unaffected; code that accidentally triggered the variadic constructor for copy semantics is now fixed.
- Flags/config: none
- Data formats/schemas: none

## Design Elements
Design elements this commit consumes:
- **Tuple<Ts...> backed by ArrayObj** (`.knowledge/designs/0005-containers.md`, section "Tuple and Variant"): The `Tuple` class wraps an `ArrayObj` and exposes typed element access. This commit modifies its constructor overload resolution, which directly interacts with how `Tuple` values are constructed and copied.
- **IterAdapter for Array<T> iteration** (`.knowledge/designs/0005-containers.md`, section "Key Classes"): `Array<T>::iterator` is `IterAdapter<Converter, const Any*>`. The iterator must satisfy `LegacyRandomAccessIterator` for use with STL algorithms like `std::vector::insert(pos, first, last)`.
- **C++ forwarding reference overload resolution**: The classic "forwarding constructor vs copy/move constructor" conflict (Scott Meyers, Effective Modern C++, Item 26). When a class has both copy/move constructors and a templated forwarding constructor, the forwarding version can be a better match for non-const lvalue or rvalue arguments because it deduces the exact type without requiring a const-qualification adjustment.

Design elements this commit produces:
- **Tuple variadic constructor SFINAE guard**: New invariant -- the variadic constructor `Tuple(UTypes&&... args)` is disabled (via `enable_if_t`) when `sizeof...(Types) == 1` and `std::remove_cv_t<UTypes>` matches `Tuple<Types>`. This prevents the forwarding constructor from hijacking copy/move semantics for single-element tuples. Evidence: `include/tvm/ffi/container/tuple.h` lines 69-73 (at commit `024e45c`).
- **Complete LegacyRandomAccessIterator for IterAdapter**: Added `operator+=` and `operator-=` which are required by the `LegacyRandomAccessIterator` named requirement (C++ standard [iterator.concept.random.access]). Without these, some STL implementations reject `IterAdapter` iterators in algorithms that require compound assignment. Evidence: `include/tvm/ffi/container/container_details.h` lines 78-86 (at commit `024e45c`).

### Skill evolution (`/commit-ledger`)

- **Note subtle SFINAE correctness issues**: This commit uses `std::remove_cv_t<UTypes>` in the guard, but for forwarding references, the deduced `UTypes` can be a reference type (e.g., `Tuple<Types>&` for lvalue arguments). `std::remove_cv_t` does not strip references, so `std::remove_cv_t<Tuple<Types>&>` is `Tuple<Types>&`, which does NOT match `Tuple<Types>`. This means the guard may fail to exclude lvalue copies for single-element tuples. The current HEAD uses `std::decay_t<UTypes>` which correctly handles both cases. The skill should flag when a SFINAE constraint appears to have a correctness gap relative to the stated intent, even if the test cases pass (the tests only exercise the rvalue/iterator path, not direct lvalue construction of single-element tuples).

For `LegacyRandomAccessIterator`, the required operations are: `+`, `-`, `+=`, `-=`, `[]`, `<`, `>`, `<=`, `>=`. This commit adds `+=` and `-=` but `IterAdapter` still lacks `operator[]`, `operator<`, `operator>`, `operator<=`, `operator>=`. The skill should flag remaining gaps when a commit partially completes an interface requirement.
