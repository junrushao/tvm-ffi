# Auto-generate __init__ for @register_object classes using __ffi_init__ or explicit error
## TL;DR
- Previously, calling `SomeObject(...)` on a `@register_object` class without an explicit `__init__` silently returned an object with `chandle=None`, leading to segfaults on field access.
- `_add_class_attrs` in `registry.py` now auto-generates `__init__` for such classes: if `__ffi_init__` is available, `__init__` delegates to it; otherwise, `__init__` raises a `RuntimeError` explaining the method is unimplemented.
- The `TestIntPair` class in `testing.py` drops its manual `__init__` since the auto-generation now handles it.

## Key Exports
**Functions**:
- `__init__invalid(self, *args, **kwargs) -> None` (module-level in `registry.py`): Sentinel `__init__` that raises `RuntimeError("The __init__ method of this class is not implemented.")`. Installed on classes that lack both a user-defined `__init__` and a C++ `__ffi_init__`, and are not subclasses of `PyNativeObject`.

**Behavioral changes to `_add_class_attrs`**:
- After processing all methods, checks `"__init__" not in type_cls.__dict__` (i.e., the class itself does not define `__init__`, ignoring inherited ones).
  - If `__ffi_init__` was found among reflected methods: sets `type_cls.__init__ = type_cls.__ffi_init__`, enabling `SomeObject(arg1, arg2)` to call the C++ constructor directly.
  - Else if the class is NOT a `PyNativeObject` subclass: sets `type_cls.__init__ = __init__invalid`, preventing silent `chandle=None` creation.
  - `PyNativeObject` subclasses are excluded because they manage their own handle lifecycle.

**Minor fix in `object.pxi`**:
- `dict(cls.__dict__)` changed to `cls.__dict__.copy()` in `make_fallback_cls_for_type_index`. This is semantically equivalent but avoids creating a new `dict` from a `mappingproxy`; `.copy()` on `mappingproxy` returns a plain `dict` directly.

## Impact
- API: Classes decorated with `@register_object` that have `__ffi_init__` but no explicit `__init__` now automatically get a working `__init__`. This is a quality-of-life improvement. The `TestIntPair` manual `__init__` is removed as proof. Callers creating `TestIntPair(1, 2)` now see `# type: ignore[call-arg]` because mypy does not see the dynamically-generated `__init__` signature.
- ABI: none
- Behavioral: Classes without `__ffi_init__` AND without a manual `__init__` (and not `PyNativeObject` subclasses) now raise `RuntimeError` on construction instead of silently producing a broken object. This is a breaking behavioral change for any code that relied on the silent `chandle=None` return (almost certainly a bug in the caller).
- Flags/config: none
- Data formats/schemas: none

## Design Elements
Design elements this commit consumes:
- `__ffi_init__` / `__c_ffi_init__` renaming convention in `_add_class_attrs` (`.knowledge/designs/0019-c-class-decorator.md` -- "Contracts, Assumptions and Invariants" section)
- `_add_class_attrs` function in `registry.py` that iterates `TypeInfo.fields` and `TypeInfo.methods` to populate Python class attributes (`.knowledge/designs/0014-python-bindings.md`)
- `Object.__ffi_init__` instance method that dispatches to `type(self).__c_ffi_init__` via `__init_handle_by_constructor__` (`.knowledge/designs/0019-c-class-decorator.md`)
- `PyNativeObject` base class for Python-native objects that manage their own handles (`.knowledge/designs/0014-python-bindings.md`)

Design elements this commit produces:
- Auto-`__init__` generation protocol for `@register_object` classes: three-way dispatch based on presence of `__ffi_init__` and `PyNativeObject` inheritance. This extends the `_add_class_attrs` contract documented in `.knowledge/designs/0014-python-bindings.md`.

## Usage Examples
**Before (segfault-prone)**:
```python
@register_object("testing.TestIntPair")
class TestIntPair(Object):
    # No __init__ defined, no __ffi_init__ auto-wiring
    pass

obj = TestIntPair(1, 2)  # Silently creates chandle=None
obj.a  # SEGFAULT
```

**After (auto-wired __init__)**:
```python
@register_object("testing.TestIntPair")
class TestIntPair(Object):
    # __ffi_init__ exists in C++ reflection -> auto-generates __init__
    pass

obj = TestIntPair(1, 2)  # Calls __ffi_init__ -> C++ constructor
assert obj.a == 1  # Works correctly
```

**After (no __ffi_init__, explicit error)**:
```python
@register_object("some.TypeWithoutInit")
class NoInitType(Object):
    pass

NoInitType()  # Raises RuntimeError: "The __init__ method of this class is not implemented."
```
