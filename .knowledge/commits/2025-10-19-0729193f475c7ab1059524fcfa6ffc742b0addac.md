# Auto-generate `__init__` from `__ffi_init__` in Python object registration

## TL;DR
- When a Python FFI class has no explicit `__init__`, `_add_class_attrs` now auto-generates one: if `__ffi_init__` is registered (via C++ reflection), it becomes `__init__`; otherwise, a sentinel `__init__` that raises `RuntimeError` is installed.
- Removes the manual `__init__` boilerplate pattern from `TestIntPair` (and by extension all FFI classes), since auto-generation handles it.
- Fixes a silent failure where calling `SomeObject(args)` with no `__init__` would produce an object with `chandle=None`, causing segfaults on field access.

## Key Exports

```python
# In python/tvm_ffi/registry.py

def _add_class_attrs(type_cls: type, type_info: TypeInfo) -> type:
    """Register fields, methods, and auto-generate __init__ for FFI classes.

    New behavior:
    - If __ffi_init__ is in type_info.methods and __init__ not in type_cls.__dict__:
        type_cls.__init__ = type_cls.__ffi_init__
    - If no __ffi_init__ and not PyNativeObject subclass:
        type_cls.__init__ = __init__invalid  (raises RuntimeError)
    """
    # Interacts with: __ffi_init__ convention from C++ ObjectDef<T> reflection (0008)
    # Interacts with: PyNativeObject exemption for Python-native objects (0012)
    # Invariant: __ffi_init__ is renamed to __c_ffi_init__ on the class to preserve
    #   the original binding, while __init__ gets the auto-forwarding behavior.
    ...

def __init__invalid(self: Any, *args: Any, **kwargs: Any) -> None:
    """Sentinel __init__ for classes without a constructor."""
    raise RuntimeError("The __init__ method of this class is not implemented.")
```

## Impact
- API: Classes with C++ `__ffi_init__` no longer need manual Python `__init__` methods. Existing manual `__init__` definitions (checked via `__dict__`) take precedence.
- Behavioral: Calling an FFI class constructor without `__init__` now raises `RuntimeError` instead of silently returning a broken object with `chandle=None`.
- Flags/config: none
- Data formats/schemas: none

## Design Elements
Design elements this commit consumes:
- `__ffi_init__` convention from [0008-reflection](../design-records/0008-reflection.md): the standard method name for FFI constructor registration via `ObjectDef<T>`
- `_add_class_attrs` wiring from [0012-python-bindings](../design-records/0012-python-bindings.md): the function that processes `TypeInfo` fields/methods onto Python classes
- `PyNativeObject` exemption from [0012-python-bindings](../design-records/0012-python-bindings.md): Python-native objects are excluded from the invalid-init sentinel

Design elements this commit produces:
- Auto-`__init__` generation pattern in [0012-python-bindings](../design-records/0012-python-bindings.md): `__ffi_init__` automatically becomes `__init__` when no explicit constructor is defined
- `__init__invalid` sentinel in [0012-python-bindings](../design-records/0012-python-bindings.md): fail-fast for classes that lack constructors

## Usage Examples

Before this commit, every Python FFI class with a C++ constructor needed manual boilerplate:
```python
@register_object("testing.TestIntPair")
class TestIntPair(Object):
    def __init__(self, a: int, b: int) -> None:
        self.__ffi_init__(a, b)  # manual forwarding
```

After this commit, the `__init__` is auto-generated from `__ffi_init__`:
```python
@register_object("testing.TestIntPair")
class TestIntPair(Object):
    pass  # __init__ auto-generated from __ffi_init__

# Works directly:
pair = TestIntPair(1, 2)
assert pair.a == 1 and pair.b == 2
```

For classes without `__ffi_init__`, calling the constructor now fails fast:
```python
@register_object("some.TypeWithoutInit")
class TypeWithoutInit(Object):
    pass

TypeWithoutInit()  # raises RuntimeError: "The __init__ method of this class is not implemented."
```
