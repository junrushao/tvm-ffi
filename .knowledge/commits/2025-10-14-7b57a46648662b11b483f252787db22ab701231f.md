# Fix FunctionInfo specialization to support ObjectRef member function pointers

## TL;DR
- `FunctionInfo<R (Class::*)(Args...)>` previously had a single specialization that treated all class member functions the same way. This PR splits it into two SFINAE branches: one for `Object`-derived classes (receiver as `Class*`) and one for `ObjectRef`-derived classes (receiver by value as `Class`).
- Without this fix, registering an `ObjectRef` member function (e.g., `&TestIntPair::Sum`) as a global function compiled incorrectly — the schema would describe the first argument as a raw pointer rather than the `ObjectRef` type, causing downstream type-schema mismatches and compilation errors.
- The change adds a `TestIntPair::Sum` method and registers it via `def_method(...)` as a test case validating the corrected schema.

## Key Exports

```python
# BEFORE (single specialization, ambiguous):
# template <Class, R, Args...>
# struct FunctionInfo<R (Class::*)(Args...)> : FuncFunctorImpl<R, Class*, Args...> {}
# -- Class* is wrong when Class is an ObjectRef subtype (value semantics, not pointer)

# AFTER (two SFINAE branches):

# Branch 1: Object-derived class — receiver passed as raw pointer
template <Class, R, Args...>
struct FunctionInfo<R (Class::*)(Args...), enable_if_t<is_base_of_v<Object, Class>>>:
    FuncFunctorImpl[R, Class*, Args...]  # receiver = Class*

template <Class, R, Args...>
struct FunctionInfo<R (Class::*)(Args...) const, enable_if_t<is_base_of_v<Object, Class>>]:
    FuncFunctorImpl[R, const Class*, Args...]  # receiver = const Class*

# Branch 2: ObjectRef-derived class — receiver passed by value (value semantics)
template <Class, R, Args...>
struct FunctionInfo<R (Class::*)(Args...), enable_if_t<is_base_of_v<ObjectRef, Class>>]:
    FuncFunctorImpl[R, Class, Args...]  # receiver = Class (by value)

template <Class, R, Args...>
struct FunctionInfo<R (Class::*)(Args...) const, enable_if_t<is_base_of_v<ObjectRef, Class>>]:
    FuncFunctorImpl[R, const Class, Args...]  # receiver = const Class (by value)

# Interacts with: FuncFunctorImpl (determines ArgType tuple and schema JSON),
#                 unpack_call (uses FunctionInfo::num_args and ArgType for dispatch),
#                 GlobalDef::def_method (calls Function::FromTyped which uses FunctionInfo),
#                 TypeSchema<> (uses FunctionInfo to emit "args" in JSON schema)
# Invariant: ObjectRef is NOT a subtype of Object; the two branches are mutually exclusive
# Invariant: schema "args" list for an ObjectRef::MemFn begins with the ObjectRef type,
#            not a pointer — Python side sees Callable[[ObjectRef], R]
```

## Impact
- API: Additive — new `FunctionInfo` specializations do not remove existing specializations; existing `Object::MemFn` paths continue to work identically.
- Behavioral: Fixes incorrect type-schema JSON for `ObjectRef` member functions registered via `GlobalDef::def_method`. Before: schema emitted `Class*` for first arg. After: schema emits `Class` (ObjectRef value type).
- Flags/config: none
- Data formats/schemas: Type-schema JSON for globals registered via `def_method("...", &ObjectRef::Method)` now correctly reflects `ObjectRef` as first argument type instead of `ObjectRef*`.

## Design Elements
Design elements this commit consumes:
- `FunctionInfo<T>` / `FuncFunctorImpl<R, Args...>` in `include/tvm/ffi/function_details.h` — the compile-time type-info template that drives schema generation and `FromTyped` argument unpacking
- `GlobalDef::def_method` in `include/tvm/ffi/reflection/registry.h` (design record: `.knowledge/design-records/0004-function-system.md`, `.knowledge/design-records/0006-reflection.md`) — wraps member pointers into `Function::FromTyped`-compatible lambdas
- `ReflectionDefBase::GetMethod` dispatch (Object vs. ObjectRef) in `reflection/registry.h` — the C++ layer that already handles the Object/ObjectRef split at runtime; this commit brings `FunctionInfo` into alignment at the schema/type level
- `ObjectDef::def` (reflection builder) in `0006-reflection.md` — used in testing.cc to register `TestIntPair::Sum` as an instance method on the C++ object

Design elements this commit produces:
- Extended `FunctionInfo` specialization set: adds two new partial specializations for `ObjectRef`-derived classes, making `FunctionInfo` SFINAE-complete for all TVM FFI class hierarchies

## Usage Examples

End-to-end trace: C++ member on ObjectRef → Python schema validation.

```cpp
// C++ (src/ffi/extra/testing.cc)
class TestIntPair : public tvm::ffi::ObjectRef {
 public:
  int64_t Sum() const { return get()->a + get()->b; }
  TVM_FFI_DEFINE_OBJECT_REF_METHODS_NULLABLE(TestIntPair, ObjectRef, TestIntPairObj);
};

TVM_FFI_STATIC_INIT_BLOCK() {
  refl::ObjectDef<TestIntPairObj>()
    .def("sum", &TestIntPair::Sum, "Method to compute sum of a and b");  // instance method

  refl::GlobalDef()
    .def_method("testing.TestIntPairSum", &TestIntPair::Sum, "Get sum of the pair");
    // Before fix: schema would emit first arg as "testing.TestIntPair*" (pointer)
    // After fix:  schema emits first arg as "testing.TestIntPair" (ObjectRef by value)
}
```

```python
# Python (tests/python/test_metadata.py)
def test_mem_fn_as_global_func() -> None:
    metadata = get_global_func_metadata("testing.TestIntPairSum")
    type_schema = TypeSchema.from_json_str(metadata["type_schema"])
    assert str(type_schema) == "Callable[[testing.TestIntPair], int]"
    # Before fix: "Callable[[testing.TestIntPair*], int]" or compilation error
```
