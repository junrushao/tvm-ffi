# Add Breathe/Exhale C++ API reference docs and annotate all public headers with Doxygen comments

## TL;DR
- Integrates Breathe + Exhale (Doxygen-based) C++ API reference generation into the Sphinx documentation site, gated behind the `BUILD_CPP_DOCS=1` environment variable. Adds a new `docs/reference/cpp/index.rst` page with header organization overview, key class table, and a toctree pointing to auto-generated API index.
- Systematically adds or fixes Doxygen doc-comments (`/*! \brief ... */`) across all 34 public C++ headers in `include/tvm/ffi/`, covering constructors, operators, type aliases, enum values, static constexpr fields, and function overloads that were previously undocumented.
- Suppresses internal implementation details from Doxygen output using `/// \cond Doxygen_Suppress` / `/// \endcond` blocks around macros, type traits specializations, iterator internals, and `TVM_FFI_DEFINE_OBJECT_REF_METHODS` invocations.
- Moves `SimpleObjAllocator` and `ObjAllocatorBase` into `namespace details` in `memory.h`, narrowing the public API surface. Changes `FObjectDeleter` signature from `TVMFFIObject*` to `void*` (matching the C ABI struct change in `c_api.h`). Fixes assorted typos and doc-comment inaccuracies.

## Impact
- **API**: The `FObjectDeleter` typedef changes from `void (*)(TVMFFIObject*, int)` to `void (*)(void*, int)` in `memory.h`. The `TVMFFIObject.deleter` field in `c_api.h` likewise changes to `void (*)(void*, int)`. This is an ABI-level change but the two structs already shared the same layout intent; callers that store or invoke the deleter directly must update the cast. `ObjAllocatorBase` and `SimpleObjAllocator` move into `namespace details`, so any code referencing `tvm::ffi::SimpleObjAllocator` must now use `tvm::ffi::details::SimpleObjAllocator` (unlikely outside the project). The `TVMFFIObject` and `TVMFFIAny` C structs lose their self-referencing tag names (changed from `typedef struct TVMFFIObject { ... } TVMFFIObject;` to anonymous `typedef struct { ... } TVMFFIObject;`), which is transparent to C and C++ users who refer to them by typedef name. `TVMFFITypeInfo` gains `#ifdef __cplusplus` to be declared as `struct TVMFFITypeInfo { ... }` in C++ and `typedef struct TVMFFITypeInfo { ... } TVMFFITypeInfo;` in C, avoiding Doxygen issues with C-style typedef structs.
- **Flags/config**: New `BUILD_CPP_DOCS` environment variable in `docs/conf.py` (default `"0"`). When set to `"1"`, the `exhale` extension is loaded and Doxygen is executed during the Sphinx build.
- **Data formats/schemas**: None.

Design elements this commit **produces**:

- **Doxygen/Exhale integration for C++ API reference**: New documentation pipeline component. `docs/conf.py` defines `exhale_args` with `containmentFolder`, `rootFileName`, `doxygenStripFromPath`, `exhaleDoxygenStdin` (INPUT, PREDEFINED, EXCLUDE_SYMBOLS, EXCLUDE_PATTERNS). The `PREDEFINED` list expands `TVM_FFI_DLL`, `TVM_FFI_INLINE`, `TVM_FFI_EXTRA_CXX_API`, `__cplusplus=201703` to ensure correct Doxygen parsing. `EXCLUDE_SYMBOLS` suppresses `*details*`, `*TypeTraits*`, `std`, `*use_default_type_traits_v*`, `*is_optional_type_v*`, `*operator*`. `EXCLUDE_PATTERNS` suppresses `*details.h`. This is a **producer** of a new design element for auto-generated C++ API docs.
- **Doxygen suppression pattern**: The `/// \cond Doxygen_Suppress` / `/// \endcond` idiom is established across the codebase to hide internal implementation details (macros, type trait specializations, iterator adapters, `TVM_FFI_DEFINE_OBJECT_REF_METHODS` expansions) from the generated API docs. Applied in 20+ headers.
- **Allocator encapsulation into `details` namespace**: `ObjAllocatorBase` and `SimpleObjAllocator` in `memory.h` are moved from `tvm::ffi` to `tvm::ffi::details`, reducing the public API surface. `make_object` and `make_inplace_array_object` remain in `tvm::ffi` as the public entry points.
- **`void*` deleter signature**: `FObjectDeleter` changes from `TVMFFIObject*` to `void*`, and the corresponding `TVMFFIObject.deleter` field in the C ABI follows suit. This enables more flexible custom allocators without forcing a cast to the specific object header type.

## Reflection

### Design docs to write

- **`.knowledge/designs/0019-doxygen-exhale-pipeline.md`**: Should document the Breathe/Exhale integration: how `BUILD_CPP_DOCS` gates the pipeline, what PREDEFINED/EXCLUDE_SYMBOLS/EXCLUDE_PATTERNS are set and why, how `/// \cond Doxygen_Suppress` is used to hide internals, and the relationship between `docs/reference/cpp/index.rst` and the generated content in `reference/cpp/generated/`. This doc helps future commit mining for any changes to the documentation build, Doxygen configuration, or header comment conventions.

### ADRs to write

- **`.knowledge/ADRs/0027-void-star-deleter-signature.md`**: Context: The `FObjectDeleter` callback was previously typed as `void (*)(TVMFFIObject*, int)`, requiring the deleter to accept the specific object header type. The decision was made to change it to `void (*)(void*, int)` to align with the C ABI struct (`c_api.h`) and enable more flexible custom allocators. The alternative was to keep the typed signature and add explicit casts inside each allocator's deleter. Trade-off: type safety at call sites vs. flexibility and ABI simplicity. The `void*` approach was chosen because the deleter is always called from within the ref-counting mechanism where the type is already known.

## Self-Evolution of Skill /commit-ledger

- **Detecting mixed-intent commits**: This commit mixes documentation annotation (no functional change) with actual ABI changes (`FObjectDeleter` signature, anonymous struct typedefs, namespace moves). The skill could add guidance in Step 2 (Quick Commit Characterization) to flag commits that touch both documentation/comments and functional code, recommending extra care during Step 3-4 to separate the two.
- **Header-by-header vs. pattern-based analysis**: For commits that touch 30+ headers with a repeating pattern (adding Doxygen comments), the skill could suggest a pattern-based approach in Step 1: "If the diff shows a repetitive pattern across many files (e.g., adding doc comments, adding `/// \cond` blocks), characterize the pattern once and then focus detailed analysis on files that deviate from the pattern." This would reduce analysis time without sacrificing completeness.
- **Doxygen convention tracking**: The skill does not currently have a concept for "codebase conventions" vs. "design elements." A convention like `/// \cond Doxygen_Suppress` is not a class or workflow stage, but it is a pattern that future commits should follow. Consider adding a "Conventions" subsection under Design Elements to capture these.
