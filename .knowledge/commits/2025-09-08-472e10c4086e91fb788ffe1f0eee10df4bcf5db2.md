# Introduce UnsafeInit and enhance ObjectRef null safety

## TL;DR
- Introduces a new tag type `ffi::UnsafeInit` that explicitly marks unsafe initialization of ObjectRef types (setting `data_` to nullptr). This replaces the previous pattern of constructing ObjectRef subtypes from `ObjectPtr<Object>`, which was an implicit and type-unsafe way to initialize references, including to null.
- Removes `RefType(ObjectPtr<Object>)` constructors from non-nullable ObjectRef types. Nullable types retain `RefType(ObjectPtr<ContainerType>)` (note: now typed to the specific container, not generic `Object`).
- Adds `ObjectUnsafe::ObjectRefFromObjectPtr<T>` helper methods that construct an ObjectRef subtype from an ObjectPtr via the UnsafeInit pathway, keeping all unsafe construction centralized in a single friend utility.
- Updates all four `TVM_FFI_DEFINE_*_OBJECT_REF_METHODS` macros to use `UnsafeInit` and typed `ObjectPtr<ContainerType>` instead of `ObjectPtr<Object>`.
- The reflection system (`ObjectDef`) now falls back to `ObjectCreatorUnsafeInit<T>` when a type is constructible from `UnsafeInit` but not default-constructible, enabling the "create with UnsafeInit, then set all fields" pattern for reflected types.
- Also includes a minor refactor of `MakeStridesFromShape` signature and a new `Shape::StridesFromShape` static factory method.

## Key Changes

### New type: `ffi::UnsafeInit` (`object.h`)

```cpp
struct UnsafeInit {};
```

A tag type for explicitly marking unsafe initialization. ObjectRef subtypes should have an `explicit T(UnsafeInit)` constructor that initializes `data_` to nullptr. This replaces the old pattern where ObjectRef subtypes accepted `ObjectPtr<Object>` directly, which was both type-unsafe (accepted any object type) and intent-ambiguous (unclear that null initialization was the purpose).

`ObjectRef` itself gains a new constructor: `explicit ObjectRef(UnsafeInit) : data_(nullptr) {}`.

### New helpers: `ObjectUnsafe::ObjectRefFromObjectPtr<T>` (`object.h`)

Two overloads (const-ref and rvalue-ref) that construct any ObjectRef subtype `T` from an `ObjectPtr<Object>`:

```cpp
template <typename T>
static T ObjectRefFromObjectPtr(const ObjectPtr<Object>& ptr);

template <typename T>
static T ObjectRefFromObjectPtr(ObjectPtr<Object>&& ptr);
```

These use the UnsafeInit constructor to create the ref, then set `data_` directly via friend access. This centralizes all unsafe ObjectRef construction in a single utility, making it easy to audit. These replace the many call sites that previously used `RefType(ObjectPtr<Object>)`.

### Macro changes (`object.h`)

**`TVM_FFI_DEFINE_OBJECT_REF_METHODS(TypeName, ParentType, ObjectName)`:**
- Before: `explicit TypeName(ObjectPtr<Object> n) : ParentType(n) {}`
- After: `explicit TypeName(ObjectPtr<ObjectName> n) : ParentType(n) {}` plus `explicit TypeName(UnsafeInit tag) : ParentType(tag) {}`

The constructor now takes `ObjectPtr<ContainerType>` instead of `ObjectPtr<Object>`, providing compile-time type checking. The UnsafeInit constructor is added separately.

**`TVM_FFI_DEFINE_NOTNULLABLE_OBJECT_REF_METHODS(TypeName, ParentType, ObjectName)`:**
- Before: `explicit TypeName(ObjectPtr<Object> n) : ParentType(n) {}`
- After: `explicit TypeName(UnsafeInit tag) : ParentType(tag) {}`

Non-nullable types no longer have any `ObjectPtr` constructor at all. The only way to construct them with a null pointer is through the explicitly-named UnsafeInit path.

**`TVM_FFI_DEFINE_MUTABLE_OBJECT_REF_METHODS`:** Same pattern -- `ObjectPtr<ObjectName>` instead of `ObjectPtr<Object>`, plus `UnsafeInit` constructor. Also fixes a stale namespace reference from `tvm::runtime` to `tvm::ffi`.

**`TVM_FFI_DEFINE_MUTABLE_NOTNULLABLE_OBJECT_REF_METHODS`:** Same as the non-mutable notnullable variant -- UnsafeInit only, no ObjectPtr constructor.

### `ObjectRef::as<T>()` change (`object.h`)

Previously returned `ObjectRefType(data_)` which relied on the `ObjectPtr<Object>` constructor. Now uses:
```cpp
ObjectRefType ref(UnsafeInit{});
ref.data_ = data_;
return ref;
```
This avoids the removed `ObjectPtr<Object>` constructor entirely.

### `ObjectUnsafe::ObjectPtrFromObjectRef` rvalue overload fix (`object.h`)

The rvalue overload for non-Object types previously did:
```cpp
return tvm::ffi::ObjectPtr<T>(std::move(ref.data_.data_));
```
Now correctly nulls out the source:
```cpp
ObjectPtr<T> result;
result.data_ = std::move(ref.data_.data_);
ref.data_.data_ = nullptr;
return result;
```
This ensures the source ObjectRef's data pointer is properly nulled after move.

### Optional<T> changes (`optional.h`)

- Removes `explicit Optional(ObjectPtr<Object> ptr)` constructor, replaced by `explicit Optional(UnsafeInit tag)`.
- All `value()`, `value_or()`, `operator*()` methods now use `ObjectUnsafe::ObjectRefFromObjectPtr<T>` instead of `T(data_)` or `T(std::move(data_))`.

### Container changes

**Array** (`array.h`), **Map** (`map.h`), **Tuple** (`tuple.h`): Add `explicit T(UnsafeInit tag) : ObjectRef(tag) {}` constructor. Tuple additionally removes its `explicit Tuple(ObjectPtr<Object> ptr)` constructor.

**Variant** (`variant.h`): `VariantBase<true>` replaces `explicit VariantBase(ObjectPtr<Object> ptr)` with `explicit VariantBase(UnsafeInit tag)`.

### Type traits changes (`type_traits.h`)

`ObjectRefTypeTraitsBase`:
- `CopyFromAnyViewAfterCheck` and `TryCastFromAnyView` now use `ObjectUnsafe::ObjectRefFromObjectPtr<TObjRef>` instead of `TObjRef(ObjectPtr<Object>)`.
- `MoveFromAnyAfterCheck` now creates a typed `ObjectPtr<ContainerType>` instead of `ObjectPtr<Object>` before constructing the ref via `ObjectRefFromObjectPtr`.

### RValueRef changes (`rvalue_ref.h`)

- Adds `using ContainerType = typename TObjRef::ContainerType`.
- Internal storage changes from `ObjectPtr<Object>` to `ObjectPtr<ContainerType>`.
- Uses `ObjectUnsafe::ObjectRefFromObjectPtr<TObjRef>` for type conversion.

### Cast changes (`cast.h`)

`GetRef<RefType, ObjectType>` now uses `ObjectUnsafe::ObjectRefFromObjectPtr<RefType>` instead of `RefType(ObjectPtr<Object>)`.

### Function changes (`function.h`)

`Function::GetGlobalFunc` now creates `ObjectPtr<FunctionObj>` instead of `ObjectPtr<Object>` when wrapping the C API handle.

### Error handling (`function_details.h`)

`MoveFromSafeCallRaised` now uses `ObjectUnsafe::ObjectRefFromObjectPtr<Error>` instead of the removed `Error(ObjectPtr<Object>)` constructor.

### Module changes (`module.h`)

`Module` gains an explicit `Module(ObjectPtr<ModuleObj> ptr)` constructor with a null check (`TVM_FFI_ICHECK(ptr != nullptr)`), plus enhanced Doxygen documentation with a usage example.

### Shape changes (`shape.h`)

- `MakeStridesFromShape` signature changes from `(int64_t ndim, int64_t* shape)` to `(const int64_t* data, int64_t ndim)` -- parameter order swapped and data pointer made const.
- New public static factory: `Shape::StridesFromShape(const int64_t* data, int64_t ndim)` -- wraps the internal helper.
- Shape gains a private `explicit Shape(ObjectPtr<ShapeObj> ptr)` constructor, replacing the previous public `ObjectPtr<Object>` constructor.

### Reflection registry changes (`registry.h`)

New `ObjectCreatorUnsafeInit<T>` creator function:
```cpp
template <typename T>
static int ObjectCreatorUnsafeInit(TVMFFIObjectHandle* result) {
    ObjectPtr<T> obj = make_object<T>(UnsafeInit{});
    *result = details::ObjectUnsafe::MoveObjectPtrToTVMFFIObjectPtr(std::move(obj));
}
```

`ObjectDef` constructor now checks: if `Class` is default-constructible, use `ObjectCreatorDefault<Class>`; otherwise if constructible from `UnsafeInit`, use `ObjectCreatorUnsafeInit<Class>`. This allows reflected types to drop their default constructor in favor of an `UnsafeInit` constructor, which is safer because it makes it explicit that the object is in an uninitialized state.

### Tensor changes (`tensor.cc`, `tensor.h`)

- `TensorObjFromNDAlloc` and `TensorObjFromDLPack` use `Shape::StridesFromShape(...)` instead of `Shape(details::MakeStridesFromShape(...))`.
- `tensor.cc` Shape construction from FFI uses `ObjectUnsafe::ObjectRefFromObjectPtr<Shape>` instead of `Shape(ObjectPtr)`.

### Test changes (`test_object.cc`, `testing_object.h`)

- New test `TEST(ObjectRef, UnsafeInit)` verifies that both `ObjectRef(UnsafeInit{})` and `TInt(UnsafeInit{})` produce null-pointer refs.
- `TIntObj`, `TVarObj`, `TFuncObj` replace default constructors with `explicit T(UnsafeInit)` constructors. Comments updated from "need default constructor for json serialization" to "need unsafe init constructor for json serialization".

## Impact

- **API**: Significant C++ API change. All ObjectRef subtypes lose their `ObjectPtr<Object>` constructors. Code that constructed refs from raw `ObjectPtr<Object>` must switch to either (a) a typed `ObjectPtr<ContainerType>` constructor (for nullable types), (b) `ObjectUnsafe::ObjectRefFromObjectPtr<T>`, or (c) the `UnsafeInit` constructor followed by setting `data_`. User-defined Object types using the standard macros get the new constructors automatically.
- **ABI**: Not ABI-breaking. No C API changes. The `UnsafeInit` struct and the `ObjectRefFromObjectPtr` helpers are C++ only. The object layout and vtable are unchanged.
- **Behavioral**: No runtime behavior change for correct code. Code that relied on constructing non-nullable refs from `ObjectPtr<Object>(nullptr)` will now fail to compile, surfacing potential null-safety bugs at compile time.
- **Reflection**: Types that previously required a default constructor for reflection-based creation (e.g., JSON deserialization) can now use `UnsafeInit` instead, which is semantically clearer -- the object starts in an explicitly unsafe state with null fields, then fields are populated by the deserializer.

## Design Elements

Design elements this commit **consumes**:
- **Object/ObjectRef pattern** (`object.h`): The core `ObjectObj` + `ObjectRef` class hierarchy with `ObjectPtr<T>` smart pointers, as established in commit 7d34eb8.
- **`_type_is_nullable` flag**: The compile-time flag on ObjectRef types that indicates whether null values are semantically valid, used to gate null-path behavior in `GetRef`, `Optional`, and type traits.
- **`ObjectUnsafe` friend class**: The pre-existing utility class with friend access to ObjectRef internals, used to bypass normal access restrictions for controlled low-level operations.
- **Reflection `ObjectDef` builder**: The reflection registration system that needs an object creator function to instantiate objects from type info alone.
- **`MakeStridesFromShape`**: The stride computation helper introduced in commit ca95b41.

Design elements this commit **produces**:
- **`UnsafeInit` tag type**: A sentinel type that makes unsafe/null initialization of ObjectRef types explicit and auditable. Replaces the previous pattern of passing `ObjectPtr<Object>(nullptr)` or `ObjectPtr<Object>` of unknown provenance. All ObjectRef types (via the macros) now accept `UnsafeInit` as a constructor argument.
- **`ObjectUnsafe::ObjectRefFromObjectPtr<T>`**: The canonical way to construct any ObjectRef subtype from an untyped `ObjectPtr<Object>`. Centralizes all unsafe ref construction in a single auditable location. This is the replacement for the removed `RefType(ObjectPtr<Object>)` constructors.
- **Typed ObjectPtr constructors**: The macro-generated constructors now take `ObjectPtr<ContainerType>` instead of `ObjectPtr<Object>`, providing compile-time type safety. For example, `Function(ObjectPtr<FunctionObj>)` instead of `Function(ObjectPtr<Object>)`.
- **`ObjectCreatorUnsafeInit<T>`**: A reflection creator for types that provide `T(UnsafeInit)` but no default constructor, enabling the "construct-then-populate" pattern for deserialization without requiring a potentially-dangerous default constructor.
- **`Shape::StridesFromShape` static factory**: A public API for computing row-major strides, encapsulating the internal `MakeStridesFromShape` detail function behind a proper `Shape` class interface.

## Usage Examples

### Defining a new ObjectRef type (updated pattern)
```cpp
class MyDataObj : public Object {
 public:
  int64_t value;
  // UnsafeInit constructor instead of default constructor
  explicit MyDataObj(UnsafeInit) {}
  MyDataObj(int64_t v) : value(v) {}
  TVM_FFI_DECLARE_FINAL_OBJECT_INFO("test.MyData", MyDataObj, Object);
};

class MyData : public ObjectRef {
 public:
  // Macro now generates:
  //   MyData() = default;
  //   explicit MyData(ObjectPtr<MyDataObj> n);   // typed!
  //   explicit MyData(UnsafeInit tag);           // unsafe null init
  TVM_FFI_DEFINE_OBJECT_REF_METHODS(MyData, ObjectRef, MyDataObj);
};
```

### Constructing an ObjectRef from an untyped ObjectPtr (internal code)
```cpp
// Old pattern (no longer compiles for non-nullable types):
// MyData ref(some_object_ptr);

// New pattern:
MyData ref = details::ObjectUnsafe::ObjectRefFromObjectPtr<MyData>(some_object_ptr);
```

### Reflection creator fallback
```cpp
// If MyDataObj has no default constructor but has UnsafeInit:
// The reflection system automatically uses ObjectCreatorUnsafeInit<MyDataObj>
// to create instances, then populates fields via the reflection setters.
```

## Reflection

### Design docs to write or update
- A design doc covering the object system (`object.h`) should document the `UnsafeInit` pattern as the standard way to handle unsafe/null initialization. It should explain the distinction between nullable types (which retain `ObjectPtr<ContainerType>` constructors) and non-nullable types (which only have `UnsafeInit`).
- The reflection design doc should note that types can provide `T(UnsafeInit)` instead of a default constructor for reflection-based creation, and that the `ObjectDef` system automatically detects which creator to use.

### Stale knowledge references
- Commit ledger entry `ca95b412` documents `MakeStridesFromShape(int64_t ndim, int64_t* shape)` -- the signature is now `(const int64_t* data, int64_t ndim)` and a public `Shape::StridesFromShape` factory exists.
- The foundation commit ledger entry `7d34eb8` describes `TVM_FFI_DEFINE_OBJECT_REF_METHODS` as defining a constructor from `ObjectPtr<Object>` -- this is now `ObjectPtr<ContainerType>` plus `UnsafeInit`.
- Any knowledge referring to `TVM_FFI_DEFINE_MUTABLE_OBJECT_REF_METHODS` using `tvm::runtime` namespace should note it was corrected to `tvm::ffi` in this commit.
