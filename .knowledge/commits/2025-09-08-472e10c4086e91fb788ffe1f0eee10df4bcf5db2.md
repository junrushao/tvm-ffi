# Introduce UnsafeInit tag and tighten ObjectRef constructor null safety
## TL;DR
- Introduces `ffi::UnsafeInit{}` tag struct to replace the implicit `ObjectPtr<Object>` constructors on `ObjectRef` subclasses. The tag explicitly marks controlled scenarios where a non-nullable ref may be temporarily null (e.g., during reflection-based construction or internal casts).
- Removes the generic `RefType(ObjectPtr<Object>)` constructor from all four `TVM_FFI_DEFINE_*_OBJECT_REF_METHODS` macros. Nullable types now accept only `ObjectPtr<ContainerType>` (not `ObjectPtr<Object>`), and non-nullable types accept only `UnsafeInit`. This eliminates an implicit narrowing loophole where arbitrary `ObjectPtr<Object>` could bypass type checks.
- All internal sites that constructed ObjectRef subclasses from raw `ObjectPtr<Object>` are migrated to `ObjectUnsafe::ObjectRefFromObjectPtr<T>()`, centralizing the unsafe cast into a single auditable helper.

## Impact
- **API (C++ public headers)**: Breaking change for any downstream code that constructs `ObjectRef` subclasses via `RefType(ObjectPtr<Object>)`. Callers must switch to `ObjectUnsafe::ObjectRefFromObjectPtr<T>()` or construct typed `ObjectPtr<ContainerType>`. Affected headers: `object.h`, `cast.h`, `type_traits.h`, `optional.h`, `function.h`, `function_details.h`, `rvalue_ref.h`, all container headers (`array.h`, `map.h`, `tuple.h`, `variant.h`, `shape.h`), `module.h`, `reflection/access_path.h`, `reflection/registry.h`.
- **Flags/config**: None.
- **Data formats/schemas**: None.

## Design Elements
Design elements this commit consumes:
- **Object system** (`.knowledge/designs/0003-object-system.md`): The `ObjectRef` / `ObjectPtr<Object>` constructor pattern, the `TVM_FFI_DEFINE_OBJECT_REF_METHODS` family of macros, and `ObjectUnsafe` friend struct for internal unsafe operations.
- **Container system** (`.knowledge/designs/0005-containers.md`): `Array`, `Map`, `Tuple`, `Variant`, `Shape` all inherited the `ObjectPtr<Object>` constructor from their ref-method macros; each needed adaptation.
- **Reflection system** (`.knowledge/designs/0006-reflection.md`): `ObjectDef<T>` uses `ObjectCreator` function pointers to construct objects for deserialization. Previously required default constructors; now UnsafeInit provides an alternative.
- **Variant ObjectRef specialization** (`.knowledge/ADRs/0006-variant-objectref-specialization.md`): `VariantBase<true>` had an explicit `ObjectPtr<Object>` constructor, now replaced with `UnsafeInit`.

Design elements this commit produces:
- **`UnsafeInit` tag struct** (`include/tvm/ffi/object.h`): A zero-size tag type that explicitly opts into unsafe nullptr initialization. Every `ObjectRef` subclass generated by the standard macros now has an `explicit T(UnsafeInit)` constructor. This is a new core design element used across the entire object system.
- **`ObjectUnsafe::ObjectRefFromObjectPtr<T>`** (`include/tvm/ffi/object.h`): Two overloads (const-ref and rvalue) that centralize the unsafe "construct ref from untyped ObjectPtr" pattern. Uses `UnsafeInit{}` internally then assigns `data_`. This replaces dozens of scattered `T(ObjectPtr<Object>)` calls with a single auditable bottleneck.
- **`ObjectCreatorUnsafeInit<T>`** (`include/tvm/ffi/reflection/registry.h`): New reflection creator function for types that have `T(UnsafeInit)` but no default constructor. The `ObjectDef<T>` constructor now checks `std::is_constructible_v<Class, UnsafeInit>` as a fallback when `std::is_default_constructible_v<Class>` is false.
- **`Shape::StridesFromShape` static factory** (`include/tvm/ffi/container/shape.h`): Replaces the free function `details::MakeStridesFromShape` in public API. The free function signature was also changed from `(int64_t ndim, int64_t* shape)` to `(const int64_t* data, int64_t ndim)` for const-correctness and conventional parameter ordering.
- **`Module(ObjectPtr<ModuleObj>)` typed constructor** (`include/tvm/ffi/extra/module.h`): Module gains an explicit constructor from typed `ObjectPtr<ModuleObj>` with a null check (`TVM_FFI_ICHECK(ptr != nullptr)`), replacing the previous `ObjectPtr<Object>` constructor inherited from the macro. This is a pattern for non-nullable types that need a safe typed construction path.

## Reflection

### Design docs to write
- **`.knowledge/designs/0003-object-system.md` (update)**: The existing design doc should be updated to document the `UnsafeInit` tag struct, the `ObjectUnsafe::ObjectRefFromObjectPtr<T>` helper, and the new constructor signatures in the `TVM_FFI_DEFINE_*_OBJECT_REF_METHODS` macros. Specifically: (1) the nullable vs. non-nullable constructor contract (nullable types get `ObjectPtr<ContainerType>` + `UnsafeInit`; non-nullable get only `UnsafeInit`), (2) the migration pattern for downstream code. This helps future commit mining by providing the canonical reference for how ObjectRef construction works post-refactor.
- **`.knowledge/designs/0006-reflection.md` (update)**: Should document the `ObjectCreatorUnsafeInit<T>` fallback in `ObjectDef<T>` and the three-tier creator resolution: default-constructible > UnsafeInit-constructible > no creator. This helps future commits that add new reflected types understand when they need an `UnsafeInit` constructor vs. a default constructor.

### ADRs to write
- **`.knowledge/ADRs/0027-unsafeinit-tag-replaces-objectptr-object-ctor.md`**: Context: `ObjectRef` subclasses previously accepted `ObjectPtr<Object>` which bypassed static type narrowing and allowed implicit null construction of non-nullable types. Alternatives considered: (1) keep `ObjectPtr<Object>` constructor but add runtime checks (rejected: runtime cost on every construction, still allows mistyped pointers), (2) require `ObjectPtr<ContainerType>` everywhere (rejected: some internal paths need untyped construction from C API handles). Trade-off: The `UnsafeInit` tag makes the unsafety explicit and auditable at the cost of requiring all internal code to route through `ObjectUnsafe::ObjectRefFromObjectPtr<T>`.

### Design diagrams to draw
- **Mermaid**: A decision flowchart for "How to construct an ObjectRef subclass" showing three paths: (1) `make_object<T>(args...) + T(ObjectPtr<ContainerType>)` for nullable types, (2) `ObjectUnsafe::ObjectRefFromObjectPtr<T>` for internal/unsafe construction, (3) factory functions (e.g., `Shape::StridesFromShape`). This would clarify the intended usage patterns after this refactor.

### Skill evolution (`/commit-ledger`)

## Self-Evolution of Skill /commit-ledger
The current template and procedure handled this commit well. One area where the skill could improve: for large refactors that touch 19 files with a uniform mechanical change pattern (replace constructor X with pattern Y), the procedure could suggest a "change pattern summary" section that captures the regex-like transformation applied, rather than narrating each file. This would make the ledger entry more useful for someone reproducing or extending the same transformation. Concretely, this commit's core transformation is: `T(ObjectPtr<Object>)` -> `ObjectUnsafe::ObjectRefFromObjectPtr<T>(ObjectPtr<Object>)` and `T(ObjectPtr<Object>(nullptr))` -> `ObjectUnsafe::ObjectRefFromObjectPtr<T>(nullptr)`. Capturing that pattern once is more valuable than listing every call site.
