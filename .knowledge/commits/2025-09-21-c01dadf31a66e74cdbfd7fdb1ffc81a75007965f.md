# Introduce `tvm_ffi::reflection::init<>` helper for simplified `__init__` registration
## TL;DR
- Adds `tvm_ffi::reflection::init<T, Args...>`, a function template that constructs an `ObjectRef` from constructor arguments, simplifying the registration of `__init__`/`__ffi_init__` static methods in `ObjectDef<T>`.
- Migrates `TestIntPairObj` from a `__create__` lambda-based registration to `__ffi_init__` using `refl::init`, establishing `__ffi_init__` as the new naming convention for FFI constructors.
- Adds `[[maybe_unused]]` to `_type_is_nullable` in the ObjectRef macros to suppress compiler warnings.
- Drops the explicit `-> property` return type annotation from `TypeField.as_property()` in Cython.

## Impact
- API: Additive -- new `refl::init<>` template in `reflection/registry.h`. Existing `__create__` registrations still work but `TestIntPairObj` is migrated to `__ffi_init__`.
- Behavioral: `TestIntPair` Python class now uses `__ffi_init__` instead of `__create__` for construction. The `[[maybe_unused]]` on `_type_is_nullable` suppresses warnings but has no semantic effect.
- Flags/config: none
- Data formats/schemas: none

## Design Elements
Design elements this commit consumes:
- **Reflection system** (`.knowledge/designs/0008-reflection.md`): `ObjectDef<T>.def_static()` for registering static methods, `reflection::GetMethod()` for retrieving registered methods.
- **Object system** (`.knowledge/designs/0002-object-system.md`): `make_object<T>()`, `ObjectRef`, `TVM_FFI_DEFINE_OBJECT_REF_METHODS_NULLABLE` macro, `_type_is_nullable`.
- **Python bindings** (`.knowledge/designs/0012-python-bindings.md`): `Object.__init_handle_by_constructor__()` pattern for Python-side construction.

Design elements this commit produces:
- **`refl::init<T, Args...>`**: New convenience template that eliminates boilerplate lambdas for `__init__` registration. Handles both `Object`-derived and `ObjectRef`-derived `T` via `if constexpr`.
- **`__ffi_init__` naming convention**: Replaces `__create__` as the standard name for FFI-registered constructors, aligning with Python `__init__` semantics. On the Python side, classes use `self.__init_handle_by_constructor__(cls.__ffi_init__, ...)`.

## Usage Examples
**C++ registration and Python construction, end-to-end:**

```cpp
// C++ side: register __ffi_init__ using refl::init
class TestIntPairObj : public Object {
 public:
  int64_t a, b;
  TestIntPairObj(int64_t a, int64_t b) : a(a), b(b) {}
  TVM_FFI_DECLARE_OBJECT_INFO("testing.TestIntPair", TestIntPairObj, Object);
};

TVM_FFI_STATIC_INIT_BLOCK() {
  namespace refl = tvm::ffi::reflection;
  refl::ObjectDef<TestIntPairObj>()
      .def_ro("a", &TestIntPairObj::a)
      .def_ro("b", &TestIntPairObj::b)
      .def_static("__ffi_init__", refl::init<TestIntPairObj, int64_t, int64_t>);
}
```

```python
# Python side: use __init_handle_by_constructor__ with __ffi_init__
@register_object("testing.TestIntPair")
class TestIntPair(Object):
    def __init__(self, a: int, b: int) -> None:
        self.__init_handle_by_constructor__(TestIntPair.__ffi_init__, a, b)

pair = TestIntPair(1, 2)
assert pair.a == 1 and pair.b == 2
```
