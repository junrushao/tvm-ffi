# Add lightweight JSON parser and writer to the extra API tier
## TL;DR
- Adds a new `tvm::ffi::json` namespace under the extra API tier (`include/tvm/ffi/extra/json.h`) with two public functions: `json::Parse` (string to `Any`) and `json::Stringify` (`Any` to string), plus type aliases `json::Value = Any`, `json::Object = Map<Any, Any>`, `json::Array = Array<Any>`.
- The parser is a hand-written recursive-descent implementation (`JSONParserContext` + `JSONParser`) that supports standard JSON, JavaScript-style `Infinity`/`NaN`/`-Infinity`, and int64 integer values (distinguishing integers from floats). Error reporting includes line/column/char-offset context strings. An optional `String* error_msg` out-parameter allows non-throwing error handling.
- The writer (`JSONWriter`) serializes `Any` values by dispatching on `type_index()`, supports optional indentation, and preserves float-vs-int distinction by printing integer-valued doubles with a `.0` suffix. Both functions are registered as global FFI functions (`ffi.json.Parse`, `ffi.json.Stringify`) via `reflection::GlobalDef`.

## Impact
- API: Two new C++ functions (`json::Parse`, `json::Stringify`) and two new global FFI functions. No changes to existing APIs. Gated behind `TVM_FFI_USE_EXTRA_CXX_API` (default ON).
- Flags/config: none.
- Data formats/schemas: none -- this commit provides the tools to work with JSON, but does not define any new data schemas.

Design elements this commit **produces**:

- **JSON module in the extra tier**: A new `tvm::ffi::json` namespace providing lightweight JSON parsing and serialization built entirely on existing FFI primitives (`Any`, `String`, `Array<Any>`, `Map<Any, Any>`). The design reuses the type-erased `Any` system as the JSON value representation rather than introducing a separate JSON value type. This is a deliberate choice that keeps the JSON module minimal (no new object types, no new type indices) at the cost of losing JSON-specific type information (e.g., there is no JSON-specific "null" type distinct from `kTVMFFINone`).
- **Non-throwing parse API pattern**: `json::Parse` accepts an optional `String* error_msg` out-parameter. When non-null, parse errors are reported via this pointer instead of throwing exceptions. This pattern enables use in contexts where exceptions are undesirable (e.g., input validation, REPL loops). The pattern is specific to this module and not yet established as a broader convention.

## Key Implementations

### JSONParserContext: Leaf-level parsing engine

`src/ffi/extra/json_parser.cc` -- `JSONParserContext` handles character-level scanning, string parsing, number parsing, and error context generation. Key design choices:

- **String parsing fast path**: `NextString` first attempts a simple loop for strings without escape characters (the common case). Only when a backslash or control character is encountered does it fall back to `NextStringWithFullHandling`, which handles all JSON escape sequences including `\uXXXX` unicode escapes and UTF-16 surrogate pairs.
- **Number type disambiguation**: `NextNumber` tracks a `maybe_int` flag. If the number contains `.`, `e`, or `E`, it is parsed as `double`; otherwise `strtoimax` is attempted first for `int64_t`, falling back to `strtod`. This preserves the int/float distinction that is lost in standard JSON but useful for FFI round-trips.
- **Extended number literals**: `Infinity`, `-Infinity`, and `NaN` are parsed as `double` special values, matching JavaScript semantics. These are not valid JSON per RFC 8259 but are commonly needed in ML contexts.
- **Error reporting**: Each error type has a dedicated setter (`SetErrorExpectingValue`, `SetErrorUnterminatedString`, etc.) that captures line/column/char-offset context via `GetSyntaxErrorContext`. Error messages follow a Python `json.loads`-compatible format: `"Expecting value: line 1 column 1 (char 0)"`.

### JSONParser: Recursive-descent structure

The top-level `JSONParser` class orchestrates recursive descent with two internal stacks (`array_temp_stack_`, `object_temp_stack_`) that serve as flat accumulation buffers for nested arrays and objects. Rather than creating intermediate `Array`/`Map` objects during recursion, values are pushed onto the stack and the final container is constructed from a `[stack_top, end)` range. This avoids redundant copies and leverages the range constructors of `Array` and `Map`. The stack-top pattern cleanly handles nesting: each recursive call records its `stack_top` and restores the stack size after constructing its result.

### JSONWriter: Type-index dispatch

`src/ffi/extra/json_writer.cc` -- `JSONWriter::WriteValue` dispatches on `value.type_index()` covering `kTVMFFINone`, `kTVMFFIBool`, `kTVMFFIInt`, `kTVMFFIFloat`, `kTVMFFISmallStr`, `kTVMFFIStr`, `kTVMFFIArray`, `kTVMFFIMap`. Key invariants:

- **Float round-trip fidelity**: Integer-valued doubles are printed with `.0` suffix (via `%.1f` format), while non-integer doubles use `%.17g` (17 significant digits). This ensures the parser can reconstruct the original `int64_t` vs `double` distinction on re-parse.
- **Unsupported types throw**: Any `type_index` not in the supported set triggers a `ValueError` with the type key, providing clear diagnostics rather than silent corruption.
- **Object key validation**: `WriteObject` validates that every key is a `String` at write time, throwing `ValueError` otherwise. This is the only runtime type check in the writer path.

### Build integration

`CMakeLists.txt` adds `json_parser.cc` and `json_writer.cc` to the `tvm_ffi_objs_sources` list inside the `TVM_FFI_USE_EXTRA_CXX_API` guard block. No new CMake options or targets are introduced.

## Reflection

### Design docs to write

- **`.knowledge/designs/0011-extra-api-tier.md` -- update to include JSON module**: The current design doc lists only `StructuralEqual` and `StructuralHash` as extra-tier features. The directory layout section, build gating section, and key classes section should all be updated to include `json.h`, `json_parser.cc`, and `json_writer.cc`. This helps future commit mining by establishing the JSON module as a known extension point of the extra tier, so that subsequent changes (e.g., adding `json::Schema`, `json::Patch`) can be classified correctly.

### ADRs to write

- **`.knowledge/ADRs/0015-json-reuses-any-as-value.md`**: Decision context: When adding a JSON module, the choice was between defining new JSON-specific value types (e.g., `JsonNull`, `JsonNumber`) or reusing the existing `Any`/`Array<Any>`/`Map<Any, Any>` system. Alternatives: (1) new JSON value types (type-safe, can distinguish JSON null from FFI null, but adds type indices, registration, and conversion overhead), (2) reuse `Any` (zero new types, but `json::Value` is just an alias with no additional type safety). Trade-off: The alias approach keeps the module lightweight (84 lines of header) and avoids type index allocation, at the cost of not being able to enforce "this `Any` came from a JSON parse" at the type level.

### Design diagrams to draw

- **Mermaid**: A data flow diagram showing the JSON parse/stringify round-trip:
  - Input: `String` -> `json::Parse` -> dispatches to `JSONParserContext::NextString`/`NextNumber`/`ParseObject`/`ParseArray` -> produces `Any` (containing `int64_t`, `double`, `bool`, `nullptr`, `String`, `Array<Any>`, `Map<Any, Any>`)
  - Output: `Any` -> `json::Stringify` -> `JSONWriter::WriteValue` dispatches on `type_index` -> produces `String`
  - The diagram should highlight the int64/double distinction preserved through the round-trip.
