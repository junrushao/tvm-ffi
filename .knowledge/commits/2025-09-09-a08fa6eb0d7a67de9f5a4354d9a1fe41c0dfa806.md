# Streamline object declaration macros to embed type key and unify mutable/immutable ref methods

## TL;DR
- Renames and restructures all object declaration macros: `TVM_FFI_DECLARE_BASE_OBJECT_INFO` -> `TVM_FFI_DECLARE_OBJECT_INFO`, `TVM_FFI_DECLARE_FINAL_OBJECT_INFO` -> `TVM_FFI_DECLARE_OBJECT_INFO_FINAL`, `TVM_FFI_DECLARE_STATIC_OBJECT_INFO` -> `TVM_FFI_DECLARE_OBJECT_INFO_STATIC`. The new macros accept `TypeKey` as their first parameter and define `_type_key` internally, eliminating the need for a separate `static constexpr const char* _type_key = ...;` line at each use site.
- Consolidates four `TVM_FFI_DEFINE_*_OBJECT_REF_METHODS` macros (nullable, not-nullable, mutable, mutable-not-nullable) into two: `TVM_FFI_DEFINE_OBJECT_REF_METHODS_NULLABLE` and `TVM_FFI_DEFINE_OBJECT_REF_METHODS_NOTNULLABLE`. Mutability is now derived automatically from `ObjectName::_type_mutable` via `std::conditional_t`, removing the need for separate `MUTABLE` macro variants.
- Adds a new intermediate macro `TVM_FFI_DECLARE_OBJECT_INFO_PREDEFINED_TYPE_KEY` for types that define `_type_key` outside the macro (e.g., `Object` itself).

## Impact
- **API**: Breaking change to all C++ object declaration macros. Every downstream `TVM_FFI_DECLARE_*_OBJECT_INFO` and `TVM_FFI_DEFINE_*_OBJECT_REF_METHODS` call site must be updated. The old macro names no longer exist. The `TVM_FFI_DEFINE_MUTABLE_OBJECT_REF_METHODS` and `TVM_FFI_DEFINE_MUTABLE_NOTNULLABLE_OBJECT_REF_METHODS` macros are fully removed -- callers must set `_type_mutable = true` on the Obj class and use the non-mutable macro names.
- **Flags/config**: None.
- **Data formats/schemas**: None. The runtime behavior (type registration, ref counting, type checking) is unchanged; only the macro surface is restructured.

## Design Elements

Design elements this commit **consumes**:

- **Object System** ([`.knowledge/designs/0003-object-system.md`](../designs/0003-object-system.md)): Directly modifies the declaration macros documented in the "Object Declaration Macros" section. The `_type_key`, `_type_final`, `_type_child_slots`, `_type_mutable`, `_type_depth`, `RuntimeTypeIndex()`, `_GetOrAllocRuntimeTypeIndex()` static fields are all wired through these macros.
- **Object mutable opt-in** ([`.knowledge/designs/0003-object-system.md`](../designs/0003-object-system.md), Extension Points): The `_type_mutable` flag, previously only consumed by `TypeTraits<TObject*>` for `Any`/`AnyView` casts, is now also consumed by the ref-method macros to select `const ObjectName*` vs `ObjectName*` for `operator->()` and `get()`.
- **Static type index allocation** ([`.knowledge/ADRs/0024-static-type-index-ordering.md`](../ADRs/0024-static-type-index-ordering.md)): The `TVM_FFI_DECLARE_OBJECT_INFO_STATIC` macro continues to use pre-assigned `_type_index` for built-in types (Array, Map, String, etc.).
- **Module system** ([`.knowledge/designs/0013-module-system.md`](../designs/0013-module-system.md)): `ModuleObj` gains `_type_mutable = true` and switches from `TVM_FFI_DEFINE_MUTABLE_NOTNULLABLE_OBJECT_REF_METHODS` to the unified `TVM_FFI_DEFINE_OBJECT_REF_METHODS_NOTNULLABLE`, which now auto-derives mutability.

Design elements this commit **produces**:

- **Unified macro naming convention**: All object-info declaration macros now follow the pattern `TVM_FFI_DECLARE_OBJECT_INFO[_SUFFIX]` where suffix encodes the variant (`_STATIC`, `_FINAL`, `_PREDEFINED_TYPE_KEY`). The base macro `TVM_FFI_DECLARE_OBJECT_INFO` is the most common case (dynamic index, non-final). This replaces the older mixed naming where `BASE` and `FINAL` appeared in different positions.
- **Type-key-in-macro invariant**: After this commit, `_type_key` is always defined by the declaration macro (except for `Object` base class and types using `_PREDEFINED_TYPE_KEY`). This eliminates a class of copy-paste errors where `_type_key` and macro call could diverge.
- **Automatic mutability dispatch in ref methods**: The `__PtrType = std::conditional_t<ObjectName::_type_mutable, ObjectName*, const ObjectName*>` pattern inside `TVM_FFI_DEFINE_OBJECT_REF_METHODS_NULLABLE` / `_NOTNULLABLE` means mutability is no longer a separate macro dimension. This reduces the macro matrix from 2x2 (nullable x mutable) to 1x2 (nullable only).

## Reflection

### Design docs to write

- **Update `.knowledge/designs/0003-object-system.md`**, "Object Declaration Macros" section: The macro table lists `TVM_FFI_DECLARE_STATIC_OBJECT_INFO`, `TVM_FFI_DECLARE_BASE_OBJECT_INFO`, `TVM_FFI_DECLARE_FINAL_OBJECT_INFO`, `TVM_FFI_DEFINE_OBJECT_REF_METHODS`, `TVM_FFI_DEFINE_NOTNULLABLE_OBJECT_REF_METHODS`. All five need to be replaced with the new names, new signatures (TypeKey parameter), and the removal of the four mutable variants should be documented. Future commits that add or modify object types will reference these macros.

### ADRs to write

- **`.knowledge/ADRs/0027-type-key-in-declare-macro.md`**: Record the decision to embed `_type_key` inside the declaration macro rather than requiring a separate `static constexpr` line. Context: the old pattern required two lines that could silently desynchronize. The alternative (keeping them separate for flexibility) was rejected because no use case required defining `_type_key` differently from the macro's type registration. Trade-off: slightly less flexibility for types that want to compute `_type_key` dynamically (none exist today).
- **`.knowledge/ADRs/0028-unified-mutable-ref-macros.md`**: Record the decision to use `std::conditional_t<ObjectName::_type_mutable, ...>` to unify mutable and immutable ref method macros. Context: the old 2x2 macro matrix (nullable x mutable) had 4 variants that were nearly identical except for const-qualification. Alternative: keep separate macros for documentation clarity. Trade-off: the unified approach requires that `_type_mutable` be correctly set on the Obj class; previously, using `MUTABLE` macro was the explicit opt-in.

### Design diagrams to draw

None. The change is a macro API reshuffle; the relationships between `Object`, `ObjectRef`, `TypeTable`, and the runtime type system are unchanged.

### Skill evolution (`/commit-ledger`)

- For refactor commits that rename symbols (macros, functions, classes) across many files, Step 1's `numstat` output can be misleading -- many files change but the semantic change is concentrated in one file (`object.h`). The skill procedure could benefit from a heuristic: if the commit message contains "refactor" or "rename" and more than 10 files change, first inspect the primary header diff to understand the renaming, then spot-check 2-3 consumer files to confirm mechanical application, rather than reading every diff exhaustively.

## Self-Evolution of Skill /commit-ledger

- The current procedure does not distinguish between "rename/mechanical-migration" commits and "semantic-change" commits. A rename commit touching 16 files may have the exact same real design impact as a commit touching 1 file. Consider adding a "commit shape classifier" in Step 2 that detects patterns like: (a) many files changed with small per-file diffs, (b) commit message contains "rename"/"migrate"/"streamline", (c) additions roughly equal deletions. When detected, the procedure could shortcut Step 3/4 to focus on the defining header rather than exhaustively mining every consumer.
- The `_type_mutable` field's scope of influence has grown: it was originally only relevant to `TypeTraits` (Any/AnyView casts), and now also governs `operator->()`/`get()` return types in ref wrappers. The design doc should track which mechanisms read `_type_mutable` so that future changes to its semantics can be impact-assessed. This is a general pattern: when a static constexpr flag gains new consumers, the design doc's "Extension Points" section should be updated.
