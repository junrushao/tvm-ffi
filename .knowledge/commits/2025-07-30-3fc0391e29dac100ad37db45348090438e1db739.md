# Isolate structural equal/hash into a new extra/ API namespace, promoting access_path to core
## TL;DR
- Moves `StructuralEqual` and `StructuralHash` from `include/tvm/ffi/reflection/` and `src/ffi/reflection/` to a new `include/tvm/ffi/extra/` and `src/ffi/extra/` directory, formalizing the "extra API" tier as a first-class directory namespace.
- Creates `include/tvm/ffi/extra/base.h` as the new home for the `TVM_FFI_EXTRA_CXX_API` visibility macro (previously defined in `c_api.h`), removing the macro from the core C ABI header.
- Promotes `access_path.cc` from the `TVM_FFI_USE_EXTRA_CXX_API`-guarded build to the unconditional core build, recognizing that `AccessPath`/`AccessStep` are used by core reflection machinery (e.g., `ForEachFieldInfo`).
- Renames `AccessStep` factory methods and `AccessKind` enum values: `kArrayIndex` -> `kArrayItem`, `kMapKey` -> `kMapItem` (and their `*Missing` variants), for naming consistency.

## Impact
- API: **Breaking for downstream C++ code** that `#include`s `tvm/ffi/reflection/structural_equal.h` or `tvm/ffi/reflection/structural_hash.h` -- include paths must change to `tvm/ffi/extra/structural_equal.h` and `tvm/ffi/extra/structural_hash.h`. The `TVM_FFI_EXTRA_CXX_API` macro is no longer available from `c_api.h`; code must include `tvm/ffi/extra/base.h` instead. The `AccessStep::ArrayIndex()` / `MapKey()` factory methods are renamed to `ArrayItem()` / `MapItem()`.
- Flags/config: The CMake option `TVM_FFI_USE_EXTRA_CXX_API` still gates the structural equal/hash `.cc` files, but `access_path.cc` is now always compiled.
- Data formats/schemas: none.

## Design Elements
Design elements this commit **consumes**:

- **Reflection system** ([`.knowledge/designs/0006-reflection.md`](../designs/0006-reflection.md)): The structural equal/hash implementations consume `ForEachFieldInfo`, `ForEachFieldInfoWithEarlyStop`, `FieldGetter`, `TypeAttrColumn`, and `TVMFFIFieldInfo` flags (`kTVMFFIFieldFlagBitMaskSEqHashIgnore`, `kTVMFFIFieldFlagBitMaskSEqHashDef`) from the reflection system. These are read-path reflection APIs in `accessor.h`.
- **Object system** ([`.knowledge/designs/0003-object-system.md`](../designs/0003-object-system.md)): The `TVMFFITypeInfo::metadata->structural_eq_hash_kind` field (enum `TVMFFISEqHashKind`) is the dispatch mechanism for selecting comparison/hash strategies (tree, DAG, free-var, unique-instance). This is declared in `c_api.h` and populated via `ObjectDef<T>` registration.
- **Container system** ([`.knowledge/designs/0005-containers.md`](../designs/0005-containers.md)): `StructEqualHandler::CompareAny` and `StructuralHashHandler::HashAny` have per-type-index switch-case arms for `Array`, `Map`, `Shape`, `NDArray`, `String`, `Bytes` -- they directly consume the container object model.
- **C ABI layer** ([`.knowledge/designs/0001-c-abi.md`](../designs/0001-c-abi.md)): `TVM_FFI_EXTRA_CXX_API` was formerly defined in `c_api.h` alongside `TVM_FFI_DLL`. This commit removes it from the C ABI header, establishing a cleaner layering where `c_api.h` only contains the stable C ABI surface.

Design elements this commit **produces**:

- **Extra API tier** (new; no existing design doc): The `include/tvm/ffi/extra/` directory and `include/tvm/ffi/extra/base.h` header formalize a new architectural tier: "extra C++ APIs" that depend on the core but are not required for essential functionality. The `TVM_FFI_EXTRA_CXX_API` visibility macro is the entry point. This tier is gated by `TVM_FFI_USE_EXTRA_CXX_API` at build time.
- **AccessStep naming convention** (minor evolution of reflection design): The rename from `ArrayIndex`/`MapKey` to `ArrayItem`/`MapItem` establishes a consistent "Item" terminology for container element access steps. This is a naming convention that future `AccessStep` additions should follow.

## Key Implementations

**New header `include/tvm/ffi/extra/base.h`**: Defines `TVM_FFI_EXTRA_CXX_API` macro (defaulting to `TVM_FFI_DLL`), with documentation explaining the extra API tier's purpose and constraints: implemented in `.cc` files to reduce compile-time overhead, inputs/outputs restricted to POD/Any/ObjectRef for ABI stability, but may have cross-ABI issues (MSVC vs Itanium). This header is the sole dependency for any `extra/` API header.

**File relocation `reflection/ -> extra/` for structural_equal and structural_hash**: The headers and `.cc` files are moved with minimal content changes. The primary include-path change is `#include <tvm/ffi/extra/base.h>` replacing the inline macro from `c_api.h`, and header guards updated to `TVM_FFI_EXTRA_*_H_`.

**`access_path.cc` promoted to core build**: In `CMakeLists.txt`, `src/ffi/reflection/access_path.cc` moves from the `TVM_FFI_USE_EXTRA_CXX_API` conditional block to the unconditional `tvm_ffi_objs_sources` list. This reflects that `AccessPath`/`AccessStep` are used beyond just structural equal/hash -- they serve as the generic path-tracing mechanism for reflection-based traversals.

**`AccessKind` enum renames**: `kArrayIndex -> kArrayItem`, `kMapKey -> kMapItem`, `kArrayIndexMissing -> kArrayItemMissing`, `kMapKeyMissing -> kMapItemMissing`. Corresponding factory methods updated: `AccessStep::ArrayIndex() -> ArrayItem()`, `AccessStep::MapKey() -> MapItem()`, etc. The "Item" naming is more accurate -- these represent container items (key-value pairs or indexed elements), not just indices or keys.

**Invariants**:
- The structural equal/hash implementations assume `TVMFFITypeInfo::metadata != nullptr` and `structural_eq_hash_kind != kTVMFFISEqHashKindUnsupported` for any object type they encounter. Violation throws `TypeError`.
- `StructEqualHandler` maintains bidirectional `equal_map_lhs_`/`equal_map_rhs_` maps for DAG and free-variable nodes to handle shared references and alpha-equivalence.
- `StructuralHashHandler::HashMap` uses a sort-by-key-hash approach for order-independent map hashing, with tie-breaking logic (skip value hash on key-hash collisions) to preserve determinism.
- `CompareNDArray` and `HashNDArray` require CPU tensors and contiguous layout for content comparison; these are `ICHECK`-guarded (internal assertions).

**Extension points**:
- Custom `__s_equal__` and `__s_hash__` type attributes (via `TypeAttrColumn`) allow per-type override of the default reflection-based field-by-field comparison/hashing. The callback protocol passes `(lhs, rhs, callback)` for equal and `(obj, init_hash, callback)` for hash.
- New `extra/` API modules can be added alongside `structural_equal.h` and `structural_hash.h` by following the same pattern: include `extra/base.h`, use `TVM_FFI_EXTRA_CXX_API` visibility, gate in `CMakeLists.txt` under `TVM_FFI_USE_EXTRA_CXX_API`.

## Reflection

### Design docs to write
- **`.knowledge/designs/0009-extra-api-tier.md`**: Should document the purpose and constraints of the `extra/` API tier -- why it exists (non-core but useful features like structural equal/hash), the build-time gating via `TVM_FFI_USE_EXTRA_CXX_API`, the ABI constraints (`TVM_FFI_EXTRA_CXX_API` visibility, POD/Any/ObjectRef-only I/O), and the directory layout (`include/tvm/ffi/extra/`, `src/ffi/extra/`). This doc helps future commit mining for any commit that adds new extra APIs, moves functionality between core and extra, or modifies the build gating.
- **`.knowledge/designs/0010-structural-equal-hash.md`**: Should document the structural equal/hash subsystem -- the `TVMFFISEqHashKind` dispatch enum, the handler pattern (`StructEqualHandler`/`StructuralHashHandler`), the container-specific comparison/hashing logic, the free-variable and DAG-node mapping protocols, the `AccessPathPair` mismatch reporting, and the `__s_equal__`/`__s_hash__` type-attribute extension mechanism. This doc helps future commits that modify comparison semantics, add new container types that need comparison support, or extend the custom equality/hash protocol.

### ADRs to write
- **`.knowledge/ADRs/0011-access-path-promoted-to-core.md`**: Context: `access_path.cc` was originally gated under `TVM_FFI_USE_EXTRA_CXX_API` along with structural equal/hash. Decision: Promote it to the unconditional core build. Rationale: `AccessPath`/`AccessStep` serve as a general path-tracing mechanism used by reflection traversals beyond just structural equal/hash. Trade-off: Slightly increases the core library size, but avoids the extra API tier depending on a core concept that happens to be gated as non-core.

### Design diagrams to draw
- **Mermaid diagram: Extra API tier layering**. Should depict the dependency relationship: `c_api.h` (C ABI) -> `extra/base.h` (extra visibility macro) -> `extra/structural_equal.h` / `extra/structural_hash.h` (extra features) -> `reflection/accessor.h` + `reflection/access_path.h` (core reflection read-path). This clarifies the layering contract: extra depends on core, not vice versa.
