# Fix out-of-bounds read in StringViewToDLDataType_ with non-null-terminated strings

## TL;DR
- `StringViewToDLDataType_` in `src/ffi/dtype.cc` used `strtoul()` which requires null-terminated strings; passing a `std::string_view` without null terminator causes undefined behavior (OOB read) particularly in Electron/Chromium's aggressive memory reuser.
- Replaces all `strtoul()` calls with bounded manual digit parsing (`parse_digits` lambda) and bounded lane parsing (`parse_lanes` lambda) that respect `str.data() + str.length()`.
- Adds 86 lines of test coverage in `tests/cpp/test_dtype.cc` covering non-null-terminated buffers, digit-past-end, lane-past-end, and scalable vector cases.

## Impact
- API: none — `DLDataType StringViewToDLDataType_(std::string_view)` signature unchanged.
- Behavioral: fixes undefined behavior when input `string_view` is not null-terminated; now correctly parses only within `[str.data(), str.data() + str.length())`.
- Flags/config: none
- Data formats/schemas: none

## Design Elements
Design elements this commit consumes:
- `0007-containers` — `String` is backed by `std::string_view` internally; dtype parsing is part of `String`-to-`DLDataType` conversion.
- `0001-c-abi` — `DLDataType` struct (from DLPack) is the wire type for dtype; parsing must be correct at ABI boundary.

Design elements this commit produces: None — restores existing invariant.

## Usage Examples

Before (unsafe, OOB read with non-null-terminated buffer):
```cpp
// "float16" in a buffer followed by garbage like "999888777"
char buf[] = {'f','l','o','a','t','1','6','9','9','9'};
std::string_view sv(buf, 7);  // length=7, NOT null-terminated
DLDataType dt = StringViewToDLDataType_(sv);
// strtoul would read '1','6','9','9','9' -> bits=16999 (BUG)
```

After (safe):
```cpp
DLDataType dt = StringViewToDLDataType_(sv);
// parse_digits stops at offset 7 -> bits=16 (CORRECT)
```
