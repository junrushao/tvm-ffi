# Add custom DLPack-to-ScalarType conversion for Float4_e2m1fn (f4) support in torch bridge
## TL;DR
- Fixes the `getDLDataTypeForDLPackv1` export path to correctly set `dtype.lanes = 2` and `dtype.bits = 4` for `Float4_e2m1fn_x2` (previously only set `dtype.code`).
- Adds a new `toScalarTypeForDLPackv1()` function that handles the full DLDataType-to-ScalarType mapping (including the `kDLFloat4_e2m1fn` f4 type with multi-lane dispatch), replacing PyTorch's built-in `at::toScalarType()` in the DLPack import path.
- Bumps package version from `0.1.0b3` to `0.1.0b4` and moves the `tvm_ffi_python_helpers.h` header install into the Python module build conditional.

## Key Exports

**Functions** (C++ inline, JIT-compiled in `_optional_torch_c_dlpack.py`):

- `toScalarTypeForDLPackv1(const DLDataType& dtype) -> ScalarType` -- Maps `DLDataType` (code + bits + lanes) to PyTorch `ScalarType`. Handles: kDLUInt (8/16/32/64), kDLInt (8/16/32/64), kDLFloat (16/32/64), kDLBfloat (16), kDLComplex (32/64/128), kDLBool (8), kDLFloat8_e5m2 (8), kDLFloat8_e5m2fnuz (8), kDLFloat8_e4m3fn (8), kDLFloat8_e4m3fnuz (8), kDLFloat8_e8m0fnu (8), kDLFloat4_e2m1fn (bits=4, lanes=2 -> Float4_e2m1fn_x2). The `kDLFloat4_e2m1fn` case is the only one that dispatches on `lanes` in addition to `bits`.

**Bugfix** (in `getDLDataTypeForDLPackv1`):

- `Float4_e2m1fn_x2` case now correctly sets `dtype.lanes = 2` and `dtype.bits = 4` (was relying on uninitialized defaults from the function's `{kDLFloat, 32, 1}` initializer, which would produce `lanes=1, bits=32` -- incorrect for the f4 type).

## Impact
- API: None -- no public Python or C API signature changes.
- ABI: None -- the changed code is JIT-compiled C++ inside a Python string literal, not part of the stable C ABI.
- Behavioral: `torch.Tensor` round-tripping through DLPack now correctly handles `Float4_e2m1fn_x2` tensors in both directions (export and import). Previously, export would produce a malformed `DLDataType` (wrong bits/lanes) and import would fall through to PyTorch's `toScalarType` which may not handle the custom f4 type code.
- Flags/config: None.
- Data formats/schemas: None.

## Design Elements
Design elements this commit consumes:
- **DLPack fast-path protocol** (`.knowledge/designs/0018-dlpack-fast-path.md`) -- the `getDLDataTypeForDLPackv1` and `fromDLPackImpl` functions are part of the JIT-compiled C++ extension that implements the torch-side of the C DLPack fast path.
- **DLDataType code taxonomy** -- uses `DLDataTypeCode` enum values from dlpack.h, including the newer float8/float4 codes (`kDLFloat8_e5m2`, `kDLFloat8_e4m3fn`, `kDLFloat4_e2m1fn`, etc.).
- **Torch version guards** -- the `#if TORCH_VERSION_MAJOR >= 2 && TORCH_VERSION_MINOR >= 8` pattern established in commit 4dee97f for `Float4_e2m1fn_x2` support.

Design elements this commit produces:
- **Custom `toScalarTypeForDLPackv1` function** -- a TVM FFI-owned DLPack-to-ScalarType converter that replaces PyTorch's `at::toScalarType()` in the import path. This is necessary because PyTorch's converter may not support the full set of DLPack type codes (especially f4 with multi-lane dispatch). This function lives entirely within the JIT-compiled C++ string in `_optional_torch_c_dlpack.py`.

## Usage Examples
**Bugfix before/after**: Torch Float4 tensor DLPack round-trip.

Before (incorrect export):
```cpp
// In getDLDataTypeForDLPackv1, Float4_e2m1fn_x2 case:
dtype.code = DLDataTypeCode::kDLFloat4_e2m1fn;
// dtype.bits and dtype.lanes inherited from initializer {kDLFloat, 32, 1}
// Result: code=kDLFloat4_e2m1fn, bits=32, lanes=1 (WRONG)
```

After (correct export + custom import):
```cpp
// Export: correctly sets all three fields
dtype.code = DLDataTypeCode::kDLFloat4_e2m1fn;
dtype.lanes = 2;
dtype.bits = 4;
// Result: code=kDLFloat4_e2m1fn, bits=4, lanes=2 (CORRECT)

// Import: toScalarTypeForDLPackv1 handles the lanes dimension
case DLDataTypeCode::kDLFloat4_e2m1fn:
  switch (dtype.bits) {
    case 4:
      switch (dtype.lanes) {
        case 2: stype = ScalarType::Float4_e2m1fn_x2; break;
      }
  }
```
