# Self-Evolution Reflection: c897e4c

## What went well
- The rename from `load_inline.py` to `extension.py` was correctly identified as a staleness trigger for the design doc `0017-inline-module-compilation.md`, which references the old module name extensively.
- The distinction between "inline" (auto-decorated source strings) and "file-based" (user-managed source files with manual exports) workflows was clearly articulated. This is the key semantic difference the commit introduces.
- The refactor pattern (extracting `_build_impl()` as shared internal) was correctly classified as an internal design element production rather than a public API change.

## What could be improved
- The template's "Key Exports" section could benefit from a dedicated sub-heading for "Internal refactors" vs "New public API" when a commit both adds public surface and refactors internals. Currently both are lumped together, which may dilute the signal about what matters to downstream consumers.
- For commits that rename files, it would be useful to have a systematic "import path migration" note in the Impact section, since Python's `from module.submodule import ...` paths break silently. This commit breaks `from tvm_ffi.cpp.load_inline import build_ninja` (used in `_build_optional_torch_c_dlpack.py`, which was updated in this commit).

## Suggested skill improvements
- Consider adding a "Migration Guide" sub-section to the template for commits that rename modules or change import paths. This would list old import paths and their new equivalents.
- For file rename commits, the staleness check should automatically flag any `.knowledge/` file that references the old filename, with a severity indicator (design doc = must update, historical commit ledger = acceptable as-is).
